## Context

Every issue before this one has been allowed to assume that the database file only grows. `#7`
stored `max_msgs` / `max_bytes` / `max_age_ms` / `discard` and explicitly deferred *enforcement*
here. `#7` also left a bare ticker NULLing dedup keys with the comment "#27's janitor takes this
over". `#19` shipped `TrimEvents` and reserved three event names (`retention.expire`,
`retention.blocked`, `disk.degraded`) plus `consumer.lag` with **#27** in the owner column and no
emission site. `#14` reserved two error codes — `disk_full` (507) and `stream_full` (507) — that no
code path can currently produce, which `TestEveryCodeIsProduced` tolerates only because they are
marked reserved. `#15` registered a `disk_low` degradation kind that nothing sets, and left its
chunked-purge resumption loop to "#27's janitor". `#17` starts and stops a janitor goroutine that
has no jobs. `#21` reads free bytes with a bare `statfs` and notes that "#27 replaces it".

This issue is where all of those seams close. It is the difference between a broker you can run for
a week and one you can run.

Governing PLAN sections:

- **§4.5** — the mandate, nearly line by line: `limits` vs `workqueue`, oldest-first deletion, *"a
  message with an outstanding delivery row is **not** deleted; the sweep emits `retention.blocked`"*,
  `discard=new` rejecting publishes instead, event trim, WAL `TRUNCATE` above a threshold,
  `incremental_vacuum` on freelist growth, `--min-free-bytes` with **acks, naks and DLQ writes
  continuing** below it, and *"`/readyz` is not tied to disk pressure"*.
- **§3.2** — the janitor is one goroutine on a 60 s tick, and it is the last row of a closed
  goroutine census. No goroutine per stream, per job, per sweep.
- **§9.2 / §9.4** — the event vocabulary is **closed**; this issue emits four already-named events
  and invents none. Metric labels stay `stream` / `consumer`.
- **§5.2 I11** — *"no unbounded queue or collection exists anywhere; every bound is config-derived."*
  The events table, the dedup index, the WAL, the freelist and every stream are collections. This is
  the issue that bounds the last of them.
- **§12** — an idle daemon costs < 0.5 % of one core, so the sweep must be cheap when there is
  nothing to do.
- **D4** — fsyncgate. `ENOSPC` reaching `COMMIT` latches the process read-only (`#6`). The whole
  point of `--min-free-bytes` is to make that unreachable in production; `#32` asserts both halves.

What it unlocks: `#32`'s ENOSPC/EIO/clock matrix has something real to test, `#33`'s soak can run for
an hour without filling a disk, `#30`'s `doctor` can compare disk headroom against retention, and the
M7 exit criterion — *"a week-long stream does not grow unbounded"* — becomes true rather than aspired
to.

## Scope

**In scope**

- `internal/janitor`: the 60 s goroutine, its job list, per-tick budgets, fair scheduling, and the
  `Component` contract `#17` already calls (`Stop` cancels a running sweep, never awaits it).
- `retention=limits`: age → count → bytes passes, oldest-first, bounded per transaction, with the
  never-delete-a-message-that-holds-a-delivery-row guard enforced **inside the deleting
  transaction**, not by the planner.
- `retention=workqueue`: interest-based reaping below `min(cursor_seq)` with no delivery rows.
- `retention.blocked` with **blame attribution** — the event, the metric, and the teaching error name
  the guilty consumer and the sequence it is sitting on.
- `discard=new`: `507 stream_full` at publish time, evaluated in-transaction against maintained
  per-stream statistics (lights up `#14`'s reserved code).
- Per-stream statistics (`stream_stats`) as a maintained table — the decision `#7` §5 left open,
  forced by `discard=new` needing an exact, O(1), in-transaction size check.
- Dedup-key expiry (adopted from `#7`'s standalone ticker) and event-table trim (calls `#19`'s
  `TrimEvents`).
- Adoption of `#15`'s chunked-purge resumption loop and `#7`'s chunked stream-delete reaper.
- WAL checkpoint policy above `--wal-max-bytes`, `PRAGMA incremental_vacuum` on freelist growth, and
  the "these are solo commands, not batch members" amendment to `#6`'s writer.
- Disk safety: the free-space monitor, the hysteretic disk state machine, the fallocated reserve file
  that makes deletion possible on a full disk, `507 disk_full` on publish-class commands only, and
  `disk_low` in `/healthz`'s `degraded[]` with `/readyz` deliberately unaffected.
- The clock-jump guard on the age pass.
- `consumer.lag` periodic emission (the one vocabulary entry `#19` assigned to the janitor).
- Normative wording in `SEMANTICS.md` (what retention may and may not delete) and an
  `OPERATIONS.md` section on sizing; `verify` checkers for the new invariants.

**Out of scope**

## Design proposal

> Everything below is a **proposal and a starting point**. Budgets, defaults and SQL are negotiable.
> The four items marked **_decision_** are not, because `#30`, `#32` and `#33` build directly on
> them, and because reversing them later means another migration.

### 1. Where the code lives

```
internal/janitor/janitor.go     the goroutine, tick loop, job list, budgets   (#17 Component)
internal/janitor/jobs.go        retention · dedup · events · reaper · checkpoint · vacuum · stats
internal/janitor/disk.go        DiskProbe, Reserve, the disk state machine wiring
internal/queue/retention.go     PURE: eviction planning arithmetic, floor rules, blame selection
internal/queue/disk.go          PURE: NextDiskState (hysteresis, actions) — no syscalls
internal/store/retention.go     the guarded DELETEs, stream_stats maintenance, blame queries
internal/store/migrations/0003_stream_stats.sql
internal/verify/checks_retention.go   V7, V8 (registered into #8's registry)
```

The arithmetic that decides *what* to delete is a pure function over a small struct, so the nasty
cases (a stream over three limits at once, a blocked head, a clock jump, `max_bytes` smaller than one
message) are table tests, not integration tests.

### 2. The janitor: one goroutine, N bounded jobs

```go
package janitor

type Job interface {
    Name() string                  // "retention" | "dedup" | "events" | "reaper" |
                                   // "checkpoint" | "vacuum" | "disk" | "stats"
    Every() time.Duration          // 0 = every tick
    Run(ctx context.Context, b *Budget) (Result, error)
}

type Result struct {
    Rows  int64
    Bytes int64
    More  bool   // work remains: reschedule immediately if the budget allows
}

// Budget is the whole answer to "how do I stop a 5 GiB delete from stalling the ack path".
type Budget struct {
    Deadline time.Time // wall deadline for this job's slice of the tick
    Rows     int64     // remaining row allowance
}
func (b *Budget) Take(rows int64) bool

type Janitor struct {
    cfg   Config
    clock queue.Clock        // #3 seam — synctest drives a week in microseconds
    w     *store.Writer      // #6: every mutation is a writer command
    ro    *sql.DB            // planning reads never touch the writer
    obs   obs.Sink           // #19
    gate  *disk.Gate         // shared atomic read by #14's publish handlers
    jobs  []Job
}
```

Tick loop, in order, because the order is load-bearing: `disk` (cheap, and everything else wants the
current state) → `reaper` (finish authorised deletions before starting new ones) → `retention` →
`dedup` → `events` → `checkpoint` → `vacuum` → `stats`. Each job gets at most
`--janitor-budget / len(due jobs)` of the tick and is re-entered while `More` is true and budget
remains; leftover work resumes next tick. **No job holds state between ticks** beyond what is in
SQLite or `meta`, so a SIGKILL mid-sweep costs one tick.

`Stop` cancels the context; a running sweep aborts between transactions (`#17`'s contract: cancelled,
never awaited). A partially applied sweep is exactly as valid as a complete one — every batch is its
own transaction.

Ticks carry ±10 % jitter so the janitor never lines up with `#11`'s 250 ms sweeper or a 60 s
Prometheus scrape.

### 3. **_Decision 1: all mutation goes through the writer; PRAGMAs go through it as solo commands._**

PLAN §3.2 says the writer owns the sole read-write connection. A second read-write connection for
maintenance would be faster and is a trap: `PRAGMA incremental_vacuum` takes a write transaction, so
the writer's `BEGIN IMMEDIATE` could return `SQLITE_BUSY`, which `#6` classifies as a `begin`
failure — the fsyncgate latch. Housekeeping must never be able to latch the broker read-only.

So: the janitor submits commands like any other producer, and `#6` gains one small amendment —
**solo commands**, which run alone, outside the batch transaction:

```go
// internal/store — amendment to #6
type Solo interface{ Solo() }   // marker: never batched, runs between commit windows

type CheckpointCmd struct{ Mode string /* "PASSIVE" | "TRUNCATE" */ }
type VacuumCmd     struct{ Pages int }
```

`PRAGMA wal_checkpoint` and `PRAGMA incremental_vacuum` cannot run inside a transaction anyway, which
is what makes this amendment honest rather than convenient. Their stall is bounded by
`--checkpoint-timeout` (`#17`, 5 s) and by `--vacuum-pages-per-tick`, and is measured by
`messq_janitor_duration_seconds{job}` rather than polluting `messq_commit_duration_seconds`.

**Checkpoint errors are not commit errors.** `SQLITE_BUSY` from `wal_checkpoint` means a reader is
holding the WAL back; it is logged and retried next tick. A test asserts a busy checkpoint does not
set the read-only latch — getting this wrong turns `messq verify --deep` into an outage.

### 4. **_Decision 2: `stream_stats` is adopted._**

`#7` §5 offered it as a proposal with the fallback of `count(*)/sum(size)` behind a 5 s cache, and
deferred the choice to this issue. The choice is forced: `discard=new` must answer *"is this stream at
its limit?"* inside the publishing transaction, on the hot path, for every publish. A cached scan
cannot do that correctly (it would admit a burst past the limit and it would be stale by construction),
and an uncached scan is O(stream) per publish.

```sql
-- internal/store/migrations/0003_stream_stats.sql   (take the next free number at implementation
-- time; 0002 is #12's msg_id lineage change)
CREATE TABLE stream_stats (
  stream       TEXT PRIMARY KEY REFERENCES streams(name) ON DELETE CASCADE,
  msgs         INTEGER NOT NULL DEFAULT 0,
  bytes        INTEGER NOT NULL DEFAULT 0,
  expired_seq  INTEGER NOT NULL DEFAULT 0,   -- highest seq removed by retention
  expired_at   INTEGER NOT NULL DEFAULT 0    -- when, ms
) STRICT;

INSERT INTO stream_stats(stream, msgs, bytes)
SELECT s.name, COUNT(m.seq), COALESCE(SUM(m.size), 0)
  FROM streams s LEFT JOIN messages m ON m.stream = s.name
 GROUP BY s.name;
```

Maintained inside the same transaction as every insert and delete — publish (`#7`), the dead-letter
copy (`#12`), retention (here), purge and stream delete (`#15`). Consequences worth naming:

- `#15`'s `GET /v1/streams/{s}` `state.messages`/`bytes` become exact with `stats_age_ms: 0`, and its
  `BenchmarkStreamStats` fallback disappears.
- `#21`'s heavy metrics tier stops estimating DLQ depth above `--metrics-count-limit`;
  `messq_metrics_estimated` goes to zero.
- `verify` gains **V7** (deep): `stream_stats` equals a full scan, per stream. Drift is a bug, and it
  is the kind of bug that silently disables `discard=new`, so it is checked, not trusted.
- `expired_seq` / `expired_at` let `peek` and `trace` answer *"seq 4711 was removed by retention at
  09:14"* instead of a bare `not_found`. Deletion is oldest-first per stream, so one watermark is
  exact. (Small follow-through in `#15`'s `not_found` refinement and `#20`'s trace footer.)

### 5. `retention=limits` — three passes, one guard

Planning runs on the `ro` pool (no writer time); the delete runs as a writer command and **re-checks
the guard in SQL**, because a delivery row can appear between planning and applying (`#9` tops up on
fetch, concurrently, all the time). The planner is a candidate generator; the transaction is the
authority.

```sql
-- pass 1: age  (index messages_age = (stream, published_at))
SELECT seq, size, published_at FROM messages
 WHERE stream = :s AND published_at < :cutoff
 ORDER BY published_at LIMIT :batch;

-- pass 2: count   excess = stream_stats.msgs - max_msgs
SELECT seq, size FROM messages WHERE stream = :s ORDER BY seq LIMIT :excess_capped;

-- pass 3: bytes   accumulate size oldest-first in Go until stats.bytes - taken <= max_bytes
SELECT seq, size FROM messages WHERE stream = :s ORDER BY seq LIMIT :batch;
```

```sql
-- apply (one transaction per batch, bounded by --retention-batch)
DELETE FROM messages
 WHERE stream = :s AND seq IN (/* candidates */)
   AND NOT EXISTS (SELECT 1 FROM deliveries d              -- deliveries_seq index
                    WHERE d.stream = messages.stream AND d.seq = messages.seq)
 RETURNING seq, size;

UPDATE stream_stats
   SET msgs = msgs - :n, bytes = bytes - :b,
       expired_seq = MAX(expired_seq, :max_deleted_seq), expired_at = :now
 WHERE stream = :s;
```

The `RETURNING` clause is what makes the guard cheap **and** honest: the rows that came back are the
rows that went, so the statistics update and the aggregate event describe reality even though the
planner's candidate list did not.

**Blocked candidates are skipped, not stopping (_decision_).** If the oldest message is pinned by a
delivery row, the sweep continues to the next-oldest candidate rather than stalling. Stopping at the
first pinned message hands one stuck consumer the power to fill the disk — which §4.5 calls out as
exactly the failure mode this feature exists to prevent. The price is that deletion is
"oldest-deletable-first" rather than strictly oldest-first during an incident; the price is paid
loudly (next section), and `PROTOCOL.md`/`SEMANTICS.md` say so in one sentence.

**`limits` may delete a message no consumer has ever seen.** That is what `limits` means, it is
already the default (`max_age_ms` = 7 d), and it goes in `SEMANTICS.md` in those words next to the
pointer at `workqueue` and `messq_expired_total`.

**Overshoot is bounded and documented, not hidden.** Retention runs on a 60 s tick, so `max_bytes` is
a soft cap enforced *within one janitor interval*; `--min-free-bytes` is the hard guard. To keep the
overshoot small without deleting on the publish path, the writer nudges the janitor over a non-blocking
channel when a publish pushes a stream more than `--retention-overshoot-nudge` (10 %) past a limit.
One line in OPERATIONS.md states the bound as `rate × janitor-interval`.

### 6. `retention=workqueue` — the interest floor

```sql
-- the floor: no consumer will ever look below this again
SELECT MIN(cursor_seq) FROM consumers WHERE stream = :s;   -- NULL when there are no consumers

-- candidates: fully consumed and unpinned
SELECT seq, size FROM messages
 WHERE stream = :s AND seq < :floor
 ORDER BY seq LIMIT :batch;                                 -- same guarded DELETE as §5
```

`#9`'s checker C1 guarantees no delivery row exists at `seq >= cursor_seq` for its own consumer, but a
*different* consumer may still hold rows below the floor, so the `NOT EXISTS` guard is required here
too, not merely reused.

Rules that need stating because they are the ones operators hit:

| Situation | Rule |
|---|---|
| Stream has **no consumers** | Floor is undefined; nothing is interest-deletable. Emit `retention.blocked` with `detail.reason="no_consumers"` (repeat-limited), and let the configured limits still apply as a ceiling. A workqueue stream nobody reads must not be a silent disk leak. |
| A **paused** consumer (`#9`) | Still holds interest, still pins the floor, and is named as the blocker. Pausing is not abandoning. |
| A consumer with a **narrow filter** | Its cursor advances past non-matching seqs on top-up (T1), so it stops pinning as soon as it fetches. A consumer that never fetches pins regardless of its filter, and is reported like any other blocker. |
| Limits configured on a workqueue stream | Interest pass first, then the limits passes as a ceiling — with one difference: in workqueue mode a still-of-interest message that the limits pass would delete counts as **blocked** unless `discard=old` was set explicitly. Silently eating an unprocessed job is the one thing a job queue may not do. |
| `discard=old` on a workqueue stream | Permitted, warned at stream create/edit ("this stream may drop unprocessed jobs when full"), and every sweep that drops one reports `detail.unprocessed=N` on `retention.expire`. Configured data loss is always an auditable number. |
| Cursor **rewinds** below the reaped range (seek, or `#9`'s `max_ack_pending` shrink) | Harmless to the engine (the range scan finds nothing) and impossible for the operator to undo. `#28`'s seek preview must report "N of M messages in the requested range no longer exist" — a requirement handed to that issue. |
| A `.dlq` stream | Created by `#12` as `limits` with a 30 d default precisely so the interest rule cannot pin it forever. Switching a DLQ to `workqueue` is allowed and warned. |

### 7. `retention.blocked` — name the guilty consumer

An event nobody can act on is noise. The blame query runs only when a sweep actually skipped
something, and only once per `--event-repeat-interval` per stream (`#19`'s limiter, not a second one):

```sql
SELECT d.consumer, MIN(d.seq) AS blocking_seq
  FROM deliveries d
 WHERE d.stream = :s AND d.seq <= :highest_skipped
 GROUP BY d.consumer ORDER BY blocking_seq LIMIT 1;
```

```json
{"event":"retention.blocked","level":"WARN","stream":"orders","consumer":"invoicer",
 "detail":{"reason":"pending_delivery","blocking_seq":10493,"age_ms":5412000,
           "would_free_bytes":1198234112,"skipped":41208}}
```

`reason ∈ {pending_delivery, cursor_behind, no_consumers}` (an addition to `#19`'s detail set for this
event — the only vocabulary amendment in this issue). Human handler rendering:

```
WARN  retention.blocked  stream=orders consumer=invoicer  blocking seq 10493 (age 1h30m)
      1.1 GiB cannot be reclaimed   next: messq pending orders invoicer --older-than 15m
```

`messq_retention_blocked_total{stream}` (declared in `#21`) increments once per emission, which is what
`MessqRetentionBlocked` already alerts on.

### 8. `discard=new` — `507 stream_full` at publish time

Checked in `publishTx`'s savepoint (`#7` §2), after the read-only latch and the disk gate, against
`stream_stats` — exact, O(1), in-transaction:

```console
$ curl -si --unix-socket /run/messq/messq.sock --data-binary @job.json \
    'http://x/v1/streams/jobs/messages?subject=jobs.resize'
HTTP/1.1 507 Insufficient Storage
Retry-After: 5
{"error":{"code":"stream_full",
  "message":"stream jobs is at max_msgs=50000 and discard=new; consumer resizer is 49,912 behind",
  "next":["messq lag",
          "messq consumer info jobs resizer",
          "messq stream edit jobs --max-msgs 100000   # if the queue should be deeper"],
  "trace_id":"…"}}
```

- **A batch publish is atomic**: if the batch would cross the limit part-way, the whole batch is
  rejected and the message says how many would have fitted. Half-accepting a batch that the client
  will retry in full is how duplicates are manufactured.
- The blocking consumer is named only when one exists (limits + `discard=new` on a stream with no
  consumers is just full).
- `stream_full` and `disk_full` are both 507; **disk is checked first** — the node-wide condition
  outranks the per-stream one, and the message must not send an operator to tune a stream when the
  filesystem is the problem.
- The dead-letter copy (`#12`) publishes with `BypassLimits`, so a full origin stream can never wedge
  the dead path.

### 9. Disk safety

**_Decision 3: the daemon starts, and keeps acking, on a full disk._** It does not refuse to start
below `--min-free-bytes` (a broker that will not start cannot drain itself), and disk pressure never
touches `/readyz` (§4.5's RabbitMQ-on-Kubernetes lesson, already encoded in `#15`'s table). It starts
degraded, rejects publishes, and says so on every surface.

```go
package queue // pure, no syscalls, table-testable

type DiskState uint8 // DiskOK | DiskLow

type DiskPolicy struct {
    MinFree   int64   // --min-free-bytes, 256 MiB
    Recover   float64 // hysteresis: leave Low above MinFree*Recover (1.25)
    Reserve   int64   // --disk-reserve-bytes, 64 MiB
}

type DiskAction uint8 // ReleaseReserve | RestoreReserve | RejectPublishes | AllowPublishes | Emit

func NextDiskState(cur DiskState, free int64, p DiskPolicy) (DiskState, []DiskAction)
```

```go
package janitor

type DiskProbe interface { Free(dir string) (free, total int64, err error) } // unix.Statfs; faked in tests

// Reserve exists to break the classic broker deadlock: on a full disk, deleting data requires
// disk space, because a DELETE writes pages into the WAL.
type Reserve struct{ path string; size int64 }
func (r *Reserve) Ensure() error            // unix.Fallocate; degrade to "unavailable" + WARN if unsupported
func (r *Reserve) Release() (int64, error)  // unlink; the space that lets retention run
```

The gate the hot path reads is a single atomic, refreshed by the monitor every
`--disk-check-interval` (10 s) — a `statfs` per publish is not acceptable and a stale reading by ten
seconds is:

```go
type Gate struct{ low atomic.Bool }
func (g *Gate) AllowPublish() error // nil | errs.ErrDiskFull
```

Checked in two places on purpose: `#14`'s handler rejects before reading the body (fast, courteous,
saves the upload), and `publishTx` rejects authoritatively — so `pkg/client`, `replay` (`#28`) and
`dlq redrive` (`#29`) cannot route around it.

**What is refused and what continues below `--min-free-bytes`** (§4.5, verbatim in intent):

| Refused (`507 disk_full`) | Continues |
|---|---|
| `POST /v1/streams/{s}/messages`, `:batch` | `ack` · `nak` · `term` · `extend` |
| `replay` (`#28`), `dlq redrive` (`#29`) — they publish | the 250 ms sweeper: timeouts, backoff, redelivery |
| stream/consumer creation (small, but they are new data) | **dead-lettering**, including the DLQ copy |
| | retention deletes, event trim, checkpoints, incremental vacuum |
| | all reads: `peek`, `trace`, `pending`, `lag`, `verify`, `/metrics` |

The DLQ copy is the interesting one: it *adds* bytes on a disk that is full. It is allowed anyway
because refusing it wedges the ack path, and mass redelivery is a worse outcome than a bounded
overshoot — and the overshoot **is** bounded: at most `Σ max_ack_pending × max_msg_size` across
consumers, a number `doctor` (`#30`) can print. That argument, not a hand-wave, is why the rule is
safe.

Surfaces:

```console
$ curl -s --unix-socket /run/messq/messq.sock http://x/healthz
{"status":"ok","degraded":[{"kind":"disk_low","since":"2026-10-28T11:02:04Z"}]}

$ curl -si --unix-socket /run/messq/messq.sock http://x/readyz
HTTP/1.1 200 OK
{"status":"ok"}
```

```
WARN  disk.degraded  free=214.7MiB min_free=256.0MiB rejecting=true eta_hours=3.1 reserve=released
      next: messq lag   # find the consumer that is not draining
...
WARN  disk.degraded  free=1.4GiB min_free=256.0MiB rejecting=false eta_hours=- reserve=restored
```

Recovery reuses the same event name with `rejecting=false` — `#19`'s rule 3 (no new names;
`consumer.pause` covers resume) applied consistently. `eta_hours` comes from a linear fit over a
one-hour ring of samples, and is omitted when free space is flat or rising; `#21`'s
`MessqDiskWillFill` does the same thing in PromQL, and this is the copy an operator reads at 3 a.m.

**Startup sanity check.** `--min-free-bytes` must exceed the largest plausible single commit:
`4 × --commit-max-batch × max(max_msg_size)`. Below that, refuse to start with a computed suggestion —
a guard that cannot cover one commit is theatre, and the failure it fails to prevent is `#6`'s fatal
latch.

### 10. The rest of the housekeeping

| Job | What it does | Bound |
|---|---|---|
| `dedup` | `#7`'s `UPDATE messages SET dedup_key = NULL …` per stream, window from `dedup_window_ms` | `--dedup-batch` (10 000) rows/tx |
| `events` | calls `#19`'s `TrimEvents` (age pass, then row-count pass, then the `meta.events_trimmed_before_*` honesty markers) | `--event-trim-batch` (5 000) |
| `reaper` | scans `meta` for `purge.<ulid>` rows (`#15`) and orphaned stream deletes (`#7`), continues in `--purge-chunk` batches, clears the `meta` row and the `purge_in_progress` degradation when done | `--purge-chunk` (10 000) |
| `checkpoint` | `PASSIVE` when `wal_bytes > --wal-max-bytes/2`; `TRUNCATE` above `--wal-max-bytes` (256 MiB); solo command, bounded by `--checkpoint-timeout` | one attempt/tick |
| `vacuum` | `PRAGMA incremental_vacuum(N)` when `freelist_count > --vacuum-freelist-pages` (10 000 ≈ 40 MiB) | `--vacuum-pages-per-tick` (2 000) |
| `stats` | refreshes the `#21` gauge inputs and emits `consumer.lag` for consumers past `--lag-report-threshold`, at most once per `--lag-report-interval` | one row per lagging consumer |

Notes that will otherwise be discovered the hard way:

- **`retention` skips streams the reaper is working on** (an open `meta.purge.*`, or a `streams` row
  already gone), so two deleters never race over the same rows.
- **`incremental_vacuum` is silently a no-op unless `auto_vacuum=INCREMENTAL` was set at file
  creation** (`#5`). Read `PRAGMA auto_vacuum` back at startup; if it is `NONE` (an old data dir from
  `#34`'s upgrade fixtures), log once at WARN with the offline remedy and disable the job — rather than
  ticking uselessly forever.
- **Checkpoint starvation.** A long-lived reader (`verify --deep`, an unlucky `/metrics` scrape) holds
  the WAL back. After `--checkpoint-starve-ticks` (5) consecutive failures above the threshold, log
  `store.checkpoint_starved` at WARN naming the WAL size; `doctor` picks it up. Never escalate, never
  kill a reader.
- **Dedup vs. retention.** Deleting a message drops its dedup key early, so a publisher retry inside a
  window that outlives the message would create a duplicate. `ValidateStreamConfig` (`#7`) gains a
  `finding` when `dedup_window_ms > max_age_ms`. Cheap, and it closes a real hole in the
  at-least-once story.
- **Housekeeping emits no new event names.** Checkpoint, vacuum, dedup trim and event trim write
  `slog` diagnostics (`store.checkpoint`, `store.vacuum`, `obs.trimmed`, `janitor.sweep`) and metrics,
  not `events` rows. An event-table trim that wrote an event row would feed itself.

### 11. The clock-jump guard

Age retention compares `published_at` (wall-clock ms) against `now - max_age_ms`. A forward NTP step
of a month would delete every stream's entire history in one tick, correctly, per the configuration,
and irreversibly.

The janitor records `(monotonic, wall)` at each tick. If `|Δwall − Δmono| > --clock-jump-tolerance`
(60 s), it **skips the age pass for one tick**, logs `janitor.clock_jump` at WARN with both deltas, and
continues with the count/byte/interest passes (which do not read the clock). One tick of grace is
enough for NTP to settle and for a human to see the line. `#32` drives ±1 h jumps against this;
`testing/synctest` makes it a unit test.

### 14. Edge cases

| Case | Behaviour |
|---|---|
| `max_bytes` smaller than a single message | The stream keeps exactly one message and `retention.expire` reports it; never an infinite delete-then-refuse loop. A `finding` at config time says so. |
| Every candidate is blocked | Zero deleted, one `retention.blocked`, no `retention.expire` (an aggregate of nothing is noise), `More=false` so the tick ends. |
| Stream deleted mid-sweep | The guarded `DELETE` matches nothing; the reaper owns those rows. No error, no event. |
| A retention batch and a purge target overlap | Impossible by construction: retention skips streams with an open `meta.purge.*`. |
| SIGKILL mid-sweep | The batch was a transaction: it either happened with its statistics update or it did not. Next start's first tick continues. `verify` V7 green either way. |
| Clock steps backwards | Age pass skipped for one tick (§11); nothing is deleted "early"; count/byte passes unaffected. |
| `--min-free-bytes` on a nearly full disk at startup | Start, `disk_low` immediately, publishes rejected, `/readyz` 200, reserve released, retention runs and (usually) recovers without operator action. This is the ENOSPC drain-and-recover story `#32` asserts. |
| Reserve file cannot be fallocated (unsupported filesystem) | One WARN at startup, `messq_disk_reserve_bytes 0`, everything else works; `doctor` reports reduced headroom. |
| Free space rises above the recovery threshold and falls again repeatedly | Hysteresis (`MinFree × 1.25`) plus the 10 s cadence bounds flapping; each transition is an event, so flapping is visible instead of mysterious. |
| `--janitor-interval 0` | All housekeeping off, startup banner at WARN, `doctor` flags it, and it is documented as a test-only setting. The disk monitor still runs — safety is not housekeeping. |
| Events table grows faster than the trim | The trim is a prefix delete and its batch is a flag; if `messq_events_rows` still climbs, `--event-max-rows` is the hard bound and `doctor` says which knob to move. |
| Message expired while a `trace` is mid-render | `trace` reads the events table, not `messages`; it renders and prints the `expired_at` footer from `stream_stats`. |
| Consumer created below `expired_seq` | `#9` already clamps `start: seq:N` into `[first_seq, next]`; the response reports the clamp and the requested value. |

### 16. Rejected alternatives

| Rejected | Why | Revisit when |
|---|---|---|
| A second read-write connection for maintenance | `SQLITE_BUSY` on the writer's `BEGIN IMMEDIATE` would trip `#6`'s fatal latch — housekeeping able to declare a storage fatality | never |
| Deleting on the publish path ("delete one, insert one") | Puts an unbounded delete inside a 2 ms commit window shared by every publisher, exactly what D4 forbids for ENOSPC | never; the nudge covers the overshoot |
| Stopping the sweep at the first blocked message | Lets one stuck consumer fill the disk | never |
| Per-message `retention.expire` events | Volume incident; the aggregate plus `messq_expired_total` answers every real question | never |
| "Keep events for unresolved messages" | Needs a join per candidate row and makes the trim unbounded (`#19`'s reasoning); the headroom rule buys the same safety for a constant | never |
| `count(*)/sum(size)` behind a cache instead of `stream_stats` | Cannot make `discard=new` exact, and lies during a burst | if V7 drift ever proves unmaintainable |
| A third `interest` retention mode (plan-05) | Not in PLAN's closed set; `limits` + `workqueue` cover the ICP | on demonstrated demand, post-1.0 |
| Blocking the ack path to reclaim disk | The failure D4 explicitly forbids | never |

## Acceptance criteria

- [ ] `retention=limits` enforces `max_age_ms`, `max_msgs` and `max_bytes` oldest-first, bounded by
      `--retention-batch` per transaction, and a stream configured with all three converges to the
      tightest of them within one `--janitor-interval` plus the drain time implied by
      `--retention-max-per-tick`.
- [ ] **No message that holds a delivery row is ever deleted**, in either retention mode, proven by a
      SQL guard inside the deleting transaction *and* by a concurrent property test — and `verify`'s
      I2 stays green throughout.
- [ ] A blocked sweep emits exactly one `retention.blocked` per stream per `--event-repeat-interval`,
      naming the consumer, `blocking_seq`, `age_ms` and `would_free_bytes`, and increments
      `messq_retention_blocked_total{stream}`; a sweep that deletes nothing emits no
      `retention.expire`.
- [ ] Blocked candidates are skipped, not stalled: with the oldest message pinned, the stream still
      returns under its limits.
- [ ] `retention=workqueue` deletes a message once every consumer's `cursor_seq` is past it and no
      delivery row remains — and never before; a stream with no consumers deletes nothing by interest
      and reports `reason="no_consumers"`.
- [ ] `discard=new` at the limit rejects publishes with `507 stream_full`, a `Retry-After`, the limit
      that was hit and the blocking consumer when there is one; a batch publish that would cross the
      limit is rejected whole.
- [ ] Below `--min-free-bytes`: publish, batch publish, replay and redrive return `507 disk_full`;
      **ack, nak, term, extend, the sweeper, dead-lettering, retention and reads all keep working**;
      `/healthz` reports `disk_low` in `degraded[]`; **`/readyz` stays 200**.
- [ ] The reserve file is released on entering `disk_low` and restored on recovery; a data dir filled
      to `--min-free-bytes` drains via retention and returns to normal **without a restart** and
      without the read-only latch being set.
- [ ] `--min-free-bytes` below `4 × --commit-max-batch × max_msg_size` is a startup refusal with a
      computed suggestion.
- [ ] The WAL is checkpointed with `TRUNCATE` above `--wal-max-bytes` and drops back; a `SQLITE_BUSY`
      checkpoint neither latches the store read-only nor fails a tick; five consecutive starved
      attempts log `store.checkpoint_starved`.
- [ ] `PRAGMA incremental_vacuum` runs when the freelist exceeds `--vacuum-freelist-pages` and the
      file shrinks after a mass delete; on a data dir without `auto_vacuum=INCREMENTAL` the job
      disables itself with one WARN.
- [ ] Dedup keys are NULLed after `dedup_window_ms`, the events table stays inside `--event-retention`
      and `--event-max-rows`, and `meta.events_trimmed_before_*` is maintained.
- [ ] A purge or stream delete above `--purge-max-rows` that was interrupted by SIGKILL is completed
      by the janitor after restart, `purging.remaining` counts down, and `purge_in_progress` clears.
- [ ] `stream_stats` equals a full scan for every stream after any mix of publish, dead-letter,
      retention, purge and stream-delete (`verify` V7, deep).
- [ ] A wall-clock jump of +1 h with `max_age_ms=30m` deletes nothing on the tick that observes the
      jump, logs `janitor.clock_jump`, and behaves normally on the next tick.
- [ ] A simulated week of traffic against configured limits keeps `messq_db_bytes`, `messq_wal_bytes`
      and `messq_events_rows` bounded (db within 1.3 × the configured `max_bytes` sum, WAL below
      `--wal-max-bytes`, events below `--event-max-rows`) with flat RSS and a flat goroutine count.
- [ ] An idle daemon with 50 empty streams stays below the §12 budget (< 0.5 % of one core) across
      janitor ticks.
- [ ] `SEMANTICS.md` states what retention may delete (including "limits may delete a message no
      consumer has seen") and OPERATIONS.md states the overshoot bound and the disk-safety table.

## Test plan

**Unit — pure (`internal/queue`)**

- Eviction planning table: streams over one, two and three limits; `max_bytes` below one message;
  `0` = unlimited on each knob; empty stream; single message; blocked head; blocked interior.
- `NextDiskState`: crossing down, crossing up, hysteresis band, flapping input series, `MinFree=0`,
  reserve unavailable. Each case asserts the emitted action list, not just the state.
- Blame selection: multiple blockers, oldest wins; no blocker; blocker on a paused consumer.
- Clock-jump detector: forward, backward, gradual drift below tolerance.

**Store (real files in `t.TempDir()`, never `:memory:`)**

- The guarded `DELETE` with a concurrently inserted delivery row (insert between plan and apply, via a
  hook) — the row survives and V7/I2 stay green. This is the test the whole issue exists for.
- `stream_stats` maintenance across publish / dead-letter / retention / purge / stream-delete, each
  compared to a full scan; plus the `0003` migration's backfill on a fixture dir from `#34`.
- Workqueue floor: multi-consumer, paused consumer, filtered consumer, zero consumers, cursor rewind.
- `discard=new` at the boundary (`msgs = max_msgs - 1`, `= max_msgs`), batch crossing the limit,
  `BypassLimits` for the dead-letter copy.
- Checkpoint under a held read transaction → `SQLITE_BUSY` → no latch, tick continues.
- `incremental_vacuum` on a dir created with `auto_vacuum=NONE` → self-disable path.

**Timing (`testing/synctest` + the `#3` Clock seam; no `time.Sleep`, lint-enforced)**

- The whole tick scheduler: job cadence, budget exhaustion and resumption, `More` loops, fair share
  between jobs, jitter bounds.
- A simulated **week** of retention (7 d of `max_age` expiry with a 2 min dedup window and 72 h event
  retention) in microseconds — the "bounded file size" criterion, executed rather than asserted.
- `retention.blocked` and `disk.degraded` repeat-limiting windows.

**Property (`pgregory.net/rapid`, extending `#13`)**

- New `JANITOR` action interleaved with publish/fetch/ack/nak/term/timeout/seek/purge/restart. The
  reference model gains retention rules. Invariants checked after every action: I2 (no delivery row
  without its message), I11, V7 (`stream_stats` == scan), plus two new ones — *no message with a
  delivery row was deleted* and *`msgs ≤ max_msgs` once a sweep has run with nothing blocked*.
- Conservation over the whole run: `published = acked + termed + dead + expired + still_pending`
  (the term `#33`'s soak needs).
- Failfiles committed as regression corpus.

**Crash (`#8`'s harness; fast subset per merge, `#32` owns the nightly matrix)**

- SIGKILL at named fault points: `retention.before_delete`, `retention.after_delete_before_commit`,
  `retention.after_commit`, `janitor.mid_checkpoint`, `disk.after_reserve_release`,
  `reaper.mid_chunk`. After restart: `verify` (incl. V7) and `PRAGMA integrity_check` clean; the
  ledger oracle unchanged (retention only ever removes messages that were already legally
  unreachable, so an `OK` ledger entry must never vanish because of a sweep — a dedicated assertion).
- Interrupted chunked purge resumed by the janitor, `detail.resumed=true`.

**Fault / resource (short forms here; full matrix in `#32`)**

- Fake `DiskProbe` driving the state machine through a full incident and back, asserting exactly which
  endpoints refuse and which continue.
- One real small loopback filesystem filled until `disk_low`: publishes `507`, acks continue, the
  reserve releases, retention frees space, the daemon returns to normal with no restart and no
  `storage.fatal`.

**Golden logs / events / API (`#18`, `#19`, `#21` harnesses)**

- Scripted scenario `publish×N → sweep → blocked → unblock → sweep` asserts the exact event sequence,
  names and `detail` field sets on all three surfaces.
- `/metrics` exposition golden extended with the new families; `promlint` clean; the cardinality
  allow-list test still fails under the sabotage tag.
- curl goldens for `507 stream_full` and `507 disk_full` (envelope, `Retry-After`, `next[]`), and for
  `/healthz` carrying `disk_low` while `/readyz` returns 200.

**Bench**

- `BenchmarkRetentionSweep` over 10 M messages (limits and workqueue): rows/s and, more importantly,
  that `messq_commit_duration_seconds` p99 stays inside the `--commit-window` order of magnitude while
  a sweep runs — the regression gate is the *interference*, not the throughput.
- `BenchmarkPublishWithStats` — the cost `stream_stats` adds to the publish path must be noise against
  the M2 gate (`#8`).
- Idle-cost measurement for the §12 budget. Nightly benchstat, not a merge gate (PLAN §11.9).
