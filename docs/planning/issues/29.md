## Context

`#12` made a dead message *land* somewhere real: `<stream>.dlq` is an ordinary stream, the copy is
atomic with the delivery-row deletion and the `msg.dead` event, and it carries full provenance
(`Messq-Origin-Stream/-Seq/-Consumer`, `Messq-Attempts`, `Messq-Cause`, `Messq-Trigger`,
`Messq-Last-Reason`, `Messq-Dead-At`, …) plus the origin's `id` and `trace_id`.

That is where the story stops today. An operator holding a DLQ can run `messq peek orders.dlq
--last 5 --headers` — `#24`'s honest placeholder hint — and then has nothing: no way to ask *"what
is in here and is it getting worse?"*, no way to read one dead message as a record rather than a
blob with headers, and **no way to put messages back** without a hand-written `curl` loop that will
happily re-publish four hundred messages into a service that is still on fire.

This issue ships the triage workflow: `messq dlq ls`, `dlq show`, `dlq redrive`, `dlq purge` — and,
more importantly, the guard rails around `redrive`, which is the one verb in messq that can turn an
incident into a bigger incident. PLAN.md is explicit that this is the point of the DLQ design:

- **D3 — DLQ is a real stream.** Its justification is that *"one mechanism then buys four features:
  inspection = `peek`, **redrive = consume+republish**, alerting = depth metric, retention = stream
  retention"*, and that *"DLQs nobody watches are the documented failure mode"*. Inspection and
  alerting landed in `#12`/`#21`. Redrive and the watching are here.
- **§5.1 T11** — the normative transition: `DEAD in DLQ → dlq redrive`, guard *"operator,
  rate-limited"*, effect *"republish to origin stream (new seq, `Messq-Redrive-Of` header, trace
  preserved)"*, event `dlq.redrive`.
- **§7 API** — `POST /v1/dlq/{s}/redrive {ids[]|limit, rate} (?dry_run=1)` is already in the
  published endpoint list; `#15` explicitly deferred it here.
- **§8 CLI** — `messq dlq ls|show|redrive|purge`, plus the two rules that shape this issue: *"Every
  destructive command has `--dry-run` (exact preview, same renderer as the real run), and
  confirmation by name, plus an `admin.*` audit event with actor"*, and *"every inspect command
  ends with the next useful command; every error names the fix."*
- **§9.2** — `dlq.redrive` and `admin.action` are already in the closed event vocabulary; this
  issue invents **no** new event names. **§14 M7 exit criterion** — *"An operator runs an entire
  incident (find → inspect → **redrive** → replay → purge) from the CLI alone."*

`#28` landed the discipline this issue inherits wholesale rather than re-invents: `--dry-run`
rendered through the same renderer as the real run, confirmation by typing the resource name (never
`y/n`), `--yes` for non-TTY, and one `admin.action` event per execution carrying actor, parameters
and before/after counts. `#24` landed the chassis (three output modes, teaching errors, the hint
registry, `--confirm`/`--yes` flag types) and left a deliberate IOU: *"During M6 the DLQ hint is
`messq peek <stream>.dlq --last 5 --headers`; **#29 changes one registry entry** and
`TestHintsResolve` keeps everyone honest."* Collecting that IOU is part of this issue.

What it unlocks: `#30`'s `doctor` gets a DLQ finding it can trust, `#35`'s incident runbook
(RB-02, referenced by `#21`'s `MessqDlqNonEmpty` alert) becomes a document about commands that
exist, and the M7 exit criterion becomes executable as a single testscript.

## Scope

### In scope

- **`GET /v1/dlq`**, **`GET /v1/dlq/{s}`**, **`GET /v1/dlq/{s}/messages`** — the read side: depth,
  bytes, growth rates, grouping by cause/subject/consumer, and a filtered row listing. All on the
  read-only pool, all non-mutating.
- **`POST /v1/dlq/{s}/redrive`** (PLAN §7) — plan/impact/apply with `?dry_run=1` and `?confirm=`,
  server-enforced rate limiting, the loop guard, batched transactions, optional NDJSON progress.
- The **redrive transaction**: republish into the origin (new seq, **new id**, `Messq-Redrive-Of`,
  `Messq-Redrive-Count`, `trace_id` preserved), delete the DLQ row, emit `msg.publish` +
  `dlq.redrive` — one transaction per message, never split.
- The **guard rails**: `--limit` default 100 with no replay-everything flag, `--rate` default 10/s,
  refusal at `Messq-Redrive-Count >= 3` without `--force`, refusal without `--confirm <stream>`,
  the duration ceiling, the concurrent-job refusal, and unroutable/oversized/in-flight detection in
  the plan phase.
- **`messq dlq ls`** (all streams), **`messq dlq ls <stream>`** (grouped detail with growth),
  **`messq dlq ls <stream> --detail`** (rows), **`messq dlq show <id|seq:N>`**,
  **`messq dlq redrive`**, **`messq dlq purge`** — in all three output modes.
- The **`dlq_unread` finding** on `GET /v1/streams/{s}` (`#15`'s `findings[]` mechanism): a DLQ with
  depth > 0, no consumer and no redrive within `--dlq-unread-age`. `#24`'s `stream info` renders it;
  this issue supplies it and gives it teeth (age + last-redrive, not just "no consumer").
- **`meta['dlq.last_redrive.<stream>']`** — written in the redrive transaction so "when did anyone
  last do something about this DLQ" survives event trimming.
- Switching `#24`'s hint-registry DLQ entry to `messq dlq ls <stream>`, and adding the
  `dlq.redrive` line to `#20`'s `trace` renderer.
- Two amendments to merged work, called out in the PR for their owners: `#12`'s header degradation
  ladder must never drop `Messq-Redrive-*`; `#15`'s purge body gains an optional `seqs[]` selector
  so a single poison message can be deleted (§9).
- Verify checkers **P-DLQ6/7/8**, metrics, the `docs/OPERATIONS.md` DLQ runbook, and the tests below.

### Out of scope

- Dead-lettering itself, the provenance header set, `StripProvenance`, `SanitizeReason`, the DLQ
  stream template, I8 → **#12**. This issue *consumes* all of it and adds no new provenance header
  beyond the two `Messq-Redrive-*` names it defines.
- `replay` (re-publishing a *live* range), `seek`, and the generic destructive-action discipline
  (`--dry-run`/`--confirm`/`--yes`/`admin.action`) → **#28**. Redrive inherits; it does not fork.
- The CLI chassis, output modes, teaching-error rendering, exit codes → **#23**; `peek`, `pending`,
  `lag`, `stream`/`consumer` verbs and the `stream info` *layout* → **#24**.
- Retention actually deleting DLQ messages, the janitor, `--min-free-bytes` → **#27**.
- `messq_dlq_depth`, the collector, `alerts.yml`, the Grafana panel → **#21**. This issue proposes
  two counters and hands registration to `#21`'s registry (its cardinality test is the gate).
- `doctor`'s DLQ findings and the "your DLQ will fill the disk in N days" projection → **#30**.
- Exporting DLQ **bodies** to a file for offline forensics → considered and deferred (§12); the
  audit/NDJSON export path is **#42**, and `messq backup` (**#30**) already snapshots everything.
- A `dlq` HTTP surface for *consuming* the DLQ — it is an ordinary stream, so `messq sub orders.dlq
  drainer` already works (`#9` forces `dead_policy=drop` there). No new mechanism.
- Auto-redrive on a schedule, or any redrive the daemon starts by itself → **rejected**, §12.

## Design proposal

> Proposal and starting point, not a mandate. Four things **are** contracts because other issues,
> operators and `#18`'s frozen shapes depend on them: the redrive transaction shape (§4), the
> `Messq-Redrive-Of`/`-Count` header semantics (§4.2), the guard-rail table (§5), and the
> JSON field names of the three read routes (§2/§3).

### 1. Where the code lives

```
internal/queue/redrive.go     PlanRedrive (pure): selection → per-message verdict, blocked reasons
internal/store/dlq.go         DLQ summary/group/list queries (read pool), RedriveBatch (writer tx)
internal/api/dlq.go           GET /v1/dlq, /v1/dlq/{s}, /v1/dlq/{s}/messages, POST …/redrive
internal/api/redrivejob.go    pacing, batching, NDJSON progress, disconnect handling
internal/cli/cmddlq.go        dlq ls|show|redrive|purge
internal/cli/render/dlq.go    the grouped table, the row table, the show record, the impact block
internal/model/inv_dlq.go     P-DLQ6/7/8 (extends #12's file)
pkg/client/dlq.go             ListDLQ, GetDLQ, ListDLQMessages, Redrive (used by the CLI, D14)
```

No new goroutine census entry: a redrive job runs on the request's goroutine, submitting ordinary
commands to the single writer (§3.2). No background scheduler, no timer wheel.

### 2. The read side

**_Decision 1: `dlq ls` is served by the daemon, not assembled by the CLI._** Grouping 40 000 dead
messages by cause and subject in the CLI means downloading 40 000 messages during an incident.
`#21`'s cardinality rule (labels are `stream` and `consumer` only) deliberately keeps the same
breakdown out of `/metrics`, so this API is where it belongs. The routes sit under the
`/v1/dlq/{s}` prefix PLAN §7 already sanctions for redrive; they are additive and read-only.

```
GET /v1/dlq                      ?limit=&non_empty=1
GET /v1/dlq/{s}                  ?window=1h&groups=cause,subject,consumer&top=5
GET /v1/dlq/{s}/messages         ?cause=&consumer=&subject=&reason_contains=&since_ms=&until_ms=
                                 &order=oldest|newest&limit=&after=
```

`{s}` is the **origin** stream name (`orders`), never `orders.dlq` — the same rule `#21` uses for
`messq_dlq_depth`. Passing `orders.dlq` is a `400 bad_request` that names the fix, because getting
this wrong silently answers about the wrong stream.

```json
// GET /v1/dlq/orders?window=1h
{"stream":"orders","dlq_stream":"orders.dlq","exists":true,
 "depth":412,"bytes":1148912,
 "oldest_dead_at":1762074842114,"newest_dead_at":1762076122903,
 "growth":{"m5":102,"h1":398,"h24":412},
 "consumer_count":0,"last_redrive_at":null,
 "groups":{
   "cause":[{"key":"max_deliver","count":401,"oldest":…,"newest":…}],
   "subject":[{"key":"orders.charge.created","count":397,
               "top_reason":"upstream 503 on POST /charge","top_reason_count":395}],
   "consumer":[{"key":"billing","count":401},{"key":"invoices","count":11}]},
 "scanned":412,"estimated":false,
 "findings":[{"code":"dlq_unread","message":"orders.dlq has no consumer and no redrive in 30d",
              "next":["messq dlq ls orders","messq dlq redrive orders --limit 100 --dry-run"]}]}
```

Queries (proposal — provenance lives in the copy's `hdr` JSON, and SQLite's JSON1 functions are
compiled into `modernc.org/sqlite`):

```sql
-- depth / bytes / extremes: PK-range and the messages_age index, no scan
SELECT count(*), coalesce(sum(size),0), min(published_at), max(published_at)
  FROM messages WHERE stream = :dlq;

-- growth: one indexed count per window (messages_age = (stream, published_at))
SELECT count(*) FROM messages WHERE stream = :dlq AND published_at >= :since;

-- grouping: bounded scan of a small stream
SELECT json_extract(hdr,'$."Messq-Cause"') AS k, count(*), min(published_at), max(published_at)
  FROM messages WHERE stream = :dlq GROUP BY k ORDER BY 2 DESC LIMIT :top;
```

**`published_at` on a DLQ copy is the writer's `now` at the moment of death** (`#12` §6), so it *is*
the dead-at time for ordering and growth purposes, and it is indexed. `Messq-Dead-At` remains the
human-facing authority and the two are asserted equal (modulo `#7`'s monotonic clamp) by a test.

**Bounded work (I11):** grouping scans at most `--dlq-scan-max` rows (default 50 000). Above that,
groups are computed from the newest `--dlq-scan-max` rows and the response sets
`"estimated":true` with `"scanned":50000` — the CLI prints `(estimated from the newest 50,000 of
412,004)`. Silently truncating a triage view is how an operator concludes the wrong thing;
`#21` set the same precedent with `messq_metrics_estimated`.

`GET /v1/dlq` returns one row per stream that has a DLQ, `non_empty=1` by default, ordered by
`growth.h1` descending — *the DLQ that is filling right now sorts first*, which is the entire
argument of the issue summary ("400 in five minutes is an incident, 400 last Tuesday is a chore").

`last_redrive_at` comes from `meta['dlq.last_redrive.<stream>']`, written inside the redrive
transaction. Deriving it from the events table instead would silently become `null` after 72 h of
event retention (`--event-retention`), which is exactly when the question matters most.

Notes:

- **`last error` is the full reason from the `msg.dead` event, not the 1 KiB `Messq-Last-Reason`
  header.** `#12` truncates the header on purpose and keeps the full text in the event `detail`;

  everything narrative is stderr.
- `-o json` emits the same record with frozen field names; `dlq ls --detail -o ndjson` emits one
  object per dead message and is the intended input to `jq`-driven bulk triage.

### 4. Redrive — the transaction

**_Decision 2: one message = one transaction; a redrive is publish-and-delete, atomically._**

```sql
-- per message, inside one writer transaction (a batch runs N of these, still one commit)
-- 1. allocate a seq in the TARGET stream (#7's primitive)
UPDATE stream_seq SET next = next + 1 WHERE stream = :target RETURNING next - 1;

-- 2. republish: new seq, NEW id, ORIGINAL trace_id, rebuilt headers, dedup_key NULL
INSERT INTO messages (stream, seq, id, subject, hdr, body, size, published_at, trace_id, dedup_key)
SELECT :target, :newseq, :newid, m.subject, :hdr, m.body, m.size, :now, m.trace_id, NULL
  FROM messages m WHERE m.stream = :dlq AND m.seq = :dlqseq;

-- 3. the DLQ row is consumed by the redrive
DELETE FROM messages WHERE stream = :dlq AND seq = :dlqseq;

-- 4. two events, same tx (D11)
INSERT INTO events (…, 'msg.publish', msg_id = :newid,  …);
INSERT INTO events (…, 'dlq.redrive', msg_id = :originid, …, detail);

-- 5. once per batch
INSERT INTO meta (k,v) VALUES ('dlq.last_redrive.'||:stream, :now)
  ON CONFLICT (k) DO UPDATE SET v = excluded.v;
```

`changes()` is asserted after steps 2 and 3, exactly as `#12` does; a zero from step 3 means the row
vanished under us (a concurrent purge) and aborts the batch loudly rather than publishing twice.

Four decisions inside that shape:

1. **The DLQ row is deleted.** Keeping it and marking it redriven was rejected: `messq_dlq_depth`
   would never fall, so `#21`'s `MessqDlqNonEmpty`/`MessqDlqGrowing` alerts would never clear, a
   second `dlq redrive --limit 100` would re-publish the same hundred messages, and the DLQ would
   grow forever with no retention pressure. No evidence is lost — the payload is now in the origin
   stream, and `msg.dead` + `dlq.redrive` + the preserved `trace_id` keep the story in the journal,
   which is what the journal is for (D11).
2. **A new ULID is minted.** `#12` pinned this while relaxing `messages_id` to a non-unique index:
   *"redrive mints a new id, it does not preserve one"*. Verify checker **P-ID1** (*no non-`.dlq`
   stream contains two rows with the same `id`*) would fail otherwise — a redriven-then-re-dead-
   then-redriven message would collide with itself in the origin stream. Continuity rides on the
   preserved `trace_id` and on the `dlq.redrive` event (§4.3).
3. **A redrive is a client-class publish, not a broker-class one.** `#12`'s dead path sets
   `publishOpts.BypassLimits` because a message must always be able to die even at `ENOSPC` (§4.5).
   Redrive is the opposite — optional, operator-initiated work — so it respects subject matching,
   `max_msg_size`, `max_msgs`/`max_bytes`/`discard=new` and the `--min-free-bytes` gate. The plan
   phase detects every one of these before a message moves (§5).
4. **`dedup_key` is NULL on the redriven message.** Copying the origin's `Messq-Msg-Id` would let
   `messages_dedup` swallow the republish as a silent `DO NOTHING` — `#12`'s "single easiest way to
   get this feature wrong", one layer up.

#### 4.1 Headers on the redriven message

```go
// proposal
func RedriveHeaders(dlqHdr map[string]string, dlqStream string, dlqSeq int64) map[string]string {
    h := queue.StripProvenance(dlqHdr)                 // #12's helper: drops the whole Messq-* namespace
    h["Messq-Redrive-Of"]    = fmt.Sprintf("%s/%d", dlqStream, dlqSeq)
    h["Messq-Redrive-Count"] = strconv.Itoa(prevCount(dlqHdr) + 1)
    return h
}
```

`StripProvenance` removes everything in the `Messq-` namespace — including the previous
`Messq-Redrive-*` — so the count survives by **arithmetic**, read out of the DLQ copy before the
strip. The result is that a redriven message carries exactly two reserved headers, set by the
broker through the same `publishOpts` escape `#12` uses (`AllowReservedHeaders`), and `#7`'s
`reserved_header` rule stays intact for actual clients.

#### 4.2 `Messq-Redrive-Of` / `Messq-Redrive-Count` (contract)

| Header | Value | Meaning |
|---|---|---|
| `Messq-Redrive-Of` | `orders.dlq/7` | The DLQ stream and seq this incarnation came from. `<stream>/<seq>` because that pair is stable and greppable; PLAN §6 already blesses `stream/seq` as the stable identity. |
| `Messq-Redrive-Count` | `2` | How many times this payload has been round-tripped through the DLQ. Starts at `1` on the first redrive. **The loop guard reads this and nothing else.** |

When this message dies again, `#12`'s dead path copies the origin's user headers into the new DLQ
copy, so both headers ride along and the count keeps climbing. **Amendment to `#12`:** its header
budget degradation ladder (drop `Messq-Last-Reason`, then `Messq-Origin-Published-At`) must never
drop `Messq-Redrive-*` — losing the count silently disarms the loop guard. One line, called out in
the PR for `#12`'s owner.

#### 4.3 Events

Two events per redriven message, in the same transaction, both from the closed vocabulary (§9.2):

```json
{"event":"dlq.redrive","ts":1762076500000,
 "stream":"orders","consumer":"billing","subject":"orders.charge.created",
 "msg_id":"01J8ZQ4K2M9V0X7Y3B5N6C8D1E", "seq":7, "trace_id":"4bf92f35…",
 "actor":"token:ops-laptop",
 "detail":{"from_stream":"orders.dlq","from_seq":7,
           "to_stream":"orders","to_seq":10981,"new_msg_id":"01JBQ9F0Z3…",
           "redrive_count":2,"forced":false,"cause":"max_deliver","attempts":5,
           "job_id":"01JBQ9EY8W…"}}
```

- `msg_id` is the **origin** id, so `messq trace 01J8ZQ4K2M…` (the id in the incident ticket) finds
  the redrive and renders *"→ redriven as `01JBQ9F0Z3…`"*. The ordinary `msg.publish` carries the
  new id, so the new lineage also traces from its start; both share the `trace_id`, so
  `messq trace --trace-id 4bf92f35…` shows the entire loop as one story.
- Level **WARN**, **never sampleable** — it joins `#19`'s allow-list beside `msg.dead`.
- One `admin.action` per *invocation* (`#28`'s discipline) with actor, parameters and before/after
  DLQ depth. `dlq purge` reuses `#15`'s `stream.purge` event unchanged.

**`#20` amendment:** one renderer row so the timeline reads

```
  09:14:55.310  dead      billing  attempt 5/5  cause=max_deliver     → orders.dlq seq 7
  18:02:11.004  redrive   ops      from orders.dlq/7 → orders seq 10981 as 01JBQ9F0Z3…  (2nd redrive)
```

### 5. Redrive — the guard rails

**_Decision 3: every guard rail is enforced server-side, and the CLI only makes them pleasant._**
`curl` is a first-class client (D2); a rate limit that lives in cobra protects nobody at 3 a.m.
when someone pastes a `curl` loop out of a runbook.

| # | Guard | Enforcement | Refusal |
|---|---|---|---|
| G1 | **`limit` defaults to 100** and there is **no `--all`** | `RedriveRequest.Limit` required; server clamps to `--dlq-max-redrive-limit` (10 000) and echoes the effective value | clamped + `warnings[]`, never silent |
| G2 | **`rate` defaults to 10/s**, ceiling `--dlq-max-rate` (1 000/s) | token bucket in the job loop, between batches | `400 bad_request` above the ceiling, naming it |
| G3 | **Loop guard**: `Messq-Redrive-Count >= --dlq-redrive-loop-limit` (3) | plan phase marks the message `blocked{reason:"redrive_loop"}` | `409 redrive_loop` unless `--force`; forced runs set `detail.forced=true` and log WARN |
| G4 | **Confirmation by name** (`?confirm=orders`) | `#15`/`#28` machinery | `409 confirm_required` / `409 confirm_mismatch` |
| G5 | **Dry run is the truth** | one `planRedrive`, `dry_run` returns before `applyRedrive` | — |
| G6 | **Duration ceiling**: `limit / rate > --dlq-redrive-max-duration` (10 m) | plan phase | `400 bad_request`: *"100 000 at 10/s is 2h47m; raise --rate or lower --limit"* |
| G7 | **One job per DLQ stream** | in-memory job registry keyed by stream | `409 redrive_conflict` naming the running `job_id`, its progress and its actor |
| G8 | **Unroutable / oversized / disk-gated messages** | plan phase evaluates the *target* stream's admission rules per message | refuse the whole job with counts, unless `--skip-blocked` |
| G9 | **In-flight to a DLQ drainer** | plan phase checks `deliveries` on the DLQ stream | blocked unless `--force`; forcing drops the delivery row **and bumps the drainer's generation** (the purge fencing rule, `#15`) |
| G10 | **Target must exist and accept the subject** | plan phase | `404 not_found` / `400 subject_mismatch`, `next` naming `--to-stream` |

**_Decision 4: a redrive job is not crash-resumable, and the daemon never resumes one by itself._**
`#15` made large purges resumable through `meta.purge.<ulid>` because a purge that stops halfway
leaves a disk problem unsolved. A redrive is the opposite: it is a deliberate act of pushing load
onto a service someone is watching. Auto-resuming after a restart would fire traffic at a
downstream nobody is watching any more. If the daemon restarts mid-job, the unredriven messages are
simply still in the DLQ (each message's publish+delete was atomic, so there is nothing torn) and
the operator re-runs the command. The `admin.action` event records `requested` vs `redriven` so the
gap is visible. Same rule for client disconnect: the job stops at the end of the current batch, and
`PROTOCOL.md` says so in one sentence.

### 6. Plan / impact / apply

Reusing `#15`'s `Impact` type and its "preview and execution share one plan" decision:

```go
// internal/queue — pure: verdicts only, no I/O, no clock beyond the passed now.
type RedriveVerdict struct {
    DLQSeq  int64
    MsgID   string
    Subject string
    Bytes   int64
    Count   int    // Messq-Redrive-Count before this redrive
    Blocked string // "" | "redrive_loop" | "subject_mismatch" | "too_large" | "in_flight" | "stream_full"
}

func PlanRedrive(rows []DLQRow, target StreamConfig, opt RedriveOptions, now int64) RedrivePlan

type RedriveImpact struct {
    Messages     int64             `json:"messages"`
    Bytes        int64             `json:"bytes"`
    Blocked      map[string]int64  `json:"blocked,omitempty"`      // reason → count
    ByCause      map[string]int64  `json:"by_cause,omitempty"`
    BySubject    map[string]int64  `json:"by_subject,omitempty"`
    FirstDLQSeq  int64             `json:"first_dlq_seq,omitempty"`
    LastDLQSeq   int64             `json:"last_dlq_seq,omitempty"`
    RatePerSec   float64           `json:"rate"`
    EstimatedMS  int64             `json:"estimated_ms"`
    DepthBefore  int64             `json:"depth_before"`
    DepthAfter   int64             `json:"depth_after"`
    Warnings     []string          `json:"warnings,omitempty"`
}
```

The plan is computed on the read pool (the DLQ is small and this is not a writer job); the apply
phase re-reads each row inside its batch transaction and re-checks the verdict, so a plan that has
gone stale (a concurrent purge, a `stream edit` lowering `max_msg_size`) degrades to a per-message
skip recorded in the response rather than a wrong write. `dry_run=1` returns after planning.

Warnings the plan emits, because they are the sentences that prevent the second incident:

- `billing is paused — redriven messages will sit in orders until you resume it`
- `96 of these died on "upstream 503 on POST /charge"; nothing indicates it is fixed`
- `orders has no consumer matching orders.charge.created — these will not be delivered`
- `redriving 100 messages into a stream with 1,284 already pending on billing`

```console

  Each redrive republished it and it died again. A fourth attempt will almost certainly
  produce a fourth death; the payload or the handler has to change first.

  See the loop:  messq trace --trace-id 4bf92f3577b34da6a3ce929d0e0e4736
  Override:      messq dlq redrive orders --ids 01J8ZQ4K2M9V0X7Y3B5N6C8D1E --confirm orders --force
  Drop it:       messq dlq purge orders --seqs 7 --confirm orders.dlq

```

Machine mode is a first-class path, not an afterthought: `--progress` plus `-o ndjson` sets
`Accept: application/x-ndjson` and streams one record per redriven message
(`{"dlq_seq":7,"msg_id":"01J8ZQ…","new_msg_id":"01JBQ9…","to_seq":10981,"redrive_count":2}`),
followed by a final summary object — D2 explicitly kept content negotiation open for exactly this.
Without `--progress`, `-o json` prints the summary object once, at the end.

### 9. `dlq purge`

A thin, safer face over `#15`'s `POST /v1/streams/orders.dlq/purge`:

- **Confirmation is by the DLQ name** (`--confirm orders.dlq`), and `--confirm orders` is a
  `confirm_mismatch` naming both — purging the origin when you meant the DLQ is a data-loss bug the
  guard rail must catch.
- The dry run prints what will be destroyed *and* what survives: *"the payloads are deleted; the
  `msg.dead` events stay until `--event-retention` (72 h), so `messq trace` keeps the story but not
  the body."*
- **Proposed amendment to `#15`**: the purge body gains an optional `seqs: [7, 9]` selector (mutually
  exclusive with `up_to_seq`/`keep`), so a single poison message can be removed without waiting for
  retention. Same plan/impact/apply path, same fencing rules, `--purge-max-rows` unchanged. Called
  out in the PR for `#15`'s owner; if it is rejected, `dlq purge --seqs` drops out and the teaching
  error in §7 points at `--up-to-seq` instead.

### 11. Edge cases, decided

| Case | Handling |
|---|---|
| `{s}` given as `orders.dlq` | `400 bad_request` naming the origin form. The route takes origin names, like `messq_dlq_depth` |
| DLQ stream does not exist | `GET` returns `{"exists":false,"depth":0}` and exit `0` (`#23`: zero rows is a successful answer). `redrive` is `404 not_found` |
| Origin stream deleted, DLQ survives (`#15` keeps it deliberately) | Plan refuses with `404`, `next` = `messq dlq redrive orders --to-stream repairs` and `messq stream add orders …` |
| Origin's subjects narrowed since the death | Per-message `blocked{subject_mismatch}`; whole job refused unless `--skip-blocked`; `--to-stream` accepts a stream that does match |
| Origin's `max_msg_size` lowered below the payload | `blocked{too_large}`, same treatment. The message can still *die* into a DLQ (that path bypasses limits, `#12`) but cannot be *published* |
| `discard=new` origin at `max_msgs` | `blocked{stream_full}` in the plan; if it fills mid-job the batch records a per-message failure and the job stops with a teaching summary |
| Free space below `--min-free-bytes` | `507 disk_full` before anything moves. Redrive is a publish; §4.5 gates publishes and not acks, deliberately |
| Store latched read-only (fsyncgate, D4) | `503 read_only`; the read routes keep working, which is the point of the latch |
| Two DLQ rows share a `msg_id` (two consumers dead-lettered the same seq) | `--ids <that id>` → `409 ambiguous_id` listing both `seq`s; `seq:N` disambiguates. `dlq show` prints both candidates |
| A drainer consumer holds an in-flight delivery on the row being redriven | `blocked{in_flight}`; `--force` drops the delivery row and bumps that consumer's generation, so its ack fails as `stale_ack` with a named cause instead of silently succeeding as T3a |
| Concurrent `stream purge orders.dlq` deletes rows mid-job | Step 3's `changes()==0` → per-message skip recorded as `failed{gone}`; nothing is published twice |
| Redrive into `orders` while `orders` is being purged (`#15`'s `202` path) | `409 purge_conflict` naming the running purge |
| Rate `0` or negative | `400 bad_request`. There is no "as fast as possible" spelling; `--rate 1000` is |
| Client disconnects, or the daemon restarts, mid-job | Stops at the current batch boundary; no resume (Decision 4). Completed messages are fully redriven, the rest untouched in the DLQ; `admin.action` records `redrove` < `requested` with `detail.stopped` |
| `Messq-Redrive-Count` absent or unparseable (hand-published header, corrupted copy) | Treated as `0`; a `dlq.redrive` `detail.count_unparseable=true` records it. Never fail a redrive over a malformed counter |
| `json_extract` unavailable in the SQLite build | A store-level capability test at startup; grouping falls back to decoding `hdr` in Go over the bounded scan. Behaviour identical, slower |
| The DLQ is 4 M rows (retention off, nobody looked for a year) | `estimated:true` grouping, exact `depth`/`bytes` (index-only), and the `dlq_unread` finding says how long it has been ignored |

### 12. Considered and deferred

| Idea | Why not now |
|---|---|
| `messq dlq redrive --all` | Deliberately absent. The summary is explicit: *"`--limit` defaults to 100 with no replay-everything flag"*. `--limit 10000` is typeable and forces a number to exist in the shell history and the audit event |
| Auto-redrive on a schedule / an exponential re-DLQ policy | The daemon must never push load at a downstream on its own. A cron calling `messq dlq redrive --limit 50 --confirm X` is the supported shape, and it is one line in `OPERATIONS.md` |
| Redrive to a *different consumer* (re-deliver to only one) | Redrive republishes into a stream; which consumers pick it up is the stream's business. Per-consumer replay is `seek`'s job (`#28`) |
| Exporting DLQ bodies to a file (`messq dlq export`) | `messq backup` (`#30`) snapshots everything consistently, and `#42` owns NDJSON export. Two export mechanisms would drift |
| Editing a payload during redrive (`--patch`) | A broker that rewrites payloads is no longer answerable: `trace` would show a message that is not the message. Consume, fix, republish with `messq pub` |
| A `redrive` route on the origin stream (`POST /v1/streams/{s}/redrive`) | PLAN §7 already names `/v1/dlq/{s}/redrive`; two spellings of one verb is a support category |

## Acceptance criteria

- [ ] `GET /v1/dlq`, `GET /v1/dlq/{s}` and `GET /v1/dlq/{s}/messages` exist, are read-only (a
      store-snapshot diff across a call proves zero mutations, including no cursor movement), take
      **origin** stream names, and reject `<stream>.dlq` with a `400` that names the fix.
- [ ] `GET /v1/dlq/{s}` reports exact `depth`/`bytes`, `growth` over 5 m / 1 h / 24 h, and groups by
      cause, subject and consumer; grouping beyond `--dlq-scan-max` sets `estimated:true` and
      `scanned`, and the CLI renders that qualifier.
- [ ] `messq dlq ls` (no argument) lists every stream with a non-empty DLQ ordered by 1 h growth
      descending; `messq dlq ls <stream>` renders the grouped view; `--detail` renders rows; all
      three work in `table`, `json` and `ndjson`.
- [ ] `messq dlq show <id>` prints origin, cause, trigger, attempts, dead-at, **the full last error
      from the `msg.dead` event**, redrive history and a bounded body preview, and ends with the
      `messq trace` next command.
- [ ] An ambiguous id (two consumers dead-lettered the same seq) is refused by `dlq show` and
      `redrive --ids` with both candidates listed and `seq:N` named as the fix — never guessed.
- [ ] `POST /v1/dlq/{s}/redrive` republishes into the origin with a **new seq and a new ULID**, the
      **original `trace_id`**, `Messq-Redrive-Of: <dlq>/<seq>`, `Messq-Redrive-Count` incremented,
      and no other `Messq-*` header from the DLQ copy.
- [ ] The DLQ row is deleted in the **same transaction** as the republish: a test counts commits and
      asserts one per batch, and a crash at any declared fault point leaves every message either
      fully redriven or fully in the DLQ — **never both, never neither**.
- [ ] `?dry_run=1` returns the same `impact` field-for-field as the real run produces, changes
      nothing, and needs no `?confirm=`.
- [ ] Redrive without `?confirm=<stream>` is `409 confirm_required`; a mismatched confirm is
      `409 confirm_mismatch` naming both values; non-TTY CLI use without `--yes` is exit `2`.
- [ ] A message with `Messq-Redrive-Count >= 3` is refused with `409 redrive_loop` and a teaching
      error offering `--force`, the `messq trace --trace-id` command, and the purge alternative;
      `--force` succeeds and records `detail.forced=true` on the `dlq.redrive` event.
- [ ] **A redrive of a still-failing message re-dead-letters, and `messq trace --trace-id T` shows
      the full loop**: publish → deliver ×5 → dead → redrive → deliver ×5 → dead, with
      `Messq-Redrive-Count: 1` on the second DLQ copy.
- [ ] Default `--limit` is 100 and default `--rate` is 10/s; there is no flag that redrives
      everything; a `limit` above `--dlq-max-redrive-limit` is clamped with the effective value
      echoed and a warning, and `limit/rate` beyond `--dlq-redrive-max-duration` is refused with a
      message naming both numbers.
- [ ] The rate limit is **server-enforced**: a raw `curl` redrive of 50 at `rate:5` takes ≥ 10 s
      (measured on the fake clock), and a second concurrent redrive on the same DLQ is
      `409 redrive_conflict` naming the running job.
- [ ] Blocked messages (loop, `subject_mismatch`, `too_large`, `stream_full`, `in_flight`) are
      detected in the **plan** phase, refuse the whole job by default with per-reason counts, and
      are skipped only with `--skip-blocked`.
- [ ] Redrive respects target-stream admission: it is refused under `--min-free-bytes`
      (`507 disk_full`) and when the store is latched read-only (`503 read_only`), while the DLQ
      **read** routes keep answering.
- [ ] Every redriven message emits one `msg.publish` (new id) and one `dlq.redrive` (origin id,
      linking both), and every invocation emits one `admin.action` with actor, parameters and
      before/after depth. No event name outside PLAN §9.2 is introduced.
- [ ] `meta['dlq.last_redrive.<stream>']` is written in the redrive transaction and surfaces as
      `last_redrive_at`; the `dlq_unread` finding fires only when depth > 0, no consumer exists and
      no redrive happened within `--dlq-unread-age`, and `messq stream info` renders it with the
      `messq dlq ls` fix command.
- [ ] `messq dlq purge <stream>` confirms with `<stream>.dlq`; `--confirm <stream>` is refused as a
      mismatch; the dry run states that payloads go and the `msg.dead` events remain.
- [ ] `#24`'s hint registry points at `messq dlq ls <stream>` and `TestHintsResolve` passes; `#20`'s
      trace renderer prints the `redrive` line.
- [ ] Verify checkers **P-DLQ6/7/8** are registered and green on a redrive-heavy workload.
- [ ] `docs/OPERATIONS.md` gains the DLQ triage runbook (RB-02, referenced by `#21`'s alert) and
      every command block in it executes in CI.

## Test plan

Per PLAN §11: `-race` everywhere, no `time.Sleep` outside soak, real SQLite files in `t.TempDir()`
(never `:memory:`), every fixed bug lands with its reproduction artefact.

1. **Unit — `internal/queue` (pure, ≥ 90 % floor).** `PlanRedrive` table: every `Blocked` reason,
   the loop threshold at `count = 2/3/4`, `--force`, `--skip-blocked`, `--order`, limit clamping,
   the duration ceiling, empty selection. `RedriveHeaders`: strips the whole `Messq-` namespace,
   sets exactly two headers, increments correctly, tolerates a missing/garbage/negative/huge
   `Messq-Redrive-Count`, and its output passes `#7`'s `reserved_header` validator for every
   *user* header. `prevCount` gets a **fuzz target** (headers are attacker-influenceable via a
   publisher that got a header past an older binary).
2. **Unit — filters and formatting.** The `cause`/`consumer`/`subject`/`reason_contains`/time
   selectors as a table over a fixture DLQ; growth-window bucketing across a clock boundary;
   `estimated` flagging at exactly `--dlq-scan-max` and one over.
3. **Store — `internal/store` (real files, ≥ 85 % floor).** `TestRedrive_Atomic` (one commit per
   batch, asserted via `messq_commit_batch_size`); `TestRedrive_NewIDPreservedTrace`;
   `TestRedrive_DeletesDLQRow`; `TestRedrive_DedupKeyNull` (a redriven message whose origin had a
   `Messq-Msg-Id` is **not** swallowed); `TestRedrive_ToStream`; `TestRedrive_RowVanished`
   (concurrent purge → `changes()==0` → skip, no double publish); `TestRedrive_InFlightForce`
   (delivery row dropped, generation bumped, the drainer's ack becomes `stale_ack`);
   `TestDLQSummary_Queries` (index usage asserted with `EXPLAIN QUERY PLAN`: no full scan for
   depth/bytes/growth).
4. **Property (`pgregory.net/rapid`), folded into `#13`'s suite.** A generator that publishes,
   fails messages into the DLQ, redrives random subsets at random rates, purges, seeks and
   restarts, with the invariant hook checking after every action:
   - **P-DLQ6 (redrive conservation)** — for every stream, `dlq_depth_before = dlq_depth_after +
     redriven + purged + expired`, and every `dlq.redrive` event has exactly one matching
     `msg.publish` in the target stream with the same `trace_id`.
   - **P-DLQ7** — no message in a non-`.dlq` stream carries any `Messq-Origin-*`, `Messq-Cause`,
     `Messq-Attempts` or `Messq-Dead-At` header (proves `StripProvenance` ran).
   - **P-DLQ8** — no message carries `Messq-Redrive-Count` above `--dlq-redrive-loop-limit` unless
     the corresponding `dlq.redrive` event has `detail.forced=true`.
   - Existing **I8** and **P-ID1** stay green: redriving must never produce two rows with the same
     `id` in a non-DLQ stream. A sabotage build that preserves the id must be caught within the PR
     check budget.
   Failfiles committed to `testdata/regressions/`.
5. **Timing (`testing/synctest`).** Rate limiting: 50 messages at 5/s takes exactly 10 s of fake
   time and is not front-loaded (inter-batch pacing asserted); the duration ceiling; the
   disconnect-stops-at-batch-boundary path. No `time.Now`/`time.Sleep` in the job loop
   (lint-enforced, `#3`'s Clock seam).
6. **Crash (`#8`'s harness; `#32` owns the nightly matrix).** New fault points behind the
   `messq_fault` tag: `redrive.before_publish`, `redrive.after_publish`, `redrive.before_delete`,
   `redrive.after_commit_before_reply`. SIGKILL at each, restart, then assert per message: fully in
   the target stream with the DLQ row gone, **or** fully in the DLQ with nothing published. The
   ledger oracle gains a REDRIVEN outcome (observed-before-kill = OK, in-flight = UNKNOWN,
   never-requested = FAILED). ≥ 200 cycles per merge, 1 000 nightly in both durability modes;
   `messq verify` and `PRAGMA integrity_check` clean after every cycle.
7. **Integration — the headline scenario.** A handler that always fails: publish → 5 attempts →
   DLQ → `dlq redrive --confirm` → 5 more attempts → DLQ again. Assert: two `msg.dead` events, one
   `dlq.redrive`, `Messq-Redrive-Count: 1` on the second copy, a third redrive attempt refused at

   as one timeline (golden, byte-for-byte).
8. **Golden events and API shapes.** Exact event sequence and `detail` field sets for redrive
