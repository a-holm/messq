## Context

`#10` and `#11` both route a delivery to a **DEAD** outcome and both stop at the same seam: a
`TODO(#12)` that deletes the delivery row, emits `msg.dead` and stamps
`detail.dlq = "not_implemented"`. This issue fills that seam and makes DEAD mean something.

PLAN **D3** adjudicated the DLQ shape: it is **a real stream, `<stream>.dlq`**, not an in-place
terminal state and not a side table. The objection to that design (atomicity across two journals)
evaporates under **D1**: the copy into `<stream>.dlq`, the deletion of the delivery row and the
`msg.dead` event are **one SQLite transaction**. One mechanism then buys four features that would
otherwise be four features:

| Feature | What it costs, given DLQ-as-stream |
|---|---|
| Inspection | `messq peek orders.dlq` — nothing |
| Redrive | consume + republish (`#29`) — nothing new in the engine |
| Alerting | stream depth gauge (`#21`) — nothing |
| Retention | stream retention (`#27`) — nothing |

The differentiating half is **provenance**. A DLQ that only holds bodies is a graveyard. PLAN
§5.1 requires the copy to carry `Messq-Origin-Stream/-Seq/-Consumer`, `Messq-Attempts`,
`Messq-Cause`, `Messq-Last-Reason`, `Messq-Dead-At`, and — the load-bearing part — **the original
`id` and `trace_id`**, so `messq trace <id>` (`#20`) shows publish → deliver → timeout → nak →
dead → *DLQ hop* → redrive as one continuous story rather than two unrelated messages.

Governing sections: **D3** (DLQ as a stream), **D1** (one transactional boundary), **§5.1**
(dead-lettering, one transaction, the reserved `Messq-` prefix), **§5.2 I8** (DLQ conservation),
**§4.2** (schema — including the `messages_id` uniqueness question this issue must settle),
**§4.5** (DLQ writes continue under disk pressure), **§9.2** (`msg.dead` is in the closed event
vocabulary; no new event names).

What it unlocks: `#13` can finally check I8 against a real implementation, and `#29`'s entire
triage workflow (`dlq ls/show/redrive/purge`) becomes ordinary stream operations.

## Scope

**In scope**

- The unified dead-path seam: one interface, replacing the two placeholders `#10` and `#11` each
  landed under different names.
- `internal/queue`: the pure dead-letter planner — cause/trigger/policy resolution, DLQ naming,
  provenance-header construction, reason sanitisation and truncation, provenance stripping.
- `internal/store`: the dead-letter transaction — auto-create `<stream>.dlq`, copy the payload,
  delete the delivery row, emit exactly one `msg.dead`. All inside the caller's existing
  transaction.
- Migration `0002`: relax `messages_id` from UNIQUE to a plain index, because a preserved `id`
  is a **lineage**, not a row key (§ *Identity*, below). Includes the `PeekID` follow-through.
- `publishOpts` extensions in `#7`'s `publishTx`: `BypassLimits`, header-cap override, event
  suppression — dead-lettering is a broker migration, not a client publish, and may never be
  refused by a stream limit.
- The auto-created DLQ stream template and its flags (`--dlq-max-age`, …).
- A per-transaction dead-letter budget so one sweeper tick cannot copy 512 MiB inside a 2 ms
  commit window.
- Invariant **I8** stated precisely (per *generation*), its checker in `internal/model`, and its
  `messq verify` checkers added to `#8`'s set.
- `dead_policy=drop`: delete + event only, no copy.
- Tests: unit, store, migration, focused property, crash, golden events, bench.

**Out of scope**

- `messq dlq ls|show|redrive|purge`, redrive guard rails, `Messq-Redrive-Of/-Count` → **#29**
  (this issue defines the reserved namespace and the `StripProvenance` helper it will use).
- `POST /v1/dlq/{s}/redrive` and every other HTTP endpoint → **#14** / **#15**.
- `messq_dlq_depth` registration, alert rules, dashboard panel → **#21**.
- `msg.dead` log rendering, sampling policy, `messq trace`'s DLQ line → **#19** / **#20**.
- Retention actually *deleting* DLQ messages (the janitor) → **#27**.
- The full rapid suite with the `RESTART` action → **#13** (this issue ships a focused,
  dead-heavy property test only).
- Fault-point activation grammar and the nightly crash matrix → **#32** (this issue *declares*
  the fault points and uses them in a fast subset).
- `stream info` warning "this DLQ has no consumer" → **#29**; `doctor`'s DLQ findings → **#30**.
- Consumer `dead_policy` validation and the "no `dlq` policy on a `.dlq` stream" rule → **#9**

## Design proposal

> Everything below is a **proposal and starting point**. Names, budgets and defaults are
> negotiable; the transaction shape, the provenance set, the identity decision and I8 are not.

### 1. Where the code lives

```
internal/queue/dead.go        DeadCtx, DeadCause, DeadTrigger, PlanDead (pure)
internal/queue/dlq.go         DLQName, IsDLQ, OriginOf, ProvenanceHeaders,
                              StripProvenance, SanitizeReason
internal/store/dead.go        DeadSink implementation (runs inside the caller's tx)
internal/store/migrations/0002_msg_id_lineage.sql
internal/model/inv_dlq.go     I8 checker (shared by verify and the property suite)
```

No new goroutine, no new command type, no new writer path: dead-lettering executes inside the
transaction `#10`'s `SettleCmd` or `#11`'s `SweepCmd` already opened.

### 2. The unified seam

`#10` shipped `store.DeadSink`/`DeadCtx` returning `(obs.Event, error)`; `#11` shipped
`store.DeadLetterer`/`DeadContext` returning `error`. Two names for one concept is a bug waiting
for a divergence. **Pick `DeadSink`, delete `DeadLetterer`**, move the context type into
`internal/queue` (it is pure data that the pure planner also needs), and return a result the
caller folds into *its* `msg.dead` event — so there is exactly **one** `msg.dead` per DEAD
transition, which is what I8 rests on.

```go
package queue

type DeadCause string   // "max_deliver" | "terminated"                       (exhaustive-linted)
type DeadTrigger string // "ack_wait" | "nak" | "term" | "policy_lowered"     (exhaustive-linted)

// DeadCtx is everything the dead path needs. Assembled by #10 (term / nak exhaustion) and
// #11 (ack_wait exhaustion / retire pass); consumed by the pure planner and by the store.
type DeadCtx struct {
    Key         ConsumerKey // {Stream, Consumer} — the ORIGIN stream
    Seq         int64
    Subject     string
    MsgID       string // ULID of the origin message — preserved on the copy
    TraceID     string // preserved on the copy
    Generation  int64
    Attempts    int
    MaxDeliver  int
    Policy      DeadPolicy // dlq | drop (from #9's consumer config)
    Cause       DeadCause
    Trigger     DeadTrigger
    LastReason  string // last nak/timeout reason; may be empty
    PublishedAt int64  // origin published_at, ms
    NowMS       int64  // writer's now — the authority for Messq-Dead-At
}
```

```go
package store

type DeadOutcome string // "written" | "dropped" | "origin_missing"

type DeadResult struct {
    Outcome   DeadOutcome
    DLQStream string // "" when dropped
    DLQSeq    int64  // 0 when not written
    Bytes     int64  // payload bytes copied (budget accounting, msg.dead detail)
}

// DeadSink runs INSIDE the caller's transaction. It never commits, never opens a nested
// transaction, and never emits an event — the caller owns the single msg.dead.
type DeadSink interface {
    Dead(ctx context.Context, tx *sql.Tx, d queue.DeadCtx, b *DeadBudget) (DeadResult, error)
}
```

Callers change by three lines each: pass the budget, take the result, merge
`result.{Outcome,DLQStream,DLQSeq}` into the `msg.dead` `detail`. The `// TODO(#12)` tests that
`#10`/`#11` wrote (asserting the seam is invoked exactly once per DEAD with the exact context a
copy will need) keep passing unchanged — that was the point of writing them.

### 4. Provenance headers (normative)

Stored in the copy's `hdr` JSON alongside the origin's user headers. There can be no collision:
`#7` rejects any user header whose canonical form starts with `Messq-` with `reserved_header`,
and that reservation exists *for this table*.

| Header | Example | Status |
|---|---|---|
| `Messq-Origin-Stream` | `orders` | PLAN §5.1 |
| `Messq-Origin-Seq` | `10493` | PLAN §5.1 |
| `Messq-Origin-Consumer` | `worker` | PLAN §5.1 |
| `Messq-Attempts` | `5` | PLAN §5.1 |
| `Messq-Cause` | `max_deliver` \| `terminated` | PLAN §5.1 (closed enum) |
| `Messq-Last-Reason` | `upstream 503 on POST /charge` | PLAN §5.1; omitted when empty |
| `Messq-Dead-At` | `2026-09-21T09:14:55.310Z` | PLAN §5.1 |
| `Messq-Max-Deliver` | `5` | *proposal* — makes "5/5" readable without fetching consumer config, which may have changed or been deleted |
| `Messq-Trigger` | `ack_wait` \| `nak` \| `term` \| `policy_lowered` | *proposal* — `#11` already distinguishes these; "died on a timeout" vs "died on a nak" is the first triage question |
| `Messq-Origin-Generation` | `1` | *proposal* — the only field that distinguishes two legitimate copies of the same `(consumer, seq)` across a seek (see I8) |
| `Messq-Origin-Published-At` | `2026-09-21T09:14:02.114Z` | *proposal* — survives retention deleting the origin; `dlq ls` shows "how old was this message when it died" |
| `Messq-Last-Reason-Truncated` | `true` | *proposal* — present only when truncation occurred; silence about truncation is how people misread errors |

Rules:

- **Keys are canonicalised** with `textproto.CanonicalMIMEHeaderKey`, values are strings, JSON is
  marshalled with sorted keys (goldens stay stable). Same conventions as `#7`.
- **Timestamps are RFC3339 with milliseconds, UTC.** Everything else in messq uses Unix ms
  integers, and that stays true in the database and the events table; headers are the one
  human-facing surface (`curl`, `dlq show`, `peek --raw`), and `1758445495310` is not a timestamp
  a human reads at 3 a.m. Decision recorded in `SEMANTICS.md`.
- **`Messq-Last-Reason` is sanitised, then truncated** to `--dlq-reason-header-bytes` (1 KiB) on a
  rune boundary. The reason can be up to 4 KiB of a child process's **stderr** (`#25`), i.e.
  arbitrary bytes: `SanitizeReason` enforces valid UTF-8 (invalid sequences → U+FFFD), maps C0/C1
  control characters to their escapes, collapses runs of whitespace, and never emits a bare
  newline into a header value. The full untruncated reason stays in `deliveries.last_reason`'s
  final value inside the `msg.dead` event `detail`, so nothing is lost — `trace` shows it in full.
- **The origin's `Messq-Msg-Id` (dedup key) is not copied**, as a header or otherwise. It is
  publisher-supplied and routinely carries an order id, an email or a tenant identifier; `#7`
  already keeps it out of events for exactly that reason (PLAN §10).
- **Header budget**: the copy's `hdr` cap is raised to `MaxHeaderBytes * 2` (8 KiB) for broker
  writes, because the origin may legitimately be at the 4 KiB user cap and provenance must still
  fit. If it *still* does not fit (pathological), drop `Messq-Last-Reason` first, then
  `Messq-Origin-Published-At`, and record `detail.headers_trimmed` on `msg.dead`. Never fail the
  dead-letter over a header.

### 5. The auto-created DLQ stream

Created lazily, inside the same transaction as the first dead letter it holds. Template:

| Field | Value | Why |
|---|---|---|
| `name` | `<origin>.dlq` | D3 |
| `subjects` | `[">"]` | must accept whatever the origin accepted, forever, including after the origin's subjects are narrowed |
| `retention` | `limits` | never `workqueue`: a DLQ must not delete itself because someone happened to consume it |
| `max_age_ms` | `--dlq-max-age`, default **30 d** | D3 / plan-03 |
| `max_msgs`, `max_bytes` | `--dlq-max-msgs`/`--dlq-max-bytes`, default `0` (unlimited) | with limits at 0, `discard` never fires, so nothing is silently dropped by count |
| `max_msg_size` | `--max-msg-size-ceiling` (8 MiB) | a message must always be able to die, whatever the origin's limit was or becomes |
| `discard` | `old` | only reachable if an operator sets a count/byte limit deliberately |
| `dedup_window_ms` | **0** | see below — this one is a correctness requirement, not a preference |
| `created_at` | writer's now | |

**`dedup_window_ms = 0` and `dedup_key = NULL` on every copy.** If the origin's dedup key were
copied, two different deaths carrying the same key (the same message dead-lettered for two
consumers; or a redriven message dying again) would hit `messages_dedup` and the second insert
would be a silent `DO NOTHING` — a dead letter that vanishes. I8 would fail and the operator
would never know. This is the single easiest way to get this feature wrong.

Auto-creation emits the ordinary `stream.create` event with `actor = "system"` and
`detail: {"reason":"dead_letter","origin":"orders"}` — no new event name (PLAN §9.2 is closed).
`StreamInfo` gains `dlq: bool` and `origin: string` (derived, not stored) so `#15`/`#24`/`#29`
can render and filter without re-deriving the suffix rule.

Operator interactions, all decided here:

- `messq stream add orders.dlq` → `reserved_name` (already `#7`'s rule).
- `messq stream edit orders.dlq --max-age 90d` → **allowed**. Tuning DLQ retention is a normal
  operation.
- `messq stream rm orders.dlq --confirm orders.dlq` → allowed; it is recreated from the template
  on the next death, and the CLI warns that operator edits will be lost.
- `messq consumer add orders.dlq drainer` → allowed (`dead_policy` forced to `drop` by `#9`).

### 6. The transaction

Executed inside the caller's open transaction, in this order:

```sql
-- 1. ensure the DLQ stream exists (idempotent; no read-then-write race — one writer, one tx)
INSERT INTO streams (name, subjects, retention, max_msgs, max_bytes, max_age_ms,
                     max_msg_size, discard, dedup_window_ms, created_at)
VALUES (?1, '[">"]', 'limits', ?2, ?3, ?4, ?5, 'old', 0, ?6)
ON CONFLICT (name) DO NOTHING;
INSERT INTO stream_seq (stream, next) VALUES (?1, 1) ON CONFLICT (stream) DO NOTHING;

-- 2. read the origin row (payload stays in SQLite; hdr comes to Go for the merge)
SELECT hdr, size FROM messages WHERE stream = ?1 AND seq = ?2;   -- PK lookup

-- 3. allocate the DLQ seq (#7's primitive, n = 1)
UPDATE stream_seq SET next = next + 1 WHERE stream = ?1 RETURNING next - 1;

-- 4. copy. The body is never materialised in Go: INSERT…SELECT moves it inside SQLite.
INSERT INTO messages (stream, seq, id, subject, hdr, body, size,
                      published_at, trace_id, dedup_key)
SELECT ?1, ?2, m.id, m.subject, ?3, m.body, m.size, ?4, m.trace_id, NULL
  FROM messages m
 WHERE m.stream = ?5 AND m.seq = ?6;

-- 5. the delivery row is gone (D5: terminal states are row deletion or DLQ migration)
DELETE FROM deliveries
 WHERE stream = ?5 AND consumer = ?7 AND seq = ?6 AND generation = ?8;

-- 6. the caller writes exactly one msg.dead event row (same tx, D11)
```

Notes that matter:

- **Step 4 is the whole atomicity argument.** Copy, delete and event are one commit; there is no
  window in which a message is in both places or neither. D1's "one transactional boundary
  collapses the crash matrix" is not a slogan here, it is the implementation.
- **The copy bypasses every publish-time check**: subject matching, `max_msg_size`, `max_msgs` /
  `max_bytes` / `discard=new`, dedup, and the `--min-free-bytes` disk gate. PLAN §4.5 is explicit:
  publishes are rejected under disk pressure while *"acks, naks and DLQ writes continue"* —
  a wedged dead-letter path becomes mass redelivery, which is the failure mode we are here to
  prevent. Implemented as `publishOpts.BypassLimits` on `#7`'s `publishTx` (one field, one
  branch, one test).
- **`changes()` is asserted** after steps 4 and 5, exactly as `#10` asserts on its settle SQL.
  Step 5 returning 0 is a bug (the caller told us the row was INFLIGHT), aborts the batch loudly
  and never reaches the event.
- **`published_at` on the copy is the writer's now**, clamped monotone per stream by `#7`'s rule.
  `Messq-Dead-At` is the authority for *when it died*; `published_at` is the DLQ stream's
  ordering key. Under a backwards wall-clock jump they can differ by the clamp; documented.
- **Multiple deaths in one transaction** (a sweeper tick retiring a batch) each run steps 1–6.
  Step 1 is a no-op after the first; step 3 reads its own uncommitted write, so seqs are
  contiguous and gap-free.

### 7. The copy budget — bounding one transaction

`#11`'s sweeper retires up to `--sweep-max-batch` (512) rows per tick. If they are all dead with
1 MiB payloads, step 4 copies 512 MiB inside a transaction that is supposed to close in 2 ms. The
WAL balloons, the commit histogram spikes, every concurrent publisher waits.

```go
type DeadBudget struct {
    Copies int   // remaining copies allowed in this transaction
    Bytes  int64 // remaining payload bytes allowed in this transaction
}

var ErrDeadBudget = errors.New("messq: dead-letter budget exhausted for this transaction")
```

`Dead` decrements before writing and returns `ErrDeadBudget` **without writing** when either
limit would be crossed. The caller (`#11`'s sweep loop; `#10`'s settle loop) treats it as
"stop routing dead transitions in this transaction", leaves the remaining rows untouched
(they are still expired INFLIGHT rows, and the next tick — 250 ms later — retries them), and
increments `messq_dlq_deferred_total`. **No correctness impact**: I4 is a bound on attempts, not
a deadline on dying, and the row is not delivered again in the meantime. This is a small
amendment to `#11`'s loop and is called out in its review.

Defaults: `--dlq-max-copies-per-commit` = 128, `--dlq-max-bytes-per-commit` = 32 MiB. A settle
batch (`#10`) is already bounded by `--max-settle-batch`, so the budget rarely binds there.

### 8. Identity: an id is a lineage, not a row

**This is the one place where PLAN §4.2's schema and PLAN §5.1's prose disagree, and this issue
must settle it.**

- §5.1 and D3: *"the original `id` and `trace_id` are preserved"* — so that `trace` shows one
  story.
- §4.2 comment: `id TEXT NOT NULL, -- ULID, stable across DLQ/replay lineage`.
- §4.2 index: `CREATE UNIQUE INDEX messages_id ON messages(id);`

The copy cannot preserve the id under a unique index. Worse, the conflict is not hypothetical at
one copy: **two consumers on the same stream can each dead-letter the same `seq`**, producing two
rows in the *same* `.dlq` stream with the same id — so neither `UNIQUE(id)` nor
`UNIQUE(stream, id)` survives contact with the design.

**Decision: preserve the id; relax the index.** Migration `0002_msg_id_lineage.sql`:

```sql
DROP INDEX messages_id;
CREATE INDEX messages_id ON messages(id, published_at);   -- same name, no longer unique
```

Supporting arguments, so this reads as a resolution rather than a concession:

- PLAN §6 already declares the row key: *"the recommended consumer-side dedup key is `stream/seq`
  (stable across every redelivery and redrive), **not** `msg_id`"*. The id was never the row key.
- D10 rejected `stream:seq` as the *only* id precisely because *"seq is not stable across DLQ
  copies and replays; we expose both"*. Both identifiers exist because each answers a different
  question: `id` = "which message is this, across its whole life"; `(stream, seq)` = "which row".
- Uniqueness was buying us a guard against ULID collision. `#3`'s monotonic factory makes
  collisions impossible within a process and astronomically improbable across restarts; the
  residual value is replaced by a cheaper, *truer* checker (below).

Consequences this issue owns:

- `Store.PeekID` (from `#7`) becomes lineage-aware:
  ```go
  type MsgRef struct{ Stream string; Seq int64; PublishedAt int64; DLQ bool }

  // LookupID returns every row sharing an id, oldest first: the origin, then its DLQ copies.
  func (s *Store) LookupID(ctx context.Context, id string) ([]MsgRef, error)

  // PeekID keeps its #7 signature and returns the OLDEST row (the origin), plus Copies.
  func (s *Store) PeekID(ctx context.Context, id string) (Message, error)
  ```
  `Message` gains `Copies []MsgRef`. `#15`'s `GET /v1/messages/{id}` renders it as
  `{"stream":"orders","seq":10493,…,"copies":[{"stream":"orders.dlq","seq":7,…}]}`, and `#20`'s
  `trace` gets the DLQ hop for free.
- New `verify` checker **P-ID1**: *no non-`.dlq` stream contains two rows with the same `id`.*
  Duplicate ids are legal only inside a DLQ, only from distinct consumers or generations. This
  also pins a requirement on `#29`: **redrive mints a new id** (per T11: new seq, linked by
  `Messq-Redrive-Of`), it does not preserve one.
- `#34`'s golden data-dir fixtures are generated at 1.0, after this migration, so nothing is
  invalidated. Forward-only numbered migrations are exactly the designed path (`#5`); the
  schema-v1 file itself is not edited.

**Considered and rejected:** mint a new ULID for the copy and record `Messq-Origin-Id`. It keeps
the unique index but breaks D3's explicit requirement and makes `messq trace <id>` — the flagship
output — stop at the DLQ boundary, requiring the renderer to chase headers to reassemble a story
the journal should have told directly.

### 9. `dead_policy=drop`

Delete the delivery row, emit `msg.dead` with `detail: {"policy":"drop"}`, copy nothing. Used by
consumers on `.dlq` streams (forced by `#9`) and by anyone who genuinely wants a black hole.
`consumer add --dead-policy drop` prints a one-time warning naming what will be unrecoverable —
the CLI half lands with `#24`.

### 10. Events

Exactly **one** `msg.dead` per DEAD transition, written by the caller, in the same transaction.
No `msg.publish` is emitted for the copy (*decision*): a second publish line for the same
`msg_id` at the same instant makes `trace` read as two messages, which is precisely the confusion
D3 set out to remove. The DLQ hop is a *fact about the death*, so it lives in the death's event.

```json
{
  "event": "msg.dead", "ts": 1758445495310,
  "stream": "orders", "consumer": "worker", "subject": "orders.created",
  "msg_id": "01J8ZQ4K2M9V0X7Y3B5N6C8D1E", "seq": 10493, "attempt": 5,
  "max_deliver": 5, "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "detail": {
    "cause": "max_deliver", "trigger": "ack_wait", "policy": "dlq",
    "attempts": 5, "held_ms": 30012,
    "last_reason": "upstream 503 on POST /charge",
    "dlq": "written", "dlq_stream": "orders.dlq", "dlq_seq": 7, "bytes": 1214
  }
}
```

`detail.dlq` is a closed enum: `written` | `dropped` | `origin_missing` | `not_implemented`
(the last removed by this issue). Level **WARN**, **never sampleable** (D11 §9.3 allow-list) —
already wired by `#10`/`#11`.

**I10 (fold ≡ state)** gains one rule, implemented in `#13`'s fold model and asserted by
`verify --deep`: `msg.dead` with `detail.dlq == "written"` creates a row in `detail.dlq_stream`
at `detail.dlq_seq` with the same `msg_id`/`trace_id` as the origin.

### 11. Metrics (`#21` owns registration and help text)

| Metric | Type | Notes |
|---|---|---|
| `messq_dead_total{stream,consumer}` | counter | already registered by `#11`; labelled with the **origin** stream, never the DLQ |
| `messq_dlq_written_total{stream}` | counter | *proposal*; origin-stream label. `dead_total - dlq_written_total` = drops |
| `messq_dlq_bytes_total{stream}` | counter | *proposal*; feeds `doctor`'s "your DLQ will fill the disk in N days" |
| `messq_dlq_deferred_total{stream}` | counter | *proposal*; copies pushed to a later transaction by the budget |
| `messq_dead_orphan_total{stream,consumer}` | counter | *proposal*; `origin_missing` — alert on any nonzero value, it is a bug signal |
| `messq_dlq_depth{stream}` | gauge | PLAN §9.4; **`#21`** computes it at scrape time from `count(messages WHERE stream = <s>.dlq)`, labelled with the origin stream |

Cardinality rule holds absolutely: `stream` and `consumer` only; `cause` is not a label here
(`messq_dead_total` stays as PLAN §9.4 defines it — the breakdown lives in the events table,
which is what it is for).

### 14. Edge cases and how they are handled

| Case | Handling |
|---|---|
| Origin message already deleted (retention/purge raced the death) | `#27`'s retention never deletes a message with an outstanding delivery row (`retention.blocked`), so this is unreachable by design. Defensively: step 4 inserts 0 rows → `Outcome = "origin_missing"`, the delivery row is still deleted (there is nothing else to do), `msg.dead` carries `detail.dlq="origin_missing"` at **ERROR**, `messq_dead_orphan_total` increments, and `verify` checker **P-DLQ4** treats any occurrence as a violation |
| Two consumers dead-letter the same `seq` | Two copies in the same DLQ, same `id`/`trace_id`, different `Messq-Origin-Consumer`. Legal, expected, and the reason the id index is not unique |
| The same `(consumer, seq)` dies twice after a `seek` | Legal: the seek bumped `generation`, the row was re-created and re-delivered. Two copies, distinguished by `Messq-Origin-Generation`. **I8 is therefore stated per `(stream, consumer, seq, generation)`** — see below |
| The same `(consumer, seq)` dying twice *without* a seek | Impossible by construction: DEAD is only reachable from INFLIGHT, the delivery row is deleted in the same transaction, and re-creating it requires a cursor rewind, which requires a generation bump. Asserted by the property suite rather than by a runtime check |
| Payload exceeds the DLQ stream's `max_msg_size` (operator edited it down) | Copy bypasses limits; it always succeeds. Documented in `OPERATIONS.md`: DLQ limits shape *retention*, never *admission* |
| Free space below `--min-free-bytes` | DLQ writes proceed (PLAN §4.5). Only the publish path is gated |
| Store latched read-only (`storage.fatal`, EIO) | The transaction fails, nothing is written, the delivery row survives as expired INFLIGHT. After restart, `#5`'s recovery reclaims it to READY, it re-expires, and it dies then. Crash-safety by construction, not by retry |
| Copy budget exhausted mid-tick | `ErrDeadBudget`; remaining rows retried next tick; `messq_dlq_deferred_total` |
| Operator deleted `orders.dlq` between deaths | Recreated from the template on the next death (step 1). `stream rm` on a DLQ warns that template defaults will replace any tuning |
| `last_reason` is empty (died on the first timeout with no prior nak) | `Messq-Last-Reason` is **omitted**, not set to `""`. `#11` in practice always sets a synthesised timeout reason, so this is mostly defensive |
| `last_reason` is 4 KiB of binary child stderr (`#25`) | Sanitised to valid UTF-8, control characters escaped, truncated to 1 KiB on a rune boundary, `Messq-Last-Reason-Truncated: true` added. Full text stays in the `msg.dead` event |
| Stream name is 64 bytes, so `<name>.dlq` would be 68 | **Amendment to `#7`'s `ValidateStreamName`**: user-created names are ≤ **60** bytes so the DLQ name always fits the 64-byte limit; broker-created `.dlq` names may use the full 64. Refusing at `stream add` beats discovering it at the first death |
| A redriven message carries provenance headers back into the origin stream | `#29` calls `StripProvenance` before republishing; otherwise `#7`'s `reserved_header` rule would reject our own output. The helper ships here so `#29` cannot forget |
| Origin has no user headers (`hdr IS NULL`) | The copy's `hdr` is the provenance object alone; `#7`'s "NULL means empty map" rule is preserved for the origin |

### 15. I8, stated precisely

> **I8** — For every `(stream, consumer, seq, generation)`, at most one DEAD transition occurs;
> it emits exactly one `msg.dead` event; and when `dead_policy = dlq` and the origin message
> exists, exactly one message row exists in `<stream>.dlq` carrying that origin's
> `Messq-Origin-Stream/-Seq/-Consumer/-Generation`, the origin's `id` and the origin's `trace_id`
> — unless the DLQ stream's `first_seq` has since advanced past it (retention or purge).

The `generation` qualifier is a **refinement of PLAN §5.2's wording**, not a weakening: without
it, I8 as literally written would forbid a legitimate re-death after a `seek`, and would be
falsified by `#28` the moment it lands. `SEMANTICS.md` (`#4`) is updated in this PR with the
refined statement and a one-line rationale.

Checkers, in `internal/model` and shared with `messq verify` (`#8`'s registry):

| ID | Check |
|---|---|
| P-DLQ1 | Every `msg.dead{detail.dlq="written"}` in the event window has its DLQ row, or the DLQ's `first_seq` passed it |
| P-DLQ2 | Every row in a `.dlq` stream carries a complete, parseable provenance header set |
| P-DLQ3 | No consumer on a `.dlq` stream has `dead_policy = dlq` |
| P-DLQ4 | Zero `msg.dead{detail.dlq="origin_missing"}` events |
| P-DLQ5 | No two `msg.dead` events share `(stream, consumer, seq, generation)` |
| P-ID1 | No non-`.dlq` stream has two `messages` rows with the same `id` |

`verify` reports the **event-retention window** it checked (default 72 h) alongside its verdict —
an honest "I checked what exists" beats a confident answer about trimmed history.

### 16. Fault points declared here, exercised fully by `#32`

Behind the `messq_fault` build tag: `dlq.before_copy`, `dlq.after_copy`, `dlq.before_delete`,
`dlq.after_commit_before_reply`. The first three exist to prove a negative: because all three sit
inside one transaction, killing at any of them must leave the message **fully pending, never
half-dead**. That test is the acceptance criterion of this issue in one sentence.

## Acceptance criteria

- [ ] `store.DeadSink` is the single dead-path seam; `DeadLetterer`/`DeadContext` are deleted,
      and `#10`'s and `#11`'s existing "seam invoked exactly once per DEAD" tests pass unchanged.
- [ ] A message that exhausts `max_deliver` on a consumer with `dead_policy=dlq` appears in
      `<stream>.dlq` with `Messq-Cause: max_deliver`, and its delivery row is gone — verified by
      reading the database directly, not through an API.
- [ ] `term` produces a DLQ copy with `Messq-Cause: terminated` and `Messq-Attempts` equal to the
      attempt that was in flight, skipping the remaining attempts (T6).
- [ ] The DLQ copy preserves the origin's `id` **and** `trace_id` byte-for-byte, and carries the
      complete provenance header set from §4 with the origin's user headers intact beside it.
- [ ] `<stream>.dlq` is auto-created on first use with the §5 template, `dedup_window_ms = 0`,
      and a `stream.create` event with `actor="system"`; the second death does not recreate it.
- [ ] Every DLQ copy has `dedup_key IS NULL`; a test dead-letters two messages that shared a
      `Messq-Msg-Id` lineage and asserts both copies exist.
- [ ] Copy, delivery-row delete and `msg.dead` occur in **one transaction**: a test counts
      commits (via `messq_commit_batch_size`) across a batch of deaths and asserts one.
- [ ] Dead-lettering succeeds when the payload exceeds the DLQ's `max_msg_size`, when the DLQ is
      at `max_msgs` with `discard=new`, and when free space is below `--min-free-bytes`.
- [ ] `dead_policy=drop` deletes the row and emits `msg.dead{detail.policy:"drop"}` with no copy
      and no DLQ stream created.
- [ ] Migration `0002` converts `messages_id` to a non-unique index; a fixture database with real
      data migrates in one transaction, and inserting two rows with the same `id` in different
      streams succeeds after and fails before.
- [ ] `LookupID`/`PeekID` return the origin plus its DLQ copies, oldest first.
- [ ] Two consumers dead-lettering the same `seq` produce two distinct DLQ rows sharing an `id`,
      distinguishable by `Messq-Origin-Consumer`.
- [ ] Exactly one `msg.dead` per DEAD transition; no `msg.publish` is emitted for the copy; the
      event's `detail` carries `cause`, `trigger`, `policy`, `dlq`, `dlq_stream`, `dlq_seq`.
- [ ] `Messq-Last-Reason` built from 4 KiB of binary child stderr is valid UTF-8, ≤ 1 KiB,
      control-free, cut on a rune boundary, and flagged with `Messq-Last-Reason-Truncated`.
- [ ] The copy budget bounds one transaction: with `--dlq-max-bytes-per-commit=1MiB`, a tick with
      10 × 1 MiB deaths defers the remainder, increments `messq_dlq_deferred_total`, and all ten
      are dead-lettered within a bounded number of subsequent ticks.
- [ ] **I8 has a named passing test** (`TestI8_DLQConservation`) covering the per-generation
      statement, including a re-death after `seek`.
- [ ] Checkers P-DLQ1…P-DLQ5 and P-ID1 are registered with `messq verify` and green on a
      dead-heavy workload; `verify` prints the event window it checked.
- [ ] **SIGKILL at `dlq.before_copy`, `dlq.after_copy` and `dlq.before_delete` never yields a
      message that is neither in the DLQ nor pending** — the headline criterion, over ≥ 200 kill
      cycles in the fast subset.
- [ ] `ValidateStreamName` refuses user-created names longer than 60 bytes with a teaching error
      naming the DLQ-name reason.
- [ ] `SEMANTICS.md` records: the refined I8, the id-is-a-lineage decision, the one-`msg.dead`
      rule, and the RFC3339 header-timestamp exception.

## Test plan

Consistent with PLAN §11: `-race` everywhere, no `time.Sleep`, real SQLite files in `t.TempDir()`
(never `:memory:`), every fix lands with its reproduction artefact.

**Unit — `internal/queue` (pure, table-driven; the ≥ 90 % coverage floor applies)**

- `PlanDead`: the matrix of `Cause × Trigger × Policy × (last_reason empty/present/huge)`, plus
  boundaries `max_deliver=1`, `attempts=max_deliver`, `MaxDeliver=0` (unlimited → only `term` can
  reach DEAD).
- `ProvenanceHeaders`: golden map per case; key canonicalisation; RFC3339-ms formatting; omission
  of empty `Messq-Last-Reason`; the header-budget degradation ladder.
- `SanitizeReason`: table (invalid UTF-8, embedded NUL, CR/LF, ANSI escapes, a 4 KiB blob, a
  multi-byte rune straddling the cut) **plus a native fuzz target** asserting the output is always
  valid UTF-8, control-free, and ≤ the cap — the input is untrusted child stderr (`#25`).
- `DLQName`/`IsDLQ`/`OriginOf`: round-trip property (`rapid`) over valid stream names.
- `StripProvenance`: removes exactly the `Messq-` namespace, preserves user headers, is
  idempotent, and its output passes `#7`'s `reserved_header` validator.

**Store — `internal/store` (real files; the ≥ 85 % floor applies)**

- `TestDeadLetter_Atomic`: one commit for a batch of N deaths (asserted via the commit histogram).
- `TestDeadLetter_AutoCreate` / `_Idempotent` / `_TwoDeathsOneTransaction` (contiguous DLQ seqs).
- `TestDeadLetter_BypassesLimits`: oversized payload, `discard=new` at `max_msgs`, subject not
  matching the DLQ's patterns after an operator edit, free space below `--min-free-bytes`.
- `TestDeadLetter_DedupKeyNull` and the shared-`Messq-Msg-Id` lineage case.
- `TestDeadLetter_TwoConsumers` (two copies, same id) and `_AfterSeek` (two copies, different
  generations).
- `TestDeadLetter_OriginMissing`: origin row deleted behind retention's back → `origin_missing`,
  row still deleted, ERROR event, orphan counter, P-DLQ4 fires.
- `TestDeadLetter_Budget`: deferral, then eventual completion.
- `TestDeadLetter_DropPolicy`: no stream created, no copy, correct event.
- `TestMigration0002`: applies to a populated fixture in one transaction; before/after duplicate
  id behaviour; `PRAGMA integrity_check` clean; index name preserved.
- `TestLookupID_Lineage`: ordering and `DLQ` flags.

**Property (`pgregory.net/rapid`) — focused here, full suite in `#13`**

- A dead-heavy generator (`max_deliver ∈ {1,2}`, `ack_wait` at the fake-clock floor, 40 % nak,
  10 % term, occasional `seek`) driving publish/fetch/settle/advance-time, with **I8, P-DLQ1–5 and
  P-ID1 checked after every action** via the `""` invariant hook. 200 checks on PRs, 20 000
  nightly; failfiles committed to `testdata/regressions/`.
- Sabotage test: a build that copies the origin's `dedup_key` into the DLQ row must be caught by
  I8 within the PR check budget. (This is the bug this feature is most likely to actually have.)

**Timing (`testing/synctest`)**

- The full timeout → backoff → death chain with a 10-minute backoff schedule, executed in
  microseconds against the `#3` Clock seam; asserts the death happens after exactly
  `max_deliver` deliveries and not one tick earlier.

**Crash (`#8`'s harness, fast subset per merge; `#32` owns the nightly matrix)**

- SIGKILL at `dlq.before_copy`, `dlq.after_copy`, `dlq.before_delete`,
  `dlq.after_commit_before_reply`; restart; assert for every killed death: the message is either
  fully in the DLQ with its delivery row gone, or fully pending with no DLQ row — **never both,
  never neither**. ≥ 200 cycles per merge in `full` durability, 1 000 nightly in both modes.
- The three-valued ledger oracle gains a DEAD outcome: a `msg.dead` observed by the driver before
  the kill is **OK** (must be in the DLQ after recovery); a death in flight at the kill is
  **UNKNOWN** (in the DLQ or still pending, both legal); a message that never exhausted its
  attempts is **FAILED** for the DLQ (must not be there).
- `messq verify` and `PRAGMA integrity_check` clean after every cycle.

**Golden events (feeds `#19`/`#20`)**

- Scripted `publish → 5 × (deliver, timeout) → dead` and `publish → deliver → term` scenarios
  assert the exact event sequence, names and `detail` field sets — including the absence of a
  `msg.publish` for the copy. Renaming a field fails the build.

**Bench**

- `BenchmarkDeadLetter/1KiB` and `/1MiB`: copies per second and, more importantly, the commit
  duration at the default budget — the regression gate is that a full dead-letter batch keeps
  `messq_commit_duration_seconds` within the `--commit-window` order of magnitude. Nightly
  benchstat, not a merge gate (PLAN §11.9).

**Not here:** testscript CLI goldens for `dlq ls/show` (**#29**), the executable-docs harness
(**#18**/**#26**), the ENOSPC loopback scenario (**#32**).
