## Context

PLAN.md §11 lists nine testing layers. Two of them have been accumulating debt since M1 because no
single feature issue could own them:

- **Layer 6, fuzzing** — *"subject matcher (differential vs. naive reference), ack-token parser (no
  forgery parses), JSON decoders, header parsing. 60 s/target per PR, 30 min nightly, corpus
  committed."* Sixteen issues from #3 onward each landed one or two `Fuzz*` targets with the same
  closing sentence ("60 s per target in CI, corpus committed"), and each was right. Nobody owns the
  *lane*: whether the surface is complete, whether the corpus survives, whether the nightly depth
  actually exists, or the one target that spans the whole state machine and therefore belongs to no
  feature issue.
- **Layer 7, soak** — *"nightly hour+ at load with 10 % naks, poison messages, kills every 5 min,
  retention on; final assertion is conservation: `published = acked + termed + dead + expired +
  still_pending`, flat RSS, flat goroutines."* This is the only test that runs long enough in real
  time for a leak, an unbounded collection (**I11**), a redelivery storm, a WAL that never
  checkpoints, or a retention sweep that fights a live consumer to become visible.

`#2` created both nightly jobs as green no-op placeholders (`fuzz-long`, `soak`) with
`echo "TODO(#33)"` in the body, precisely so the schedule, timeouts, artifact upload and failure
notification were debugged once on an empty pipeline. This issue fills both bodies.

The decisions that govern it:

- **D13 (testing)** — fuzzing on every parser and soak are both named in the adopted discipline.
  Rejected in the same breath: mutation testing, LazyFS and dm-log-writes as 1.0 *gates*. The
  ground rules still apply: `-race` everywhere, PR CI ≤ 10 min, every bug fix lands with a committed
  reproduction artifact. **PLAN §11's "no `time.Sleep`" rule carves out exactly one exception —
  *"outside soak"* — and this issue is that exception**; §7 says how it is contained.
- **PLAN §3.3 / §5** — `internal/queue` is a pure function with no I/O and no `time.Now()`. That is
  what makes a coverage-guided command-sequence fuzzer possible at all: hundreds of thousands of
  state-machine steps per second, no SQLite in the loop, libFuzzer's coverage feedback actually
  steering. An impure state machine would cap the fuzzer at disk speed and make this layer
  worthless.
- **PLAN §5.2** — the soak's oracles are **I1** (nothing acknowledged is lost across ten kills),
  **I8** (each DEAD produces exactly one DLQ record), **I9** (every duplicate has a named cause),
  **I10** (the events fold reproduces state) and **I11** (nothing grows without a bound).
- **PLAN §4.5 / §12** — retention is *on* during the soak, so "a week-long stream does not grow
  unbounded" is executed rather than asserted, and recovery stays inside the ≤ 2 s target across
  every restart.

What it unlocks: **#36**, whose release-gate checklist requires *"all fuzz targets clean; two
consecutive green soak nights before the v1.0 tag."* This issue produces the machine-readable
verdict that checklist item reads.

Blocked by **#13** because the command-sequence fuzzer decodes bytes into that issue's action set and
reuses its invariant checkers and reference model verbatim; blocked by **#31** because the soak's
load engine is `messq bench` — open-loop, coordinated-omission-corrected, and already able to declare
a run *invalid* when the generator saturates. Neither is re-implemented here.

## Scope

**In scope**

- `test/fuzz`: **`FuzzCommandSequence`** — the unguided model checker. Fuzz bytes decode into a
  command program applied step-by-step to `internal/queue` (production, in memory) with
  `internal/model` (#13) as a differential oracle and I2–I11 checked after every step.
- The **corpus-stability design** that stops the corpus rotting the first time an action is added: a
  fixed opcode space, an append-only opcode table with a golden guard, and live-state-relative
  operands (so a fuzzer can actually mint a *valid* ack token).
- `TestCorpusAgainstStore` — the same committed corpus replayed against a **real SQLite data dir**
  via #13's `sutBroker`, so the corpus pays twice: cheap in the fuzz loop, expensive but exact in
  the nightly.
- The **fuzz registry**: a committed inventory of every target in the repo, a completeness test that
  fails when a hostile-bytes entry point has no target or a target is not wired into CI, and the
  handful of missing targets that inventory turns up.
- **Corpus discipline**: layout, minimization, size budgets, the "a crasher is never deleted" rule,
  and the distil-to-a-table-test rule inherited from #13 §11.
- **CI lanes**: a sharded `fuzz` PR job (60 s/target, deterministic shard assignment, budget test),
  a `fuzz-long` nightly (30 min/target, corpus cache carried between nights, crasher artifacts +
  auto-filed issue).
- `test/soak`: the orchestrator — workload profile, chaos schedule (broker SIGKILL, worker kills,
  SIGHUP, client disconnects), the **chaos phase / quiet tail** split, and artifact preservation.
- The **soak oracles**: set-level conservation computed three independent ways, flatness with a
  warm-up exclusion and a slope test, the exact-poison-set DLQ assertion, `verify --deep` and
  `PRAGMA integrity_check`.
- `TestSoakShort` (90 s) in PR CI so the soak harness cannot rot between nights, and
  `TestSoakOracleDetects*` self-sabotage tests so the oracles are known to bite.
- `scripts/soak-gate.sh` + `soak-report.json`: the two-consecutive-green verdict #36 consumes.

**Out of scope**

- Fuzz targets for parsers owned by other issues — they land with their issue. This issue *adopts*
  them into the registry and CI, and writes only the ones the completeness scan proves missing.
- Named fault points, the `messq_fault` build tag, the kill×fault-point×durability matrix, and the
  ENOSPC/EIO/clock-jump scenarios → **#32**. The soak kills with a plain `SIGKILL` on a real
  filesystem; it is a *duration* test, not a *fault-coverage* test.
- The SIGKILL harness, the three-valued ledger, the reconciler and `internal/verify` → **#8**
  (reused wholesale).
- The `rapid` suite, shrinking, and SUT-vs-model equivalence on real SQLite per action → **#13**.
  §4 explains why the two layers are not redundant.
- The load generator, open-loop scheduling, latency percentiles, `--kill-every`, `benchstat` and the
  performance baseline → **#31** (reused wholesale). A soak is *not* a benchmark and never reports a
  throughput number as a result.
- Upgrade fixtures and schema-version gates → **#34**.
- The release-gate checklist and the v1.0 tag itself → **#36**.
- `seek`, `purge` and `dlq redrive` as soak actions — each rewrites the conservation ledger's
  meaning for a 1.5-day issue's worth of gain. They stay in the fuzzer (cheap, in-memory) and in
  #28/#29's own tests. §7 records the decision.
- Mutation testing (`gremlins`) — **rejected by D13**; #13's sabotage corpus already provides the
  "does the suite bite?" signal, and §5/§9 reuse it.

## Design proposal

> Sketches, not mandates. The settled parts are: the fuzzer runs the **pure state machine, not
> SQLite**, in its loop; the opcode space is **fixed and append-only**; the soak's conservation
> oracle compares **sets, not counts**; and flatness is measured in a **kill-free tail**. Names,
> thresholds and file layout are the arguable parts.

### 3. `FuzzCommandSequence` — the unguided model checker

Fuzz bytes are a **program**, not a payload. The decoder turns them into a command sequence; the
harness applies each command to the production pure state machine and to the reference model, and
checks invariants after every step.

```go
func FuzzCommandSequence(f *testing.F) {
	seedFromRapidFailfiles(f)              // #13's committed regressions, transcoded
	seedFromHandTable(f)                   // one seed per T1–T11 row of SEMANTICS.md
	f.Fuzz(func(t *testing.T, in []byte) {
		w := newWorld()                    // 2 streams × 3 consumers, fixed config pool
		for _, c := range Decode(in, w) {  // decoding is live-state-aware; see below
			qres, qerr := w.q.Apply(c, w.now)   // internal/queue — the production function
			mres, merr := w.m.Apply(c, w.now)   // internal/model — the reference (#13)
			requireSameOutcome(t, qres, qerr, mres, merr)
			requireSameView(t, w.q.View(), w.m.View())
			model.CheckAll(t, w.q.View(), w.hist)   // I2–I11, #13's checkers verbatim
		}
	})
}
```

**No SQLite in the loop, on purpose.** A `synchronous=FULL` commit is ~1 ms; a `queue.Apply` step is
~1 µs. libFuzzer's coverage feedback needs execution *count* to steer, and three orders of magnitude
is the difference between a fuzzer that explores and one that decorates a CI badge. `internal/queue`
being pure (PLAN §3.3) is what buys this, and this target is the clearest payoff for that
constraint. The store is exercised by `TestCorpusAgainstStore` (§5) and by #13's rapid suite.

**Why this is not a duplicate of #13.** They fail in opposite directions and the package doc says so:

| | #13 (`rapid`) | #33 (`FuzzCommandSequence`) |
|---|---|---|
| Search | uniform random draws | **coverage-guided** — new edges are kept and mutated |
| Under test | real store on real SQLite + model | pure `internal/queue` + model |
| Speed | ~200 sequences/PR run | ~10⁵–10⁶ sequences/PR run |
| Counterexample | shrunk to a minimal action list | minimized bytes, then distilled by hand |
| Finds | anything involving persistence, recovery, SQL | deep 30–50 step sequences uniform random never reaches |
| Corpus | failfiles (rot when actions change) | byte corpus (stable by construction, §4) |

### 4. The decoder: two rules that keep the corpus alive

A byte corpus is only an asset if a byte string means the same thing next quarter. Two rules do it.

**Rule 1 — the opcode space is fixed at 32 and the table is append-only.**

```go
const opSpace = 32 // NEVER change. `b % opSpace` is the corpus's coordinate system.

type Op uint8

const ( // append only; a removed op becomes opRetired and keeps its slot forever
	OpPublish Op = iota
	OpFetch
	OpAck
	OpNak
	OpTerm
	OpExtend
	OpAdvance
	OpSweep
	OpRestart
	OpCreateConsumer
	OpUpdateConsumer
	OpSeek
	OpPurge
	OpJanitor
	opN
)
```

Slots `opN..opSpace` decode to a no-op. The naive `b % len(ops)` would remap **every byte in every
corpus file** the moment a fourteenth action is added; a fixed modulus means a new op only claims a
previously-dead slot. `TestOpcodeTableIsAppendOnly` compares the table against
`testdata/opcodes.golden` and fails on any reorder, renumber or deletion — the golden is updated
only by appending.

**Rule 2 — operands address live state, not absolute values.**

Uniformly random bytes will never produce a syntactically valid ack token, so a naive fuzzer would
spend its whole budget bouncing off the parser and never reach the fencing logic (D7) — the code most
worth fuzzing. Operands are therefore *relative*:

| Operand | Encoding | Why |
|---|---|---|
| stream / consumer | `b % 2`, `b % 3` from fixed pools | tiny alphabet ⇒ constant collisions between consumers |
| subject | `b % 6` from a fixed pool matching every filter shape | ditto |
| token | mode byte: `0`=the *i*-th live in-flight token · `1`=live token with one field perturbed by ±δ · `2`=raw bytes from the stream | mode 0 reaches T3/T4/T6/T7; mode 1 reaches T3b and the generation fence (**I7**); mode 2 reaches `FuzzParseToken`'s territory from the other side |
| seq | mode byte: `0`=relative to `cursor` · `1`=relative to head · `2`=absolute varint | absolute-only would land outside every stream forever |
| delay / duration | `b % 8` from `{0, 1ms, 1s, ack_wait-1ms, ack_wait, ack_wait+1ms, backoff[k]±1ms, 1h}` | boundaries are drawn, not hoped for |
| body size | `b % 6` from `{0, 1, 1KiB, max_msg_size-1, max_msg_size, max_msg_size+1}` | the limit is a boundary, not a random integer |

Consumer configs come from a fixed pool of eight that hard-codes D13's boundary matrix
(`max_deliver ∈ {0,1,2,5}`, `max_ack_pending ∈ {1,2,8,1000}`, backoff ∈ `{[], [0], [1s], default}`),
because a fuzzer that has to *discover* `max_ack_pending=1` wastes its budget on arithmetic.

`Decode` stops at end of input, caps the program at 512 commands, and is a **total function** — every
byte string is a valid program. There is no "malformed input" branch, so the fuzzer never wastes an
exec on a rejected file.

### 5. `TestCorpusAgainstStore` — the corpus pays twice

```go
// Nightly (and on demand). Replays every committed corpus file against a real data dir via #13's
// sutBroker, so the sequences the fuzzer found cheaply are also checked expensively.
func TestCorpusAgainstStore(t *testing.T) {
	if testing.Short() { t.Skip("nightly: ~5ms/command against real SQLite") }
	for _, f := range corpusFiles(t, "FuzzCommandSequence") {
		t.Run(f.name, func(t *testing.T) {
			w := newStoreWorld(t)          // real messq.db under t.TempDir(); never :memory:
			for _, c := range Decode(f.bytes, w) {
				requireSameOutcome(t, w.sut.Apply(c), w.ref.Apply(c))
				model.CheckAll(t, w.sut.View(), w.hist)
			}
			requireVerifyClean(t, w.dir)   // internal/verify, #8
		})
	}
}
```

A file that diverges here but not in the fuzz loop is the most valuable result this issue can
produce: the pure state machine and its SQL realisation disagree, which is exactly the bug class the
D1 argument ("one transactional boundary") is supposed to prevent.

### 6. Corpus discipline and CI lanes

**Layout.** Go's native locations, no invention: seeds and crashers in
`<pkg>/testdata/fuzz/<Target>/`, one file each, committed. The *cache* corpus (`$(go env
GOCACHE)/fuzz`) is CI-only and never committed.

**Rules.**

1. **A crasher is never deleted.** It moves from artifact → `testdata/fuzz/<Target>/` in the PR that
   fixes the bug, named `crash-<issue>-<slug>`. It then runs as a plain unit test on every
   `go test ./...` forever, at zero marginal cost.
2. **A crasher is also distilled** into a deterministic Go test in `regress_test.go` (#13's rule):
   corpus files are opaque bytes and rot when the grammar grows; the distilled test is the durable
   artifact and says in English what the bug was.
3. **Minimize before committing** — `-fuzzminimizetime=60s`; a committed seed is ≤ 4 KiB and a
   target's committed corpus is ≤ 200 files (`TestCorpusBudget`, so the repo does not silently gain
   a megabyte of noise).
4. **No known-crasher allow-list, ever.** A red nightly is either fixed or the target is deleted in a
   reviewed PR. An allow-list is how a fuzz lane becomes decoration.

| Job | When | What it runs | Budget |
|---|---|---|---|
| `fuzz` (matrix ×6) | every PR | one `go test -run=^$ -fuzz=^<T>$ -fuzztime=60s` per target, targets assigned to shards by `crc32(name) % 6` | ≤ 7 min/shard (lane stays under #2's 10 min) |
| *(implicit)* | every PR | `make test` already replays every committed corpus file as unit tests | included |
| `fuzz-long` (matrix ×6) | nightly | `-fuzztime=30m` per target, `-race` off (throughput), corpus cache restored and saved per target | ≤ 2.5 h |
| `corpus-vs-store` | nightly | `TestCorpusAgainstStore` | ≤ 20 min |
| `soak` | nightly | `TestSoak -soak.duration=60m` | ≤ 80 min |
| `soak-long` | weekly | `TestSoak -soak.duration=8h -soak.quiet-tail=2h` | ≤ 9 h |

`TestFuzzShardBudget` computes the projected wall clock of the PR matrix from the registry and fails
when a shard exceeds 7 minutes — so the sixteenth issue to add a target is told to bump the shard
count instead of quietly eroding the 10-minute lane.

**Corpus persistence** is what makes the nightly compound: `actions/cache` keyed
`fuzz-<target>-<goversion>-<sha>` with a `restore-keys` prefix so each night starts from the last
night's coverage. Without it, thirty minutes of nightly fuzzing restarts from the seed corpus every
night and never gets past the shallow states.

**Crasher triage** (nightly): upload the minimized input as an artifact → open a GitHub issue titled
`fuzz: <Target> crasher <sha256[:8]>` with the base64 input, the `go test -run=<Target>/<name>`
reproduce line and the owning issue's area label → **never** auto-commit to the corpus, because a
committed crasher reddens `make test` for everyone and that must be a deliberate, fixed-in-the-same-PR
act.

### 7. The soak

```
go test ./test/soak                            driver process (never killed)
  ├─ messq bench e2e (#31, in-process)          open-loop, 500 msg/s, 8 publishers
  │    └─ ledger.jsonl (#8)                     fsynced outside the data dir
  ├─ 2 × messq sub --exec (#24) worker subprocs  10% nak, 1% term, poison always fails
  ├─ chaos goroutine    SIGKILL(-pgid) broker every 5m ±20%
  │                     SIGKILL worker every 90s ±20%
  │                     SIGHUP (log level flip) every 10m
  │                     abandon 1% of long-poll fetches mid-flight
  ├─ metrics sampler    GET /metrics every 15s → samples.csv
  └─ reconciler         conservation · flatness · DLQ set · verify --deep · integrity_check
```

**Two phases, and the reason for them.** A 60-minute soak that kills the broker every 5 minutes
gives you ten five-minute RSS observations — useless for detecting a leak, because the process never
lives long enough to grow. So:

| Phase | Default length | Kills | What it proves |
|---|---|---|---|
| warm-up | 10 min | yes | nothing; excluded from every trend |
| chaos | 20 min | broker + worker + HUP + disconnects | conservation and **I1** across ten restarts, redelivery storms, recovery latency |
| **quiet tail** | 30 min | **none** | **flatness**: RSS, goroutines, FDs, WAL, event rows — the leak window |

The weekly `soak-long` widens both (6 h chaos, 2 h quiet tail).

**Workload.** One `retention=limits` stream (`soak`, `max_msgs` capped so expiry actually runs) and
one `retention=workqueue` stream (`soakwq`, so the reaper runs), each with two consumers on
overlapping filters — because "the message is acked" is meaningless (PLAN §5) and a single-consumer
soak never tests that.

| Class | Share | Subject | Worker behaviour | Expected fate |
|---|---|---|---|---|
| normal | 88 % | `soak.ok.*` | exit 0 | acked, or expired if retention wins the race |
| nak | 10 % | `soak.flaky.*` | exit 75 once, then 0 | acked after ≥ 2 attempts |
| term | 1 % | `soak.bad.*` | exit 65 | DEAD, `Messq-Cause: terminated` |
| poison | fixed count (200) | `soak.poison.*` | always exit 75 | DEAD, `Messq-Cause: max_deliver`, in DLQ |

Poison messages carry a unique `Messq-Msg-Id` each (E16) and are injected at known offsets across the
run so that "did retention or a restart eat one?" has a per-message answer.

**Flags** (Go test flags, so `-run` composes):

| Flag | Default | Meaning |
|---|---|---|
| `-soak.duration` | `60m` | total wall clock |
| `-soak.warmup` | `10m` | excluded from all trends |
| `-soak.quiet-tail` | `30m` | trailing kill-free window (the flatness oracle) |
| `-soak.rate` | `500` | offered msg/s, open loop (deliberately well under the §12 gate) |
| `-soak.publishers` / `-soak.workers` | 8 / 2 | load shape |
| `-soak.nak-rate` / `-soak.term-rate` | `0.10` / `0.01` | PLAN §11.7's "10 % naks" |
| `-soak.poison` | `200` | injected poison messages |
| `-soak.kill-every` / `-soak.worker-kill-every` | `5m` / `90s` | chaos cadence (chaos phase only) |
| `-soak.durability` | `full` | `relaxed` for the weekly variant |
| `-soak.seed` | time-derived, **always printed** | seeds every chaos decision |
| `-soak.keep` | `false` | keep the data dir on success |
| `-soak.artifacts` | `$RUNNER_TEMP` | where a failure preserves evidence |

**The `time.Sleep` exemption.** PLAN §11 bans `time.Sleep` in tests *"outside soak"*, and #2 enforces
that with `forbidigo`. This issue adds `test/soak` to the exclusion list with a comment naming PLAN
§11 — the chaos schedule is real elapsed time by definition, and pretending otherwise with a fake
clock would test a different program. `TestSoakShort` and the oracles' unit tests still use the Clock
seam; only the chaos goroutine sleeps.

### 8. The conservation oracle — sets, not counts

PLAN §11.7 states the identity `published = acked + termed + dead + expired + still_pending`. Two
refinements make it actually catch things:

**It is per `(stream, consumer)`, and `termed ⊂ dead`.** T6 emits both `msg.term` *and* `msg.dead`,
so adding the two counters double-counts. The reconciler computes, for each consumer `c`:

```
matched(c)  = { seq : published on c.stream, subject matches c.filters, seq >= c.start_cursor }

matched(c) = acked(c) ⊎ dead(c) ⊎ expired(c) ⊎ pending(c) ⊎ unseen(c)          (⊎ = disjoint union)

  acked(c)   distinct seq with an msg.ack   (msg.ack_dup and msg.ack_stale count for NEITHER side)
  dead(c)    distinct seq with an msg.dead  (of which dead_by_term(c) also have an msg.term)
  expired(c) distinct seq deleted by retention.expire with no ack/dead for c
  pending(c) rows in `deliveries` for c at the end of the run
  unseen(c)  matching seqs still present with seq >= c.cursor_seq
```

**It compares sets, not cardinalities.** `|A| = |B|` can hold while two messages have swapped fates —
the exact bug an at-least-once broker produces. The reconciler therefore builds the five sets and
asserts pairwise disjointness and an exact union, and on failure prints the symmetric difference:

```
soak: CONSERVATION FAILED  stream=soak consumer=w
  matched 1 803 442   accounted 1 803 441   missing 1
  seq 998 214  id 01K9…  subject soak.ok.7  published 03:12:19.402Z
    in none of {acked, dead, expired, pending, unseen}

  reproduce: MESSQ_DATA_DIR=/tmp/soak-1731301/dir messq trace 01K9…
```

**Three independent computations, cross-checked:**

| Source | Built from | Strength |
|---|---|---|
| **ledger** (primary) | #8's `ledger.jsonl` + worker-side exit records | external to the SUT; survives the SUT lying |
| **events fold** | fold the `events` table from row 1 (**I10**) | proves the audit trail agrees with reality — the product's core claim |
| **state + metrics** (advisory) | final SQL state + accumulated `/metrics` counters | catches metric bugs, not broker bugs |

Ledger and events-fold disagreement is a **hard failure**. Metrics disagreement is a hard failure
*only* if it exceeds the windows lost to kills: Prometheus counters reset on restart, so the sampler
scrapes immediately before each planned kill and accumulates per process generation, and any publish
committed between the last scrape and the kill is unrepresented. That loss is bounded, reported
(`metrics: 3 of 1 803 442 unattributable (0.0002 %) — window loss across 10 kills`), and capped at
0.01 % — above which the *sampler* is broken, not the broker.

**The DLQ set.** `dlq(soak)` must equal exactly `poison ⊎ term`, plus a possibly-empty *explained*
set: a message that is neither may appear in the DLQ **only if** its event history contains a
complete named-cause chain of `max_deliver` attempts (**I9** — a killed worker legitimately burns
attempts via `msg.timeout`). In the **quiet tail** no such excuse exists, so a non-poison
dead-letter during the kill-free window fails the run outright. `soakwq`'s DLQ must be empty.

### 9. The flatness oracle

The sampler writes `samples.csv` every 15 s from `/metrics` (#21 registers the Go and process
collectors, so these exist):

| Series | Assertion over the quiet tail |
|---|---|
| `process_resident_memory_bytes` | OLS slope ≤ **+8 MiB/h**, and `end ≤ 1.10 × median` |
| `go_goroutines` | `max − median ≤ 20`; returns to the §3.2 census (6) + open conns within 30 s of load stop |
| `process_open_fds` | slope ≤ 0; no monotone rise (a leaked conn/file shows here first) |
| `messq_wal_bytes` | never exceeds `--wal-max-bytes`; **shrinks** during the quiet tail (checkpointing works) |
| `messq_db_bytes` | `end ≤ 1.05 × (value at end of warm-up)` — retention is holding (PLAN §4.5) |
| `messq_events_rows` | ≤ `--event-max-rows` |
| `messq_pending`, `messq_backlog` | bounded; `Σ pending ≤ Σ max_ack_pending` (**I5**) at every sample |
| `messq_oldest_pending_age_seconds` | ≤ 3 × `ack_wait` in the quiet tail (no stuck message) |
| `messq_stale_acks_total` | rate is *reported*; a nonzero rate in the quiet tail fails (nothing should race there) |

A slope test on a sawtooth (grow-then-GC) is famously easy to fool, so the test is the pair —
**slope AND end-vs-median** — and the CSV is uploaded on every run, pass or fail, so a human can look
at the shape when a threshold is argued about.

`scripts/soak-gate.sh` answers #36's checklist item by reading the last N nightly runs
(`gh run list --workflow=nightly.yml --json`) and requiring **two consecutive** runs with
`valid == true && verdict == "green"`. A saturated or aborted run is `valid == false` and counts as
neither pass nor fail — it **breaks the streak** rather than satisfying it, because an invalid soak
proves nothing and must not be able to unlock a release tag.

### 11. Edge cases

| # | Case | Handling |
|---|---|---|
| E1 | **Metrics counters reset on every restart.** | Accumulate per process generation; scrape immediately before each planned kill; report the unattributable remainder and cap it at 0.01 %. Metrics are the *third*, advisory source — never the primary oracle. |
| E2 | **Duplicates inflate `messq_delivered_total`.** | Conservation counts **distinct seqs with an `msg.ack`**, not ack events. `msg.ack_dup` and `msg.ack_stale` count for neither side; both are reported separately, and a nonzero `ack_stale` rate in the quiet tail fails the run. |
| E3 | **Retention deletes a message the driver expected.** | Legal only for messages with no delivery row (PLAN §4.5). `expired(c)` is derived from `retention.expire` events and asserted disjoint from `acked`/`dead`; a `retention.blocked` event is *expected* under a killed worker and is reported, not failed. |
| E4 | **A worker is killed after doing the work but before acking.** | The canonical at-least-once duplicate. The worker ledger records `handled` separately from `acked`; conservation uses `acked`. The duplicate is legal but must carry a named cause (**I9**) — an unnamed duplicate fails the run. |
| E5 | **A PR fuzz run finds a crasher.** | The PR goes red, Go writes the input under `testdata/fuzz/<Target>/`, and the author commits it **with the fix**. This is the designed behaviour, not a flake — the failure message says so and prints the `go test -run` reproduce line. |
| E6 | **Corpus rot when the action set grows.** | Fixed `opSpace = 32` + append-only opcode table + `testdata/opcodes.golden`. A new action claims a dead slot; no existing byte changes meaning. |
| E7 | **Corpus bloat in git.** | `-fuzzminimizetime=60s` before commit; `TestCorpusBudget` caps ≤ 200 files and ≤ 4 KiB/file per target. The unbounded coverage corpus lives in the CI cache, never in the repo. |
| E8 | **`go test -fuzz` runs one target at a time.** | The shard matrix invokes one process per target (`-run=^$ -fuzz=^FuzzX$`). `TestFuzzShardBudget` keeps the projected wall clock inside the lane budget as targets are added. |
| E9 | **A soak on a noisy CI runner.** | #31's open-loop generator declares the run **invalid** when scheduling debt exceeds its threshold. An invalid run is neither pass nor fail, breaks the two-night streak, and never reports a throughput number — a soak is not a benchmark. |
| E10 | **WAL grows during the kill-heavy phase.** | Expected: an unclean exit skips the `TRUNCATE` checkpoint. The bound (`--wal-max-bytes`) must hold throughout, and the quiet tail must shrink it — a WAL still at its peak after 30 kill-free minutes is a checkpointing bug. |
| E11 | **Long-poll waiters leak.** | `go_goroutines` must return to the §3.2 census within 30 s of load stop. 1 % of fetches are abandoned mid-flight specifically to hunt this. |
| E12 | **The daemon latches read-only** (`storage.fatal`) mid-soak. | A hard failure with the full artifact set — there is no ENOSPC/EIO injection here (that is #32), so a latch on a healthy filesystem is a real bug. `disk.degraded` is likewise a failure, not a tolerated state. |
| E13 | **The driver itself dies** (CI timeout, OOM). | The ledger's torn-tail rule (#8) applies; the job's `timeout-minutes` is `duration + 20m`; a timed-out run is `valid == false`. The soak never runs longer than its `-soak.duration` — the chaos goroutine stops at the deadline even mid-kill. |
| E14 | **The soak harness rots between nights.** | `TestSoakShort` (`-soak.duration=90s -soak.warmup=10s -soak.quiet-tail=30s -soak.kill-every=20s`) runs on every PR in ≤ 3 min. It is an orchestration smoke test — its oracles run but its thresholds are advisory, and it says so, because 90 s of data cannot support a slope test. |
| E15 | **`FuzzCommandSequence` finds a *model* bug.** | Expected. #13's fixed triage order applies unchanged: fix the SUT, or fix the model, or **amend `SEMANTICS.md` first** and then both. Never "make the model match the code". |
| E16 | **Poison messages deduplicated away** after a publisher retry across a restart. | Each poison message carries a unique `Messq-Msg-Id`; a `duplicate: true` response for a poison key is recorded and the message is not re-counted. Poison injection is idempotent by construction. |
| E17 | **DLQ retention eats the poison set** before the final assertion. | `<stream>.dlq` is created with retention effectively off for the soak (`max_age_ms=0`, `max_msgs=0`); the exact-set assertion depends on it. Asserted at setup, not assumed. |
| E18 | **A flaky message dead-letters legitimately.** | Timeouts consume attempts (D6), so a worker killed repeatedly on one message can exhaust `max_deliver`. Hence the "explained set" rule in §8: allowed in the chaos phase with a complete named-cause chain, forbidden in the quiet tail. |

### Considered and deferred

| Idea | Why not now |
|---|---|
| `seek` / `purge` / `dlq redrive` as soak actions | each redefines `matched(c)`, and the conservation oracle is the whole value of the run. They stay in the fuzzer (in-memory, cheap) and in #28/#29's own tests. Revisit when the oracle can express generation boundaries. |
| Driving the fuzzer through HTTP | ~4 orders of magnitude slower per exec; the API's hostile-bytes surface is covered by #14/#15/#18's own targets |
| `go-fuzz-headers` / `gofuzz` for struct generation | a dependency for what §4's decoder does in 150 lines, and it would not give the live-state-relative operands that are the whole trick |
| Continuous fuzzing (OSS-Fuzz / ClusterFuzzLite) | a 1.0-era conversation; the nightly with a persisted corpus captures most of the value at none of the integration cost. Recorded in `docs/non-goals.md` as "revisit post-1.0". |
| LazyFS / dm-log-writes under soak | D13 explicitly rejected these as 1.0 gates |
| Reporting soak throughput as a result | a soak runs deliberately below the gate; publishing its numbers would invite comparison with #31's measured ones |
| Mutation testing | D13 rejected it; §9's `TestSoakOracleDetects*` and #13's sabotage corpus give the same signal where it matters |

      malformed-input branch, verified by a property test over random inputs.
- [ ] The opcode space is fixed at 32 and the table is append-only;
      `TestOpcodeTableIsAppendOnly` fails on any reorder, renumber or removal against
      `testdata/opcodes.golden`.

      exceeding 7 minutes; `TestFuzzShardBudget` fails when adding a target would break that.

- [ ] The conservation oracle compares **sets**, asserts pairwise disjointness and exact union per
      `(stream, consumer)`, and on failure prints the symmetric difference with a `messq trace`
      reproduce line for each unaccounted message.
- [ ] Conservation is computed **three independent ways** (ledger, events fold, state+metrics);
      ledger-vs-events disagreement is a hard failure, and metrics disagreement is bounded at 0.01 %

## Test plan

The deliverable is two test lanes, so the plan splits into "what the lanes prove" and "why anyone
should believe the lanes".

**What the lanes prove**

- `FuzzCommandSequence` — invariants I2–I11 and queue↔model outcome/state equivalence over
  coverage-guided command programs. 60 s/target on PRs, 30 min nightly, corpus persisted.
- `TestCorpusAgainstStore` — the same programs against real SQLite, plus `internal/verify` clean.
  Nightly; the fastest 20 files run under `-short` on PRs.
- The adopted target set (§2) — unchanged in behaviour, newly guaranteed to be complete, wired and
  budgeted.
- `TestSoak` — conservation, DLQ exactness, flatness, `verify --deep`, `integrity_check`, recovery
  latency. Nightly at 1 h; weekly at 8 h with a 2 h quiet tail and a `relaxed`-durability variant.

**Why anyone should believe the lanes** (the part that matters most in a 1.5-day issue)

- `TestCommandFuzzerCatchesSabotage` — run `FuzzCommandSequence` for 30 s against three of #13's
  `messq_sabotage` builds (`ack_no_fence`, `claim_no_attempt`, `backoff_off_by_one`); each must
  produce a crasher. A fuzzer nobody has seen catch anything is a CI badge.
- `TestSoakOracleDetects*` — the oracles' own sabotage suite, mirroring #8's `TestOracleDetects*`.
  Each takes a **recorded good run's artifacts** and doctors them:
  - delete one `msg.ack` from the events copy → conservation must report `missing 1` with that seq;
  - move one seq from `acked` to `dead` without changing counts → the **set** comparison must fail
    where a count comparison would pass (this is the test that justifies §8's design);
  - inject a DLQ record with no poison key and no cause chain → DLQ-set failure;
  - replace the RSS series with a +40 MiB/h ramp → flatness failure;
  - replace it with a sawtooth whose slope is flat but whose end is 1.4 × median → end-vs-median
    failure;
  - add 200 goroutines at the end of the quiet tail → goroutine failure;
  - mark the generator saturated → `valid: false`, and `soak-gate.sh` must **not** count it green.
- `TestFuzzRegistryComplete` negative cases — a fixture package with an uncovered `ParseThing`, and a
  registry entry naming a deleted target; both must fail.
- `TestOpcodeTableIsAppendOnly` negative cases — a reordered and a renumbered table; both must fail.
- `TestCorpusBudget`, `TestFuzzShardBudget` — each with a fixture that exceeds the budget.
- `TestSoakShort` — the orchestration smoke; also the fixture generator for the oracle sabotage
  tests, so the self-tests run against real artifacts rather than hand-written JSON.

**Property/unit**

- `Decode` totality and determinism (`rapid`): every input decodes; the same bytes always produce the
  same program; a program's length is bounded; `opSpace` slots above `opN` are no-ops.
- The conservation reconciler as a pure function over synthetic ledgers (`rapid`): random fate
  assignments, then assert the reconciler reports exactly the injected discrepancy set.
- The slope/end-vs-median estimators against synthetic series (flat, ramp, sawtooth, step at a
  restart boundary) with known verdicts.

**Not tested here, by design:** fault points and the crash matrix (**#32**), ENOSPC/EIO/clock jumps
(**#32**), upgrade fixtures (**#34**), throughput and latency (**#31**), shrinking and per-action SUT
equivalence (**#13**). Each is named in the package docs of `test/fuzz` and `test/soak` alongside the
issue that owns it, so a green nightly is never mistaken for a durability proof.
