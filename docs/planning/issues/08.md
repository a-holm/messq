## Context

M2's exit criterion is the sentence the whole product rests on: *"SIGKILL loop never loses an
acknowledged publish; ≥ 5 000 durable 1 KiB msg/s on NVMe."* Everything before this issue —
schema and recovery (#5), the group-commit writer (#6), the publish path (#7) — is a **claim**.
This issue builds the apparatus that turns it into **evidence**, and it deliberately lands
*before* the delivery engine (M3) for two reasons:

1. **D1 has a revisit trigger and it fires here.** If measured durable throughput on reference
   hardware misses 5 k msg/s, PLAN.md §2/D1 says payload BLOBs move to append-only segment files
   behind `internal/store`, wire unchanged. That is a two-day change at M2 and a two-week change
   at M8. The number must be measured now, on a recorded machine, with a recorded methodology.
2. **D13 ranks the crash harness as critical-path infrastructure, not hardening.** Every
   subsequent issue (#9–#12 delivery, #14 API, #27 retention) mutates state through the same
   writer. A kill/restart oracle that exists from M2 catches their crash bugs on the day they are
   written; one that arrives at M8 catches them after three months of accumulated interactions.

The oracle itself is the interesting part. Under at-least-once semantics with crashes, a
two-valued "did it survive?" oracle is *wrong*: a publish that was in flight when the process
died has no correct answer, so a strict oracle produces false failures and a lenient one hides
real loss. PLAN.md §11 (layer 3) and D13 therefore mandate a **three-valued external ledger** —
`OK` (server answered 2xx: the message **must** exist), `UNKNOWN` (in flight at the kill: either
outcome is legal), `FAILED` (server rejected before the command could reach a commit: the message
must **not** exist). Invariant **I1** ("every publish that returned 2xx under `full` durability is
present after any crash") is exactly the `OK` column of that ledger, and this is the issue that
gives I1 its named test.

The second deliverable, `messq verify`, is the same idea pointed at the operator: the invariant
checkers this harness needs are shipped as a subcommand, so an operator can ask *"is my broker's
state sound?"* and get an answer in seconds — against a live data dir, a stopped one, or a
`backup` copy. It is a product feature (PLAN.md §8, and §5.2/I10 names `verify --deep` as the
log ≡ state checker) *and* the test suite's structural oracle: one implementation, four consumers
(this harness, #13's `rapid` invariant hook, #33's soak, #34's upgrade fixtures).

Governing sections: **§11 Testing strategy** (ground rules + layer 3), **D13**, **D1** (the
revisit trigger), **D4** (what a 2xx means, per durability mode), **§4.4 Crash recovery**,
**§5.2 Invariants**, **§12 Performance targets**, **§8** (CLI output and exit-code contract).

What it unlocks: **#32** (the full fault matrix — named fault points, ENOSPC, EIO, clock jumps,
power-loss simulation) plugs into this harness's `KillStrategy` and filesystem seams instead of
building a second one; #13 reuses the `verify` registry as its invariant hook; #33's soak reuses
the load generator and the ledger; #30's `doctor` reuses the fsync probe; #34 asserts
`verify --deep` on migrated golden data dirs.

## Design proposal

Everything below is a **starting point, not a mandate**. The settled parts are: the three-valued
classification, the ordering rule *"the ledger record is durable before the request is sent"*, the
closed `FAILED` allow-list, and the vacuity guards. Names, encodings, thresholds and file layout
are the arguable parts.

### 1. What the harness drives (and the M2 serve skeleton)

The SUT is the **real binary**, started as a real subprocess against a real data directory. No
in-process store, no test-only publish path: a harness that drives different code than production
proves nothing, and `SIGKILL` is only meaningful against a process.

```
go test ./test/crash                         driver process (never killed)
  ├─ builds dist/messq once per run          (or takes $MESSQ_BIN from CI)
  ├─ ledger.jsonl        ← fsynced, OUTSIDE the data dir
  ├─ loadgen × P goroutines ──HTTP/unix──▶  messq serve --data-dir DIR --durability full
  └─ killer goroutine ──SIGKILL(-pgid)──────────┘   → restart → reconcile → verify
```

The daemon surface this issue needs is deliberately tiny:

| Route | Why the harness needs it |
|---|---|
| `POST /v1/streams` | create the harness stream once per data dir (idempotent) |
| `POST /v1/streams/{s}/messages` | the load; raw body, `Messq-Subject`, `Messq-Msg-Id` |
| `GET /healthz` | readiness after start/restart; nothing else |

The full data plane (long-poll fetch, settle endpoints, the complete error envelope, listener
policy, `MaxBytesReader`, `ReadHeaderTimeout`, waiter caps) is **#14**, and #14 is free to replace
the mux wholesale — the harness only depends on the three routes above and on the frozen publish
response shape `{stream, seq, id, trace_id, duplicate}` from #7. If #7 landed a `serve` that
already exposes them, this issue writes zero daemon code; if it did not, this issue owns the
skeleton (`cmd/messq serve` → open store → start writer → `http.Server` on a Unix socket →
SIGTERM = graceful-ish close). Graceful shutdown quality does not matter here: `kill -9` is always
safe, and that is precisely what is under test.

Reconciliation reads state through a **read-only `database/sql` handle on the data dir**, not
through the API: it is the same access mode `messq verify --data-dir` uses, it works while the
daemon is down, and it does not depend on inspection endpoints that arrive in #15.

### 2. The ledger (`internal/testutil/ledger`)

```go
// Package ledger records, durably and outside the system under test, what the load
// generator asked for and what it was told — the external oracle for a crash test
// (PLAN.md §11 layer 3, D13). Proposal; shapes are negotiable, ordering is not.
package ledger

type Verdict uint8

const (
	Unknown Verdict = iota // in flight at the kill: either outcome is legal
	OK                     // server returned 2xx: the message MUST exist after recovery
	Failed                 // server rejected pre-commit: the message MUST NOT exist
)

type Record struct {
	Key       string  `json:"key"`        // ULID minted by the driver; also the Messq-Msg-Id
	Stream    string  `json:"stream"`
	Subject   string  `json:"subject"`
	Size      int     `json:"size"`       // body is deterministic: Payload(Key, Size)
	Cycle     int     `json:"cycle"`
	SentAt    int64   `json:"sent_at_ms"`
	Verdict   Verdict `json:"verdict"`
	Seq       uint64  `json:"seq,omitempty"`       // set on OK
	ID        string  `json:"id,omitempty"`        // server ULID, set on OK
	Duplicate bool    `json:"duplicate,omitempty"`
	Status    int     `json:"status,omitempty"`    // HTTP status; 0 = transport failure
	Code      string  `json:"code,omitempty"`      // error-envelope code, or transport error
	CRC       uint32  `json:"crc"`                 // crc32c over the record with CRC zeroed
}

// Attempt appends an intent record and returns only once it is fsynced.
func (l *Ledger) Attempt(r Record) error

// Resolve appends the outcome; durable by the next Sync. Sync is called before every
// kill and before every reconciliation.
func (l *Ledger) Resolve(key string, v Verdict, o Outcome) error
func (l *Ledger) Sync() error

// Replay folds the file into the latest record per key. A final line that fails to
// parse or fails its CRC is a torn tail from a killed driver: truncate and continue,
// never error. A bad line anywhere else is a hard error.
func Replay(path string) (map[string]Record, Stats, error)
```

Design notes:

- **NDJSON, not a binary format.** A human reads this file during a failure investigation; `jq`
  must work on it. The CRC exists only to recognise a torn last line.
- **The intent record is durable before the request is sent.** Without that ordering, a driver
  death makes an in-flight publish indistinguishable from one that was never attempted, and the
  `GHOST` check (§5) loses its meaning.
- Per-record `fsync` would cap offered load at the device's fsync rate, which is the very thing
  under measurement. The ledger therefore runs **its own group commit** (2 ms / 256 records,
  mirroring #6); `Attempt` blocks until its record's flush returns. This is the only place the
  harness is permitted to look like the SUT, and it is commented as such.
- **Bodies are not stored.** `Payload(key, size)` is a deterministic keyed fill, so the reconciler
  byte-compares a recovered body without a ledger the size of the workload.
- **Every publish carries `Messq-Msg-Id: <key>`.** This is the linchpin: it makes every attempt —
  including the `FAILED` and `UNKNOWN` ones the server never named back to us — addressable by a
  key the *driver* chose, and it makes retrying an `UNKNOWN` publish safe and observable
  (`duplicate: true` carrying the original seq, per §5.1 of PLAN.md).

### 3. Verdict classification (the rule that decides everything)

| Client observation | Verdict | Why |
|---|---|---|
| `201` with `{seq,id}` | `OK` | D4: under `full`, a 2xx is a durability promise |
| `201` with `duplicate:true` | `OK` | must exist, at the **returned** seq |
| `400 bad_request`, `404 not_found`, `413 too_large`, `422 subject_mismatch`, `507 disk_full` | `FAILED` | closed allow-list: errors the server can only produce **before** the command enters a commit batch |
| `500`, `503`, any code not on the allow-list | `UNKNOWN` | a read-only latch (fsyncgate, D4) can follow a commit whose fate we cannot know |
| connection reset / EOF / write error / client timeout | `UNKNOWN` | the kill window |
| no response and the process is gone | `UNKNOWN` | ditto |

The allow-list is **closed and small on purpose**. Adding a code to it is a claim about the
server's internals and must be argued in review. The failure modes are asymmetric: a wrong
`UNKNOWN` merely weakens the oracle, a wrong `FAILED` produces false failures, and a wrong `OK` is
unthinkable. An error code the harness has never seen before does **not** silently become a
verdict — it fails the cycle with "unclassified response code" so the mapping stays deliberate.

Because `UNKNOWN` weakens the oracle, the harness *measures* how much (§5).

### 4. The cycle loop

```go
type Config struct {
	Bin        string        // built once per run, or $MESSQ_BIN
	Root       string        // t.TempDir(); data dir and ledger both live under it
	Durability string        // "full" | "relaxed"
	Publishers int           // default 8
	Sizes      []int         // default {64, 1024, 16384, 65536}, round-robin
	Cycles     int
	Seed       int64
	Kill       KillStrategy
	Clock      clock.Clock   // clock.Real() from #3 — the seam, so forbidigo stays happy
}

type KillStrategy interface {
	// NextKill returns when to kill, given what the driver has observed so far.
	// #32 adds AtFaultPoint(name) behind the messq_fault build tag.
	NextKill(rng *rand.Rand, obs Observations) time.Duration
}
```

One cycle:

1. Start `messq serve` with `SysProcAttr{Setpgid: true}`, stdout/stderr captured to a ring buffer.
   Poll `GET /healthz` until ready or the 10 s readiness deadline expires — **polling through
   `cfg.Clock`, never `time.Sleep`** (§11 ground rule, lint-enforced by #2).
2. Ensure the harness stream exists: `dedup_window_ms = 86_400_000` (see edge case 4),
   `max_msg_size` above the largest payload, `max_age_ms`/`max_msgs` unlimited (retention is #27;
   nothing must delete a message the oracle expects to find).
3. Start `P` publisher goroutines: mint key → `ledger.Attempt` (durable) → POST → `ledger.Resolve`.
4. After `Kill.NextKill(...)`, `syscall.Kill(-pgid, SIGKILL)`; assert
   `WaitStatus.Signal() == SIGKILL`. An exit *code* here means the process died some other way —
   itself a bug worth failing on.
5. Stop issuing new publishes; wait (bounded) for every outstanding request to return or fail;
   `ledger.Sync()`.
6. Restart the daemon on the same data dir. Assert it becomes ready within 10 s **with no manual
   cleanup** of the stale socket file, the `-wal`/`-shm` files, or the lock.
7. Reconcile ledger ↔ state; run the full `verify` set plus `PRAGMA integrity_check`.
8. Assert the §4.4 recovery contract: `recovery.unclean` appears in the restart's log output, and
   a probe publish after restart receives `seq > max(seq)` observed before the crash (the seq
   allocator is durable and never reuses a number).
9. On any violation: preserve the seed, the ledger, both server logs and a gzipped copy of the
   data dir into the artifact directory; print a one-line reproduction command; fail.

Kill strategies v1 — the seeded RNG picks one per cycle, so a sweep covers all three:

| Strategy | Draw | Window it targets |
|---|---|---|
| `randomDelay` | uniform in [50 ms, 2 s] after load starts | steady state, mid-batch |
| `afterNOK` | kill after the driver observes `N ~ U(1, 200)` OK responses | post-commit / pre-response |
| `immediate` | uniform in [0, 150 ms] after start | migrations, recovery-during-recovery |

Harness flags (Go test flags, so `go test -run … -crash.x=y` composes normally):

| Flag | Default | Meaning |
|---|---|---|
| `-crash.cycles` | 8 | kill/restart cycles to run |
| `-crash.seed` | time-derived, always printed | cycle *N* uses `seed+N` |
| `-crash.cycle` | 0 (all) | run one cycle only, for reproduction |
| `-crash.durability` | `full` | `full`, `relaxed`, or `both` |
| `-crash.publishers` | 8 | concurrent publisher goroutines |
| `-crash.keep` | false | keep the data dir and ledger even on success |
| `-crash.resume` | "" | reconcile an existing ledger + data dir, run no new load |
| `-crash.gate` | false | run the throughput measurement instead of the kill loop |

### 5. Reconciliation and the vacuity guards

```go
type Violation struct {
	Rule   string // "OK-LOST", "FAILED-PRESENT", "GHOST", "SEQ-COLLISION", …
	Key    string
	Detail string
}

func Reconcile(state StateSnapshot, recs map[string]Record) []Violation
```

`StateSnapshot` is loaded in chunks from the read-only handle: `dedup_key → {seq, id, subject,
size, body_sha256}` for the harness's streams, plus `stream_seq.next` and `MAX(seq)` per stream.

| Rule | Assertion |
|---|---|
| `OK-LOST` | every `OK` record has a message at its recorded `(stream, seq)` with the same `id` (**I1**) |
| `OK-CORRUPT` | that message's body equals `Payload(key, size)` and `size == length(body)` |
| `FAILED-PRESENT` | no `FAILED` record's key appears in state |
| `GHOST` | no message in state carries a `dedup_key` absent from the ledger |
| `SEQ-COLLISION` | no two ledger keys map to the same `(stream, seq)` |
| `SEQ-REGRESSION` | the post-restart probe's seq exceeds every pre-crash seq |
| `DUP-INCONSISTENT` | a `duplicate:true` response returned the seq of the **first** record with that key |

`UNKNOWN` records assert **nothing** individually — that is the whole point — but they are not
free:

| Guard | Assertion | Why it exists |
|---|---|---|
| liveness | each cycle produced ≥ 50 `OK` records | a cycle that killed before any publish tests nothing |
| kill-lands | sweep-wide, `UNKNOWN` is ≥ 1 % and ≤ 20 % of records | too few ⇒ the kill never lands mid-flight; too many ⇒ the oracle has gone blind |
| classification | every non-2xx code is on the allow-list or explicitly mapped to `UNKNOWN` | an unknown code must not silently become a verdict |
| survivorship | sweep-wide, ≥ 1 `UNKNOWN` record found present **and** ≥ 1 found absent | proves the window is real and both outcomes actually occur |
| wal-tail | sweep-wide, a non-empty `-wal` file existed at least once at kill time | proves kills land with durable-but-unreplayed frames, i.e. recovery is exercised |

These are printed as a report, not merely asserted, because they are the answer to *"is this test
testing anything?"*:

### 6. `internal/verify` — the checker registry

```go
type Check struct {
	ID    string // "I4", or "V2" for structural checks with no invariant number
	Name  string
	Deep  bool   // excluded unless --deep: O(rows) or O(events)
	Query string // most checks are one SQL statement returning violating rows
	Run   func(context.Context, *sql.Conn) ([]Violation, error) // for the few that are not
}

func Registry() []Check
func Run(ctx context.Context, db *sql.DB, opt Options) (Report, error)
```

All checks run inside **one `BEGIN DEFERRED` read transaction**, so a live daemon committing
between two checks cannot make them disagree. Checks available at M2 — the delivery ones are
written *now* against schema v1 and are vacuously true until #9–#12 create rows, which is
deliberate: they must be green the day the first delivery row is written, not three issues later.

| ID | Check | Shape |
|---|---|---|
| V1 | schema version matches the binary; a newer schema is refused, never interpreted | `meta` |
| V2 | `PRAGMA quick_check` (`integrity_check` under `--deep`) | pragma |
| V3 | `PRAGMA foreign_key_check` | pragma |
| V4 | pragma readback: `journal_mode=wal`, `synchronous` matches the recorded durability mode | pragma |
| V5 | `size = length(body)`; `hdr` is valid JSON ≤ 4 KiB; subject matches one of the stream's patterns | SQL + matcher (#3) |
| V6 | seq allocator: `stream_seq.next > MAX(messages.seq)` per stream | SQL |
| I2 | every delivery row references an existing message; `state ∈ {0,1}` | SQL |
| I4 | `attempts <= max_deliver` for every delivery row (where `max_deliver > 0`) | SQL |
| I5 | `COUNT(deliveries) <= max_ack_pending` per consumer | SQL |
| I6 | `cursor_seq <= stream_seq.next`; no delivery row at `seq >= cursor_seq` | SQL |
| I8 | ≤ 1 DLQ message per `(origin_stream, origin_seq, consumer)` | SQL (`--deep`) |
| I10 | folding `events` from the beginning reproduces the persisted state | Go fold (`--deep`) |

Representative queries (proposal):

```sql
-- V6  the seq allocator must be ahead of every row it allocated
SELECT s.stream, s.next, IFNULL(MAX(m.seq), 0) AS max_seq
FROM stream_seq s LEFT JOIN messages m ON m.stream = s.stream
GROUP BY s.stream HAVING s.next <= IFNULL(MAX(m.seq), 0);

-- I2  a delivery row without its message is a partition violation
SELECT d.stream, d.consumer, d.seq FROM deliveries d
LEFT JOIN messages m ON m.stream = d.stream AND m.seq = d.seq
WHERE m.seq IS NULL LIMIT 100;

-- I4  the delivery bound must hold across restarts (D6: attempts is durable)
SELECT d.stream, d.consumer, d.seq, d.attempts, c.max_deliver
FROM deliveries d JOIN consumers c ON c.stream = d.stream AND c.name = d.consumer
WHERE c.max_deliver > 0 AND d.attempts > c.max_deliver LIMIT 100;

-- I5  flow control
SELECT d.stream, d.consumer, COUNT(*) AS pending, c.max_ack_pending
FROM deliveries d JOIN consumers c ON c.stream = d.stream AND c.name = d.consumer
GROUP BY d.stream, d.consumer HAVING pending > c.max_ack_pending;
```

**I10's fold is where the `exhaustive` linter earns its keep.** The fold switches over the closed
event vocabulary (§9.2); with `default-signifies-exhaustive: false` from #2, adding an event in a
later issue **fails compilation** until the fold handles it. At M2 the fold covers `msg.publish`,
`msg.dup`, `stream.*` and `recovery.*`; every later event arrives with its fold arm. That is how
I10 stays true instead of quietly decaying into a check of half the vocabulary.


Two rules matter more than the layout:

- **`verify` never writes.** Checks run with `query_only(1)` and no temp tables — the reconciler's
  joins happen in Go. See edge case 15 for the one place WAL recovery complicates "read-only".
- **A violation says "messq is broken", not "your config is odd".** Configuration opinions belong
  to `doctor` (#30), and `verify` says so in its output rather than growing a second personality.

### 8. The M2 throughput gate (D1's revisit trigger)

`messq bench` is #31. This issue needs a number *now*, so it ships a **measurement mode of the
load generator** — `go test ./test/crash -run TestDurableThroughput -crash.gate` — plus a written
methodology, not a polished command:

- 1 KiB payloads, open-loop, publishers ramped 8/16/32/64 until latency knees,
  `--durability=full`, 60 s steady state after a 10 s warm-up, one stream, no consumers.
- Reported: msg/s; p50/p99/p99.9 publish→durable-response; the observed
  `messq_commit_batch_size` distribution from #6; and a raw fsync-latency probe on the same
  filesystem (write 4 KiB + `fdatasync`, 1 000 samples) so the result is *interpretable*:
  `achievable ≈ batch_size / fsync_latency`.
- At M2 there are no consumers, so the measured quantity is **publish → durable response**, which
  is the D1 gate. The full publish+ack e2e round trip in §12 is measured by #31 once M3/M4 exist;
  `docs/perf/M2-baseline.md` says which number it holds.
- Recorded with: CPU, RAM, disk model, filesystem + mount options, kernel, Go version, binary
  commit, and the **verdict**.

Gate semantics, stated honestly because shared CI runners cannot meet the target:

| Environment | Assertion |
|---|---|
| Reference machine (NVMe, ext4, 8 cores) — the D1 gate | ≥ 5 000 msg/s; this recorded number is the one we publish |
| GitHub-hosted runner (`crash-smoke`) | ≥ 200 msg/s **smoke floor only** — catches "one fsync per message"; never quoted as evidence |
| tmpfs | measured and recorded, **never quoted as a durability number** (tmpfs fsync is a no-op) |

A cross-check that must be run before believing a *passing* number: if throughput passes while the
commit-batch histogram sits at 1, the device is not really syncing (lying write cache). Compare
against the fsync probe; a per-commit cost far below the device's physical sync latency invalidates
the run and hands the finding to #30.

**If the reference number misses 5 000 msg/s**, this issue does not fix it — it *decides*. Try, in
order: commit window (2 → 4 ms), `--commit-max-batch`, `wal_autocheckpoint`, `cache_size`. If the
gap persists, open the D1 escape-hatch issue (payload BLOBs to append-only segment files behind
`internal/store`, wire unchanged) **at M2**, citing the recorded baseline. That decision is this
issue's most valuable output even when the number passes.

### 9. Edge cases and how they are handled

| # | Edge case | Handling |
|---|---|---|
| 1 | **Stale Unix socket after SIGKILL** — the socket inode survives; a naive `Listen` fails with `address already in use` | the harness restarts with **no** cleanup, on purpose. The daemon must take the data-dir `flock` (released by the kernel on death), then unlink a socket it has proven dead. This is the most likely real bug the first cycle finds; if #5/#7 did not handle it, fixing it belongs here. |
| 2 | **Kill during first start (migrations)** | migrations are one transaction (§4.2); restart either replays or completes them. The `immediate` strategy targets this window explicitly. |
| 3 | **Kill between fsync and HTTP response** | the message exists, the client got nothing ⇒ `UNKNOWN`-present. Legal; the `survivorship` guard requires this case to be *observed*. |
| 4 | **Dedup keys expire** — the janitor NULLs `dedup_key` after `dedup_window_ms` (default 2 min), breaking key→message lookup | the harness stream is created with `dedup_window_ms = 24 h`, and reconciliation happens seconds after the kill. Documented in the harness, not silently worked around. |
| 5 | **Retrying an `UNKNOWN` publish** | same `Messq-Msg-Id` ⇒ `duplicate:true` with the original seq. The reconciler upgrades the record `UNKNOWN → OK` and asserts `DUP-INCONSISTENT`. The harness dogfoods the dedup feature #7 shipped. |
| 6 | **The driver itself dies** (CI timeout, OOM) | `Replay` truncates a torn final line; `-crash.resume` reconciles an existing ledger against an existing data dir with no new load. |
| 7 | **A leaked SUT from a failed cycle** holds the flock and breaks every later cycle | kill by process *group*, `Wait` to reap, assert the flock is acquirable before restart; `t.Cleanup` kills unconditionally. |
| 8 | **`-wal` / `-shm` left behind by SIGKILL** | expected and required: recovery must **replay** the WAL, never delete it. The `wal-tail` guard asserts a non-empty `-wal` was observed at kill time at least once per sweep. |
| 9 | **`relaxed` is not weaker under SIGKILL** | a process kill leaves the page cache intact, so `relaxed` must also lose nothing. The oracle asserts the **same** no-loss rule in both modes. Loss is permitted only under simulated power loss, which is **#32**. Encoding "relaxed may lose data" here would be a silent hole. |
| 10 | **No `time.Sleep`** (§11, lint-enforced) | readiness and kill timing use `cfg.Clock` and context deadlines. `testing/synctest` is deliberately **not** usable here — a real subprocess runs on real time — and that deserves a comment, since the rest of the suite depends on it. |
| 11 | **Subprocess coverage** — a SIGKILLed process flushes no `GOCOVERDIR` counters, so #2's `internal/store` floor gets nothing from killed cycles | every sweep runs a few **clean cycles** (start → load → SIGTERM → exit 0) against a `go build -cover` binary with `GOCOVERDIR` set. Killed cycles are known to contribute nothing and the harness does not pretend otherwise. |
| 12 | **Race detector** | the driver always runs under `-race`; the **SUT** is built with `-race` in the nightly sweep only — it is ~3× slower and would distort the throughput gate, which uses a plain `CGO_ENABLED=0` build. |
| 13 | **Non-determinism** | one seed drives kill timing, payload sizes, publisher scheduling and strategy choice; cycle *N* uses `seed+N`, so `-crash.cycle=N` replays one cycle's *plan*. Wall-clock interleaving is not reproducible, which is why failures always preserve artifacts instead of relying on replay. |
| 14 | **Vacuous green** | the guards in §5 plus the self-sabotage tests below. A harness nobody has watched fail is a harness nobody should trust. |
| 15 | **Read-only open of an unclean WAL database** — SQLite must run WAL recovery to see committed frames, and recovery *writes* (`-shm`) | `verify` opens a connection that is permitted to recover but sets `query_only(1)` so no check can mutate rows; a truly immutable open (`immutable=1`) is **refused** because it would ignore the WAL tail and report every recent message as lost. Verifying a *copy* therefore requires the `.db`, `-wal` and `-shm` files together, or a `messq backup` output — `verify` detects a lone `.db` beside a missing `-wal` that `meta.clean_shutdown` says should exist, and says exactly that instead of reporting phantom loss. |
| 16 | **Retention or the janitor deleting a message the oracle expects** | the harness stream sets no limits and the harness asserts no `retention.expire` event occurred during a cycle; when #27 lands, retention crash-testing is a #32 scenario with its own oracle rule. |

### 10. CI wiring

| Lane | Job | Content | Budget |
|---|---|---|---|
| PR (`pr.yml`) | `crash-smoke` | 8 cycles, `full`, default runner, plus the 200 msg/s smoke floor | ≤ 3 min |
| push to `main` | `crash-kill9` | 100 cycles × {`full`, `relaxed`} | ≤ 20 min |
| nightly (`crash-sweep`, replacing #2's placeholder) | full sweep | 1 000 cycles × {`full`, `relaxed`} × {ext4, tmpfs}, SUT built `-race`, artifacts uploaded | ≤ 90 min |

The PR lane's ≤ 10 min total budget (§11) is why only a smoke subset runs there. Nightly uploads
`crash-report.json` (cycle count, verdict histogram, recovery latencies, guard values) so drift in
the `UNKNOWN` ratio becomes visible *before* the oracle goes blind.

## Acceptance criteria

- [ ] `internal/testutil/ledger` implements append-only NDJSON with per-record CRC, group-fsynced
      writes, `Attempt` durable **before** the request is sent, and `Replay` that truncates a torn
      final record instead of erroring (while rejecting a corrupt record anywhere else).
- [ ] Every publish the harness issues carries a driver-minted `Messq-Msg-Id`, and bodies are the
      deterministic `Payload(key, size)` so recovered bodies are byte-compared.
- [ ] Verdict classification uses a **closed allow-list** for `FAILED`; every other non-2xx and
      every transport failure classifies as `UNKNOWN`; an unrecognised error code fails the cycle
      rather than silently becoming a verdict.
- [ ] The harness starts the real `messq serve` binary against a real data dir, SIGKILLs the
      process group at a seeded point, and restarts **with no manual cleanup** of the socket, lock,
      or `-wal`/`-shm` files; a failed restart is a test failure with artifacts preserved.
- [ ] Reconciliation implements `OK-LOST`, `OK-CORRUPT`, `FAILED-PRESENT`, `GHOST`,
      `SEQ-COLLISION`, `SEQ-REGRESSION` and `DUP-INCONSISTENT`, and asserts nothing about an
      individual `UNKNOWN` record's existence.
- [ ] The vacuity guards are enforced **and reported**: ≥ 50 OK per cycle; sweep-wide `UNKNOWN`
      ratio within [1 %, 20 %]; at least one `UNKNOWN` found present and one found absent; a
      non-empty `-wal` observed at kill time.
- [ ] Both `--durability=full` and `--durability=relaxed` assert **zero acknowledged loss** under
      SIGKILL; no code path in the oracle permits loss in either mode.
- [ ] After every restart the harness asserts: `recovery.unclean` was emitted, `PRAGMA
      integrity_check` is clean, `verify` is clean, and a probe publish receives a seq greater than
      every pre-crash seq.
- [ ] `internal/verify` exposes a check registry with stable IDs; V1–V6, I2, I4, I5, I6 run by
      default and I8, I10 under `--deep`; every check executes inside one read transaction and no
      check can write.
- [ ] The I10 event fold switches exhaustively over the closed event vocabulary, so adding an event
      in a later issue fails the build until the fold handles it.
- [ ] `messq verify [--data-dir] [--deep] [--output table|json]` ships and works against a
      **stopped** data dir, a **live** one, and a `backup` copy; exit codes 0/1/2/3/7 honoured; a
      copy missing its `-wal` is diagnosed explicitly rather than reported as data loss.
- [ ] A 1 000-cycle sweep is green in both durability modes; the run report (cycles, verdict
      histogram, recovery p50/p99, guard values) is uploaded as a CI artifact.
- [ ] The M2 throughput gate is measured on the reference machine and recorded in
      `docs/perf/M2-baseline.md` with hardware, filesystem, mount options, kernel, Go version,
      commit, fsync-probe result, commit-batch distribution and methodology; the **D1 verdict**
      (pass, or the number of the escape-hatch issue) is written down.
- [ ] CI runs `crash-smoke` on PRs (≤ 3 min), `crash-kill9` on push to `main` (100 cycles × 2
      modes), and #2's nightly `crash-sweep` placeholder is replaced by the real sweep.
- [ ] On failure the harness preserves seed, ledger, both server logs and a gzipped data dir, and
      prints a single-line reproduction command.
- [ ] No `time.Sleep` anywhere in the harness (`forbidigo` clean); all waiting goes through the
      clock seam or a context deadline.

## Test plan

Consistent with §11: the harness is code, so it is tested like code — and specifically, it is
tested by being **made to fail on purpose**.

**Unit — `internal/testutil/ledger`**
- Round-trip encode/replay; a CRC mismatch on a middle line is a hard error, on the final line a
  truncation; a file ending mid-line, a zero-length file, and a file ending in a block of `\0`
  (the fsync-hole shape) all replay to the last intact record.
- `Attempt` returns only after the record is on disk (asserted with a fake syncer counting `Sync`).
- Last-writer-wins folding: `Attempt` then two `Resolve`s yields the final verdict.
- Classification table test: one case per row of Design §3, including an unmapped code, which must
  produce an error rather than a verdict.

**Unit — `internal/verify`**
- One pair of fixture databases per check (clean / violating), built by direct SQL inserts into a
  migrated schema — this is where I2/I4/I5/I6/I8 get real coverage before the delivery engine
  exists. *A check that cannot be made to fail is not a check.*
- Registry meta-test: every ID in the §5.2 invariant register is either implemented here or listed
  explicitly as "checked elsewhere" with the owning issue number, so the register cannot drift.
- I10 fold: an events table folded to state; a deliberately mutated state row must be detected; the
  fold's switch is exhaustive (enforced by `exhaustive` from #2, asserted by a build-tag test).
- Read-only enforcement: a check that attempts a write fails loudly (`attempt to write a readonly
  database`), asserted once so nobody adds a writing check later.
- WAL-copy diagnosis: a data dir copied without its `-wal` is reported as an incomplete copy, not
  as missing messages (edge case 15).

**Harness self-sabotage** (`TestOracleDetects*`) — each takes a good run's data dir and ledger,
injects exactly one defect, and asserts the exact rule fires:
- delete one message with an `OK` record → `OK-LOST`
- flip one byte of a message body → `OK-CORRUPT`
- insert a message whose key is `FAILED` → `FAILED-PRESENT`
- insert a message with a key absent from the ledger → `GHOST`
- rewind `stream_seq.next` → `V6` and `SEQ-REGRESSION`
- corrupt a page in the DB file → `integrity_check` fails and `verify` exits 1
- a run whose kill lands after all load finished → the `liveness`/`kill-lands` guards fail, proving
  a vacuous run cannot pass
- a build that classifies every response as `UNKNOWN` → the `kill-lands` upper bound fails

**Crash (the harness driving the real daemon)**
- `TestCrashKill9` — seeded cycles across all three kill strategies, both durability modes; the
  per-merge, main and nightly lanes are this test with different `-crash.cycles`.
- `TestCrashDuringMigration` — `immediate` strategy against a fresh data dir, ≥ 50 cycles.
- `TestRestartNoCleanup` — 20 consecutive kill/restart cycles with zero filesystem intervention
  (the stale-socket + flock regression test).
- `TestResumeAfterDriverDeath` — kill the driver mid-run, then `-crash.resume` reconciles the
  existing ledger against the existing data dir correctly.
- `TestRecoveryLatency` — recovery time recorded per cycle; nightly asserts p99 ≤ 2 s (§12).

**testscript (`test/script/verify.txtar`)** — the first entries in the suite #26 completes
- `messq verify` on a fresh data dir → exit 0, golden human output.
- On a sabotaged copy → exit 1, violation text present; `--output json` parses and carries the
  frozen field names.
- Missing data dir → exit 3; unreadable data dir → exit 7; unknown flag → exit 2.
- `--deep` on a data dir with events → exit 0 with I10 reported as *run*, not *skipped*.

**Benchmark / gate**
- `TestDurableThroughput -crash.gate` produces the numbers for `docs/perf/M2-baseline.md`; CI
  asserts only the smoke floor. `benchstat` comparison against a stored baseline is #31.
- The lying-write-cache cross-check (commit-batch distribution vs. fsync probe) runs with the gate
  and fails the measurement — not the build — when the numbers are physically implausible.

**Leak checks**
- After every cycle: no surviving child process, no leaked file descriptors in the driver, and
  (nightly) a goroutine-stack diff after the driver's own shutdown.

**Explicitly not tested here**: ack/nak/term crash behaviour (no consumers yet — #9–#12, asserted
via #13 and the extended sweep in #32), ENOSPC/EIO/clock faults and power-loss semantics (#32),
golden event and log assertions (#19), schema-upgrade paths (#34).
