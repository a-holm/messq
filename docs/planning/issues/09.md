## Context

Everything up to here stores messages. Nothing has ever *delivered* one. This issue opens M3 by
building the half of the delivery engine that decides **which message goes to whom, when, and how
many are allowed to be outstanding**: consumer configuration, the durable cursor, the top-up that
materialises delivery rows, the claim that hands a message out, and the flow-control bound that
keeps the pending set small by construction.

It is the load-bearing issue of the milestone. #10 (settle verbs), #11 (sweeper), #12 (DLQ) are
all *reactions* to a delivery that this issue created; #13's property suite has nothing to drive
until delivery rows exist; #14's long-poll fetch is a parking loop around the `Fetch` command
defined here. Three PLAN.md decisions are realised in code for the first time:

- **D5 — durable rows, ack = DELETE.** The pending set *is* `deliveries`. This issue is what makes
  that table non-empty, and what guarantees it stays bounded (`max_ack_pending` enforced at
  top-up). There is no in-memory delivery state anywhere; the only in-memory structure introduced
  here is a rate-limit map for `flow.blocked`, bounded by consumer count.
- **D6 — attempt counting at claim, durable before the fetch response.** `attempts++` happens in
  the same transaction that flips the row to `INFLIGHT`, and #6's writer only replies after the
  commit's fsync. `max_deliver = 5` therefore means exactly five handler invocations, across
  crashes, forever.
- **D1/D11 — one transactional boundary.** Top-up, cursor advance, claim and the `msg.deliver`
  event rows commit together or not at all.

Governing sections: **§5** (state machine; T1, T2, T9), **§5.1** (transition rules), **§5.2**
(I2, I4, I5, I6, I11), **§4.2** (the `consumers` and `deliveries` tables and the
`deliveries_ready` index), **§7** (consumer and fetch endpoints), **§9.2** (`consumer.create`,
`consumer.update`, `consumer.delete`, `consumer.pause`, `msg.deliver`, `flow.blocked` — a closed
set; this issue invents no new event names), **§3.2** (all of this runs as commands through the
single writer, so two concurrent fetches for one consumer cannot double-claim — there is no
`SELECT … FOR UPDATE`, no busy-retry loop, and no lock).

#4's SEMANTICS.md is normative for everything below; where this issue found the spec
under-determined (the `max_ack_pending` overshoot case in §5 of the design, the fetch-response
crash window) the resolution is written here **and fed back into SEMANTICS.md in the same PR** —
the spec and the engine ship together or the spec is wrong.

## Scope

### In scope

- **Consumer configuration as a pure, validated type** in `internal/queue`: name grammar, filters,
  `ack_wait`, `max_deliver`, `max_ack_pending`, `backoff_ms`, `dead_policy`, `paused`, plus the
  computed **retry horizon** the CLI prints later (#24).
- **Consumer CRUD** as writer commands: create/update (idempotent), delete (name-confirmed, drops
  delivery rows), pause/resume at the engine level, with `consumer.create` / `consumer.update` /
  `consumer.delete` / `consumer.pause` event rows in the same transaction.
- **Start position at creation** (`start` | `new` | `seq:N` | `time:T`) resolved to `cursor_seq`.
- **Cursor top-up (T1)**: bounded range scan from `cursor_seq`, subject filtering in Go with the
  #3 compiled matcher, `deliveries` inserts for matches, and the cursor advanced past everything
  *decided* — including non-matches — so a narrow filter on a busy stream is amortised O(1) per
  message, not O(stream) per fetch.
- **Claim (T2)**: candidate selection in ascending `seq`, byte budget, `attempts++`,
  `state = INFLIGHT`, `visible_at = now + ack_wait`, `delivered_at = now`, one `msg.deliver` event
  per claimed row — committed **before** the response.
- **Ack-token minting** in the fenced, human-readable D7 form (`ParseToken`/`Fence` land in #10).
- **Flow control**: top-up refuses once `pending(c) >= max_ack_pending(c)`, emitting a rate-limited
  `flow.blocked` event and returning an empty batch with a typed **hold reason**.
- **`Fetch` as a single writer command** (top-up + claim + events in one transaction) with a
  single-shot, non-blocking contract, plus the post-commit payload read from the read pool.
- **Consumer info on the read pool**: `pending`, `inflight`, `ready_now`, `in_backoff`, `backlog`,
  `oldest_pending_age_ms`, `cursor_seq`, `generation`, `blocked_by`.
- **Consumer invariant checkers `C1`–`C6`** registered into #8's `internal/verify` registry, which
  makes the already-written I2/I4/I5/I6 checks non-vacuous for the first time.
- **A provisional HTTP slice** on #7's M2 server (consumer CRUD + a single-shot `fetch`) so this
  issue is testable end to end and #10 has something to settle against.

### Out of scope

- `ack` / `nak` / `term` / `extend`, token **parsing** and fencing, stale-ack detection → **#10**.
- Ack-timeout expiry, backoff *application*, `max_deliver` routing to the dead path → **#11**
  (the backoff array is validated and the horizon computed here; nothing consumes it yet).
- Dead-lettering and `<stream>.dlq` → **#12**. `dead_policy` is stored and defaulted here only.
- The reference model and the full `rapid` suite → **#13** (this issue contributes its actions and
  its invariant hooks).
- Long-poll: the waiter registry, `wait_ms`, wake-on-publish, `--max-waiters`, the final fetch
  response shape and the closed error enum → **#14**. The provisional route here accepts `wait_ms`
  and ignores it.
- Consumer HTTP admin surface (`pause`/`resume`, `seek`, `pending` listing, `?dry_run=1`) → **#15**;
  `seek` semantics and the `generation` bump → **#28**. This issue **reads** `generation` and mints
  it into tokens; it never writes it.
- Auth, roles, `actor` provenance beyond passing a string through → **#16**.
- Event fan-out, slog, sampling, metrics (`messq_delivered_total`, `messq_pending`,
  `messq_backlog`, `messq_oldest_pending_age_seconds`) → **#19** / **#21**. This issue writes event
  *rows* and exposes the derived-stat functions those metrics will call.
- Retention interaction (`retention.blocked`, workqueue reaping below `min(cursor_seq)`) → **#27**.
- `ordered = subject` → **#38**; per-consumer rate limiting → **#39**. Both are accepted as
  *config* here only if they are rejected as unsupported — see the edge-case table.
- `messq consumer …`, `messq sub`, `messq lag` → **#24**.

## Design proposal

Everything below is a proposed starting point except the four items marked **decision**, which
#10–#14 build on and are expensive to reverse.

### 1. Pure configuration and validation (`internal/queue`)

No I/O, no `time.Now`, no map-iteration dependence — so #13 drives it and the fuzzers hammer it.

```go
package queue

type DeadPolicy string // "dlq" | "drop"   (exhaustive-linted)

type ConsumerConfig struct {
    Name          string
    Filters       []string      // NATS subject patterns; default [">"]
    AckWait       time.Duration // default 30s
    MaxDeliver    int32         // default 5; 0 = unlimited (warned)
    MaxAckPending int64         // default 1000
    Backoff       []time.Duration // default [1s,5s,30s,2m,10m]; last value repeats
    DeadPolicy    DeadPolicy    // default "dlq"; "drop" on a .dlq stream
    Paused        bool
}

// StartPosition is honoured ONLY at creation. Moving an existing cursor is seek (#28).
type StartPosition struct {
    Kind Start // StartFirst | StartNew | StartSeq | StartTime
    Seq  int64
    Time int64 // unix ms
}

type ConsumerLimits struct { // process-wide ceilings from flags
    MaxAckWait        time.Duration // --max-ack-wait, 1h
    MinAckWait        time.Duration // 100ms
    MaxFilters        int           // 32
    MaxBackoffEntries int           // 16
    MaxBackoffDelay   time.Duration // 24h
    MaxAckPendingCap  int64         // 1_000_000
    MaxConsumers      int           // --max-consumers, 1024 (process-wide)
}

func ValidateConsumerName(name string) error
func ValidateConsumerConfig(c ConsumerConfig, l ConsumerLimits) (Warnings, error)
func RetryHorizon(c ConsumerConfig) time.Duration // Σ backoff(1..max_deliver-1); ∞ if max_deliver=0
```

**Name grammar (decision)** — identical to the stream-name grammar in #7 and constrained by the
ack-token grammar in #4 (`stream/consumer/seq/attempt/generation`): ASCII, 1–64 bytes,
`[A-Za-z0-9_.-]`, starts and ends alphanumeric, **no `/`**, no `..`. Case-insensitive uniqueness
within a stream. The dependency runs both ways and is stated in both places: relaxing the name
grammar later silently breaks token parsing.

**Bounds**: `AckWait ∈ [100ms, MaxAckWait]`; `MaxDeliver ∈ [0, 1000]`; `MaxAckPending ∈ [1,
MaxAckPendingCap]`; `Backoff` 1–16 entries, each `∈ [0, 24h]`; `Filters` 1–32 valid patterns
(compiled once with #3's matcher and cached beside the consumer).

**Warnings, not errors** (returned to the caller, logged, surfaced by #24): `max_deliver = 0`
("a poison message will retry forever; you probably want a DLQ alert instead"); a non-monotonic
backoff array; `RetryHorizon` shorter than `ack_wait` (retries will pile up); `dead_policy = dlq`
on a stream whose `.dlq` has no consumer (#29 owns the real check).

**Defaults**, verbatim from §4.2 so schema defaults and Go defaults cannot drift — a table test
asserts `ValidateConsumerConfig(zero-value defaults)` equals the column defaults read back from a
freshly created row.

### 2. CRUD commands and what "idempotent create/update" means

```go
// internal/store — writer commands (one Cmd each, per #6's interface)
func (s *Store) CreateConsumer(ctx context.Context, stream string, c queue.ConsumerConfig,
    start queue.StartPosition, actor string) (ConsumerInfo, queue.Warnings, error)
func (s *Store) UpdateConsumer(ctx context.Context, stream, name string, p ConsumerPatch,
    actor string) (ConsumerInfo, queue.Warnings, error)
func (s *Store) DeleteConsumer(ctx context.Context, stream, name, actor string) (DeleteResult, error)
func (s *Store) SetPaused(ctx context.Context, stream, name string, paused bool, actor string) (ConsumerInfo, error)

// read-only pool, never queued on the writer
func (s *Store) GetConsumer(ctx context.Context, stream, name string) (ConsumerInfo, error)
func (s *Store) ListConsumers(ctx context.Context, stream string) ([]ConsumerInfo, error)
```

- `POST /v1/streams/{s}/consumers` with a **new** name creates: `cursor_seq` from `StartPosition`,
  `generation = 1`, `consumer.create` event.
- …with an **existing** name and an identical config: `200`, no write, no event (deploy scripts
  run it every boot).
- …with an existing name and a different config: applied as an update, `consumer.update` event
  carrying a `detail` diff of changed fields only.
- **`start` is immutable after creation (decision).** Supplying a `start` that differs from the
  consumer's creation value returns `409 immutable_field` with
  `next: ["messq seek {s} {c} --to …"]`. Silently ignoring it would make "why didn't my consumer
  reprocess?" a support category; silently applying it would make a deploy script a data-loss
  device.
- **Config changes are forward-only** (§5.1 via #4): a new `ack_wait` applies to future claims and
  does not move an in-flight deadline; a new `backoff` applies to the next scheduling decision; a
  new `max_ack_pending` applies at the next top-up. Changing `filters` does **not** retroactively
  deliver skipped messages (the cursor already passed them — `seek` is the tool) and does **not**
  drop already-admitted rows whose subject no longer matches (they carry attempts and backoff
  state that dropping would silently discard). The update response reports
  `{"filters_changed": true, "pending_now_unmatched": N}` so the operator learns what they did.
- `DELETE …?confirm={name}` deletes the consumer row and all its delivery rows in one transaction
  (bounded: `pending ≤ max_ack_pending`), reports `{"deleted":{"pending":N,"inflight":M}}`, emits
  `consumer.delete`. Outstanding tokens for a deleted consumer then resolve to `not_found`, **not**
  idempotent success (#4 §8, implemented in #10).
- Pause/resume both emit `consumer.pause` with `detail:{"paused":true|false}` — §9.2 is a closed
  vocabulary and has no `consumer.resume`. Do not invent one.

### 3. `Fetch`: one command, one transaction

```go
type FetchReq struct {
    Stream, Consumer string
    Batch            int   // 1..--max-fetch-batch
    MaxBytes         int64 // 0 = --fetch-max-bytes
}

type FetchResult struct {
    Messages  []Delivered
    Hold      HoldReason // why the batch is short/empty; HoldNone when full
    CursorSeq int64
    Pending, Inflight, Backlog int64
}

type Delivered struct {
    Stream, Consumer string
    Seq        int64  `json:"seq"`
    ID         string `json:"id"`
    Subject    string `json:"subject"`
    Headers    map[string]string `json:"headers,omitempty"`
    BodyB64    []byte `json:"body_b64"`
    Size       int64  `json:"size"`
    Attempt    int32  `json:"attempt"`
    MaxDeliver int32  `json:"max_deliver"` // 0 = unlimited
    AckToken   string `json:"ack_token"`
    DeadlineMS int64  `json:"deadline_ms"`
    AckWaitMS  int64  `json:"ack_wait_ms"`
    PublishedAt int64 `json:"published_at"`
    TraceID    string `json:"trace_id"`
}

type HoldReason string // "" | "paused" | "flow_control" | "backoff" | "catching_up" | "empty"
```

`Apply` (inside #6's batch transaction, on the writer goroutine, wrapped in its own savepoint):

1. Load the consumer row `FOR the transaction` (plain `SELECT`; the writer is the only mutator).
   Missing stream or consumer → `ErrNotFound` (a `CmdError`: rolls back this savepoint only).
2. `paused = 1` → return empty, `Hold = paused`. No scan, no event.
3. `pending, inflight := SELECT COUNT(*), IFNULL(SUM(state),0) FROM deliveries WHERE stream=? AND consumer=?`
   — bounded by `max_ack_pending` and index-satisfiable on `deliveries_ready`'s `(stream,
   consumer)` prefix. **This is the payoff of D5: the pending set is small by construction, so the
   flow-control check is a cheap counting query rather than a maintained counter that can drift.**
4. **Top-up** (§4) while `pending < max_ack_pending` and fewer than `Batch` claimable rows exist.
5. **Claim** (§5) up to `Batch` rows / `MaxBytes` bytes, ascending `seq`.
6. One `msg.deliver` event row per claimed row, same transaction (D11).
7. Return metadata only. After the commit returns, the handler reads the payloads from the **read
   pool** (§6) and assembles the response.

**Single-shot (decision).** `Fetch` never blocks, never sleeps, never registers a waiter. #14
wraps it in the long-poll: call, and if the result is empty and `wait_ms > 0`, park on the waiter
registry and call again on wake or timeout. Keeping the blocking out of the writer command is what
keeps the commit window at 2 ms and the goroutine census in §3.2 honest. `Hold = catching_up` is
the one signal to the caller that it should retry **immediately** rather than park (§4).

### 4. Top-up (T1) — the cursor and why it advances past non-matches

```sql
-- wildcard filters: bounded primary-key range scan; gaps from retention are harmless
SELECT seq, subject FROM messages
 WHERE stream = :s AND seq >= :cursor
 ORDER BY seq LIMIT :scan_limit;
```

Then, in Go, for each row in order: match against the compiled filters; on a match insert

```sql
INSERT INTO deliveries (stream, consumer, seq, subject, state, attempts,
                        visible_at, generation, delivered_at, last_reason)
VALUES (:s, :c, :seq, :subject, 0, 0, 0, :generation, NULL, NULL)
ON CONFLICT (stream, consumer, seq) DO NOTHING;
```

and finally one cursor write:

```sql
UPDATE consumers SET cursor_seq = :next_cursor WHERE stream = :s AND name = :c;
```

**`next_cursor` is the whole design.** Three cases, in priority order:

| Situation | `next_cursor` | Why |
|---|---|---|
| Stopped because `pending` reached `max_ack_pending` at seq *k* (a match we did **not** insert) | *k* | The cursor must never pass a message this consumer has not admitted, or the message is skipped forever. Flow control must delay, never drop. |
| Scan returned `scan_limit` rows, last examined seq *k* | *k + 1* | Every seq ≤ *k* has been decided (admitted or filtered out). |
| Scan returned fewer than `scan_limit` rows | `stream_seq.next` | Nothing exists between the last row and the head; #7 guarantees gap-free allocation, so jumping to head+1 is safe and keeps a `>`-filtered consumer at O(1). |

Advancing past non-matches is what makes a narrow filter cheap — but it also means **changing
`filters` cannot un-skip history** (§2), and it means every delivery row is always at
`seq < cursor_seq` (checker C1, sharpening I6).

**`ON CONFLICT DO NOTHING` is defensive, not expected.** With `seq < cursor_seq` always true, a
conflict can only mean a stale row survived a `seek` rewind. #28 must drop delivery rows in the
same transaction as the `generation` bump (T10). Until then, conflicts are counted into the
command result and a non-zero count is a `verify` violation (C3), not a silent recovery.

**Catch-up on a rare subject.** A consumer filtered to `orders.eu.refund` on a 10 M-message stream
scans `--scan-limit` (4096) rows per fetch and may match nothing. The fetch returns empty with
`Hold = catching_up` and the new `cursor_seq`, and #14's waiter re-calls immediately instead of
parking for `wait_ms` — progress is durable, so catch-up is monotone and survives restarts.
**Proposed optimisation, benchmarked before adoption:** when every filter is literal (no `*`, no
`>`), replace the range scan with one indexed query per filter over `messages_subj`
(`WHERE stream=? AND subject=? AND seq>=? ORDER BY seq LIMIT n`), merged by seq — O(matches)
instead of O(scanned), and the cursor still jumps to the last examined seq. Wildcard filters keep
the range scan. Add the index-path variant only with `BenchmarkTopUpRareSubject` showing the win.

### 5. Claim (T2) and flow control

Candidate selection first, then one update — **`UPDATE … ORDER BY … LIMIT` requires SQLite's
`SQLITE_ENABLE_UPDATE_DELETE_LIMIT` compile option, which we must not depend on across the
`modernc` / `mattn` build-tag matrix (decision)**:

```sql
-- candidates: ascending seq, with the size needed for the byte budget
SELECT d.seq, d.attempts, m.size
  FROM deliveries d JOIN messages m ON m.stream = d.stream AND m.seq = d.seq
 WHERE d.stream = :s AND d.consumer = :c AND d.state = 0 AND d.visible_at <= :now
 ORDER BY d.seq LIMIT :batch;

-- claim exactly the chosen seqs, one statement
UPDATE deliveries
   SET state = 1, attempts = attempts + 1,
       visible_at = :now + :ack_wait_ms, delivered_at = :now
 WHERE stream = :s AND consumer = :c AND seq IN (/* chosen */)
RETURNING seq, attempts;
```

- **Byte budget**: accumulate `m.size` in Go; stop before exceeding `MaxBytes`, but **always
  return at least one message** even if it alone exceeds the budget — otherwise a 1 MiB message on
  a consumer with a 256 KiB budget is undeliverable forever.
- **Index note**: `deliveries_ready(stream, consumer, state, visible_at, seq)` orders by
  `visible_at` before `seq`, so `ORDER BY seq` under a `visible_at` range costs a temp sort — over
  at most `pending ≤ max_ack_pending` rows, which is why the bound exists. If `BenchmarkClaim` at
  `max_ack_pending = 100 000` says otherwise, migration `000X` adds
  `CREATE INDEX deliveries_claim ON deliveries(stream, consumer, state, seq)`. Measure first.
- **`attempts` is post-increment-visible**: during attempt *n*, `row.attempts = n`; the token
  carries *n*; the response carries `attempt: n, max_deliver: M`. This is the arithmetic #10's
  fence and #11's `attempts >= max_deliver` test depend on.
- **Deadline** = `now + ack_wait`, from #4's derived monotonic clock (`now_ms()`), never raw
  `time.Now` — a wall-clock step must not expire a lease early (#32 tests it).

**Flow control.** The bound is on `pending(c)` (READY + INFLIGHT), enforced at **top-up**, not at
claim — the reading #4's spec fixes. Consequences worth stating in SEMANTICS.md:

- A consumer at its bound stops *accumulating*; it keeps being able to claim rows it already has,
  so a stalled downstream degrades to "no new work" rather than "no work at all".
- `flow.blocked` is emitted **rate-limited to once per 10 s per consumer**
  (`--flow-blocked-interval`), from a `map[consumerKey]int64` owned by the writer, entries pruned
  on consumer delete — bounded by consumer count, which is bounded by `--max-consumers` (I11).
- The fetch returns `Hold = flow_control` with `pending` and `max_ack_pending`, so a worker (and
  #24's `lag`) can say *why* the backlog is growing without reading logs.

**Lowering `max_ack_pending` below current `pending` (decision, and a spec amendment).** Refusing
an operator who is throttling a consumer mid-incident is unacceptable, so the update is accepted
and converges in two steps: (a) the update command drops **undelivered** rows (`state = READY AND
attempts = 0`) from the tail, highest seq first, and rewinds `cursor_seq` to the lowest dropped
seq — safe and lossless, because those seqs have never been delivered and no attempt or backoff
state exists to discard; (b) if in-flight and in-backoff rows alone still exceed the new bound, the
surplus is reported as `{"overshoot": N}` and drains as work is settled. I5 is therefore an
**admission** invariant — *no top-up inserts a row when `pending >= max_ack_pending`* — with
`pending ≤ max_ack_pending` as its at-rest consequence except during a deliberate shrink. #8's I5
check reports the shrink case as an **advisory** naming the consumer, not a violation. SEMANTICS.md
§S15 gets this wording in the same PR.

### 6. Payload reads happen *after* the commit

**Decision:** the claim transaction touches metadata only; bodies are read from the `ro` pool after
the commit returns.

```sql
SELECT seq, id, subject, hdr, body, size, published_at, trace_id
  FROM messages WHERE stream = ?1 AND seq IN (/* claimed */);
```

Reading up to `--fetch-max-bytes` of BLOBs inside the writer's transaction would put an 8 MiB read
inside a 2 ms commit window shared by every publisher in the process. Messages are immutable and
retention may not delete a message holding an outstanding delivery row (#27), so the read is safe.
D6 is unaffected: `attempts++` is committed before anything is sent to the client.

Residual case: the row is gone anyway (a purge that did not drop delivery rows). The entry is
omitted from the response and logged at WARN; the row times out and redelivers normally. The real
fix is a requirement on #15/#28: **purge must drop the delivery rows for the seqs it removes, in
the same transaction.** A `verify` C2 violation catches any purge that forgets.

### 8. Consumer info — derived stats, defined once

Metrics (#21), `consumer info` (#24), `lag` (#24) and alerts must all be the same number, so they
call one function over one query. Definitions verbatim from #4 §3.

```sql
SELECT COUNT(*)                                        AS pending,
       IFNULL(SUM(d.state), 0)                         AS inflight,
       IFNULL(SUM(d.state = 0 AND d.visible_at <= :now), 0) AS ready_now,
       IFNULL(MIN(m.published_at), 0)                  AS oldest_published_at
  FROM deliveries d JOIN messages m
    ON m.stream = d.stream AND m.seq = d.seq
 WHERE d.stream = ?1 AND d.consumer = ?2;
```

`in_backoff = pending - inflight - ready_now`. `oldest_pending_age_ms = now - oldest_published_at`
(0 when empty) — age since **publish**, because that is the user-facing SLI ("how long has this
work been waiting"), not age since the current attempt.

`backlog(c) = pending(c) + |{messages with seq >= cursor_seq matching filters}|`. The second term
is exact and O(1) for the default `[">"]` filter (`stream_seq.next - cursor_seq`), exact via
`messages_subj` for literal-only filters, and otherwise an **upper bound** (all messages at or
above the cursor). The response carries `"backlog_exact": false` in that case and #21's gauge
carries the same value — an approximate number everyone agrees on beats two exact numbers that
disagree.

`blocked_by` (first match wins): `paused` → `flow_control` → `backoff` (pending > 0, ready_now = 0)
→ `catching_up` (cursor_seq < head and nothing pending) → `empty` → `none`. #38 inserts
`ordered_hol` and #39 inserts `rate_limit` into this precedence list.

### 11. Edge cases, decided

| Case | Handling |
|---|---|
| Two concurrent fetches, same consumer | Serialised by the single writer; the second sees the first's claims. No double-claim is possible by construction — stated in SEMANTICS.md as a property of §3.2, not of a lock |
| SIGKILL between the claim commit and the fetch response | The attempt is **burned**: recovery reclaims the row to READY without touching `attempts` (T9). Legal and deliberate under D6 — it is what stops a crash-looping broker from replaying a poison message forever. Documented in SEMANTICS.md and in `docs/guarantees.md` |
| `batch = 0` or negative | `400 invalid_argument`. A fetch is not a status probe; `consumer info` is |
| `batch > --max-fetch-batch` | Clamped, and the effective value echoed. Silent clamping builds wrong dashboards |
| Single message larger than `max_bytes` | Returned alone, over budget, rather than never |
| `max_ack_pending = 1` | Strict serial delivery: top-up admits one row, claim hands it out, no second row until it is settled. A named test — it is the boundary every bound-check bug hides in |
| `max_deliver = 0` | Stored, warned at creation; nothing here consumes it (#11 does) |
| Consumer created on an empty stream | `cursor_seq = stream_seq.next` (= 1); `start:first` and `start:new` coincide, and that is fine |
| `start = seq:N` with `N` below `first_seq` or above head | Clamped to `[first_seq, stream_seq.next]`; the response reports the clamped value and the requested one |
| `start = time:T` | Binary search on `messages_age`; `T` after head → `stream_seq.next`; `T` before first → `first_seq` |
| Cursor below `first_seq` after retention | Harmless: the range scan finds nothing there and the cursor jumps forward. #27 owns not deleting messages that still hold delivery rows |
| Consumer on a `.dlq` stream | `dead_policy` defaults to `drop` and `dlq` is refused (#4: no DLQ of a DLQ). The `.dlq` stream is otherwise an ordinary stream and consumable |
| `ordered: true` or `max_rate` in the request | `400 unsupported`, naming #38/#39 — accepting and ignoring a delivery-semantics flag is a correctness lie |
| Consumer deleted while messages are in flight | Rows deleted with it; later tokens get `not_found` (#10), never idempotent success |
| Stream deleted with consumers | #7's chunked delete removes consumers and their delivery rows; the first (small) transaction makes the stream disappear |
| Fetch while the store is latched read-only (#6) | `503 read_only` — a claim is a write. `consumer info` and `pending` keep working: reading the evidence must survive the failure |
| Filter change leaves unmatched pending rows | Kept and delivered; count reported. Dropping them would discard attempts and backoff state |
| `hdr` JSON on a claimed message is invalid | Impossible via #7's validation; if it happens, the entry is skipped, logged at ERROR, and `verify` V5 catches the row. Never crash a fetch on one bad row |

### 12. Invariant checkers (`C1`–`C6`, registered into #8's registry)

Numbered `C*` so they never collide with the normative `I*` IDs; each is one SQL statement in
`internal/verify` and is reused verbatim as a `rapid` invariant hook by #13.

| ID | Statement | Sharpens |
|---|---|---|
| C1 | No delivery row exists at `seq >= consumers.cursor_seq` | I6 |
| C2 | Every delivery row references an existing `messages` row in the same stream, and `deliveries.subject` equals that message's `subject` | I2 |
| C3 | Every delivery row's `generation` equals its consumer's `generation` | I7 (fencing) |
| C4 | `1 <= consumers.cursor_seq <= stream_seq.next` for every consumer | I6 |
| C5 | `pending(c) <= max_ack_pending(c)`, **advisory** when the bound was lowered below the current pending set (§5) | I5 |
| C6 | Row well-formedness: `state ∈ {0,1}`; `attempts >= 0`; `attempts <= max_deliver` when `max_deliver > 0`; `state = 1 ⇒ delivered_at IS NOT NULL AND visible_at > delivered_at`; `state = 0 ⇒ delivered_at IS NULL OR attempts > 0` | I4 |

```sql
-- C1  the cursor dominates every delivery row
SELECT d.stream, d.consumer, d.seq, c.cursor_seq
  FROM deliveries d JOIN consumers c ON c.stream = d.stream AND c.name = d.consumer
 WHERE d.seq >= c.cursor_seq LIMIT 100;

-- C3  a surviving pre-seek row would let a stale token fence incorrectly
SELECT d.stream, d.consumer, d.seq, d.generation, c.generation
  FROM deliveries d JOIN consumers c ON c.stream = d.stream AND c.name = d.consumer
 WHERE d.generation <> c.generation LIMIT 100;
```

## Acceptance criteria

- [ ] `POST /v1/streams/{s}/consumers` creates a consumer with validated name, filters, `ack_wait`,
      `max_deliver`, `max_ack_pending`, `backoff_ms` and `dead_policy`; re-posting an identical
      config returns `200` with no write and no event; a different config is applied as an update
      with a `consumer.update` event whose `detail` names only the changed fields.
- [ ] Column defaults in §4.2 and Go defaults are proven equal by a test that reads back a row
      created from the zero-value config.
- [ ] `start` resolves `cursor_seq` correctly for `first`, `new`, `seq:N` (including clamping below
      `first_seq` and above head) and `time:T` (including before-first and after-head); supplying a
      different `start` to an existing consumer returns `immutable_field` pointing at `seek`.
- [ ] `DELETE …?confirm={name}` is refused without a matching `confirm`, removes the consumer and
      every delivery row in one transaction, reports the counts, and emits `consumer.delete`.
- [ ] Pause returns an empty fetch with `hold: "paused"` and performs no scan and no claim; resume
      restores delivery; both emit `consumer.pause` with the boolean in `detail`.
- [ ] A fetch on a consumer whose filter matches admits only matching messages, and `cursor_seq`
      advances past non-matching messages so a second fetch does not rescan them.
- [ ] A consumer filtered to a rare subject on a 1 M-message stream reaches the head in a bounded
      number of fetches, each within the scan limit, with `hold: "catching_up"` while it works;
      a restart mid-catch-up resumes from the persisted cursor without rescanning.
- [ ] Every delivery row always satisfies `seq < cursor_seq` (C1) and carries the message's subject
      (C2) — asserted by `verify` after every test in this issue's suite.
- [ ] A claim increments `attempts` by exactly one, sets `state = INFLIGHT`,
      `visible_at = now + ack_wait` and `delivered_at = now`, mints a token
      `stream/consumer/seq/attempt/generation` matching the row, and writes one `msg.deliver` event
      in the same transaction.
- [ ] `attempts` survives a SIGKILL taken between the claim commit and the fetch response: after
      restart the row is READY with `attempts` unchanged, and the crash harness (#8) records it.
- [ ] Messages are claimed in ascending `seq`; a fetch of `batch = N` returns at most `N`, at most
      `max_bytes` bytes, and always at least one message even if that message alone exceeds
      `max_bytes`.
- [ ] Top-up refuses to insert once `pending >= max_ack_pending`; the cursor does **not** advance
      past the first message it declined to admit, and that message is delivered after the pending
      set drains.
- [ ] A consumer at `max_ack_pending` returns `hold: "flow_control"` with `pending` and the bound,
      emits `flow.blocked` at most once per `--flow-blocked-interval`, and **does not affect any
      other consumer on the same stream** (a second consumer keeps receiving).
- [ ] `max_ack_pending = 1` yields strictly serial delivery.
- [ ] Lowering `max_ack_pending` below the current pending set drops only `READY AND attempts = 0`
      rows, rewinds `cursor_seq` to the lowest dropped seq, loses no message, reports `overshoot`
      for the residue, and leaves `verify` with an advisory rather than a violation.
- [ ] Two concurrent fetches for one consumer never claim the same seq (asserted under `-race` with
      64 concurrent fetchers).
- [ ] `consumer info` reports `pending`, `inflight`, `ready_now`, `in_backoff`, `backlog`
      (+ `backlog_exact`), `oldest_pending_age_ms`, `cursor_seq`, `generation` and `blocked_by`,
      and the values match a full-table recomputation; all inspection paths use the `ro` pool and a
      full store dump is byte-identical before and after an arbitrary read workload.
- [ ] `ordered: true` and `max_rate` are rejected with `unsupported` naming #38/#39.
- [ ] `C1`–`C6` are registered in `internal/verify`, run in #8's `messq verify`, report zero
      violations across this issue's suite, and each reports its seeded violation when one is
      deliberately introduced.
- [ ] SEMANTICS.md is amended in the same PR with: I5 as an admission bound plus the shrink clause,
      the burned-attempt crash window, and forward-only config semantics.
- [ ] Coverage floors from #2 still pass (`internal/queue` ≥ 90 %, `internal/store` ≥ 85 %).

  event row and its `detail` in the same transaction as the change.

- Read-path side-effect freedom: `go-cmp` diff of a full dump of every table before/after a

- Named properties: (a) no message matching a consumer's filter at admission time is ever skipped
  — for any interleaving of publish/fetch/flow-control-block, every matching seq below the cursor
