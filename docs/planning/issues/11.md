## Context

After #9 and #10 a delivery can be claimed, acked, naked, termed and extended. There is exactly one
transition in PLAN.md §5.1 with **no actor**: **T8 — the sweeper**. Until this issue lands, a worker
that fetches a message and then dies takes that message with it. The row sits `INFLIGHT` with a
`visible_at` in the past forever, `max_deliver` is a number nobody enforces, the backoff array is
config that nothing reads, and the pending set only ever grows. This issue is what makes
`ack_wait` mean something.

It is also the smallest issue in M3 by line count and the one with the widest blast radius, because
it is the component that converts *absence of an ack* into a durable decision. Three PLAN.md
decisions are realised here:

- **§3.2 goroutine census — one sweeper, 250 ms, work submitted as commands through the writer.**
  Not a goroutine per message, not a goroutine per consumer, not a timer per lease. The sweeper
  never opens a transaction of its own; it builds a `Cmd` and hands it to #6's writer, so the
  single-writer invariant and the group commit are untouched.
- **§2 / D5 — one indexed `UPDATE` in a 250 ms tick, not per-message timers.** plan-06 proposed a
  timing wheel; PLAN.md rejected it as premature at our throughput. The whole scheduler is an
  indexed column plus a ticker. The cost of that choice is 250 ms of timeout granularity, which is
  documented, measured and irrelevant to any real `ack_wait` budget.
- **§2 / D6 — attempts increment at claim.** The sweeper therefore **never touches `attempts`**. A
  timeout on attempt *n* releases the row still at *n*; the *next claim* makes it *n+1*. That single
  rule is why `max_deliver = 5` means exactly five handler invocations and why a poison message
  dead-letters after exactly five, whether it failed by nak, by timeout, or by five successive
  broker crashes.

Governing material, section by section:

- **§5.1 T8** (timeout → READY at `now + backoff[attempts-1] ± 20 %`), **T5** (timeout at
  `attempts >= max_deliver` → DEAD), and the **Backoff** paragraph (last value repeats, ±20 % jitter
  always applied and not configurable off).
- **§5.2 — I4** (`attempts <= max_deliver` for every non-terminal row; delivery stops at the bound,
  across restarts) is *enforced* here for the first time: #10 covered the nak arm, this issue covers
  the arm that fires when nobody is talking to us. **I9** ("every duplicate has a named cause") gets
  its third and most common cause. **I11** (no unbounded collection) constrains every batch below.
- **§9.2 / §9.3 — `msg.timeout` is a WARN, never-sampleable event.** It is the single most
  diagnostic line messq emits: it is the one that says *your handler is slower than your `ack_wait`*.
- **§9.4 — `messq_timeouts_total`, `messq_redelivered_total{cause}`, `messq_dead_total`.**
- **§12 — idle daemon < 0.5 % of one core**, and **§11 — `testing/synctest`, no `time.Sleep`**. A
  ticker waking four times a second must cost nothing when idle (§3), and a 10-minute backoff chain
  has to test in microseconds or it will not be tested at all.

What this unlocks: **#12** (the dead path finally has its dominant trigger — `max_deliver`
exhaustion by timeout is how the overwhelming majority of real DLQ entries are created), **#13** (the
`advance_time` action in the rapid suite is a call into this issue's `Sweep`; without it the model
can never exercise expiry), **#19** (its golden `publish → timeout → nak → ack` scenario needs a real
`msg.timeout` row, which is why #19 lists this issue as a blocker), **#14** (the `Waker` interface is
declared here and implemented there), **#37** (delayed delivery is "a READY row with a future
`visible_at`" — it needs no new machinery precisely because this issue exists), and the M3 exit
criterion itself: *a poison message lands in the DLQ after exactly `max_deliver` attempts*.

## Scope

**In scope**

- `internal/queue/sweep.go` — the **pure** decision function `DecideSweep`: `(row, consumer policy,
  now, jitter) → (redeliver at T | dead | skip)`. No I/O, no `time.Now`, no map iteration.
- `internal/store/sweep.go` — three writer commands: `SweepCmd` (expiry), `RetireCmd` (READY rows
  stranded above a lowered `max_deliver`), and the shared row-loading/decision-application code.
- **The sweeper goroutine** (`internal/store/sweeper.go` or `internal/api`, see §3): the ticker on
  #3's `Clock` seam, the three passes, burst catch-up, coalescing, backpressure handling, and clean
  shutdown.
- **Migration `000N_deliveries_expiry.sql`**: a partial index over in-flight rows that turns "what
  expires next, globally" from a table scan into an O(log n) lookup, and gives the expiry scan a
  total order for free (an amendment #13 explicitly requires).
- **The timeout arm of the backoff schedule**, reusing `queue.BackoffFor` and the `Jitter` seam from
  #10; the last-entry-repeats rule; explicit `TimeToDead` / `RetryHorizon` arithmetic.
- **`max_deliver` routing to the dead path** through the `OnDead` seam (`DeadDelivery{Trigger:
  "ack_wait"}` / `"policy_lowered"`), against #10's provisional drop-only implementation until #12
  replaces it with the canonical `DeadLetterer`.
- **The `Waker` interface declaration** (`Waiting() []queue.ConsumerKey`, `Wake(queue.ConsumerKey)`)
  plus a `NopWaker`, and the post-commit wake calls — the fast path #14 and #12 both build on.
- **Events**: `msg.timeout` (WARN, never sampleable, with `held_ms`, `lateness_ms`, `delay_ms`,
  `retry_at`) and `msg.dead` via the dead seam. No new event names.
- **Sweeper self-observability**: `messq_sweep_lateness_seconds`, `messq_sweep_duration_seconds`,
  `messq_sweep_rows`, `messq_sweep_backlog`, `messq_sweep_skipped_total`, plus the clock-step
  detector. A scheduler you cannot see is a scheduler you cannot trust.
- **Invariant checkers `S1`–`S3`** registered into #8's `internal/verify` registry, closing I4's
  timeout arm and making the "no expired in-flight row survives a sweep" property checkable.
- Flags: `--sweep-interval`, `--sweep-batch`, `--sweep-catchup`, `--retire-interval`.
- Reserved fault-point names for #32's kill matrix.

**Out of scope**

## Design proposal

> Everything below is a proposed starting point, not a mandate — concrete enough to argue with.
> Four items are marked **decision** because #12, #13, #14 and #37 build on them and they are
> expensive to reverse. Two items are spec refinements that need a matching edit to
> `docs/SEMANTICS.md` (#4) in the same PR; both are called out.

### 1. Where the code lives

```
internal/queue/sweep.go              SweepRow, SweepPolicy, SweepDecision, DecideSweep — pure
internal/queue/backoff.go            BackoffFor, TimeToDead, RetryHorizon (extends #10's file)
internal/store/migrations/000N_deliveries_expiry.sql
internal/store/sweep.go              SweepCmd, RetireCmd, row loading, decision application
internal/store/sweeper.go            the goroutine: ticker, three passes, catch-up, shutdown
internal/store/waker.go              Waker, NopWaker
internal/verify/sweep.go             checkers S1–S3
```

`internal/queue` still knows nothing about `database/sql`; `internal/store` loads a bounded working
set, calls the pure planner, applies what comes back. Same split as #9 and #10, same payoff: #13
drives the planner directly and every timing test runs in `synctest`.

### 2. The index that makes this cheap (**decision**)

The existing `deliveries_ready(stream, consumer, state, visible_at, seq)` is keyed on `stream`
first, so *"which lease expires next, anywhere"* — the question the sweeper asks four times a second
— cannot use it. One partial index fixes that:

```sql
-- 000N_deliveries_expiry.sql
CREATE INDEX deliveries_expiry
    ON deliveries(visible_at, stream, consumer, seq)
 WHERE state = 1;
```

Three properties, all load-bearing:

1. **It is tiny.** It indexes only `INFLIGHT` rows, whose count is bounded by
   `Σ max_ack_pending` across consumers (I5, #9). A million-message stream with 20 workers has a few
   thousand entries here.
2. **The expiry scan is an ordered range scan with no temp sort.** `WHERE state = 1 AND visible_at
   <= :now ORDER BY visible_at, stream, consumer, seq LIMIT :n` is exactly index order. That is also
   the **total order #13's amendment requires** (a `LIMIT` over a partial order is a coin flip at
   ties), and it comes for free rather than as a sort.
3. **The idle probe is O(log n).** `SELECT visible_at FROM deliveries WHERE state = 1 ORDER BY
   visible_at LIMIT 1` is one descent of the b-tree.

Cost: one extra b-tree insert per claim and one delete per settle. Both are already inside a
transaction that is doing more work than that. `BenchmarkClaim` and `BenchmarkSettle` from #9/#10 are
re-run in this PR and the delta is recorded; if it is not in the noise, say so in the PR rather than
hiding it.

An `EXPLAIN QUERY PLAN` golden test pins `USING INDEX deliveries_expiry` and the **absence** of
`USE TEMP B-TREE FOR ORDER BY`. Query plans regress silently; this one is worth a golden.

### 3. The goroutine: three passes, one ticker

```go
type Sweeper struct {
    w     *Writer          // #6
    ro    *sql.DB          // #5's read pool
    clock clock.Clock      // #3 seam
    waker Waker            // NopWaker until #14
    cfg   SweepConfig
}

type SweepConfig struct {
    Interval       time.Duration // --sweep-interval, 250ms
    Batch          int           // --sweep-batch, 1024
    Catchup        int           // --sweep-catchup, 8
    RetireInterval time.Duration // --retire-interval, 60s
}

func (s *Sweeper) Run(ctx context.Context) error   // returns on ctx.Done or a fatal latch
```

Every tick, in order:

| Pass | Reads | Writes | Purpose |
|---|---|---|---|
| **A. Expiry** | `ro` probe, then the scan inside the writer tx | yes (`SweepCmd`) | `INFLIGHT ∧ visible_at <= now` → redeliver or dead (T8/T5) |
| **B. Wake** | `ro` only | never | `READY ∧ visible_at <= now` for **parked** consumers → `Wake` |
| **C. Report** | `ro` only | never | refresh `messq_sweep_backlog`, `next_due`, clock-step detection |

**The idle path costs one index lookup per tick (decision).** Pass A begins with a probe on the
**read pool** — WAL readers never block the writer — and only submits a `SweepCmd` if the probe
finds an expired row:

```sql
SELECT visible_at FROM deliveries WHERE state = 1 ORDER BY visible_at LIMIT 1;
```

`NULL` or a value `> now` means nothing to do: no command, no transaction, no fsync, no writer wake.
An idle daemon therefore does four b-tree descents per second on an idle connection, which is what
PLAN §12's `< 0.5 %` budget requires. The probe reads a snapshot that may be microseconds stale — a
lease that expired between the probe and the tick is caught on the next tick, ≤ 250 ms later, which
is within the granularity we already document.

> Considered and deferred: sleeping until `next_due` instead of ticking at a fixed interval. It
> removes the last four wakeups per second, but it needs cache invalidation from every claim (a
> `Fetch` with a short `ack_wait` can create a deadline earlier than the cached one), which couples
> the sweeper to the writer's hot path for no measurable gain. Revisit if `messq bench --idle` (#31)
> shows the ticker at all.

**One sweep in flight at a time.** Ticks are coalesced, never queued: if a sweep is still running
when the ticker fires, that tick is dropped and `messq_sweep_skipped_total` increments. A queue of
sweeps behind a slow disk is a way to turn one problem into two.

**Burst catch-up.** `SweepResult.More` is true when the scan hit `--sweep-batch`. The sweeper then
re-submits immediately, up to `--sweep-catchup` (8) times per tick, before yielding to the ticker so
that publishes and fetches are not starved by a redelivery storm. Drain rate is therefore
`batch × catchup / interval` = **32 768 rows/s** at the defaults — a 100 000-lease fleet death
drains in about 3 s. Both numbers go in `docs/OPERATIONS.md`.

**Backpressure.** `Writer.Do` blocks when `cmdCh` is full (#6). The sweeper submits with a context
whose deadline is `2 × Interval`; on expiry it abandons the tick, counts
`messq_sweep_skipped_total{reason="writer_busy"}`, and logs at WARN once per
`--event-repeat-interval`. The sweeper must yield to real work; a redelivery that is 500 ms late is
a non-event, and a sweeper that deadlocks the writer is an outage.

**Shutdown and fatal.** `ctx.Done()` (from #17's drain) returns immediately — an in-flight `SweepCmd`
either commits with the drain's final batch or is rolled back, and both are safe. A `*FatalError`
from `Do` (storage latched read-only, #6) stops the loop permanently after one ERROR line; it must
never spin against a latched store.

### 4. The pure decision

```go
package queue

type SweepRow struct {
    Key         ConsumerKey // {Stream, Consumer}
    Seq         int64
    Subject     string
    Attempts    int32
    Generation  int32
    VisibleAt   int64  // unix ms — the expired deadline
    DeliveredAt int64  // unix ms — when this attempt was claimed
    LastReason  string
    MsgID       string // "" when the origin message is gone (see §11)
    TraceID     string
}

type SweepPolicy struct { // loaded once per (stream, consumer) per command
    AckWait    time.Duration
    MaxDeliver int32           // 0 = unlimited
    Backoff    []time.Duration // 1..16 entries; last repeats
    DeadPolicy DeadPolicy
    Generation int32           // the consumer's live generation — the fence
}

type SweepAction uint8 // SweepRedeliver | SweepDead | SweepSkip   (exhaustive-linted)

type SweepDecision struct {
    Action     SweepAction
    VisibleAt  int64     // ms, when Action == SweepRedeliver
    DelayMS    int64     // the jittered delay actually applied (event detail)
    ScheduleMS int64     // the pre-jitter schedule entry (event detail; explains DelayMS)
    Cause      DeadCause // DeadMaxDeliver, when Action == SweepDead
    Trigger    string    // "ack_wait" | "policy_lowered"
    HeldMS     int64     // now - DeliveredAt — how long the worker held the lease
    LatenessMS int64     // now - VisibleAt — how late the sweeper was
    Skip       string    // why, when Action == SweepSkip ("not_expired" | "generation")
}

// DecideSweep is total: every input produces exactly one decision, and it never panics.
// j is the keyed jitter seam (#13's N1 amendment) so the model and the broker agree exactly.
func DecideSweep(r SweepRow, p SweepPolicy, nowMS int64, j Jitter) SweepDecision
```

The rules, in evaluation order:

| # | Condition | Action |
|---|---|---|
| 1 | `r.VisibleAt > nowMS` | `SweepSkip{"not_expired"}` — defensive; the scan should not have returned it |
| 2 | `r.Generation != p.Generation` | `SweepSkip{"generation"}` + a `verify` S3 violation. Cannot happen (#28 drops rows when it bumps); never mutate on a fence mismatch |
| 3 | `p.MaxDeliver > 0 ∧ r.Attempts >= p.MaxDeliver` | `SweepDead{Cause: DeadMaxDeliver, Trigger: r.Attempts > p.MaxDeliver ? "policy_lowered" : "ack_wait"}` |
| 4 | otherwise | `SweepRedeliver{VisibleAt: nowMS + jitter(BackoffFor(r.Attempts))}` |

Rule 3 is the whole `max_deliver` contract. Because `attempts` was incremented at claim (D6), a row
in flight on attempt 5 of a `max_deliver = 5` consumer has already had **five** handler invocations;
letting its lease expire is the fifth failure, and it dies. `attempts` is **never modified by the
sweeper** — not on redelivery, not on death. That is what makes I4 hold across crashes: a broker that
dies mid-sweep loses nothing and burns nothing.

### 5. Backoff arithmetic, stated once and for all

```go
// BackoffFor is 1-based on attempts and repeats the last entry. Defined in #10, reused verbatim.
//   attempt 1 failed -> wait Backoff[0]   before attempt 2
//   attempt n failed -> wait Backoff[min(n, len)-1]
func (c ConsumerConfig) BackoffFor(attempt int32) time.Duration

// RetryHorizon is the total time spent *waiting between* attempts.
//   Σ BackoffFor(i) for i in 1..MaxDeliver-1 ; +Inf when MaxDeliver == 0
func RetryHorizon(c ConsumerConfig) time.Duration

// TimeToDead is the wall-clock worst case from first delivery to DEAD for a consumer whose
// worker never responds at all: every attempt burns a full ack_wait, plus every backoff.
//   MaxDeliver*AckWait + RetryHorizon ; +Inf when MaxDeliver == 0
func TimeToDead(c ConsumerConfig) time.Duration
```

Worked out for the §4.2 defaults (`ack_wait = 30s`, `max_deliver = 5`,
`backoff = [1s, 5s, 30s, 2m, 10m]`), with a worker that fetches and then dies:

| t | Event | Attempt | Next |
|---|---|---|---|
| 0.0 s | `msg.deliver` | 1/5 | deadline 30 s |
| 30.0 s | `msg.timeout` | 1/5 | READY at +1 s ± 20 % |
| 31.0 s | `msg.deliver` | 2/5 | deadline 61 s |
| 61.0 s | `msg.timeout` | 2/5 | READY at +5 s ± 20 % |
| 66.0 s | `msg.deliver` | 3/5 | deadline 96 s |
| 96.0 s | `msg.timeout` | 3/5 | READY at +30 s ± 20 % |
| 126.0 s | `msg.deliver` | 4/5 | deadline 156 s |
| 156.0 s | `msg.timeout` | 4/5 | READY at +2 m ± 20 % |
| 276.0 s | `msg.deliver` | 5/5 | deadline 306 s |
| **306.0 s** | `msg.timeout` → **`msg.dead`** | 5/5 | `cause=max_deliver`, `trigger=ack_wait` |

`RetryHorizon = 1 + 5 + 30 + 120 = 156 s`. `TimeToDead = 5 × 30 + 156 = 306 s ≈ 5 min 6 s`. The
fifth backoff entry (`10m`) is **never used** at `max_deliver = 5` — worth saying out loud, because
"why doesn't my 10-minute backoff ever happen" is otherwise a support ticket. `messq consumer info`
(#24) and `doctor` (#30) print both numbers; the DLQ alert threshold in `contrib/prometheus/alerts.yml`
(#21) is derived from `TimeToDead`.

> **Spec refinement (`SEMANTICS.md` §S13, plus #9's example payload).** #9's `consumer info` example
> reports `retry_horizon_ms: 756000`, which is the sum of *all five* backoff entries. With
> `max_deliver = 5` there are only **four** waits, so the correct value is `156000`. Fix the example
> and the formula together, and add `time_to_dead_ms` beside it — the horizon alone answers the
> wrong question.

**Jitter.** `±20 %`, always, not configurable off (§5.1). Applied through #10's `Jitter` seam,
widened per #13's N1 amendment to be keyed on row identity so the reference model and the broker
produce byte-identical schedules:

```go
type Kind uint8 // KindNak | KindTimeout | KindReclaim
type Jitter interface {
    Frac(k ConsumerKey, seq int64, attempt int32, kind Kind) float64 // in [-0.20, +0.20]
}
```

The sweeper always passes `KindTimeout`. `NoJitter` (always `0`) exists for tests and **is never
wired to a flag** — same rule #13 applies to `KeyedJitter`. Production uses a PCG source from
`math/rand/v2`, one per writer goroutine, never `crypto/rand` (this is not a security decision and
the writer must not block on entropy).

### 6. `SweepCmd`

```go
type SweepCmd struct {
    Limit int // --sweep-batch
    dead  DeadLetterer // #10's seam; #12 replaces the implementation
    jit   queue.Jitter
}

func (c *SweepCmd) Kind() CmdKind { return CmdSweep }
func (c *SweepCmd) Bytes() int    { return 0 } // metadata only until #12's copy lands

type SweepResult struct {
    Expired      int
    Redelivered  int
    Dead         int
    Skipped      int
    Woke         []queue.ConsumerKey // distinct; wake AFTER the commit
    More         bool                // hit Limit — re-submit immediately
    NextDueMS    int64               // MIN(visible_at) over remaining INFLIGHT rows; 0 = none
    MaxLatenessMS int64              // worst (now - visible_at) in this batch
}
```

`Apply`, inside #6's batch transaction, on the writer goroutine, with `now` = the **batch
timestamp** (never `time.Now`, never the sweeper's own clock read — one timestamp per batch is what
makes the events, the deadlines and the model agree):

```sql
-- 1. the expired set, in total order, bounded
SELECT d.stream, d.consumer, d.seq, d.subject, d.attempts, d.generation,
       d.visible_at, d.delivered_at, d.last_reason,
       m.id AS msg_id, m.trace_id
  FROM deliveries d
  LEFT JOIN messages m ON m.stream = d.stream AND m.seq = d.seq
 WHERE d.state = 1 AND d.visible_at <= :now
 ORDER BY d.visible_at, d.stream, d.consumer, d.seq
 LIMIT :limit;
```

```sql
-- 2. consumer policies, one row per distinct (stream, consumer) in the batch
SELECT stream, name, ack_wait_ms, max_deliver, backoff_ms, dead_policy, generation
  FROM consumers WHERE (stream, name) IN (…);
```

```sql
-- 3a. redeliver (T8) — one prepared statement, executed per decided row.
--     The fence is repeated in the WHERE so a sibling command in the same batch
--     that already released or resolved this row cannot be written over.
UPDATE deliveries
   SET state = 0, visible_at = :vis, last_reason = 'ack_wait'
 WHERE stream = :s AND consumer = :c AND seq = :q
   AND state = 1 AND attempts = :att AND generation = :gen;
```

```sql
-- 3b. dead (T5) — DeadLetterer runs inside this transaction, then the row goes.
--     #12 substitutes the DLQ copy for #10's drop-only implementation.
```

Notes on the shape:

- **Per-row `UPDATE`, not one set-based statement.** Every row gets its own jittered `visible_at`,
  so a `CASE`-built single statement would be a 1024-branch expression; a prepared statement executed
  1024 times inside one transaction is a few hundred microseconds in SQLite and is readable. Measured
  in `BenchmarkSweep`; revisit only if it shows up.
- **The `LEFT JOIN` is deliberate.** An orphaned delivery row (message purged under it) must still be
  retirable — a row that cannot be swept is a permanently stuck consumer. `msg_id`/`trace_id` come
  back `NULL`, the event is flagged, and the dead path handles `origin_missing` (#12).
- **`last_reason = 'ack_wait'`** so `messq pending` (#24) and the DLQ header `Messq-Last-Reason`
  (#12) say *why* rather than showing an empty column. A previous nak reason is deliberately
  overwritten: the most recent cause is the useful one, and the full history is in `trace`.
- **No `changes()` assertion on 3a.** Unlike #10's settle statements, a `changes() == 0` here is a
  legal outcome: a sibling `SettleCmd` in the same batch may have acked the row after the scan ran.
  It is counted into `SweepResult.Skipped` and *not* treated as a bug. This is the one place the
  #10 pattern is deliberately not copied, and it needs the comment saying so.
- **`Bytes()` returns 0 today and must return the payload estimate once #12 copies bodies into the
  DLQ** — otherwise a sweep that dead-letters 1024 × 1 MiB messages bursts the WAL past
  `--commit-max-bytes`. Flagged in #12's scope as a one-line follow-up; a `TODO(#12)` and a test that
  fails if `Bytes()` is still 0 after `DeadLetterer` gains a copying implementation.

### 7. `RetireCmd` — the stranded-row pass

Lowering `max_deliver` from 5 to 2 can strand `READY` rows at `attempts >= max_deliver`. Nothing else
would ever retire them: the expiry pass only scans `INFLIGHT`, and #9's claim has no `max_deliver`
guard — if such a row were claimed it would reach `attempts = max_deliver + 1` and violate I4.

```sql
-- once per --retire-interval, per consumer with max_deliver > 0; bounded by pending(c)
SELECT d.seq, d.subject, d.attempts, d.generation, d.delivered_at, d.last_reason,
       m.id, m.trace_id
  FROM deliveries d
  LEFT JOIN messages m ON m.stream = d.stream AND m.seq = d.seq
 WHERE d.stream = :s AND d.consumer = :c AND d.state = 0 AND d.attempts >= :max_deliver
 ORDER BY d.seq
 LIMIT :limit;
```

Each hit goes to the dead path with `Trigger: "policy_lowered"`, `Cause: DeadMaxDeliver` — exactly
the trigger value #12's edge-case table already expects.

**Only `READY` rows (decision).** An `INFLIGHT` row above the new cap is left alone: a worker is
holding it right now and may well ack it. It retires through the ordinary expiry pass at its next
deadline, where rule 3 sends it to DEAD. Killing in-progress work the instant an operator edits a
config would be a nasty surprise; delaying it by at most one `ack_wait` is not.

Cost: one indexed query per consumer per minute (`deliveries_ready` covers the
`(stream, consumer, state)` prefix), bounded above by `--max-consumers` = 1024 → ~17 queries/s on
the read pool in the worst configured case, and the scan is skipped entirely for consumers with
`max_deliver = 0`. Run once at startup too — a restored backup or a hand-edited database is exactly
when a stranded row appears.

### 8. The `Waker` seam

```go
// Waker is implemented by #14's waiter registry. NopWaker until then.
// Both methods are non-blocking and safe to call from the sweeper goroutine.
type Waker interface {
    Waiting() []queue.ConsumerKey // nil when nobody is parked — the fast path
    Wake(k queue.ConsumerKey)
}

type NopWaker struct{}
func (NopWaker) Waiting() []queue.ConsumerKey { return nil }
func (NopWaker) Wake(queue.ConsumerKey)       {}
```

**Wakes happen after the commit returns, never inside `Apply`.** Two reasons, both hard: `Apply` must
not block (#6's contract), and waking before commit would let a fetch claim a row that then rolls
back — a message delivered from a transaction that never happened.

Two wake sources live here:

1. **Immediate redelivery.** When a decision's `VisibleAt <= now` (possible when `backoff[0] = 0`),
   the consumer key goes into `SweepResult.Woke`. After `Do` returns, the sweeper calls `Wake` for
   each distinct key.
2. **A backoff came due** — pass B. A row released at `now + 30s` is `READY` but invisible; 30 s
   later nothing changes state, so nothing would wake a parked fetch. Pass B closes that:

```sql
-- for each parked key from Waker.Waiting(), bounded to 256 keys per tick (round-robin beyond)
SELECT 1 FROM deliveries
 WHERE stream = :s AND consumer = :c AND state = 0 AND visible_at <= :now
 LIMIT 1;
```

on the **read pool**, one index lookup on `deliveries_ready`, and `Wake(key)` on a hit. `Waiting()`
returning `nil` — the overwhelmingly common case — skips the pass entirely.

This is the **fast path only**. #14's fetch handler already parks until `min(deadline,
NextVisibleAt)`, so a sweeper that is late, busy or absent costs latency, never correctness. Saying
that plainly in both issues is what keeps the two designs from each assuming the other is the
guarantee.

#12 also marks the origin consumer on this seam when a dead-letter frees a `max_ack_pending` slot;
that call site is theirs, the interface is this one.

### 9. Events and metrics

Two events, no new names (D11, closed vocabulary):

| Event | Level | Sampleable | `detail` |
|---|---|---|---|
| `msg.timeout` | **WARN** | **never** (allow-list) | `held_ms`, `lateness_ms`, `ack_wait_ms`, `schedule_ms`, `delay_ms`, `retry_at`, `attempt`, `max_deliver`, `cause:"ack_wait"` |
| `msg.dead` | **WARN** | **never** | owned by #12; this issue supplies `trigger: "ack_wait"｜"policy_lowered"`, `cause: "max_deliver"`, `attempts`, `last_reason`, `held_ms` |

Coordinates on every row: `stream`, `consumer`, `subject`, `seq`, `msg_id`, `attempt`, `trace_id`.

`msg.timeout` rows are **never rate-limited**: a timeout is real work being redone, and D11's
repeat-limiter applies to *rejections* (#10 §8), not to state changes. A fleet dying and producing
100 000 `msg.timeout` rows is a correct audit trail of 100 000 redeliveries, and the operator wants
every one of them in `trace`. The corresponding 100 000 WARN log lines are the honest cost of the
never-sampleable rule; the aggregate view is the metric, and `--log-level error` is the escape hatch
during a known incident. This is stated in `docs/log-schema.md` (#19) rather than quietly softened.

Metrics — names, labels and units specified here, registered by #21:

| Metric | Type | Labels | Meaning |
|---|---|---|---|
| `messq_timeouts_total` | counter | `stream`, `consumer` | leases expired (§9.4) |
| `messq_redelivered_total` | counter | `stream`, `consumer`, `cause="timeout"` | shares the counter with #10's `cause="nak"` and #5's `cause="broker_restart"` |
| `messq_dead_total` | counter | `stream`, `consumer` | incremented by this path with `cause=max_deliver` |
| `messq_sweep_lateness_seconds` | histogram | — | `now - visible_at` per swept row. **The sweeper's own SLI.** p99 should sit under one interval; above `2 × --sweep-interval` means the writer is saturated or the disk is slow |
| `messq_sweep_duration_seconds` | histogram | — | wall time of one `SweepCmd`, including its share of the group commit |
| `messq_sweep_rows` | histogram | — | rows per sweep; pinned at `--sweep-batch` means a sustained burst |
| `messq_sweep_backlog` | gauge | — | expired-but-unswept rows at scrape time, from pass C |
| `messq_sweep_skipped_total` | counter | `reason` | `writer_busy` ｜ `overlap` |

Alert lines handed to #21: *sustained `messq_sweep_backlog > 0`* (the sweeper is not keeping up) and
*`messq_timeouts_total` rate rising with a flat `messq_acked_total`* (workers are dying rather than
failing, which looks nothing like a nak storm).

### 10. Flags (D8: flags + `MESSQ_*` env, no config file)

| Flag | Env | Default | Meaning |
|---|---|---|---|
| `--sweep-interval` | `MESSQ_SWEEP_INTERVAL` | `250ms` | Ack-timeout resolution; the maximum lateness of a redelivery. Bounds: `[10ms, 10s]` |
| `--sweep-batch` | `MESSQ_SWEEP_BATCH` | `1024` | Rows expired per sweep command (I11) |
| `--sweep-catchup` | `MESSQ_SWEEP_CATCHUP` | `8` | Back-to-back sweep commands per tick during a burst |
| `--retire-interval` | `MESSQ_RETIRE_INTERVAL` | `60s` | How often stranded `READY` rows above a lowered `max_deliver` are retired; `0` = startup only |

### 11. Edge cases, decided

| Case | Handling |
|---|---|
| **Worker fetches and dies** | The canonical path. Lease expires, `msg.timeout`, redeliver at `backoff[attempts-1] ± 20 %`, dead after exactly `max_deliver` deliveries. This is the M3 exit criterion test. |
| **Sweep releases a row, an ack for that attempt arrives afterwards** | Accepted by #10 with `late = true` (the token still names the current attempt — the sweeper did not touch `attempts`). A duplicate was *avoided*, and `messq_late_acks_total` says so. |
| **A `SettleCmd` in the same batch acks a row the sweep already released** | Legal and expected; the fence in 3a means order does not matter. If the settle ran first, the scan (inside the same tx) never sees the row. |
| **`extend` arrives between expiry and the sweep tick** | #10 accepts it while the row is still `INFLIGHT`, pushing `visible_at` forward; the sweep, running later inside its own transaction, no longer sees it expired. If the sweep wins the race, the extend hits a `READY` row and is rejected `stale_ack / not_inflight` — but the ack that follows is still accepted `late`. Documented as a ≤ 250 ms window; #22's `Worker` heartbeats at `ack_wait/2` and never enters it. |
| **`max_deliver = 0` (unlimited)** | Never dies by count. The backoff index saturates at the last entry, so the steady state is one redelivery per `ack_wait + backoff[last]`. Warned at consumer creation (#9); `TimeToDead` reports `+Inf`; `doctor` (#30) flags it. |
| **`max_deliver` lowered below current `attempts`** | `READY` rows retire on the next `--retire-interval` pass with `trigger="policy_lowered"`; `INFLIGHT` rows retire at their next expiry. Never mid-flight. |
| **`max_deliver` raised** | Nothing to do — rows below the new bound simply keep retrying. |
| **`ack_wait` changed while rows are in flight** | Forward-only (#9). The sweep uses the row's stored `visible_at`; existing deadlines never move. The new value applies at the next claim. |
| **Consumer paused with in-flight rows** | Leases still expire, rows still go `READY`, exhausted rows still dead-letter — #15's documented decision, and this issue is the code that makes it true. The redelivered rows simply are not claimed until resume. `POST …/pause` reports the count and earliest deadline so #24 can warn. |
| **Wall clock jumps forward by an hour** | Every lease is instantly "expired". `#6`'s `batchNow()` is monotone within a process, so the jump cannot be undone, and a stored absolute deadline that has passed *is* passed. Damage is bounded three ways: `--sweep-batch × --sweep-catchup` per tick caps the rate, `attempts` is untouched so nothing dies early, and I4 still holds. The sweeper detects a tick-to-tick gap > 5 s, logs one WARN naming the observed step, and stamps `detail.clock_step_ms` on the affected `msg.timeout` rows so `trace` explains the burst. #32 owns the injection test. |
| **Wall clock jumps backwards** | `batchNow()` clamps to `max(clock.Now(), lastNow)`, so deadlines never move back and nothing expires late. |
| **Grace period after a long process pause** | Considered (defer expiry by the observed tick gap, the JVM-GC-pause trick) and **deferred**: it adds a knob and a subtle behaviour, and D6 already makes an early redelivery harmless rather than corrupting. Revisit if the soak (#33) shows redelivery storms after suspend/resume. |
| **100 000 leases expire in one tick** | Drains at 32 768 rows/s (§3); `messq_sweep_backlog` shows the queue draining. Publishes and fetches keep flowing because the sweeper yields after `--sweep-catchup`. |
| **Redelivery stampede after a fleet death** | All rows expire in the same tick and are rescheduled at `backoff[0] ± 20 %` — with a 1 s first entry that is a 400 ms-wide window. The real throttle is `max_ack_pending`: only that many rows can be in flight per consumer regardless. Documented as a characteristic, not hidden; the fix if it ever bites is a wider first backoff entry, which is already configurable. |
| **The message was purged under the delivery row** | `LEFT JOIN` yields a `NULL` id. Redeliver normally (the claim will drop it, #9 §6) or dead-letter with `degraded="origin_missing"` (#12). The row is always retired; a row that cannot be swept is a stuck consumer. A `verify` C2 violation names the purge that forgot to drop its delivery rows. |
| **Row's `generation` ≠ consumer's** | `SweepSkip{"generation"}`, no mutation, `verify` S3 violation, WARN. #28's seek must drop delivery rows in the same transaction as the bump; this is the belt. |
| **SIGKILL mid-sweep** | The transaction rolls back. Rows stay `INFLIGHT` with a past deadline; #5's recovery reclaims them to `READY` with `attempts` untouched and `reason=broker_restart`. No attempt is burned by the sweeper, ever. The #8 ledger is unaffected — a sweep resolves nothing a client is waiting on. |
| **Writer queue saturated for many ticks** | Ticks are skipped and counted; redeliveries are late, not lost. Lateness is visible in `messq_sweep_lateness_seconds` and `messq_sweep_backlog`, which is exactly the signal an operator needs to know the broker is overloaded rather than broken. |
| **Store latched read-only (fsyncgate, #6)** | The sweeper stops after one ERROR line and does not retry. The process is exiting; recovery on restart reclaims everything. |
| **Disk below `--min-free-bytes`** | Sweeping continues. §4.5: publishes are rejected, but the paths that *retire* work must never be blocked — a wedged sweeper turns a full disk into unbounded redelivery. |
| **Two sweeps at once** | Impossible: one goroutine, one in-flight command, ticks coalesced. |
| **`backoff = [0]`** | Immediate redelivery: `visible_at = now`, the key lands in `Woke`, a parked fetch is woken. Legal and useful for a "retry now, cap at max_deliver" consumer; a `RetryHorizon` of 0 is warned at creation (#9). |
| **`--sweep-interval` larger than `ack_wait`** | Accepted with a startup WARN naming both values: the effective redelivery latency is the interval. `doctor` (#30) flags it. Refusing would break the legitimate `ack_wait = 100ms` test configuration. |
| **Hook for #37** | Delayed delivery is a `READY` row with a future `visible_at`. Pass B already wakes on it, and the retire/expiry passes ignore it. The only change #37 needs here is counting scheduled rows separately in pass C's gauge. Noted, not built. |

### 13. Invariant checkers (`S1`–`S3`, registered into #8's `verify` registry)

| ID | Statement | Sharpens |
|---|---|---|
| S1 | No `INFLIGHT` row has `visible_at <= now - (sweep_interval + grace)`. **Advisory**, not a violation, while `messq_sweep_backlog > 0` — it is a liveness property, and a saturated writer is late, not wrong | I4 liveness |
| S2 | No row exists with `attempts > max_deliver` where `max_deliver > 0` and `state = 0` **and** the last `--retire-interval` has elapsed since startup | I4 |
| S3 | Every delivery row's `generation` equals its consumer's (restating #9's C3, checked again after every sweep because this is the code that would violate it) | I7 |

```sql
-- S2  a stranded row the retire pass has not collected
SELECT d.stream, d.consumer, d.seq, d.attempts, c.max_deliver
  FROM deliveries d JOIN consumers c ON c.stream = d.stream AND c.name = d.consumer
 WHERE c.max_deliver > 0 AND d.attempts > c.max_deliver AND d.state = 0
 LIMIT 100;
```

## Acceptance criteria

- [ ] Migration `000N` creates `deliveries_expiry` as a partial index over `state = 1`; an
      `EXPLAIN QUERY PLAN` golden asserts the expiry scan uses it and contains no
      `USE TEMP B-TREE FOR ORDER BY`.
- [ ] `DecideSweep` is **total**: a generated cross-product over
      `{not expired, expired} × attempts{<, =, >} max_deliver × max_deliver{0, 1, 5} ×
      generation{matching, stale} × backoff{empty-guarded, 1 entry, 5 entries}` produces a decision
      for every combination, and the test fails on any unclassified input.
- [ ] The sweeper **never modifies `attempts`** — asserted by a before/after column diff over every
      test in this issue's suite (D6, I4).
- [ ] A never-acked message is redelivered on the exact schedule
      `now + BackoffFor(attempts) ± 20 %` and is dead-lettered after **exactly** `max_deliver`
      deliveries — counted as `msg.deliver` events, not as attempts read off a row (the M3 exit
      criterion).
- [ ] `BackoffFor` repeats the last entry; `RetryHorizon` and `TimeToDead` match the §5 table
      (`156 s` / `306 s` for the defaults), and `SEMANTICS.md` plus #9's example payload are
      corrected in the same PR.
- [ ] With `NoJitter`, redelivery times are exact to the millisecond; with the production jitter over
      10 000 draws, every delay lies in `[0.8 d, 1.2 d]` and the distribution is not degenerate.
- [ ] Expiry, redelivery, the `msg.timeout` event row and (where applicable) the dead-letter all
      commit in **one** transaction: a forced commit failure at #6's seam leaves the row `INFLIGHT`
      with its original deadline and no event row.
- [ ] A `SweepCmd` whose scan hits `--sweep-batch` returns `More = true`; the sweeper re-submits up
      to `--sweep-catchup` times per tick and then yields, and a 100 000-row burst drains at the
      documented rate without starving concurrent publishes (asserted on commit-batch composition,
      not on wall clock).
- [ ] Ticks are coalesced: a sweep taking longer than `--sweep-interval` causes skipped ticks
      counted in `messq_sweep_skipped_total{reason="overlap"}`, never a queue of pending sweeps.
- [ ] An idle daemon submits **zero** writer commands from the sweeper: a 60-second synctest idle run
      asserts `messq_commit_batch_size` observes nothing and the probe count equals the tick count.
- [ ] A row released by a sweep can still be acked with its existing token, returns `ok` with
      `late = true`, and is never redelivered afterwards (I3).
- [ ] A `SettleCmd` and a `SweepCmd` touching the same row in one batch converge to the same final
      state in either execution order, and the sweep's zero-`changes()` outcome is counted as
      `Skipped`, not raised as an error.
- [ ] Lowering `max_deliver` below current `attempts` retires stranded `READY` rows within one
      `--retire-interval` with `trigger="policy_lowered"`, and leaves `INFLIGHT` rows alone until
      their next expiry.
- [ ] `max_deliver = 0` never dead-letters by count, saturates the backoff index at the last entry,
      and reports `TimeToDead = +Inf`.
- [ ] A paused consumer's in-flight rows still time out and still dead-letter at the bound.
- [ ] A stale-generation row is skipped with no mutation and reported by `verify` S3.
- [ ] An orphaned delivery row (message purged) is still retired, with the event flagged and the
      transaction succeeding.
- [ ] The `Waker` fast path fires: a redelivery scheduled with zero delay wakes its key immediately
      after commit, and a backoff coming due wakes a parked key within one tick; with `NopWaker`
      everything else behaves identically.
- [ ] `Waiting()` returning `nil` skips pass B entirely (asserted by a counting fake).
- [ ] `msg.timeout` carries `held_ms`, `lateness_ms`, `ack_wait_ms`, `schedule_ms`, `delay_ms`,
      `retry_at`, `attempt`, `max_deliver` and full coordinates; it is on the never-sampleable
      allow-list and is **not** repeat-rate-limited.
- [ ] A writer-queue saturation of `2 × --sweep-interval` abandons the tick with
      `reason="writer_busy"` rather than blocking, and the sweeper recovers on the next tick.
- [ ] A fatal storage latch stops the sweeper permanently after one ERROR line, with no spin
      (asserted on CPU-free progress in synctest, not on a sleep).
- [ ] SIGKILL at each reserved fault point leaves the database `integrity_check`-clean, `verify`-clean
      and every affected row recoverable with `attempts` unchanged.
- [ ] `internal/queue` ≥ 90 % and `internal/store` ≥ 85 % coverage (#2 floors); no `time.Now()`
      outside the `Clock` seam; no `time.Sleep` in tests (lint-enforced).
- [ ] `BenchmarkSweep/{expire,dead}/batch={1,256,1024}` and the re-run
      `BenchmarkClaim`/`BenchmarkSettle` index-cost delta are recorded in the PR with hardware and
      durability mode stated.

## Test plan

Per §11: `-race` everywhere, real SQLite files in `t.TempDir()` (never `:memory:`), no `time.Sleep`,
all timing through the `Clock` seam and `testing/synctest`, every fixed bug landing with a committed
reproduction artifact.

**Unit — pure planner (`internal/queue`, no DB)**

- `TestDecideSweepMatrix` — the generated cross-product from the acceptance criteria, each case
  asserted against an explicit expectation table. The file a reviewer should read first.
- `TestBackoffSchedule` — 1-based indexing, last-entry repeat, single-entry arrays, a `[0]` array,
  `attempts` beyond `len(backoff)`; `RetryHorizon` and `TimeToDead` against a hand-computed table
  including the `max_deliver = 0` and `max_deliver = 1` boundaries.
- `TestJitterBounds` — deterministic `NoJitter` exactness; `KeyedJitter` purity (same key ⇒ same
  answer regardless of call order); production PRNG distribution within `[-0.2, +0.2]`.
- Local property (`rapid`, this issue only): random `(attempts, max_deliver, backoff, now)` inputs —
  a decision is always produced, `attempts` is never in the output mutation set, `SweepRedeliver`
  always yields `VisibleAt >= now`, and `SweepDead` is produced **iff** `max_deliver > 0 ∧ attempts
  >= max_deliver`. Observational equivalence against the reference model is #13's.

**Deterministic timing (`testing/synctest`)** — the centre of gravity of this issue

- `TestFullBackoffChain` — the whole default `[1s, 5s, 30s, 2m, 10m]` schedule with
  `ack_wait = 30s`, `max_deliver = 5`, from publish to `msg.dead`, asserting the exact event
  sequence and the exact timestamps in the §5 table. Runs in microseconds of wall clock.
- `TestSweeperIdleCost` — 60 simulated seconds idle: exactly 240 probes, zero writer commands.
- `TestTickCoalescing` — a sweep artificially longer than the interval produces skipped ticks and no
  backlog of commands.
- `TestBurstDrain` — 100 000 simultaneously expiring rows drain at `batch × catchup / interval` with
  interleaved publishes still committing.
- `TestWriterBusyAbandon` — a saturated `cmdCh` causes an abandoned tick and clean recovery.
- `TestRetireInterval` — `max_deliver` lowered mid-run; stranded rows retire on the next pass and not
  before.
- `TestClockStepDetector` — a 1-hour forward step produces one WARN, `clock_step_ms` on the affected
  events, and no early death (`attempts` untouched).

**Unit — store (`internal/store`, real DB)**

- End-to-end per decision: publish → fetch → advance clock → sweep → assert rows, events, results.
- Transactionality: inject a commit failure mid-sweep (#6 seam) — no row mutated, no event row, no
  metric increment observable after reopen.
- Batch interaction: `SweepCmd` and `SettleCmd` for the same row in one batch, both orderings,
  asserting identical final state and the `Skipped` accounting.
- Orphan row (message deleted underneath) and stale-generation row.
- `EXPLAIN QUERY PLAN` golden for the expiry scan, the probe and the retire scan.
- `assertInvariants(t, db)` (the shared helper from #9/#10, extended with S1–S3) runs after every
  test in the package and is the same helper `messq verify` (#8) and #13 call.

**Concurrency**

- 32 workers fetching and randomly abandoning, with the sweeper running against the real writer,
  `-race` clean: `attempts` never exceeds `max_deliver`, every message reaches exactly one terminal
  outcome, and every `attempts > 1` is preceded by a `msg.nak`, `msg.timeout` or
  `recovery.reclaimed` for that pair (**I9**).
