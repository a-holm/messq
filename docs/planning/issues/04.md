## Context

messq's thesis is *answerability*: every state transition is durably recorded and replayable
(`PLAN.md` §1.2). That only works if there is one precise, agreed answer to "what is the state
of this message, and what may happen to it next" — written down **before** any feature code
exists. `PLAN.md` §14 makes this an M1 exit criterion in so many words: *"spec merged before
feature code"*.

This issue produces two artefacts:

1. **`docs/SEMANTICS.md`** — the normative specification of the per-`(consumer, seq)` delivery
   state machine: states, the transition table (`PLAN.md` §5.1, T1–T11), guards and their error
   outcomes, ack-token fencing, backoff, dead-lettering, dedup, recovery, the durability
   contract, the guarantee statement (`PLAN.md` §6) and the invariants I1–I11 (`PLAN.md` §5.2)
   with stable IDs.
2. **`docs/adr/`** — the adjudicated decisions D1–D15 (`PLAN.md` §2) recorded as ADRs in the
   repository, with the template and index that `PLAN.md` §13 already assumes exists (*"every
   [dependency] addition needs an ADR"*).

Why it is P0 and why it is scheduled before the store:

- **The transition table is the test suite's spine.** `PLAN.md` §11.1 requires "one table row
  per transition in §5.1"; §11.2's reference model in `internal/model` is written *from the
  spec, not from the implementation* — an independent oracle is only independent if it has an
  independent source. #13 cannot be built without this document.
- **Invariant IDs are a naming contract.** `messq verify` output (#8), rapid's invariant hook
  (#13), test names, log messages and the `docs/guarantees.md` table (#35) all cite I-numbers.
  Renaming one later is a cross-repo rename.
- **It is where the spec-level contradictions get found**, cheaply, in a text editor, instead of
  expensively, in #12's dead-letter transaction. This issue already surfaces two (see
  *Open questions* below: DLQ id lineage vs. the global unique index on `messages.id`, and
  wall-clock deadline arithmetic vs. clock jumps).
- ADRs make D1–D15 legible to a contributor who has not read a 1000-line plan, and give
  later dependency/design additions a place to land.

Governing sections: `PLAN.md` §2 (all of D1–D15), §5 (state machine, transition table,
invariants), §6 (guarantees), plus §4.2 (schema — the spec's states are defined against it),
§4.3–4.5 (durability, recovery, retention) and §9.2 (event vocabulary).

## Scope

**In scope**

- `docs/SEMANTICS.md`: the full normative spec, RFC 2119 keywords, stably-numbered sections
  (`S1`…`S16`) that tests and other docs cite by number.
- The transition table T1–T11 reproduced with two columns `PLAN.md` §5.1 does not have:

### 3. States defined against the schema (S5)

The spec's states MUST be defined as predicates over `PLAN.md` §4.2's tables, so there is no gap
between "the spec" and "the rows":

| State | Predicate over `deliveries` / `consumers` | Notes |
|---|---|---|
| `UNSEEN` | no row for `(s,c,seq)` **and** `seq >= consumers.cursor_seq` | implicit; costs no storage |
| `READY` | row exists, `state = 0` | *deliverable* iff `now >= visible_at` |
| `INFLIGHT` | row exists, `state = 1` | `visible_at` is the ack deadline |
| `RESOLVED` | no row **and** `seq < consumers.cursor_seq` | ack/term/dead/filtered-out are indistinguishable at rest — the **events table** is what distinguishes them |

That last row is the load-bearing one and MUST be stated explicitly: *messq deliberately does
not keep a per-message terminal status column; the terminal state is the absence of a row, and
the reason is recorded in `events`.* This is D5 plus D11 in one sentence, and it is the thing a
reader must understand before `trace` makes sense.

Derived quantities, defined once here because metrics (§9.4), `consumer info` and alerts all
depend on them being the same number:

```
pending(c)             = |{rows in deliveries where consumer = c}|            (READY + INFLIGHT)
inflight(c)            = |{rows where consumer = c and state = INFLIGHT}|
backlog(c)             = pending(c) + |{messages with seq >= c.cursor_seq matching c.filters}|
oldest_pending_age(c)  = now - min(messages.published_at) over pending(c) rows   (0 if empty)
```

`max_ack_pending` bounds **`pending(c)`**, not `inflight(c)` — that is what I5 says
(`count(deliveries WHERE consumer=c) ≤ max_ack_pending`), so the bound MUST be enforced at
top-up (T1), not only at claim (T2). #9 implements it; the spec is where the two readings get
reconciled once.

### 4. Transition table (S6) — proposed shape

Same rows as `PLAN.md` §5.1, plus the failure column. Abridged; the deliverable carries all of
T1–T11.

| ID | From | Trigger | Guard | Effect | Event | On guard failure |
|---|---|---|---|---|---|---|
| T1 | UNSEEN | fetch top-up | filter matches ∧ `pending(c) < max_ack_pending` ∧ ¬paused | insert READY row; advance `cursor_seq` past every scanned seq incl. non-matches | — | `pending` full → no insert, `flow.blocked` (rate-limited), fetch returns empty batch with a hold reason |
| T2 | READY | fetch claim | `now >= visible_at` ∧ `pending(c) <= max_ack_pending` | `attempts++`, `state=INFLIGHT`, `visible_at = now + ack_wait`, mint token; **committed before the response** | `msg.deliver` | not yet visible → row is skipped, not an error |
| T3 | INFLIGHT | `ack(token)` | `token.attempt = row.attempts` ∧ `token.generation = consumer.generation` | DELETE row | `msg.ack` | see T3a/T3b |
| T3a | RESOLVED | `ack(token)` | generation matches, no row | idempotent success, `stale: true` in the result | `msg.ack_dup` (DEBUG) | — |
| T3b | INFLIGHT | `ack(token)` | attempt or generation mismatch | **row untouched** | `msg.ack_stale` (WARN) | `stale_ack` (409), `detail.cause ∈ {attempt, generation}` |
| T4 | INFLIGHT | `nak(token, delay?, reason?)` | fenced ∧ `attempts < max_deliver` | `state=READY`, `visible_at = now + (delay ?? backoff(attempts))`, `last_reason = reason` | `msg.nak` | fence fail → T3b; `attempts >= max_deliver` → T5 |
| … | | | | | | |
| T11 | DEAD in DLQ | `dlq redrive` | operator, rate-limited, redrive-count guard | republish into the origin stream: **new seq, new id**, `Messq-Redrive-Of`, `trace_id` preserved | `dlq.redrive` | already redriven 3× without `--force` → `conflict` |

Normative notes that belong under the table:

- **All transitions are totally ordered by the single writer** (`PLAN.md` §3.2). There is no
  race between `extend` and the sweeper, only an order: whichever command the writer applies
  first wins. A transition MUST therefore be specified as a function of the state *at apply
  time*, never of the state observed by the handler. This one paragraph deletes a whole class
  of "what if two things happen at once" questions from the rest of the spec.
- **`attempts` is post-increment-visible.** During attempt *n*, `row.attempts = n`. With
  `max_deliver = 5`, the fifth delivery leaves `attempts = 5`; its nak/timeout matches T5's
  `attempts >= max_deliver` and dead-letters. **Exactly five handler invocations** — the spec
  MUST carry this worked table, including `max_deliver = 1` (one delivery, then DEAD on the
  first failure) and `max_deliver = 0` (unlimited; never dead-letters; warned at consumer
  creation).
- **T1's cursor advance is irreversible within a generation** (I6). Consequence, stated
  explicitly because it will otherwise be a support ticket: *changing a consumer's `filters`
  does not retroactively deliver messages the old filter skipped; use `seek`.*
- **Config changes apply forward only:** a new `ack_wait` applies to future claims; already-
  INFLIGHT deadlines are unchanged. A new `backoff` array applies to the next scheduling
  decision. A new `max_ack_pending` applies at the next top-up.
- **Purge and seek both bump `generation`** (T10) and drop delivery rows; `cursor_seq` is
  clamped to `>= first_seq` afterwards.

### 5. Ack-token grammar (S3)

```abnf
ack-token   = stream "/" consumer "/" seq "/" attempt "/" generation
stream      = name
consumer    = name
name        = ALPHA / DIGIT 1*63( ALPHA / DIGIT / "_" / "-" / "." )   ; no "/", no "..",
                                                                      ; no leading/trailing "."
seq         = 1*19DIGIT      ; positive, no leading zeros
attempt     = 1*10DIGIT
generation  = 1*10DIGIT
```

Sketch (proposal — the real one lands in #10):

```go
// Token is the fenced, deliberately human-readable delivery token (D7).
type Token struct {
	Stream, Consumer  string
	Seq               uint64
	Attempt           uint32
	Generation        uint32
}

// ParseToken never allocates unbounded, never panics, and rejects anything a
// fuzz target can produce. Length is capped at MaxTokenLen (proposal: 160 bytes).
func ParseToken(s string) (Token, error)

// Fence reports whether t may mutate row. Cost: two integer comparisons (D7).
func (t Token) Fence(row Delivery, gen uint32) error // nil | ErrStaleAck
```

The `/` separator is what forbids `/` in names; the spec MUST state that dependency in both
directions so nobody "relaxes" the name grammar later without noticing.

### 6. Backoff (S8) — normative algorithm

```
backoff(attempts):                      # attempts = the attempt that just failed, >= 1
    b   = consumer.backoff_ms           # non-empty array, validated at consumer creation
    i   = min(attempts - 1, len(b) - 1) # last value repeats
    d   = b[i]
    return jitter(d)                    # uniform in [0.8*d, 1.2*d), always applied
```

- Jitter is **±20 %, uniform, and not configurable off** (`PLAN.md` §5.1). The spec constrains
  only the *range*, not the source of randomness, so implementations and the reference model can
  differ and the property test asserts the bound rather than the value.
- An explicit `nak --delay D` **overrides** the schedule for that attempt and is not jittered
  (the handler knows better; a stampede from an explicit delay is the caller's choice).
- Proposed clamp, because `PLAN.md` leaves it open: `delay_ms ∈ [0, 86_400_000]` (24 h);
  outside → `invalid_argument`. `delay_ms = 0` means "immediately eligible".
- Worked example table for the default `[1s, 5s, 30s, 2m, 10m]` with `max_deliver = 5`,
  showing the retry horizon (≈ 12 m 36 s ± jitter) — the same number `messq consumer add` prints
  (#24), so the CLI has a spec to be right against.

### 7. Time and clocks (S7) — an open question this issue must close

`deliveries.visible_at` is stored as Unix **wall-clock** milliseconds (schema §4.2), but
`PLAN.md` §11.4 and #32 require that a ±1 h clock jump leave deadlines unaffected. Proposal:

```
now_ms() = anchor_wall_ms + (mono_now - anchor_mono) / 1e6
```

- The anchor pair is captured once at startup (and re-captured only at startup).
- A detected step (|wall − derived| > `--clock-jump-threshold`, default 5 s) emits a WARN event
  and **does not** re-anchor: in-flight deadlines are unaffected, exactly as specified.
- `published_at`, event `ts` and `seek --to time:T` use the same derived clock, so a trace's
  timeline is internally consistent even across a step.
- Drift between the derived clock and true wall time is bounded by process lifetime × NTP slew;
  documented, and `doctor` (#30) reports it.
- Sweeper granularity (250 ms) is normative and documented: a deadline may fire up to one tick
  late, never early.

### 8. Lineage (S4) — the second open question

`PLAN.md` §4.2 declares `CREATE UNIQUE INDEX messages_id ON messages(id)` (global), while D3
says the DLQ copy preserves "the original `msg_id`/`trace_id`". Both cannot hold while the
origin row still exists — and `GET /v1/messages/{id}` (§7) needs `id` to be globally unique to
work at all. Proposed resolution, to be ratified in ADR-0003 and implemented by #12:

| Operation | `id` | `seq` | `trace_id` | Provenance header |
|---|---|---|---|---|
| publish | new ULID | new | intake or minted | — |
| dead-letter → `<s>.dlq` | **new ULID** | new (in `.dlq`) | **preserved** | `Messq-Origin-Id`, `-Stream`, `-Seq`, `-Consumer`, `Messq-Attempts`, `Messq-Cause`, `Messq-Last-Reason`, `Messq-Dead-At` |
| redrive (#29) | new ULID | new (origin stream) | **preserved** | `Messq-Redrive-Of`, `Messq-Redrive-Count` |
| replay (#28) | new ULID | new | **preserved** | `Messq-Replay-Of` |

"One continuous story" is then preserved by (a) `trace_id`, which `messq trace --trace-id`
follows, and (b) the `msg.dead` / `dlq.redrive` events carrying **both** ids in `detail`, so
`messq trace <id>` can walk the lineage forward and backward through the `events_msg` index
without a table scan. The rejected alternative — scoping the unique index to
`(stream, id)` — loses the by-ULID lookup endpoint and makes `trace <id>` ambiguous; record it
as the rejected option in the ADR.

Related edge cases the spec MUST settle:

- **No DLQ of a DLQ.** The `.dlq` suffix is reserved: user-created streams MUST NOT end in
  `.dlq`; consumers on a `.dlq` stream default to `dead_policy = drop` and MUST NOT auto-create
  `<s>.dlq.dlq`.
- **`Messq-` is a reserved header prefix** on publish; user headers with it are rejected
  (`invalid_argument`) rather than silently dropped.
- **Dedup key reuse after the window is a new message**, not a duplicate — stated plainly,
  because it is the one place where messq's dedup is weaker than a reader might assume.
- **Ack for a deleted consumer** → `not_found`, *not* idempotent success (T3a only applies when
  the consumer still exists and the generation matches).

### 12. Change control (S16)

- The document carries `Spec-Version: 1.0-draft` in its header; the v1.0 tag (#36) flips it to
  `1.0` and freezes it.
- After v1.0: weakening a MUST, renaming an invariant or transition ID, adding a state, or
  changing an event name is a **breaking change** to the compatibility promise (#36) and needs
  a superseding ADR plus an entry in A3 (spec changelog). Adding a MAY, a clarification, or a
  new reserved ID is not.
- Divergence rule: if implementation and spec disagree, **the spec is the bug report** — fix one
  or the other in the same PR, never neither.

## Acceptance criteria

- [ ] `docs/SEMANTICS.md` exists with stably-numbered sections S1–S16 plus appendices A1–A3 and
      a `Spec-Version: 1.0-draft` header, and states its RFC 2119 keyword convention.
- [ ] Every transition T1–T11 from `PLAN.md` §5.1 appears exactly once, with guard, effect,
      emitted event **and** the outcome when the guard fails.
- [ ] Every state in S5 is defined by an explicit predicate over the `PLAN.md` §4.2 schema, and
      `RESOLVED` is documented as "no row; the reason lives in `events`".
- [ ] `pending`, `inflight`, `backlog` and `oldest_pending_age` are each defined by one formula,
      and the spec states that `max_ack_pending` bounds `pending`, enforced at top-up.
- [ ] The attempt-counting semantics are worked through for `max_deliver` ∈ {0, 1, 5} showing
      the exact number of handler invocations (D6).
- [ ] The backoff algorithm is specified as pseudo-code including the last-value-repeats rule,
      the mandatory ±20 % jitter range, the explicit-delay override and its clamp.
- [ ] The ack-token grammar is given in ABNF, the fencing rules are normative, and the
      name-grammar consequence (no `/` in names) is stated in both places.
- [ ] The dead-lettering procedure is specified as one transaction with the full provenance
      header set, both `dead_policy` values, and the no-DLQ-of-a-DLQ rule.
- [ ] The lineage table (publish / dead-letter / redrive / replay) is present and reconciles D3
      with the global unique index on `messages.id`; the resolution is recorded in ADR-0003 with
      the rejected alternative.
- [ ] The clock rule is specified: monotonic-anchored `now`, no re-anchoring on a step, WARN
      event on detection, sweeper granularity documented as "up to one tick late, never early".
- [ ] The durability contract states, per mode and per verb, what a 2xx means — including that
      under `full` an **ack** response is a durability promise (D4).
