## Context

#9 gave a message a way *out* of the stream: a delivery row goes `INFLIGHT`, `attempts` is
incremented durably, and a token is minted. Nothing can currently finish that work. This issue
implements the four settle verbs — **ack, nak, term, extend** — and the fencing rule that decides
whether a settle is allowed to touch the row at all.

This is the issue where messq's central honesty claim gets its teeth. Every at-least-once broker
has the same failure: a worker takes too long, the message is redelivered, the first worker's ack
arrives anyway and silently completes a message a second worker is still processing. The result is
one message processed twice, one completion lost, and no evidence anywhere. **D7** makes that
sequence a `409 stale_ack`, a WARN event, and a metric you can alert on — for the price of one
integer comparison. Everything §6 promises ("a stale ack is rejected and reported rather than
silently accepted") is implemented here.

Governing PLAN.md material:

- **§5.1 — Transition rules T3, T3a, T3b, T4, T5, T6, T7.** This issue implements those seven rows
  and nothing else; T8 (sweeper timeout) is #11 and T9 (recovery) already landed in #5.
- **§2 / D7 — plain fenced tokens, no HMAC.** The token is
  `"<stream>/<consumer>/<seq>/<attempt>/<generation>"`, human-readable on purpose, validated
  against the live delivery row. No signature, no key management, no crypto: a token is **not a
  capability**, authorization (#16) is what decides who may settle, and the token only decides
  *which attempt* is being settled.
- **§2 / D5 — ack is a `DELETE`.** The terminal state is the absence of the row. There is no
  "acked" flag, no pending-entry list to compact, and no way for the pending set to leak.
- **§2 / D6 — attempts increment at claim.** Consequently a nak arriving when `attempts ==
  max_deliver` is the *fifth* failure of a `max_deliver=5` consumer and goes straight to DEAD.
- **§4.3 — an ack response is a durability promise.** Under `--durability=full` the settle rides
  the same group commit as everything else, so a 2xx on ack means the delete survived a power cut
  at ~zero marginal fsync cost. No lazy ack-flush window, and therefore no documented duplicate
  window from ack loss.
- **§5.2 — invariant I7** ("no stale-fenced ack/nak/term ever mutates a live row") is born here and
  gets its checker here. I3, I4 and I8 gain their settle-side arms.
- **§9.2 — event vocabulary:** `msg.ack`, `msg.ack_dup`, `msg.ack_stale`, `msg.nak`, `msg.term`,
  `msg.extend`, `msg.dead`. All written in the same transaction as the state change (**D11**).
- **§9.4 — `messq_stale_acks_total{stream,consumer}`**, the metric §9.4 annotates with *"alert on
  any nonzero rate (ack_wait too short)"*. This issue is where it starts counting.

What this unlocks: the sweeper (#11) reuses the release-and-maybe-dead path defined here; DLQ
dead-lettering (#12) fills in the `DeadSink` seam this issue introduces; the property suite (#13)
gets `ack`/`nak`/`term`/`extend`/`stale_ack` as first-class actions; the HTTP data plane (#14)
wraps the per-token result type in `/v1/ack|nak|term|extend`; worker attribution (#41) is possible
at all *because* acks are fenced — its own summary says so.

## Scope

**In scope**

- Ack-token **parsing** and validation in `internal/queue` (minting landed in #9): a zero-allocation
  canonical parser, strict grammar, bounded length, plus `FuzzParseToken`.
- The pure `PlanSettle` decision function: `(consumer config, generation, cursor, live row, verb,
  now) → (outcome, mutation, event)`. No I/O, no `time.Now`, deterministic jitter through a seam.
- The complete fencing decision table over `verb × row state × attempt relation × generation
  relation × max_deliver boundary`, exhaustive and tested as a cross-product.
- **ack (T3, T3a, T3b):** delete the row; emit `msg.ack` with `held_ms`; observe ack latency;
  idempotent success (`stale`) when the row is already resolved; `409 stale_ack` when the token
  names a spent attempt.
- **nak (T4, T5):** release to READY at `now + (delay ?? backoff[attempts-1]) ± 20 %`, store
  `last_reason`, or route to DEAD when `attempts >= max_deliver`.
- **term (T6):** straight to DEAD, skipping remaining attempts — the permanent-error escape.
- **extend (T7):** push `visible_at` by one `ack_wait`, clamped so that a single attempt can never
  hold a message longer than `--max-ack-wait`; `attempts` unchanged.
- The `SettleCmd` writer command: batched, **per-token results, never all-or-nothing**, one
  transaction, one group commit.
- The `DeadSink` seam that nak-exhaustion and term route into, with a provisional
  delete-and-event implementation until #12 lands the DLQ copy.
- Stale/duplicate accounting: `msg.ack_stale` (WARN, never sampleable) and `msg.ack_dup` (DEBUG)
  event rows, repeat-rate-limited per consumer so a broken client cannot grow the audit trail
  without bound.
- Metric names specified (registered in #21): `messq_acked_total`, `messq_naked_total`,
  `messq_termed_total`, `messq_stale_acks_total`, `messq_extends_total`,
  `messq_ack_latency_seconds`, plus the proposed `messq_late_acks_total`.
- Invariant checker for **I7**, and the settle-side arms of I3/I4, exported for `messq verify`
  (#8) and the model suite (#13).
- Flags: `--max-settle-batch`, `--max-reason-bytes`, `--event-repeat-interval`
  (`--max-ack-wait` already exists from #9).

**Out of scope**

- The 250 ms timeout sweeper, the timeout arm of the backoff schedule, and `max_deliver`
  exhaustion *by timeout* — **#11**. This issue owns the backoff *computation* and the nak arm;

- The DLQ stream, provenance headers and the atomic copy — **#12**. This issue defines and calls

- HTTP endpoints `/v1/ack|nak|term|extend`, the error envelope, and the sentinel → status mapping

- CLI `messq ack|nak|term|extend`, teaching-error rendering and exit codes — **#24** (framework in

- The `Worker` helper's automatic `extend` heartbeat at `ack_wait/2` — **#22**; `--exec`'s

- The reference model and the full `rapid` suite — **#13**. This issue lands a local property test

### 1. Token parsing (D7)

```go
package queue

// Token was defined in #9 (minting) — same struct, same field types. This issue adds the parser.
type Token struct {
	Stream, Consumer string
	Seq              int64
	Attempt          int32
	Generation       int32
}

// ParseToken accepts only the canonical rendering, so ParseToken(t.String()) == t and
// ParseToken(s).String() == s for every accepted s. Zero allocations.
func ParseToken(s string) (Token, error)
```

| Rule | Detail |
|---|---|
| Length | ≤ `MaxTokenLen` = 192 bytes (64 stream + 64 consumer + 20 + 10 + 20 + 4 separators). Checked first, before any scanning. |
| Shape | Exactly four `/` separators. Parsed with four `strings.Cut` calls — never `strings.Split` (which allocates a slice on a hot path). |
| `stream`, `consumer` | Validated with the #3 name validator (S11): no `/`, 1–64 bytes. This is what keeps the grammar unambiguous and bounds the subsequent lookup. |
| `seq` | `strconv.ParseUint`, base 10, ≥ 1, ≤ `math.MaxInt64`, then narrowed to the `int64` field (the column is a signed `INTEGER`). |
| `attempt` | ≥ 1, ≤ `math.MaxInt32`. Attempt 0 is never minted: the claim increments before minting (D6). |
| `generation` | ≥ 1, ≤ `math.MaxInt32` (`consumers.generation` starts at 1). |
| Canonicality | No leading zeros, no `+`, no whitespace, no unicode digits. `strconv` accepts `+1`; the parser rejects it explicitly, because "one token, one string" is what makes tokens greppable across a log line, a DLQ header and an event row. |

Every rejection is `errs.ErrUnknownToken` (#3), wrapped with the offending field. **No forged
token parses into a well-formed `Token` that names a different message** — that is the fuzz
property, and it is the entire security story a non-HMAC token needs, given that authorization
(#16) already gates the endpoint.

### 2. The fencing rule

Three facts decide everything: the consumer's current `generation`, the live row's `attempts`, and
the live row's `state`.

```
1. parse                  → malformed                        ⇒ unknown        (400)
2. load consumer          → absent                           ⇒ unknown        (404)   [see note A]
3. token.gen != consumer.generation                          ⇒ wrong_generation (409)
4. load delivery row      → absent ∧ token.seq >= cursor_seq ⇒ unknown        (404)   [see note B]
                          → absent ∧ token.seq <  cursor_seq ⇒ stale          (200)   [T3a]
5. token.attempt != row.attempts                             ⇒ stale_ack      (409)   [T3b]
6. otherwise                                                 ⇒ apply the verb          [T3–T7]
```

Steps 3–5 produce **zero mutations** — that is invariant I7, and it is enforced twice: the planner
returns no mutation, and every mutating statement repeats `AND attempts = ? AND generation = ?` in
its `WHERE` clause so that even a planner bug cannot write through the fence (`changes() == 0`
then raises an internal error, which aborts the batch rather than lying).

> **Note A — spec refinement of #9.** #9's consumer-deletion section says outstanding tokens for a
> deleted consumer "resolve to missing row → idempotent success flagged stale". This issue narrows
> that to `unknown`: `stale` must mean exactly one thing — *this specific work item was already
> resolved* — and that cannot be asserted when the consumer itself is gone. `unknown` with a
> teaching message ("the consumer was deleted or never existed; the work is gone either way")
> serves the deleted-consumer worker and the typo'd CLI invocation equally, and the Go client (#22)
> treats it as terminal instead of retrying forever. Two-line edit to #9's text and to
> `SEMANTICS.md`.

> **Note B — plausibility check.** A delivery row only ever exists for `seq < cursor_seq` (the
> cursor advances past everything it scanned, #9). So an absent row with `seq >= cursor_seq` proves
> the message was never delivered to this consumer: the token is fabricated or mistyped, and
> answering "idempotent success" would be a lie. One integer comparison against a column we already
> loaded. This is a clarification of T3a's "on missing row", not a change to it.

### 3. The decision table (normative for this issue; mirrors §5.1)

`gen` = generation matches. `att` compares `token.attempt` to `row.attempts`. Rows marked ✗ produce
no mutation.

| Verb | Row | gen | att | Outcome | Effect | Event |
|---|---|---|---|---|---|---|
| any | absent, `seq<cursor` | ✓ | — | `stale` | none ✗ | `msg.ack_dup` (DEBUG, rate-limited) |
| any | absent, `seq>=cursor` | ✓ | — | `unknown` | none ✗ | — |
| any | any | ✗ | — | `wrong_generation` | none ✗ | `msg.ack_stale` `detail.reason="generation"` (WARN) |
| any | any | ✓ | `<` | `stale_ack` | none ✗ | `msg.ack_stale` (WARN) + `messq_stale_acks_total` |
| any | any | ✓ | `>` | `stale_ack` | none ✗ | `msg.ack_stale` `detail.anomaly="future_attempt"` (WARN) |
| **ack** | INFLIGHT | ✓ | `=` | `ok` | `DELETE` row | `msg.ack` |
| **ack** | READY | ✓ | `=` | `ok`, `late=true` | `DELETE` row | `msg.ack` `detail.late=true` + `messq_late_acks_total` |
| **nak** | INFLIGHT | ✓ | `=`, `attempts < max_deliver` | `ok` | READY, `visible_at = now + jitter(delay ?? backoff)`, `last_reason` | `msg.nak` |
| **nak** | INFLIGHT | ✓ | `=`, `attempts >= max_deliver` | `ok`, `dead=true` | → DEAD (`DeadSink`, cause `max_deliver`) | `msg.nak` + `msg.dead` |
| **nak** | READY | ✓ | `=` | `ok` | `visible_at = min(current, computed)`; event only if the row changed | `msg.nak` |
| **term** | INFLIGHT or READY | ✓ | `=` | `ok`, `dead=true` | → DEAD (`DeadSink`, cause `terminated`) | `msg.term` + `msg.dead` |
| **extend** | INFLIGHT | ✓ | `=` | `ok` | `visible_at = min(max(now, visible_at) + ack_wait, delivered_at + max_ack_wait)` | `msg.extend` (DEBUG) |
| **extend** | READY | ✓ | `=` | `stale_ack` `detail.reason="not_inflight"` | none ✗ | `msg.ack_stale` (WARN) |

Four rows deserve their reasoning, because none of them is in PLAN.md's table and all four are
reachable in production:

**`ack` on a READY row with a matching attempt — accept it.** This is the worker whose ack_wait
expired but whose message has not been re-claimed yet (either the sweeper released it for backoff
and the backoff has not elapsed, or the worker naked it and changed its mind). `attempts` is
unchanged by a timeout — only a claim increments it (D6) — so the token still names the current
attempt. Accepting deletes a message whose work is provably done and **prevents a redelivery that
would otherwise certainly happen**; rejecting would manufacture the exact duplicate D7 exists to
eliminate. It is flagged `late=true` and counted separately: the diagnosis ("ack_wait is shorter
than your handler") is identical to a stale ack, so #21's alert rule sums both, but conflating the
counters would destroy the distinction between *a duplicate happened* and *a duplicate was
narrowly avoided*.

**`extend` on a READY row — reject it.** You cannot extend a lease you no longer hold. The row is
already scheduled for redelivery; pushing its `visible_at` would delay work on behalf of a worker
that is no longer the fenced owner. The heartbeating client (#22) sees `stale_ack` and stops.

**`nak` never moves `visible_at` later.** A retried HTTP nak (the response was lost) must not push
the retry further out each time, and a client loop must not be able to defer a message forever.
`min(current, computed)` makes nak idempotent under replay while still letting an explicit shorter
`--delay` pull a retry *in*. The event is emitted only when the row actually moved.

**`term` works on a READY row.** "This will never succeed" is a property of the payload, not of the
lease state.

### 4. Backoff and jitter

```go
// BackoffFor is 1-based on attempts and repeats the last entry (#9 defined it; #11 reuses it).
func (c ConsumerConfig) BackoffFor(attempt int) time.Duration

// Jitter is a seam so property tests and synctest runs are reproducible.
// Production: math/rand/v2 PCG, one per writer goroutine (never crypto/rand — this is not a
// security decision and the writer must not block on entropy).
type Jitter func(d time.Duration) time.Duration

const JitterFraction = 0.20 // ±20%, PLAN §5.1: "always applied and not configurable off"
```

- The delay is `delay ?? backoff[attempts-1]`, then jittered. **The jitter applies to an explicit
  `--delay` too** — PLAN §5.1's `±20 %` sits outside the parenthesis, and the reason is the same
  either way: fifty workers naking with `--delay 30s` because one downstream is down will
  resynchronize into a second outage otherwise.
- `delay_ms = 0` means *retry immediately*; `0 ± 20 %` is `0`, the row becomes visible now, and
  #14's waiter registry wakes a parked fetch.
- `max_deliver = 0` (unlimited) never dead-letters by count; the backoff index still saturates at
  the last entry.
- **No `--nak-jitter` flag.** plan-01 proposed one; a knob whose only interesting setting is
  forbidden is a knob that will be set to `0.01` in production. The constant is reported by
  `/v1/info` so `doctor` (#30) can explain observed retry spread.

### 5. The extend cap without a new column

PLAN §5.1 T7 caps *total* extension at `--max-ack-wait` (1 h). No extra state is needed:
`delivered_at` records when the current attempt was claimed, so the total lease held by this
attempt is `visible_at - delivered_at` and the clamp is one expression. The cap is therefore
**per attempt**, which is the useful reading: one delivery may hold a message for at most an hour,
after which it goes back in the queue no matter how loudly the worker heartbeats.

At the cap, extend returns `ok` with `capped: true` and the **unchanged** deadline, and the event
carries `detail.capped=true` (logged at WARN, unlike ordinary extends). Rejecting instead was
considered and dropped: it would need a new sentinel in the closed #3 set, and the worker's actual
need is not an error but the deadline — `capped:true` tells the `Worker` helper (#22) to stop
heartbeating and log "this handler has held orders/10493 for 1h; it will be redelivered at 09:41".

`max(now, visible_at)` in the formula matters: an extend that arrives inside the ≤250 ms window
after expiry but before the sweeper runs still buys a full `ack_wait`, rather than a deadline in
the past that the next tick immediately reaps.

### 6. The dead path seam (filled in by #12)

```go
package store

type DeadCause string // "max_deliver" | "terminated"

// DeadSink runs INSIDE the settle transaction. #12 implements the DLQ copy against it;
// until then DropSink deletes the row and records the event only (dead_policy=drop).
type DeadSink interface {
	Dead(ctx context.Context, tx *sql.Tx, d DeadCtx, now time.Time) (obs.Event, error)
}

type DeadCtx struct {
	Stream, Consumer, Subject string
	Seq                       uint64
	MsgID, TraceID            string
	Attempts                  int
	Cause                     DeadCause
	LastReason                string
}
```

Until #12 lands, `dead_policy=dlq` behaves as `drop` behind a `TODO(#12)`, the daemon logs the
substitution once at startup, and a test asserts the sink is called with the exact `DeadCtx` a DLQ
copy will need. This mirrors how #5 and #9 wrote event rows against local constants that #19
replaces — the seam is the deliverable, the implementation is the next issue's.

### 7. The writer command

```go
package store

type Verb uint8 // VerbAck | VerbNak | VerbTerm | VerbExtend

type SettleItem struct {
	Token  queue.Token
	Verb   Verb
	Delay  *time.Duration // nak only; nil = use the backoff schedule
	Reason string         // nak/term; truncated to --max-reason-bytes
}

type SettleCmd struct{ Items []SettleItem } // <= --max-settle-batch

type ItemStatus string // "ok" | "stale" | "stale_ack" | "wrong_generation" | "unknown"

type ItemResult struct {
	Token          queue.Token
	Status         ItemStatus
	Attempt, Of    int
	CurrentAttempt int           // set on stale_ack — what the row is actually on
	Deadline       time.Time     // extend
	RetryAt        time.Time     // nak
	Dead           bool
	Capped, Late   bool
	HeldFor        time.Duration // ack: now - delivered_at
	Err            error         // sentinel for non-ok statuses
}

type SettleResult struct {
	Results     []ItemResult // request order
	OK, Failed  int
}
```

`SettleCmd.Apply` **never returns a `CmdError`.** Partial success is the defined semantics
(§7: "batch; per-token result"), so business rejections travel in `Results` and only infrastructure
errors abort the batch. The savepoint machinery from #6 stays unused on this path, which is
correct — a rejected item produced no writes to roll back.

Execution inside the transaction:

```
1. group items by (stream, consumer); dedupe exact repeats within the batch
   (2nd occurrence of the same token -> "stale", no second event)
2. load each distinct consumer once (config, generation, cursor_seq)
3. one batched row load per (stream, consumer) group:

   SELECT d.seq, d.state, d.attempts, d.visible_at, d.generation, d.delivered_at, d.subject,
          m.id AS msg_id, m.trace_id
     FROM deliveries d
     LEFT JOIN messages m ON m.stream = d.stream AND m.seq = d.seq
    WHERE d.stream = :s AND d.consumer = :c AND d.seq IN (…);   -- <= 200 seqs per chunk

4. for each item, in (stream, consumer, seq) order: PlanSettle(...) -> apply
5. emit events; return Results in REQUEST order
```

The `LEFT JOIN` is deliberate: an orphaned delivery row (message gone) must still be settleable —
the settle touches `deliveries` only; `messages` is read solely to stamp `msg_id`/`trace_id` on the
event (§9.2 requires both on every message event). Execution is sorted for index locality and
determinism; results are returned in request order so a client can zip them against its input.

Mutating SQL (the fence repeated in every `WHERE`):

```sql
-- ack (T3): the terminal state IS the absence of the row
DELETE FROM deliveries
 WHERE stream=:s AND consumer=:c AND seq=:q AND attempts=:att AND generation=:gen;

-- nak (T4): release
UPDATE deliveries
   SET state = 0, visible_at = :vis, last_reason = :reason
 WHERE stream=:s AND consumer=:c AND seq=:q AND attempts=:att AND generation=:gen;

-- extend (T7): attempts untouched, INFLIGHT only
UPDATE deliveries
   SET visible_at = :vis
 WHERE stream=:s AND consumer=:c AND seq=:q AND attempts=:att AND generation=:gen AND state = 1;

-- term / nak-exhaustion: DeadSink, then
DELETE FROM deliveries
 WHERE stream=:s AND consumer=:c AND seq=:q AND attempts=:att AND generation=:gen;
```

Each is followed by a `changes() == 1` assertion; a zero means the planner and the database
disagree, which is a bug, not a business outcome, and aborts the batch loudly.

### 8. Events and their bounds

| Outcome | Event | Level (§9.3) | Sampleable |
|---|---|---|---|
| ack | `msg.ack` (`detail: {held_ms, late?}`) | DEBUG | yes (per message) |
| ack on resolved row | `msg.ack_dup` | DEBUG | yes |
| stale_ack / wrong_generation / not_inflight | `msg.ack_stale` (`detail: {token_attempt, current_attempt, reason}`) | **WARN** | **never** |
| nak | `msg.nak` (`detail: {delay_ms, reason, explicit}`) | **WARN** | **never** |
| term | `msg.term` (`detail: {reason}`) | **WARN** | **never** |
| extend | `msg.extend` (`detail: {deadline_ms, capped}`) | DEBUG (WARN when capped) | yes |
| dead | `msg.dead` (`detail: {cause, attempts, last_reason}`) | **WARN** | **never** |

No new event names: the vocabulary is closed (D11) and `wrong_generation` reuses `msg.ack_stale`
with a `detail.reason`, rather than inventing `msg.ack_gen`.

> **Bound proposal (needs ratification in #19).** Event *rows* must be bounded by real work, not by
> client behaviour: a worker looping on one bad token could otherwise write `msg.ack_stale` rows
> forever. Rule: rows for **rejections** (`msg.ack_stale`, `msg.ack_dup`) are rate-limited per
> `(consumer, event)` through the same bounded in-memory limiter #9 uses for `flow.blocked`
> (`--event-repeat-interval`, default 10 s), carrying `detail.suppressed = N`. Rows for **state
> changes** are never rate-limited. The metric is always exact, and the WARN log keeps its D11
> allow-list behaviour. Trade-off stated plainly: `messq trace` may show "3 stale acks
> (2 suppressed)" instead of three rows, and that is the right price for a bounded audit trail.

### 9. Illustrative wire shapes (#14 owns the endpoints)

```http

{"tokens":["orders/worker/10493/2/1","orders/worker/10494/1/1"]}

200 OK
{"results":[
   {"token":"orders/worker/10493/2/1","status":"ok","attempt":2,"of":5,"held_ms":531},
   {"token":"orders/worker/10494/1/1","status":"stale_ack","attempt":1,"current_attempt":2,
    "error":{"code":"stale_ack","message":"ack names attempt 1; orders/worker/10494 is on attempt 2"}}
 ],"ok":1,"failed":1}
```

```http
POST /v1/ack
{"tokens":["orders/worker/10493/1/1"]}

409 Conflict
{"results":[{"token":"orders/worker/10493/1/1","status":"stale_ack","attempt":1,"current_attempt":2}],
 "error":{"code":"stale_ack",
          "message":"ack names attempt 1; orders/worker/10493 is on attempt 2 — this message may have been processed twice",
          "next":["messq trace 01J8ZQ4K2M9V0X7Y3B5N6C8D1E",
                  "messq consumer edit orders worker --ack-wait 2m"],
          "trace_id":"4bf92f35…"}}
```

Status rule, one sentence: **200 unless every item failed, in which case the status of the first
failure** (409 stale/generation, 404 unknown, 400 malformed). The `results` array is present on
every response, error or not, so machine clients need only one parse path — and a single-token
request, which is what `curl`, the CLI and `/v1/nak|term` all send, naturally yields the `409
stale_ack` D7 specifies.

{"token":"orders/worker/10493/2/1","reason":"unparseable payload"}

> **Spec clarification needed in `docs/PROTOCOL.md` / `SEMANTICS.md` (#4).** PLAN §7 abbreviates the
> per-token result as `(ok|stale|unknown)`, while D7 requires a distinct `409 stale_ack`. The full
> enum is the five values above; `stale` and `stale_ack` are *opposites* in meaning — the first is
> "nothing to do, all is well", the second is "a duplicate probably happened". Collapsing them
> would delete the feature. Two-line edit.

CLI shape for context only (#24 owns the rendering and the exit codes):

```console
$ messq ack orders/worker/10493/1/1
stale ack: this token names attempt 1, but orders/worker/10493 is on attempt 2
  the work was probably processed twice — see: messq trace 01J8ZQ4K2M9V0X7Y3B5N6C8D1E
  likely cause: ack_wait (30s) is shorter than your handler
  fix: messq consumer edit orders worker --ack-wait 2m
$ echo $?
4
```

### 10. Flags added by this issue (D8: flags + `MESSQ_*` env only)

| Flag | Env | Default | Meaning |
|---|---|---|---|
| `--max-settle-batch` | `MESSQ_MAX_SETTLE_BATCH` | `1024` | Tokens per settle request; above it, `ErrBadRequest` (I11: every bound is explicit) |
| `--max-reason-bytes` | `MESSQ_MAX_REASON_BYTES` | `4096` | Cap for nak/term reasons; longer is truncated with `detail.truncated=true`, matching `--exec`'s 4 KiB stderr capture (#25) |
| `--event-repeat-interval` | `MESSQ_EVENT_REPEAT_INTERVAL` | `10s` | Repeat-rate limit for rejection event rows (§8 above) |

`--max-ack-wait` (1 h) already exists from #9 and is the extend cap here.

Documentation note for #35: *reasons are operator-visible and land in a DLQ header (#12) — do not
put payloads or secrets in them.* The daemon does not inspect the string beyond truncation.

### 11. Edge cases and how they are handled

| Case | Handling |
|---|---|
| Late ack arrives while attempt N+1 is INFLIGHT | `409 stale_ack`, row untouched, `msg.ack_stale` WARN, `messq_stale_acks_total++`. The canonical acceptance test. |
| Late ack arrives while the row is READY (not yet re-claimed) | **Accepted**, `late=true`, `messq_late_acks_total++`. A duplicate was avoided, not created. |
| Double ack of the same token | First `ok`, second `stale` (row gone) — idempotent, exit code 0. |
| Two identical tokens inside one batch | Deduped: first applies, second returns `stale`, one event. |
| Batch spanning several consumers/streams | Allowed; grouped for lookup, one transaction, one fsync. |
| Ack after the message was dead-lettered by #11 | Row is gone ⇒ `stale`. The DLQ copy is **not** recalled — `trace` shows `dead` then `ack_dup`, and the operator uses `dlq` tooling (#29). Documented, not fixed. |
| Ack after the consumer was deleted | `unknown` (Note A), terminal for the client. |
| Ack after `seek` bumped the generation | `wrong_generation`, `msg.ack_stale` `reason="generation"`. Work done under the old cursor cannot silently resolve a rewound message. |
| Row exists but `row.generation != consumer.generation` | Cannot happen (#28's seek deletes rows when it bumps); if seen, `unknown` + WARN anomaly, never a mutation. `messq verify` (#8) reports it. |
| `token.attempt > row.attempts` | Impossible without a bug or a restored-from-backup file. Treated as `stale_ack` with `detail.anomaly="future_attempt"` — the safe direction is always "do not mutate". |
| Consumer is paused | Settles proceed normally. Pausing stops *delivery*, never resolution; blocking acks would manufacture redeliveries. |
| Disk below `--min-free-bytes` | Settles proceed (§4.5: "acks, naks and DLQ writes continue" — a wedged ack path becomes mass redelivery). Only publish is rejected with `507`. |
| Storage latched read-only after `storage.fatal` | Everything rejected `503`; the writer rejects before `Apply` (#6). |
| Extend called forever by a stuck worker | Clamped at `delivered_at + --max-ack-wait`; `capped:true`; WARN event makes the stuck worker visible instead of invisible. |
| Extend arriving after expiry but before the sweeper tick | Accepted while the row is still INFLIGHT; `max(now, visible_at)` gives a full `ack_wait`. |
| Nak with `attempts == max_deliver` | DEAD with cause `max_deliver` — exactly `max_deliver` handler invocations, because the increment happened at claim (D6). |
| Nak with `max_deliver = 0` | Never dead by count; backoff index saturates at the last entry. |
| Nak retried after a lost response | Idempotent: `visible_at = min(current, computed)`, no second event. |
| Reason larger than `--max-reason-bytes` | Truncated at a UTF-8 boundary, `detail.truncated=true`. Never rejected — a worker failing to report *why* is worse than a long string. |
| Crash after the settle commit, before the response | Client retries; row already gone ⇒ `stale` ⇒ success. This is the UNKNOWN window the #8 ledger oracle exists for, and it resolves to OK on retry. |
| Crash before the settle commit | Ack lost; the message redelivers via #11 with `attempt+1` and a named cause. Ledger: UNKNOWN. At-least-once, honestly. |
| 32 workers settling the same consumer concurrently | Serialized by the single writer (§3.2). Exactly one gets `ok`; the rest get `stale` or `stale_ack`. No locks anywhere. |

## Acceptance criteria

- [ ] `ParseToken` accepts exactly the canonical grammar: round-trips every minted token, and
      rejects wrong separator count, empty fields, `/` inside a name, leading zeros, `+1`,
      whitespace, non-ASCII digits, `attempt=0`, `seq=0`, `generation=0`, `seq` overflow past
      `MaxInt64`, `attempt`/`generation` overflow past `MaxInt32`, and anything longer than
      `MaxTokenLen` — each with `errs.ErrUnknownToken`.
- [ ] `ParseToken` performs **zero allocations** (`testing.AllocsPerRun == 0`) and never panics on
      arbitrary bytes (fuzz).
- [ ] The `PlanSettle` decision table is **exhaustive**: a test enumerates the full cross-product of
      `verb × {absent<cursor, absent>=cursor, READY, INFLIGHT} × attempt{<,=,>} ×
      generation{<,=,>} × {attempts<max_deliver, attempts==max_deliver}` and fails on any
      combination the planner does not classify.
- [ ] A rejected settle (`stale_ack`, `wrong_generation`, `unknown`) mutates nothing: a full
      before/after diff of `deliveries` and `consumers` is empty (**I7**), asserted around every
      rejection case in the suite.
- [ ] Ack deletes the delivery row and writes `msg.ack` in **one** transaction — a forced commit
      failure at the #6 seam leaves both the row and the event absent.
- [ ] A late ack from attempt 1 while attempt 2 is INFLIGHT returns `409 stale_ack`, leaves
      `attempts = 2` and the row INFLIGHT, emits `msg.ack_stale` with both attempt numbers, and
      increments `messq_stale_acks_total`.
- [ ] A late ack from attempt 1 while the row is READY at attempt 1 is **accepted**, deletes the
      row, sets `late=true`, increments `messq_late_acks_total`, and the message is never
      subsequently delivered (**I3**).
- [ ] Acking the same token twice returns `ok` then `stale`; both are successes at the API and CLI
      levels, and only one `msg.ack` event exists.
- [ ] A batch of 100 tokens mixing all five outcomes across three consumers returns 100 results in
      request order, applies exactly the `ok` ones, and commits once (asserted on
      `messq_commit_batch_size`, not on wall clock).
- [ ] A batch above `--max-settle-batch` is rejected whole with `ErrBadRequest`.
- [ ] Nak releases to READY with `visible_at = now + jitter(backoff[attempts-1])` within ±20 %,
      stores `last_reason`, and leaves `attempts` unchanged.
- [ ] An explicit `delay_ms` overrides the schedule and is jittered; `delay_ms = 0` makes the row
      visible immediately.
- [ ] A repeated nak of the same token never moves `visible_at` later and emits no second event.
- [ ] Nak at `attempts == max_deliver` routes to the dead path with cause `max_deliver`, deletes
      the row, and emits `msg.nak` + `msg.dead`; the message is delivered exactly `max_deliver`
      times over the whole run (**I4**).
- [ ] Term at any attempt count routes to the dead path with cause `terminated`, skips the
      remaining attempts, and works on both INFLIGHT and READY rows.
- [ ] The `DeadSink` seam is called exactly once per DEAD transition with a `DeadCtx` carrying
      stream, consumer, subject, seq, msg id, trace id, attempts, cause and last reason (**I8**'s
      settle-side arm).
- [ ] Extend pushes `visible_at` by exactly one `ack_wait`, leaves `attempts` unchanged, and never
      lets `visible_at - delivered_at` exceed `--max-ack-wait`; at the cap it returns `ok` with
      `capped=true` and an unchanged deadline.
- [ ] Extend on a READY row is rejected with `stale_ack` / `reason="not_inflight"`.
- [ ] An absent row with `seq >= cursor_seq` returns `unknown`, not `stale`; with
      `seq < cursor_seq` it returns `stale`.
- [ ] A token whose generation differs from the consumer's returns `wrong_generation` and emits
      `msg.ack_stale` with `detail.reason="generation"`.
- [ ] Settles succeed while the consumer is paused and while the disk is below
      `--min-free-bytes`; they fail with `503` when storage is latched read-only.
- [ ] Every mutating statement carries the fence in its `WHERE`; a deliberately sabotaged planner
      (fence check removed) produces `changes() == 0` and an aborted batch rather than a write.
- [ ] Repeated rejections from one consumer emit at most one event row per `--event-repeat-interval`
      with `detail.suppressed`, while the metric counts every occurrence exactly.
- [ ] `internal/queue` coverage ≥ 90 % and `internal/store` ≥ 85 % (#2 floors); no `time.Now()`
      outside the Clock seam; no `time.Sleep` in tests.
- [ ] `BenchmarkSettle/ack/batch=256` and `BenchmarkParseToken` are recorded in the PR with
      hardware and durability mode stated.

## Test plan

Per §11: `-race` everywhere, real SQLite files in `t.TempDir()` (never `:memory:`), no
`time.Sleep`, timing through the Clock seam and `testing/synctest`, every fixed bug landing with a
committed reproduction artifact.

**Unit — pure planner (`internal/queue`, no DB)**
- `TestPlanSettleMatrix`: the generated cross-product from the acceptance criteria, each case
  asserted against an explicit expectation table. Any unclassified combination fails the test —
  this is the "no case unthought" gate, and it is the file a reviewer reads first.
- `TestParseToken`: one row per grammar rule, both directions; canonicality (`Parse(s).String() ==
  s`) as a table-wide assertion.
- `TestBackoffJitter`: with a deterministic `Jitter`, assert exact `visible_at`; with a real PRNG
  over 10 000 draws, assert the distribution lies in `[0.8d, 1.2d]` and is not degenerate.
- `TestExtendCap`: extend chains at `ack_wait = {1s, 30s, 59m}` against `--max-ack-wait = 1h`,
  including the exactly-at-cap and past-expiry cases.
- Local property (`rapid`, this issue only): random sequences of `settle` against a synthetic row,
  asserting I7 (no rejected op mutates), I4 (`attempts` never exceeds `max_deliver`) and
  monotonicity of `visible_at` under repeated naks. The observational-equivalence suite is **#13**.

**Fuzz**
- `FuzzParseToken`: never panics; accepted input round-trips byte-for-byte; **no accepted input
  names a different `(stream, consumer, seq, attempt, generation)` than its own text** — the
  no-forgery property that stands in for a signature (D7). Seeds: every table row plus mutated
  real tokens, embedded NULs, invalid UTF-8, 4 KiB inputs. 60 s/PR, 30 min nightly, corpus
  committed (#33).

**Unit — store (`internal/store`, real DB)**
- End-to-end per verb through the writer: publish → fetch → settle → assert rows, events and
  results.
- The canonical stale-ack scenario, fully constructible with #9 + #10 alone (no sweeper yet):
  `fetch → nak(delay=0) → fetch → ack(attempt-1 token)` ⇒ `409 stale_ack` with attempt 2 in flight.
- Transactionality: inject a commit failure mid-settle (#6 seam) — no row mutated, no event row,
  no metric increment observable after reopen.
- Batch behaviour: mixed outcomes, mixed consumers, duplicate tokens, request-order results,
  over-limit rejection.
- Orphan row (message deleted underneath): settle still succeeds; the event carries a null msg id
  and is flagged.
- `assertInvariants(t, db)` (the shared helper from #9, extended with I7's history arm) runs after
  every store test and is the same helper `messq verify` (#8) and #13 call.

**Deterministic timing (`testing/synctest`)**
- The whole nak → backoff → visibility chain across the default `[1s, 5s, 30s, 2m, 10m]` schedule
  in microseconds of wall clock, including the last-entry-repeat.
- The extend heartbeat pattern at `ack_wait/2` up to the cap (the #22 `Worker` loop's arithmetic,
  tested here before the client exists).
- The `--event-repeat-interval` limiter.

**Concurrency**
- 32 goroutines settling the same 100 messages with random verbs: exactly one `ok` per
  `(seq, attempt)`, everything else `stale`/`stale_ack`, `-race` clean, invariants green.

**Crash (#8's harness)**
- Named fault points `store.settle.after_commit` and `store.settle.before_reply` (the
  `MESSQ_FAULTS` grammar from #8, expanded in #32): SIGKILL, restart, client retries the ack ⇒
  `stale`, and the ledger oracle records **OK**; the message is never redelivered.
- Fault point before commit: SIGKILL ⇒ ledger **UNKNOWN**; after restart the message is
  redeliverable with `attempts` unchanged (T9) and its next delivery is `attempt+1`.
- `messq verify` and `PRAGMA integrity_check` clean after every kill.

**Golden**
- The event fixture for the flagship `messq trace` output (§8): `publish → deliver(1) → timeout →
  deliver(2) → ack.stale → nak → deliver(3) → ack`. This issue produces the events; #20 renders
  them. Asserting the exact sequence, order and field set here means #20's byte-for-byte golden has
  a stable input. (The `timeout` step is stubbed via a direct row release until #11 lands.)
- Sentinel coverage: every settle outcome maps to a distinct sentinel from `errs.All()`, checked by
  the exhaustiveness test #3 installed.

**Benchmarks**
- `BenchmarkParseToken` — must be 0 allocs/op.
- `BenchmarkSettle/{ack,nak,extend}/batch={1,16,256}` through the writer — settle cost must be
  dominated by the shared group commit, not by per-token work; this is the number the §12 e2e
  round-trip gate depends on.

**Not tested here:** timeout expiry and the sweeper's arm of the schedule (#11), the DLQ copy and
provenance headers (#12), reference-model equivalence (#13), HTTP status/envelope mapping (#14),
authorization (#16), the `Worker` heartbeat as shipped (#22), CLI rendering and exit codes (#24).
