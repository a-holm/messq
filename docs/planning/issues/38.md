## Context

PLAN.md makes exactly one ordering promise beyond "claimed in ascending `seq`", and it is deferred
to phase 2 (§6):

> `ordered=subject` (phase 2) gives per-subject serial processing at the documented cost of
> head-of-line blocking.

This issue ships it. It is the ordering guarantee people actually want — *per entity*, not global —
and the one a single-node broker can honestly give: put the entity id in the subject
(`orders.acme.4711`) and messq will not hand out message *n+1* for that subject until message *n*
is resolved. No partitions, no consumer groups, no rebalancing protocol (all permanent non-goals,
§1.4).

The whole feature is **one extra predicate in the claim step, plus the reporting that makes its cost
visible**. Nothing else moves: top-up, the cursor rule, flow control (#9), the sweeper and backoff
(#11), dead-lettering (#12), tokens and fencing (#10), attempt counting (D6) are all untouched. If
this issue ends up changing any of them, the design is wrong.

The second half of the title is the part that is easy to skip and must not be: **head-of-line
blocking is displayed, never hidden** (D15's wording). An ordered consumer that stalls behind one
poison message looks exactly like a healthy idle consumer unless the daemon says otherwise, and a
queue whose differentiator is *answerability* (§1.1) cannot ship a feature whose failure mode is
"nothing happens and nobody knows why". So the blocked set is a first-class read: in
`consumer info`, in the pending listing, in a metric, in an alert rule, and — because a display can
lie — compared against the reference model in the property suite (#13).

Governing PLAN.md material:

- **D15** — phase 2 is strictly demand-ordered; *"ordered-by-subject consumers (with head-of-line
  blocking displayed, not hidden)"*.
- **§6 Delivery semantics** — the promise above, plus the framing that processing order is not
  guaranteed while multiple messages are in flight.
- **§5.1 T2** (fetch claim) — the only transition whose guard this issue changes; **§5.2** — the
  invariant register, which gains I13.
- **§4.2** — `consumers.ordered INTEGER NOT NULL DEFAULT 0` (*"phase 2: per-subject serial
  delivery"*) and `deliveries.subject` (*"denormalized for ordered mode (phase 2)"*). Schema v1
  already reserved both; this issue is what makes them mean something.
- **§9.2 / §9.4** — the closed event vocabulary (so this issue adds no event *name*) and the
  cardinality rule (so no metric is ever labelled by subject).
- **§14 M9** — *"Each feature ships with a new invariant, events, metrics, docs — or it does not
  ship."* That sentence is the acceptance criteria list below, in one line.

Sibling issues have already reserved the seams: #9 §8 says *"#38 inserts `ordered_hol`"* into the
`blocked_by` precedence and rejects `ordered: true` with `unsupported` naming this issue; #22 defers
*"ordered-by-subject consumption ergonomics → #38"*; #25 declares a placeholder cap
(*"`ordered=1` consumers (#38): concurrency capped to 1"*) that this issue replaces with the correct
rule; #24 already renders unknown `blocked_by` strings verbatim for forward compatibility with
#37–#41; #4 reserved the invariant ID space (I12+) for phase 2.

**This lands after v1.0.0 (#36), so it is additive or it does not ship**: new optional request
fields, new response fields, new values in already-open string enums, one additive index migration.
No wire shape changes, no event renames, no behaviour change for any consumer that does not opt in.

## Scope

### In scope

- **`ordered` as a consumer config value**: `none` (default) | `subject`, on the HTTP API, the CLI,
  `pkg/client`, and the already-present `consumers.ordered` column. Validation, warnings, and the
  semantics of flipping it on a live consumer.
- **The ordered claim predicate** in `internal/queue` (pure) and `internal/store` (SQL): only the
  lowest-seq delivery row per subject is claimable, and only when it is READY and visible.
- **Additive index migration** `deliveries(stream, consumer, subject, seq)` + an upgrade fixture.
- **Ordered-aware derived stats**: `claimable_now`, `ordered_subjects`, `hol_blocked`, and the
  `ordered_hol` value in the `HoldReason` and `blocked_by` enums (#9 §8's reserved slot).
- **The blocked report** — per-subject head, its state, attempt, next-retry time, how many messages
  wait behind it, and the worst-case unblock time — as one read-pool query, surfaced in
  `GET /v1/streams/{s}/consumers/{c}` (inline sample), a new paged
  `GET /v1/streams/{s}/consumers/{c}/blocked`, `state=blocked` in #15's pending listing, and
  `messq consumer info` / `messq pending --by-subject` / a `BLOCKED` column in `messq lag`.
- **Metrics** `messq_hol_blocked`, `messq_hol_blocked_oldest_age_seconds`,
  `messq_ordered_subjects` (labels `stream`,`consumer` only) + a shipped alert rule + a dashboard
  panel.
- **Event detail, no new event names**: `flow.blocked` gains `detail.cause = "ordered_hol"`;
  `msg.dead` and `msg.ack` gain `detail.hol_released` when they unblock a subject.
- **Invariant I13** (a: at most one outstanding delivery per subject per ordered consumer; b: claims
  within a subject are in ascending seq order) in SEMANTICS.md, in `internal/verify` (checkers
  C7/C8, #8's registry), and in `internal/model` + the `rapid` suite with a new `ordered` dimension
  in the generator and new vacuity guards.
- **Client ergonomics**: `client.Worker` detects an ordered consumer, dispatches per-subject
  serially, settles without coalescing delay; `messq sub --exec` replaces #25's cap-to-1 placeholder
  with the real rule and reports blocked subjects.
- **Docs**: SEMANTICS.md section + T2-o + I13, `docs/ordered.md` (when to use it, the poison
  interaction, the ordering gap, the escape hatch, sizing), a `docs/guarantees.md` row naming the
  test, README §6 updated from "(phase 2)" to shipped, `docs/metrics.md` rows, release note on the
  schema bump.
- **Bench** `BenchmarkOrderedClaim` across subject cardinalities, and a published "ordering costs
  N% of fetch throughput" number (§12's honesty rule).

### Out of scope

- **Global / cross-subject ordering** — a permanent non-goal (§1.4); `docs/non-goals.md` gets the
  line so "can it do total order" is a link, not a debate.
- **Ordering keyed by anything other than the message subject** (a header, a body field): post-1.0,
  on demonstrated demand, per D15's demand-ordering rule. No issue is opened speculatively.
- **Any change to top-up, the cursor rule, or flow control** → owned by **#9**; **the sweeper and
  backoff** → **#11**; **dead-lettering** → **#12**; **tokens/fencing** → **#10**.
- **Delayed delivery** (`Messq-Deliver-At`) → **#37**; this issue documents and tests the
  interaction if #37 has landed, and does not depend on it.
- **Per-consumer rate limiting** (`rate_limit` in the same precedence list) → **#39**;
  **per-worker attribution and caps** → **#41**.
- **Redrive/replay ordering repair** — redrive (**#29**) and replay (**#28**) republish at the tail
  with a new seq and therefore *break* per-subject order by construction. This issue documents the
  gap and adds a warning to the redrive path; it does not attempt to reinsert messages in place.
- **A `messq consumer blocked` subcommand** — the blocked view rides on `consumer info` and
  `messq pending --by-subject` rather than growing PLAN §8's command tree.
- **Ordering inside the DLQ stream** beyond "it is an ordinary stream and may have an ordered
  consumer" — `.dlq` order is dead-at order, not origin order.

## Design proposal

> Everything below is a proposed starting point. Three items are marked **decision** because later
> work (the property suite, the docs, and any future ordering key) builds on them and they are
> expensive to reverse.

### 1. Configuration surface and compatibility

**Decision — the API field is a string enum, not a boolean.** `"ordered": "none" | "subject"`. A
boolean forecloses a future ordering key for no gain, and #9 already rejects `ordered: true` with
`unsupported`, so there is no legacy shape to keep. The DB column stays `INTEGER` (0 = none,
1 = subject) exactly as schema v1 reserved it — **no column migration**.

```go
package queue

type OrderMode string // "none" | "subject"   (exhaustive-linted, like DeadPolicy)

const (
    OrderNone    OrderMode = "none"
    OrderSubject OrderMode = "subject"
)

// ConsumerConfig gains one field (#9 §1).
type ConsumerConfig struct {
    // …existing fields…
    Ordered OrderMode // default OrderNone
}
```

| Surface | Shape |
|---|---|
| HTTP create/patch | `{"name":"shipper","ordered":"subject", …}`; unknown value → `400 invalid_argument` listing the enum |
| HTTP consumer info | `"ordered":"subject"` always present (`"none"` for everyone else) |
| CLI | `messq consumer add <s> <c> --ordered subject`, `messq consumer edit <s> <c> --ordered none` |
| `pkg/client` | `ConsumerConfig.Ordered OrderMode` |
| DB | `consumers.ordered` 0/1 (existing column) |

**Flipping it on a live consumer (decision).** `none → subject` is accepted immediately and takes
effect at the next claim; it is never refused, because refusing an operator mid-incident is the one
thing #9 established we do not do. Consequence: rows already in flight may violate the at-rest form
of I13a until they drain. So **I13a is an admission-form invariant** — *no claim creates a second
outstanding delivery for a subject* — with the at-rest form as its consequence except during a
drain, exactly like #9's I5 shrink rule. `verify` reports pre-existing overlap as an **advisory**
naming the consumer and the subjects, not a violation, and the `consumer.update` event's `detail`
carries `{"ordered":"subject","pre_existing_overlap":N}`. `subject → none` is immediate and
unconditionally safe.

**Validation warnings** (via #9's `Warnings` channel — warnings, never errors):

| Condition | Warning |
|---|---|
| `ordered=subject` ∧ `max_deliver=0` | "a poison message will stall its subject forever; set `max_deliver` or expect a permanent stall" — this is the single most dangerous combination in the product and `messq doctor` (#30) flags it too |
| `ordered=subject` ∧ `max_ack_pending=1` | "with `max_ack_pending=1` ordering is already total; `ordered` buys nothing and costs a query" |
| `ordered=subject` ∧ `TimeToDead(c) > stream.max_age_ms` | "a stalled subject can hold its head message past the stream's retention limit; expect `retention.blocked`" |

### 2. The one rule

Definitions, for a consumer *c* with `ordered = subject` and its delivery rows *D(c)*:

- **head(s)** — the row in *D(c)* with subject *s* and the minimum `seq`.
- **claimable(r)** — `r = head(subject(r)) ∧ r.state = READY ∧ r.visible_at ≤ now`.
- **outstanding(s)** — head(s) exists and is INFLIGHT, or is READY with `visible_at > now`
  (in backoff), i.e. head(s) is not claimable now.
- **blocked(s)** — outstanding(s) ∧ at least one row for *s* sits behind the head.

T2 gains an ordered variant in the transition table (SEMANTICS.md; the conformance tests mirror it
1:1):

| # | From | Trigger | Guard | Effect | Event |
|---|---|---|---|---|---|
| T2-o | READY | fetch claim on `ordered=subject` | T2's guard **∧** the row is `head(subject)` | identical to T2 | `msg.deliver` |

That is the entire semantic change. Note what falls out of it for free:

- At most one INFLIGHT row per subject (a non-head is never claimed; a claimed row is the minimum
  and stays the minimum until it is resolved).
- Delivery within a subject is in ascending `seq`, across retries, restarts and crashes.
- A naked or timed-out message waiting out its backoff is still the head, so it **blocks later
  messages on the same subject** — which is what "ordered" has to mean; a design where a nak lets
  the next message through is not ordered, it is ordered-until-something-goes-wrong.
- Different subjects proceed in parallel, bounded only by `max_ack_pending` and the worker's
  concurrency.

**Invariant I13** (new, into the I12+ space #4 reserved; #37 takes I12):

| ID | Statement |
|---|---|
| I13a | For an ordered consumer, no claim creates a second outstanding delivery for a subject; at rest, `count(INFLIGHT rows per (consumer, subject)) ≤ 1`, except while a `none → subject` flip drains (advisory, non-increasing). |
| I13b | For an ordered consumer, every claimed row is the minimum `seq` among that consumer's delivery rows for its subject; therefore, per subject, `msg.deliver` events are in strictly non-decreasing `seq` order within a generation. |

**Delivery order, not processing order (decision, and the honest caveat that goes in the docs).**
messq guarantees at most one *outstanding delivery* per subject. A handler that keeps working after
its lease expires can still overlap with the next attempt for the same subject — that is
at-least-once, not an ordering bug (§6). Processing order additionally requires the worker to stop
when it loses the lease, which is exactly #22's default `OnLeaseLost: CancelHandler` and #25's
child-kill. This sentence goes in `docs/guarantees.md` next to the guarantee, with the named test
that proves the client side does it.

### 3. Claim SQL and the index

#9's candidate selection gets one `NOT EXISTS` clause; the `UPDATE … RETURNING` that follows is
unchanged.

```sql
-- ordered=subject: heads only, claimable now, ascending seq
SELECT d.seq, d.subject, d.attempts, m.size
  FROM deliveries d
  JOIN messages   m ON m.stream = d.stream AND m.seq = d.seq
 WHERE d.stream = :s AND d.consumer = :c
   AND d.state = 0 AND d.visible_at <= :now
   AND NOT EXISTS (SELECT 1 FROM deliveries e
                    WHERE e.stream = d.stream AND e.consumer = d.consumer
                      AND e.subject = d.subject AND e.seq < d.seq)
 ORDER BY d.seq
 LIMIT :batch;
```

The `NOT EXISTS` covers all three blocking cases with one predicate — a lower-seq sibling that is
INFLIGHT, one in backoff, and one that is READY-and-visible but earlier in this same batch (it is
still in the table during the `SELECT`, so the later row is excluded and the earlier one is
claimed). No second pass, no dedup in Go.

**Decision — the guard is written as "no lower-seq sibling", not as "no INFLIGHT sibling".** Under
I13b the two are equivalent, but the min-seq form is *self-correcting*: given a corrupted state (a
seek that left a stale row, a bug in #28), it degrades to delivering the wrong-but-earliest message
rather than to double delivery. Correctness over one index probe.

Migration `000N_deliveries_subject_index.sql` (next free number in #5's forward-only ladder):

```sql
CREATE INDEX IF NOT EXISTS deliveries_subject
  ON deliveries(stream, consumer, subject, seq);
```

`deliveries` holds only unfinished work (D5), bounded by `Σ max_ack_pending`, so the index build is
instantaneous even on a large database and the write amplification is one small index entry per
delivery row. **The ladder bumps the schema version, so a binary older than this release refuses to
open the data dir** (§4.4) — that is the documented behaviour, it is what #34's fixtures test, and
the release note must say it in one sentence: *upgrading enables ordered consumers; downgrading
below vX.Y requires a restore from backup.* Creating the index outside the ladder to dodge the bump
was considered and rejected: two mechanisms for schema state is exactly the "which one won?"
category D8 deleted.

**Cost.** SQLite scans `deliveries_ready` for `(state=0, visible_at ≤ now)` and probes
`deliveries_subject` per candidate — at most `pending ≤ max_ack_pending` probes of a small index,
and in the common case (work flowing, heads claimable) the `LIMIT :batch` stops it after `batch`
probes. `BenchmarkOrderedClaim` (§13) measures it at subject cardinality 1 / 10 / 1 000 / 100 000
with `pending = 1000`; the number is published, not assumed.

**Rejected: an in-memory per-subject head map.** Subject cardinality is unbounded, so any in-memory
index is an unbounded collection (I11), and it would be a second source of truth that can drift
across restart, seek, purge and retention — the mistake §9.4's scrape-time collector exists to
avoid. Every per-subject fact in this issue is derived from `deliveries` by SQL, every time.

### 4. Derived stats and the blocked report

`claimable_now` replaces `ready_now` as the input to `blocked_by` for ordered consumers (`ready_now`
keeps its meaning and is still reported — a row that is READY and visible but not a head is *ready*
and *not claimable*, and saying so is the point of the feature):

```sql
-- claimable_now, ordered variant: same NOT EXISTS as the claim
SELECT COUNT(*) FROM deliveries d
 WHERE d.stream = :s AND d.consumer = :c AND d.state = 0 AND d.visible_at <= :now
   AND NOT EXISTS (SELECT 1 FROM deliveries e
                    WHERE e.stream=d.stream AND e.consumer=d.consumer
                      AND e.subject=d.subject AND e.seq < d.seq);
```

The blocked report, one read-pool query over a set bounded by `max_ack_pending`:

```sql
WITH heads AS (
  SELECT subject, MIN(seq) AS seq, COUNT(*) - 1 AS behind
    FROM deliveries
   WHERE stream = :s AND consumer = :c
   GROUP BY subject
)
SELECT h.subject, h.seq, h.behind, d.state, d.attempts, d.visible_at, d.delivered_at,
       d.last_reason, m.id, m.published_at
  FROM heads h
  JOIN deliveries d ON d.stream = :s AND d.consumer = :c AND d.seq = h.seq
  JOIN messages   m ON m.stream = :s AND m.seq = h.seq
 WHERE h.behind > 0 AND (d.state = 1 OR d.visible_at > :now)
 ORDER BY m.published_at ASC
 LIMIT :k OFFSET :after;
```

Derived per row: `next_retry_at = visible_at` (for `state = scheduled`), `deadline = visible_at`
(for `state = inflight`), `attempt/of`, and `unblocks_by = delivered_at_first + TimeToDead(c)`
(#11's arithmetic) — the worst-case moment the subject frees itself by dead-lettering. Aggregates:
`ordered_subjects = COUNT(*) FROM heads`, `hol_blocked = COUNT(*) FROM heads WHERE blocked`,
`hol_blocked_oldest_age_ms = now − MIN(published_at of the rows waiting behind blocked heads)` —
i.e. how long the oldest message delayed *by ordering specifically* has been waiting.

**`blocked_by` precedence** (#9 §8's list, with this issue's and #39's slots filled):
`paused → flow_control → rate_limit (#39) → ordered_hol → backoff → catching_up → empty → none`.
`ordered_hol` wins over `backoff` only when `hol_blocked > 0` — if every head is in backoff with
nothing behind it, ordering is costing nothing and the honest answer is `backoff`.

- `blocked` mirrors #15's pending listing conventions exactly: `limit` capped by
  `--blocked-max-limit`, `after` cursor pagination, `older_than_ms` filter, `ack_token` present only
  for `inflight` rows (#15's rule, same reasoning), `consume` or `admin` role (#16).
- `consumer info` gains `ordered`, `ordered_subjects`, `blocked_subjects`,
  `hol_blocked_oldest_age_ms` and an inline `blocked[]` sample of at most
  `--ordered-blocked-sample` (10) items — the full list is the paged endpoint.
- #15's pending listing gains `state:"blocked"` for a row that is READY-and-visible but not its
  subject's head, plus `blocked_by_seq`. Calling such a row `ready` would be a lie told by the one
  surface an operator checks first.
- The `hold` and `blocked_by` enums gain `ordered_hol`. SEMANTICS.md states the compatibility rule
  that #24 already implements: **clients MUST treat an unknown hold/blocked_by value as "no work
  right now" and render it verbatim.**
- `fetch` computes `ordered_subjects`/`blocked_subjects` **only** when the consumer is ordered *and*
  the batch came back short — when work is flowing, the extra query never runs.

### 7. Metrics, alert, events

| Metric | Type | Labels | Source |
|---|---|---|---|
| `messq_ordered_subjects` | gauge | `stream`,`consumer` | collector — distinct subjects in the pending set; the parallelism actually available |
| `messq_hol_blocked` | gauge | `stream`,`consumer` | collector — subjects with ≥1 message waiting behind a non-claimable head |
| `messq_hol_blocked_oldest_age_seconds` | gauge | `stream`,`consumer` | collector — the alertable SLI for this feature |

All three ride #21's scrape-time `Collector` (heavy tier, 5 s cache), are zero-valued for
non-ordered consumers, and are **never labelled by subject** (§9.4 is not negotiable; a golden
`/metrics` label-set test enforces it).

```yaml
- alert: MessqOrderedHeadOfLineStall
  expr: messq_hol_blocked_oldest_age_seconds > 900
  for: 10m
  annotations:
    summary: "{{$labels.stream}}/{{$labels.consumer}}: messages delayed >15m by subject ordering"
    runbook: "messq consumer info {{$labels.stream}} {{$labels.consumer}}"
```

**No new event names.** §9.2 is a closed vocabulary and operators build alerts on it, so:

- `flow.blocked` gains `detail.cause ∈ {"max_ack_pending","ordered_hol"}` (the `cause` pattern
  already used by `messq_redelivered_total{cause}`), with the `subject` column set to the oldest
  blocked subject and `detail.subjects` / `detail.behind` counts. Rate-limited by #9's existing
  `--flow-blocked-interval`, keyed `(consumer, cause)` so one cause cannot mask the other.
- `msg.dead` and `msg.ack` gain `detail.hol_released: N` when the resolved row was a blocked head —
  so `messq trace` shows *"…and this unblocked 12 messages on orders.acme.4711"*, which is the
  sentence an operator is actually looking for.
- #19's event-detail schema registry and #4's docsguard get the new keys and enum values; the log
  schema doc is versioned like an API, so this is a documented additive change.

### 8. Client and `--exec`

**#25's `ordered ⇒ concurrency 1` placeholder is wrong and is replaced here (decision).** The server
never hands one worker two messages of the same subject, so N children across N *distinct* subjects
is safe and is the entire point of per-subject rather than global ordering. The real rules:

- `--concurrency` keeps its normal clamp (`min(N, max_ack_pending)`); no ordered-specific cap.
- `client.Worker` learns `Ordered` from the consumer info call it already makes and then:
  - dispatches **serially per subject** — a no-op under the current server guarantee, and defence in
    depth if a batch ever contains two rows of one subject (a bug, a future relaxation, or a
    non-ordered consumer whose *user* wants ordering);
  - defaults `AckWindow` to `0` for ordered consumers: coalescing settles for 5 ms adds 5 ms to
    every subject's serial chain, and a delayed ack extends a head's lease hold for no benefit;
  - emits a `WorkerEvent` when a fetch returns `hold: "ordered_hol"` so a worker's own logs explain
    an idle-looking loop.
- `messq sub --exec` prints, once: `consumer "shipper" is ordered by subject — at most one message
  per subject in flight; running 4 children across distinct subjects`, and, rate-limited, `waiting:
  3 of 9 subjects blocked (messq pending orders shipper --by-subject)`.

### 9. Model, property suite, and `verify`

- `internal/model`: `ConsumerCfg.Ordered`, and ~6 naive lines in `Fetch` — group rows by subject,
  take the min seq, claim it if READY and visible. Naive on purpose; it must be obviously the spec.
- The `rapid` generator (#13 §6) gains an **ordered dimension**: `create_consumer` draws
  `ordered ∈ {none, subject}` weighted 70/30, and `update_consumer` sometimes flips it mid-run
  (exercising the drain advisory). #13's alphabet is already small (6 subjects, 4 consumers), so
  subject collisions are frequent by construction — no new generator tuning needed.
- The invariant hook gains I13a/I13b. **The blocked report is part of observational equivalence**:
  the SUT's blocked report is compared field-for-field against the model's recomputation after every
  action. That is what turns "blocked-subject display matches reality" from a claim into a test.
- **Vacuity guards** (#13 §9) — a run fails if it never observed: a fetch cut short by ordering; a
  subject with ≥2 rows waiting behind a head in backoff; a DEAD head that released ≥1 waiter; a
  `none → subject` flip while rows were in flight.
- **Sabotage corpus** (#13 §10) — three new entries, each must be caught within the PR budget:
  (a) drop the `NOT EXISTS` from the claim; (b) `MAX(seq)` instead of `MIN(seq)` for the head;
  (c) the blocked report counts an INFLIGHT head with nothing behind it as blocked.
- `internal/verify` (#8's registry), reused verbatim as `rapid` hooks:

```sql
-- C7  two outstanding deliveries for one subject on an ordered consumer
SELECT d.stream, d.consumer, d.subject, COUNT(*) AS n
  FROM deliveries d JOIN consumers c ON c.stream = d.stream AND c.name = d.consumer
 WHERE c.ordered = 1 AND d.state = 1
 GROUP BY d.stream, d.consumer, d.subject HAVING n > 1 LIMIT 100;

-- C8  an in-flight row that is not its subject's head
SELECT d.stream, d.consumer, d.subject, d.seq
  FROM deliveries d JOIN consumers c ON c.stream = d.stream AND c.name = d.consumer
 WHERE c.ordered = 1 AND d.state = 1
   AND EXISTS (SELECT 1 FROM deliveries e
                WHERE e.stream = d.stream AND e.consumer = d.consumer
                  AND e.subject = d.subject AND e.seq < d.seq) LIMIT 100;
```

C7/C8 report **advisory** (not violation) for a consumer whose `ordered` flipped while rows were in
flight, until the overlap count reaches zero — the #9 C5 precedent, same wording, same
non-increasing assertion.

### 11. Edge cases, decided

| Case | Handling |
|---|---|
| One subject's backlog fills `max_ack_pending` | Other subjects starve: the cursor is FIFO by seq and admission is not per-subject. **No per-subject admission cap** — declining a match pins the cursor (#9 §4), which would convert per-subject blocking into whole-consumer blocking. Documented in `docs/ordered.md`; the mitigations are a larger `max_ack_pending`, `term`, or a non-ordered consumer |
| Poison head | Stalls its subject for `TimeToDead(c)` (default ≈ 5 min 6 s), then dead-letters and the subject unblocks **in the same transaction** as the DLQ copy (#12). The skipped message is an **ordering gap**: later messages of that subject are delivered without it. Stated in `docs/ordered.md` and `docs/guarantees.md`, not buried |
| Need to unblock now | `messq term <token> --reason "…"` — immediate DEAD, subject free, `msg.term`+`msg.dead` with `hol_released`. The documented escape hatch, printed by `consumer info` |
| `max_deliver = 0` + ordered | Permanent stall is possible. Warned at create, flagged by `doctor`, and the only combination `docs/ordered.md` tells you not to use |
| Long `extend` loop on a head | Subject stalls up to `--max-ack-wait` (1 h). T7's cap is the guard; the head shows `state:inflight` with a growing deadline |
| `nak --delay 1h` on a head | Honoured; the operator asked for it. Displayed as `next_retry_at`, and it is the `unblocks_by` |
| Subject cardinality of 1 M | Costs nothing: every per-subject query groups over the pending set (≤ `max_ack_pending`), never over the stream or over subject space. No in-memory per-subject state exists (I11) |
| Wildcard filters | The ordering key is the **exact message subject string**, never the filter pattern. `orders.eu.created` and `orders.us.created` are two subjects and run in parallel |
| Flip `none → subject` with overlap in flight | Accepted; admission-form I13a; `verify` advisory until drained; recorded in `consumer.update` detail |
| Two consumers, one ordered one not | Fully independent — delivery state is per `(consumer, seq)` (§5) |
| Ordered consumer on a `.dlq` stream | Allowed. DLQ messages keep the original subject (#12), so per-subject order *within the DLQ* is dead-at order, not origin order. Documented |
| Redrive (#29) / replay (#28) | Republish at the tail with a new seq: the redriven message arrives **after** newer messages of its subject. An unavoidable ordering break; `messq dlq redrive` warns when the origin stream has an ordered consumer, and `docs/ordered.md` explains it |
| Purge removes a head | The next row becomes the head automatically — the rule is `MIN(seq)`, not a stored pointer. No bookkeeping, no repair path |
| `seek` (#28) | Bumps `generation`, drops delivery rows; ordering simply restarts from the new cursor |
| Head's message row is missing (a purge that forgot to drop rows — C2) | Inherits #9 §6: the entry is omitted from the response, logged at ERROR, the row times out and eventually dead-letters, so the subject unblocks after `TimeToDead` rather than never. A wedge is never the failure mode |
| Retention vs. a stalled subject | The head keeps its message alive past `max_age`; `retention.blocked` fires as designed and `doctor` correlates it with `hol_blocked`. This is the honest interaction, and the third create-time warning exists for it |
| Long-poll wake (#14) on a blocked subject | A publish to a blocked subject wakes the parked fetch, which finds nothing claimable and re-parks **without resetting its deadline** (so a hot blocked subject cannot starve the waiter or spin it). Measured by `BenchmarkOrderedWakeStorm`; if it ever matters, the fix is wake filtering, not a timer |
| Delayed delivery (#37) on a head | The delay blocks the subject for its duration — delayed delivery working as asked. If #37 has landed, a joint test asserts exactly that; this issue does not depend on it |
| Rate limiting (#39) | `rate_limit` outranks `ordered_hol` in the precedence list; the two gauges are independent |
| Store latched read-only (#6) | `fetch` → `503 read_only` (a claim is a write); `consumer info` and the blocked listing keep working on the read pool. Reading the evidence must survive the failure |
| Clock jump | `visible_at` comparisons use #4's derived monotonic clock, unchanged by this issue; covered by #32's existing scenario with an ordered consumer added |

## Acceptance criteria

- [ ] A consumer can be created and edited with `ordered: "subject"` over HTTP, the CLI and
      `pkg/client`; the value round-trips through `consumers.ordered` with **no column migration**;
      an unknown value returns `400 invalid_argument` listing the enum; `ordered: true` still
      returns the pre-existing error rather than silently meaning something.
- [ ] Default behaviour is unchanged: every existing test, golden, and testscript passes untouched,
      and a consumer without `ordered` reports `"ordered":"none"` and takes no extra query on the
      fetch path.
- [ ] For an ordered consumer, a fetch never returns two messages with the same subject, and never
      returns a message whose subject has an unresolved lower-seq delivery row — asserted over
      randomised loads with a small subject alphabet.
- [ ] Within a subject, `msg.deliver` events are in non-decreasing `seq` order across nak, timeout,
      restart and redelivery (I13b), verified from the events table alone.
- [ ] A naked head blocks later messages of its subject for the whole backoff, and the *other*
      subjects of the same consumer keep flowing during it.
- [ ] A poison head dead-letters after exactly `max_deliver` attempts and the subject is claimable
      in the very next fetch after that commit; `msg.dead` carries `hol_released` equal to the
      number of rows that were waiting.
- [ ] `messq term` on a blocked head unblocks the subject immediately (same transaction), and
      `messq trace` on the terminated message shows the term, the dead-letter and the release.
- [ ] `consumer info` reports `ordered`, `ordered_subjects`, `blocked_subjects`,
      `hol_blocked_oldest_age_ms` and a blocked sample whose `subject`, `seq`, `id`, `state`,
      `attempt/of`, next-retry/deadline, `behind` and `unblocks_by` match a full recomputation from
      the tables under a seeded poison message.
- [ ] `GET …/consumers/{c}/blocked` pages with `limit`/`after`/`older_than_ms`, caps `limit` at
      `--blocked-max-limit`, returns `ack_token` only for `inflight` heads, and requires
      `consume`/`admin`.
- [ ] A short fetch on an ordered consumer returns `hold: "ordered_hol"` with `blocked_subjects`
      when at least one subject has messages waiting; it returns `backoff` (not `ordered_hol`) when
      heads are in backoff with nothing behind them.
- [ ] #15's pending listing reports `state:"blocked"` with `blocked_by_seq` for rows behind a head,
      and never calls such a row `ready`.
- [ ] `messq_hol_blocked`, `messq_hol_blocked_oldest_age_seconds` and `messq_ordered_subjects` are
      exported with `stream`,`consumer` labels only; the `/metrics` golden label-set test proves no
      subject label anywhere; `promtool check rules` passes with the new alert; the dashboard's
      metric-name anti-rot test passes.
- [ ] `flow.blocked` carries `detail.cause="ordered_hol"` (rate-limited per consumer *per cause*),
      the event vocabulary gains **no new name**, and #19's detail-schema registry and #4's
      docsguard are updated in the same PR.
- [ ] Flipping `none → subject` with overlapping in-flight rows is accepted, records
      `pre_existing_overlap` in `consumer.update`, produces a `verify` **advisory** whose count is
      non-increasing until zero, and never a violation; flipping back is immediate.
- [ ] `verify` checkers C7 and C8 are registered, report zero violations across the suite, and each
      reports its seeded violation when deliberately introduced.
- [ ] The `rapid` suite runs with `ordered` in the generator, checks I13a/I13b plus blocked-report
      equivalence after every action, passes the PR budget (`-rapid.checks=200`) and the nightly
      long run, satisfies the four new vacuity guards, and catches all three sabotages.
- [ ] `client.Worker` at concurrency 8 against an ordered consumer never runs two handlers for one
      subject, settles without coalescing delay, and surfaces `ordered_hol`; `messq sub --exec` at
      `--concurrency 4` runs 4 children across distinct subjects (no cap-to-1) and prints the
      ordered note once.
- [ ] Migration `000N` applies to every committed golden data dir (#34), the resulting dir passes
      `verify --deep`, and an older binary refuses the newer dir with the documented instruction.
- [ ] SEMANTICS.md gains the ordered section, T2-o and I13a/I13b; `docs/guarantees.md` gains a row
      naming the test; `docs/ordered.md` documents the poison interaction, the DLQ ordering gap, the
      redrive/replay gap, the starvation case, the `max_deliver=0` warning and the delivery-vs-
      processing caveat; README §6 no longer says "(phase 2)"; `docs/non-goals.md` states that
      global ordering is not coming.
- [ ] `BenchmarkOrderedClaim` numbers are published in `docs/perf/` with hardware, durability mode
      and subject cardinality, and the ordered-vs-unordered fetch throughput delta is stated as a
      number, not an adjective.
- [ ] Coverage floors hold (`internal/queue` ≥ 90 %, `internal/store` ≥ 85 %); PR CI stays ≤ 10 min.
