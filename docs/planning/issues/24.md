## Context

PLAN.md's §1.2 claim is *"CLI-first: every daemon capability is a subcommand"*, and §8 prints the
command tree that claim cashes out to. Right now the tree is a chassis with almost nothing in it:
#23 built the cobra root, the persistent flags, the three-mode output renderer, the teaching-error
type and the exit-code contract; #22 built `pkg/client`; #14/#15 exposed the whole HTTP surface.
**Nobody can drive any of it from a terminal.** An operator with a stuck queue still has to write
`curl | jq`.

This issue implements the working command surface — the commands an operator actually types during
an incident and a developer types on their first day:

- **Management, noun-verb:** `messq stream add|ls|info|edit|rm|purge`,
  `messq consumer add|ls|info|edit|rm|pause|resume`.
- **The hot path, one word deep** (§8: *"the six things you do while firefighting are one word
  deep"*): `pub`, `sub`, `peek`, `pending`, `lag`.
- **Manual transitions, for symmetry with the daemon:** `ack`, `nak`, `term`, `extend` by token —
  *anything the daemon can do to a message, a human can do by hand.*

It is the load-bearing issue of M6: #25 (`sub --exec`), #26 (quickstart, completions, testscript),
#28 (seek/replay), #29 (DLQ ops), #30 (backup/doctor) and #31 (bench) all attach to the tree and the
conventions established here.

Governing PLAN.md material:

- **§8 CLI design** — the command list and signatures (frozen here), and the four rules this issue
  is judged by: human output on a TTY / machine output otherwise and **never a third mode**; data to
  stdout, narration to stderr; **every inspect command ends with the next useful command**; every
  destructive command has `--dry-run` and confirmation by name.
- **§7 API / protocol** — every command here is a rendering of an endpoint. The CLI invents no
  state, no computation the daemon does not already do, and no error text (§5.3 of plan-04, adopted
  by #23: *a fix to an error message ships in the daemon and improves every client, including
  `curl` users*).
- **D9 (cobra)** — `RunE` everywhere, persistent flags, `ValidArgsFunction` hooks left for #26's
  dynamic completion, `Long` + `Example` on every command (#23's DX lint enforces it).
- **D8** — flags + `MESSQ_*` env only; no config file, no viper.
- **D14** — the CLI consumes `pkg/client`, *which is what guarantees the client is real*. No command
  in `internal/cli` may build an HTTP request.
- **D7 / §5.1 T3–T7** — the ack family operates on fenced tokens `<stream>/<consumer>/<seq>/<attempt>/<generation>`,
  human-readable on purpose. `stale_ack` is a first-class, alertable outcome and the CLI must not
  paper over it.
- **§5.2 I5 / I11** — every listing is bounded; the pending set is `≤ max_ack_pending` by
  construction; every client-side loop has a documented bound.

Three properties this issue owns:

1. **Looking is free and safe.** `peek`, `pending`, `lag`, `*/info`, `*/ls` never mutate anything —
   not delivery state, not cursors, not attempt counters. #15 proved that server-side; this issue
   proves that no CLI path smuggles a mutation in (e.g. by "conveniently" fetching to show a
   message).
2. **The CLI teaches its own command tree at the moment of need.** Every inspect command ends with
   the next useful command, and those hints are *generated from a registry that is tested to
   resolve* — a hint naming a command that does not exist yet is worse than no hint.
3. **A human can finish any message by hand.** `messq pending … --tokens | xargs messq term` is the
   escape hatch that makes the whole ack model operable without writing a client.

## Design proposal

> A starting point, not a mandate — except the six items marked **_decision_**, which get expensive
> after #26 freezes goldens and #28/#29/#30/#31 attach to these conventions.

### 1. The tree, its data sources, and its exit codes

Every command is a rendering of one or two API calls. Nothing here computes queue state.

| Command | `pkg/client` call → endpoint | Non-zero exits |
|---|---|---|
| `stream add <name>` | `CreateStream` → `POST /v1/streams` | 4 exists-with-different-config |
| `stream ls` | `ListStreams` → `GET /v1/streams?stats=1` | 5 none |
| `stream info <s>` | `GetStream` → `GET /v1/streams/{s}` | 3 |
| `stream edit <s>` | `PatchStream` → `PATCH /v1/streams/{s}` | 3, 4 `would_lose_data` |
| `stream rm <s>` | `DeleteStream` → `DELETE …?confirm=` | 2 no confirm, 3, 4 |
| `stream purge <s>` | `PurgeStream` → `POST …/purge[?dry_run=1]` | 2, 3, 4 |
| `consumer add <s> <c>` | `PutConsumer` → `POST …/consumers` | 3 stream, 4 |
| `consumer ls [<s>]` | `ListConsumers` → `GET /v1/consumers[?stream=]` | 5 |
| `consumer info <s> <c>` | `GetConsumer` → `GET …/consumers/{c}` | 3 |
| `consumer edit <s> <c>` | `PatchConsumer` → `PATCH …/consumers/{c}` | 2 no flags, 3, 4 |
| `consumer pause\|resume` | `SetPaused` → `POST …/pause\|resume` | 3 |
| `consumer rm <s> <c>` | `DeleteConsumer` → `DELETE …?confirm=` | 2, 3, 4 |
| `pub <s> <subj>` | `Publish` → `POST …/messages` (`:batch` for `--count`) | 3, 4 `discard=new` full, 1 `507` |
| `sub <s> <c>` | `Fetch` + `Ack` → `…/fetch`, `/v1/ack` | 5 nothing before timeout, 4 stale ack |
| `peek <s>` | `GetMessage`/`ListMessages`/`GetMessageData` | 3, 5 |
| `pending <s> <c>` | `Pending` → `…/consumers/{c}/pending` | 3, 5 |
| `lag` | `ListConsumers` + `GetStream` per DLQ | 5 no consumers |
| `ack\|nak\|term\|extend` | `Settle` → `/v1/ack\|nak\|term\|extend` | 2 bad token, 3 unknown, 4 stale |

Exit codes are #23's contract: `0` ok · `1` error · `2` usage · `3` not found · `4` conflict/stale ·
`5` empty/timeout · `6` daemon unreachable · `7` permission. `6`/`7`/`1` come from the transport and
envelope mapping in #23 and are not re-decided per command.

**_Decision 1: no command in `internal/cli` may construct an HTTP request._** Everything goes
through `pkg/client` (D14). A missing method is a `pkg/client` change; a `net/http` import in
`internal/cli` is a failing lint (`depguard` rule, added to #2's config). This is what keeps the
published client honest — the moment the CLI takes a shortcut, the client stops being the tested
path.

### 2. Command skeleton and the View contract

```go
// internal/cli/pending.go — the shape every command in this issue follows.
func newPendingCmd(env *Env) *cobra.Command {
	var (
		olderThan flagx.Duration // shared value type, §11
		limit     int
		state     string // "", "inflight", "scheduled", "ready"
		tokens    bool
	)
	cmd := &cobra.Command{
		Use:               "pending <stream> <consumer>",
		Short:             "Show what is in flight or waiting to retry",
		Long:              longPending,    // #23's DX lint requires Long + Example
		Example:           examplePending,
		Args:              cobra.ExactArgs(2),
		ValidArgsFunction: env.CompleteStreamConsumer, // seam; #26 implements
		RunE: func(cmd *cobra.Command, args []string) error {
			res, err := env.Client().Pending(cmd.Context(), client.PendingReq{
				Stream: args[0], Consumer: args[1],
				OlderThanMS: olderThan.Millis(), Limit: limit, State: state,
			})
			if err != nil {
				return err // #23 maps envelope → teaching error → exit code
			}
			return env.Render(pendingView{res: res, tokensOnly: tokens, filter: olderThan})
		},
	}
	// … flags …
	return cmd
}
```

```go
// internal/cli/view.go — the contract #23's renderer consumes.
type View interface {
	Table(w io.Writer, o RenderOpts) error // human face; aligned columns, relative times
	JSON() any                             // one frozen document
	NDJSON() []any                         // per-record stream, or nil if the command is scalar
	Hints() []Hint                         // next-command footer (§12)
	ExitCode() int                         // 0, or a documented outcome code (5 empty, 4 stale…)
}
```

Three faces from one value is what makes "never a third mode" enforceable: `TestEveryViewHasThreeFaces`
walks the command tree, runs each command against a recorded fixture server, and fails any command
whose `--output json` is empty, whose table face panics, or whose NDJSON records disagree with the
JSON document's items.

### 3. `messq pub`

```
messq pub <stream> <subject> [-d DATA | -f FILE | -]
     [-H k=v]... [--msg-id KEY] [--trace-id HEX] [--count N] [--batch-size N]
```

```console
$ messq pub orders orders.eu.created -d '{"order":4711}' -H tenant=acme --msg-id order-4711
published  seq=10494  01J8ZQ4K2M9V0X7Y3B5N6C8D1E  14 B  trace=4bf92f35…

  next  messq trace 01J8ZQ4K2M9V0X7Y3B5N6C8D1E
        messq peek orders --seq 10494

$ messq pub orders orders.eu.created -d '{"order":4711}' --msg-id order-4711
duplicate  seq=10494  01J8ZQ4K2M9V0X7Y3B5N6C8D1E  (Messq-Msg-Id "order-4711", published 41s ago)
```

- A duplicate is **exit 0**. Idempotency working as designed is not an error; the word `duplicate`
  and the original seq are the whole report (#7's `duplicate:true`).
- Exactly one body source. `-d`, `-f` and `-` are mutually exclusive; none of them with a
  non-empty stdin pipe prints a usage error rather than silently publishing an empty body.
- `-H k=v` becomes `Messq-Header-k: v`. A key already starting with `Messq-` is exit `2` naming the
  reserved prefix (§5.1) — client-side, before the round trip.
- `--count N` uses `POST …/messages:batch` in chunks of `--batch-size` (256), reports
  `published 1000 messages seq=10494..11493 in 412ms (2427 msg/s)`, and stops at the first chunk
  error reporting exactly how many were stored. It exists for smoke tests and demos; honest
  benchmarking is `messq bench` (#31), and the help text says so.
- `--count > 1` with `--msg-id` is exit `2`: all N copies would dedup into one message. The error
  names the reason and suggests dropping `--msg-id` or looping in the shell.
- A body over `max_msg_size` gets `413`; the teaching error carries `messq stream edit <s>
  --max-msg-size …` from the daemon (#15), not from the CLI.

### 4. `messq sub` (print + settle; `--exec` is #25)

```
messq sub <stream> <consumer> [--auto-ack | --manual] [--count N] [--batch N]
     [--wait 30s] [--timeout 0] [--preview-bytes 80]
```

```console
$ messq sub orders worker --count 2
09:14:02.190  10494  orders.eu.created  attempt 1/5  1.2 KiB  {"order":4711,"total":…  ack
09:14:04.771  10495  orders.eu.created  attempt 2/5  0.9 KiB  {"order":4712,"total":…  ack

2 messages, 2 acked, 0 failed.

$ messq sub orders worker --manual --count 1
09:14:09.002  10496  orders.eu.created  attempt 1/5  1.2 KiB  {"order":4713,…  orders/worker/10496/1/1

1 message left in flight; deadline 09:14:39.002.
  next  messq ack orders/worker/10496/1/1
        messq pending orders worker
```

**_Decision 2: the default is `--auto-ack`, and the ack is sent only after the message has been
written and flushed to stdout ("ack-after-write")._** `sub` with no flags must be useful in the
quickstart (#26), and an ack that precedes the write would lose a message to a full pipe. What
ack-after-write does *not* promise is stated in `Long` and in `messq help scripting` (#26): if the
downstream consumer of the pipe dies after we flush, the message is gone as far as messq is
concerned. Durable pipelines use `--manual` or `--exec` (#25). Half a guarantee stated precisely
beats a guarantee implied.

- `--manual` prints the ack token as the last column and leaves messages in flight. The summary
  line names the deadline, because tokens expire.
- `--wait` is the long-poll `wait_ms` (default 30 s, clamped server-side to `--max-fetch-wait` with
  the effective value echoed — the CLI prints the effective value if it differs from the request).
- `--count N` exits after N messages. Without `--count`, `sub` runs until SIGINT.
- **Exit 5** when `--count` or `--timeout` elapses with zero messages received (the documented
  "empty/timeout" code) — `messq sub jobs w --count 1 --timeout 5s || echo "queue idle"` is a
  scriptable idiom.
- `hold_reason` is surfaced **once per distinct reason**, on stderr, then the loop keeps polling:
  `consumer is paused — messq consumer resume orders worker`, or
  `at max_ack_pending (1000/1000): workers are not acking — messq pending orders worker --older-than 60s`.
  Printing it every poll would drown the terminal; never printing it is the "why is nothing
  happening?" support ticket.
- SIGINT: stop fetching, finish settling what is already printed, print the summary, exit `0`. In
  `--manual`, print the outstanding tokens so nothing is stranded silently. SIGPIPE (`| head -3`)
  exits `0`.
- `--output json` emits one document `{"messages":[…],"acked":N,"failed":N}`; `ndjson` emits one
  object per message as it arrives (that is the streaming face, and it is what `jq` users want).

### 5. `messq peek`

```
messq peek <stream> [--seq N | --id ULID | --last N | --from-seq N] [--subject PAT]
     [--limit N] [--raw] [--headers]
```

```console
$ messq peek orders --last 3
SEQ     ID          SUBJECT            SIZE     AGE     PREVIEW
10496   01J8ZQ4P…   orders.eu.created  1.2 KiB  12s     {"order":4713,"total":19.9…
10495   01J8ZQ4M…   orders.us.created  0.9 KiB  1m41s   {"order":4712,"total":4.10…
10494   01J8ZQ4K…   orders.eu.created  1.2 KiB  2m14s   {"order":4711,"total":88.0…

  next  messq peek orders --seq 10496 --raw | jq .
        messq trace 01J8ZQ4P0000000000000000

$ messq peek orders --seq 10494 --raw > order.json
```

- **Side-effect-free, and the tests say so** (a full store snapshot diff, mirroring #15). `peek`
  never claims, never advances a cursor, never mints a live lease.
- `--raw` requires exactly one selected message (else exit `2`) and writes **only** the payload
  bytes to stdout, via `GET …/messages/{seq}/data` — no headers, no newline, no narration.
- **_Decision 3: `--raw` refuses to write non-printable bytes to a TTY._** Exit `2` with
  `binary payload (1.2 KiB); redirect it or pipe it: messq peek orders --seq 10494 --raw | xxd`.
  `--force-raw` overrides. A wedged terminal at 3 a.m. is a self-inflicted second incident.
- `--headers` adds a detail block (user headers, `Messq-*` provenance on DLQ messages, trace id).
  On a `<stream>.dlq` message the provenance headers are rendered as prose:
  `dead from orders/worker after 5 attempts, cause=max_deliver, last reason "upstream 503"`.
- Range listings render #7's honest partial answer: when the server returns `complete:false`, print
  `scanned to seq N (--limit reached); continue with --from-seq N` on stderr rather than implying
  the list is the whole truth.

### 6. `messq pending`

```
messq pending <stream> <consumer> [--older-than 60s] [--state inflight|scheduled|ready]
     [--limit N] [--tokens]
```

```console
$ messq pending orders worker --older-than 60s
SEQ     ID          SUBJECT            STATE      ATT   DEADLINE    AGE     LAST REASON
10493   01J8ZQ4K…   orders.eu.created  inflight   2/5   in 28s      1m34s   upstream 503
10501   01J8ZQ4M…   orders.eu.created  scheduled  3/5   retry 12s   1m02s   timeout

2 of 37 pending are older than 1m0s; oldest pending 1m34s.

  next  messq trace 01J8ZQ4K2M9V0X7Y3B5N6C8D1E
        messq pending orders worker --older-than 60s --tokens | xargs -r messq term --reason stuck
```

- Deadline-ascending, straight from #15 (*the first row is the next thing to go wrong*).
- `--tokens` prints one ack token per line, nothing else — the machine face for
  `xargs messq ack|nak|term`. Scheduled/ready rows have no live lease and therefore no token; they
  are **omitted** from `--tokens` output and the omitted count goes to stderr. Emitting a token that
  is guaranteed to fence would turn the pipeline into a stale-ack generator.
- Exit `5` when the filtered set is empty (with a `no pending messages older than 1m0s` line), so
  `messq pending … --older-than 15m && alert` works in cron.

### 7. `messq lag` — the incident overview

```
messq lag [--stream S] [--consumer C] [--attention-age 15m] [--attention-dlq 100] [--no-dlq]
```

```console
$ messq lag
STREAM   CONSUMER   FILTER            BACKLOG  INFLIGHT  BACKOFF  OLDEST PENDING  DLQ  STATE
orders   billing    orders.>            1,284    12/256        3           4m12s    2  working
orders   invoices   orders.invoice.>       17      2/32        0           2h07m   41  backoff  (!)
orders   audit-tap  orders.>                0       0/64       0               -    2  idle
jobs     worker     >                      93     64/64        0             38s    0  flow-control (!)

2 consumers need attention

  invoices   oldest pending 2h07m (limit 15m), 41 dead-lettered
    messq pending orders invoices --older-than 15m
    messq peek orders.dlq --last 5 --headers
  worker     at max_ack_pending (64/64) — workers are fetching but not acking
    messq pending jobs worker --older-than 30s
```

**_Decision 4: `lag` is one call plus at most `--lag-max-dlq-lookups` (32) DLQ lookups._** PLAN §8
calls it *the incident overview*; an overview that is an N+1 is slowest exactly when it matters. It
uses `GET /v1/consumers` (#15's cross-stream listing) for every row, then `GET /v1/streams/{s}.dlq`
only for streams that have a DLQ sibling. Past the cap, the DLQ column renders `?` with a stderr
note and `--no-dlq` skips the lookups entirely. Alerting on DLQ depth is #21's gauge, not a CLI
poll, and the help text says so.

- Every number comes from #9's single `ConsumerInfo` query, so `lag`, `consumer info`, `/metrics`
  and the shipped alerts cannot disagree — that identity is a test (`TestLagMatchesConsumerInfo`).
- `BACKLOG` prints `~1,284` when `backlog_exact:false` (a non-literal filter — #9's documented upper
  bound). An approximate number everyone agrees on beats two exact numbers that disagree; hiding the
  approximation would be dishonest.
- `INFLIGHT` is `inflight/max_ack_pending`, so a saturated window is visible without arithmetic.
- `DLQ` is the depth of `<stream>.dlq`, a **stream-level** number repeated on each of that stream's
  rows. Per-consumer attribution requires scanning `Messq-Origin-Consumer` headers and belongs in
  `messq dlq ls --consumer` (#29); the column header footnote says so in `--help`.
- `STATE` is `blocked_by` (#9) rendered: `working` (`none`), `idle` (`empty`), `backoff`,
  `flow-control`, `paused`, `catching-up`. #38/#39 add `ordered-hol`/`rate-limit` to the same map;
  an unknown value renders verbatim rather than blank (forward compatibility).
- `(!)` attention rule: `oldest_pending_age > --attention-age` (15 m, matching PLAN §9.4's SLI
  alert), `blocked_by ∈ {flow_control, paused}`, or DLQ depth `> --attention-dlq`. A DLQ with no
  consumer is always named in the footer (an unread DLQ is a silent data sink — #29's rule, adopted
  early because `lag` is where it is noticed).
- Exit `0` even with attention markers; `lag` reports, `doctor` (#30) judges. Making `lag` exit
  non-zero would break every `messq lag | tee incident.txt` pipeline.

### 8. `ack` / `nak` / `term` / `extend`

```
messq ack   <token>... | -
messq nak   <token>... | -   [--delay 5m] [--reason "…"]
messq term  <token>... | -   [--reason "…"]
messq extend <token>... | -
```

```console
$ messq ack orders/worker/10493/2/1
ack  orders/worker/10493/2/1  attempt 2/5  held 531ms

$ messq ack orders/worker/10493/1/1
stale ack: this token names attempt 1, but orders/worker/10493 is on attempt 2
  the work was probably processed twice — see: messq trace 01J8ZQ4K2M9V0X7Y3B5N6C8D1E
  likely cause: ack_wait (30s) is shorter than your handler
  fix: messq consumer edit orders worker --ack-wait 2m
$ echo $?
4

$ messq pending orders worker --older-than 1h --tokens | messq term - --reason "manual drain"
term  37 tokens: 35 ok, 2 stale
  2 tokens were already resolved (idempotent, no action taken)
$ echo $?
0
```

**_Decision 5: `-` reads tokens from stdin, and the exit code is the worst outcome in the batch._**
Precedence, highest first: `2` malformed token (client-side parse, no request sent) → `4`
`stale_ack` / `wrong_generation` → `3` `unknown` → `0`. The five per-token statuses from #10 render
as: `ok`, `stale` (already resolved — a *success*, prints as such), `stale_ack` (**WARN**, the
duplicate-processing signal), `unknown` (never delivered here — a typo or a purge), `wrong_generation`
(seek/purge fenced it). `stale` and `stale_ack` never share a word in the output; collapsing them
would delete the feature D7 exists for.

- Tokens are parsed with #10's `ParseToken` before any request: a typo costs no round trip and gets
  exit `2` with the grammar printed.
- Batches are chunked at the server's `--max-settle-batch` (1024) and the chunk count is reported at
  `-v`. Chunking is sequential; a failing chunk stops the run and reports exactly how far it got.
- `nak --delay` accepts a duration and overrides the backoff schedule for that attempt (T4);
  `--reason` is capped client-side at `--max-reason-bytes` (4096, #10) with visible truncation.
- `extend` prints the new deadline and `capped` when `--max-ack-wait` clipped it (T7), because a
  silently capped extension is exactly the surprise that produces a mystery timeout.

### 9. `messq stream …`

```
messq stream add <name> --subject PAT... [--retention limits|workqueue]
     [--max-msgs N] [--max-bytes 10GiB] [--max-age 7d] [--max-msg-size 1MiB]
     [--discard old|new] [--dedup-window 2m]
messq stream ls [--stats|--no-stats] [--limit N]
messq stream info <name>
messq stream edit <name> [same limit flags] [--allow-data-loss] [--dry-run]
messq stream rm <name> --confirm <name> [--dry-run] [--yes]
messq stream purge <name> [--up-to-seq N | --keep N] [--subject PAT] --confirm <name>
     [--dry-run] [--yes]
```

```console
$ messq stream info orders
orders   created 2026-09-14T08:00:11Z
  subjects     orders.>
  retention    limits   max-age 7d   max-bytes 10 GiB   max-msgs unlimited   discard old
  messages     1,204,913   (seq 9,204,001..10,408,913)   1.9 GiB
  dedup        2m window
  consumers    billing (backlog 1,284)  invoices (backlog 17)  audit-tap (backlog 0)
  dlq          orders.dlq   43 messages   no consumer  (!)

  next  messq lag --stream orders
        messq peek orders.dlq --last 5 --headers
```

**_Decision 6: `stream ls` requests `?stats=1` by default._** #15 made stats opt-in so the overview
is not the API's most expensive call — but a stream list without message counts is not an answer to
the question people type it for. The cost is bounded by the (clamped) number of streams, `--no-stats`
opts out, and the revisit trigger is explicit: if `BenchmarkStreamList` at 1 000 streams exceeds
~200 ms, the default flips and the columns render `-` with a `--stats` hint.

- `edit` sends only flags the user actually set (`cmd.Flags().Changed`), so an edit never
  resurrects a default. A narrowing change is refused server-side with `would_lose_data`; the CLI
  renders the daemon's message verbatim and maps `--allow-data-loss` → `?allow_data_loss=1`.
  `--dry-run` prints the impact through the **same renderer** as the real run (§8's rule).
- `rm` requires `--confirm <name>` (never `y/n` — typing the name is the safety), and `--yes` when
  stdin is not a TTY. It reports the surviving `<stream>.dlq` as a finding: deleting the thing that
  failed must not delete the evidence of how (#15).
- `purge` renders exact counts from the dry run, and handles #15's `202 Accepted` chunked path:
  print `fenced immediately; deleting 4,120,000 messages in the background`, then poll
  `GET /v1/streams/{s}` `purging.remaining` at 1 s (bounded by `--purge-wait`, default 5 m) with a
  single rewritten progress line on a TTY and one line per poll otherwise. `Ctrl-C` detaches from
  the *poll*, not the purge, and says so.

### 10. `messq consumer …` and the retry horizon

```
messq consumer add <stream> <name> [--filter PAT...] [--ack-wait 30s] [--max-deliver 5]
     [--max-ack-pending 1000] [--backoff 1s,5s,30s,2m,10m] [--dead-policy dlq|drop]
     [--start start|new|seq:N|time:T] [--paused]
messq consumer ls [<stream>]   |   info <stream> <name>   |   edit <stream> <name> [flags]
messq consumer pause|resume <stream> <name>   |   rm <stream> <name> --confirm <name>
```

```console
$ messq consumer add orders invoices --filter 'orders.invoice.>' --ack-wait 2m --max-deliver 5
created consumer orders/invoices
  filters      orders.invoice.>
  ack-wait     2m0s     max-deliver 5     max-ack-pending 1,000     dead-policy dlq
  backoff      1s, 5s, 30s, 2m, 10m  (last value repeats)
  retry horizon 12m36s — a message that keeps failing reaches orders.dlq after 5 attempts,
                about 12m36s (+/- 20% jitter) after its first delivery
  starting at  seq 10494 (new messages only)

  next  messq sub orders invoices --count 1
        messq lag --stream orders
```

- The **retry horizon** is `retry_horizon_ms` from #9/#15 — computed by the daemon, rendered here.
  The CLI must not re-derive it: two implementations of the backoff fold is exactly the sort of
  drift this project exists to prevent.
- Server `findings[]` render as warnings on stderr with the fix command inline, verbatim from the
  daemon (#15's `unbounded_redelivery` and friends). The three the summary calls out:

| Finding | Rendered warning |
|---|---|
| `max_deliver=0` | `max_deliver=0 retries a poison message forever; nothing reaches the DLQ. Alert on messq_dlq_depth or set --max-deliver 5` |
| backoff shorter than `max_deliver` | `backoff has 3 entries for max_deliver=5; the last value (30s) repeats, so attempts 4-5 also wait 30s` |
| `ack_wait` implausibly short | `ack_wait 5s is shorter than the p99 handler time observed for this consumer (8.2s); expect timeouts and stale acks` (present only when the daemon has the data; #30's `doctor` owns the general form) |

- `add` is a **declarative upsert** onto #15's `POST` (omitted fields take documented defaults);
  `edit` is the **sparse** `PATCH` built from `Flags().Changed`, which is why `--max-deliver 0` and
  "did not mention max-deliver" stay distinguishable. `edit` with no flags set is exit `2`.
- A rerun of `add` with an identical config prints `consumer orders/invoices is unchanged` and exits
  `0` (#9's no-churn rule; provisioning scripts must be idempotent and quiet).
- `pause` renders #15's in-flight finding: `3 in-flight messages will still time out (earliest in
  28s) and be redelivered on resume — pausing does not freeze ack_wait deadlines.`
- `info` renders `blocked_by` as prose plus the numbers `lag` shows, and ends with the next command
  for whatever is wrong (`backoff` → `messq pending`, `flow_control` → `messq pending --older-than`,
  `paused` → `messq consumer resume`).

### 11. Shared flag value types (`internal/cli/flagx`)

| Type | Accepts | Notes |
|---|---|---|
| `Duration` | `500ms`, `30s`, `5m`, `2h`, `7d` | Go durations plus `d`; `0` legal where documented; fuzzed |
| `Bytes` | `1024`, `64KiB`, `10GiB`, `1MB` | IEC and SI; rejects negatives; fuzzed |
| `Headers` | repeatable `-H k=v` | Rejects `Messq-` prefix, empty key, control chars, `=`-less values |
| `Patterns` | repeatable `--subject`/`--filter` | Validated by #3's matcher before sending |
| `Backoff` | `1s,5s,30s,2m,10m` | Non-empty, ascending not required, each `> 0` |
| `Position` | `start`, `new`, `seq:N`, `time:RFC3339` | #9's `queue.ParseStartPosition`; #28 reuses it for `--to` |

One parser per concept, shared by every command and fuzz-tested — `--max-age 7d` and `--older-than
7d` cannot disagree.

### 12. The hint registry (§8's next-command rule, mechanised)

```go
type Hint struct {
	Cmd  string // "messq pending orders worker --older-than 15m"
	Why  string // optional one-line reason, rendered only in table mode
}

// hints.go
func hintsForConsumer(c client.ConsumerInfo) []Hint // switch on BlockedBy, DLQ depth, age
func hintsForMessage(m client.Message) []Hint
```

**_Decision 7: every emitted hint must resolve to a command that exists in this binary._**
`TestHintsResolve` renders every command against fixtures covering every branch, extracts each
hinted command line, and asserts cobra can `Find` it and that its flags parse. Without this, M6
ships hints pointing at #29's `messq dlq ls` and every one of them is a lie for three weeks. During
M6 the DLQ hint is `messq peek <stream>.dlq --last 5 --headers`; #29 changes one registry entry and
the test keeps everyone honest.

Hints render in the table face on stdout as the `next` block (identical in shape to #20's `trace`
footer), and in the JSON face as a `next[]` array. They never appear as loose text in JSON mode.
Warnings, findings and progress are stderr, always.

### 14. Edge cases, decided

| Case | Handling |
|---|---|
| `peek`/`pending`/`lag` against a busy daemon | Read-pool only; a store-state snapshot diff in tests proves zero mutations, including no cursor movement |
| `pub` with `-d` and a piped stdin | Exit `2` — ambiguous input is never resolved by precedence |
| `pub -f -` and `pub -` | Identical; both read stdin to EOF as one body |
| `pub` over `max_msg_size`, or to a full `discard=new` stream | Daemon's `413`/`507` teaching error rendered verbatim (including its `stream edit` fix); exit `1` |
| `sub` on a paused consumer | One stderr line naming the resume command, then keep polling; resume just works |
| `sub` at `max_ack_pending` | One stderr line with the `pending --older-than` hint; keep polling |
| `sub --count N` interrupted mid-batch | Settle what was printed, print the summary, exit `0`; `--manual` prints outstanding tokens |
| `sub` and the daemon restarts | `pkg/client` reconnects with jittered backoff (#22); one `reconnecting` line at `-v`, not one per attempt |
| `peek --raw` selecting 0 or >1 messages | Exit `2` naming the selector that would fix it |
| `peek --raw` binary to a TTY | Refused; `--force-raw` or a redirect (Decision 3) |
| `pending --tokens` with scheduled rows | Tokens omitted (no live lease); count of omitted rows on stderr |
| Token typo / wrong field count | Exit `2` client-side with the grammar; no request sent |
| Ack of an already-acked token | `stale` → success, exit `0`, qualified in words as *already resolved* |
| Ack after a seek/purge | `wrong_generation`; exit `4`; hint is `messq consumer info` (the generation moved) |
| Destructive command without `--confirm` | Exit `2` printing the exact command with `--confirm <name>` filled in; a mismatched confirm is the daemon's `confirm_mismatch`, exit `4`; a non-TTY stdin without `--yes` is exit `2` naming `--yes` |
| `stream purge` returning `202` | Poll `purging.remaining` with progress; `Ctrl-C` detaches from the poll and says the purge continues |
| `consumer edit` with no flags | Exit `2` — a no-op PATCH that emits an event is worse than an error |
| `consumer add` rerun, identical | `unchanged`, exit `0`, no event (#9's no-churn rule) |
| Server clamps `limit`/`wait_ms` | Effective value echoed by the API and printed when it differs from the request |
| Unknown `blocked_by`/`status` string from a newer daemon | Rendered verbatim; never blank, never a panic (forward compatibility for #37–#41) |
| Non-UTF-8 or control bytes in a subject, reason, or preview | Escaped with `strconv.Quote` semantics before rendering; a fuzz target asserts no control byte or ANSI escape reaches the terminal |
| Very long stream/consumer names | Columns widen; identifiers are never wrapped or truncated (truncating a name you must type back is hostile) |
| `NO_COLOR` / `TERM=dumb` / not a TTY | Colour off, layout unchanged (goldens stable); output mode switches to JSON per §8 |
| `--output ndjson` on a scalar command (`consumer pause`) | Exactly one JSON line — an NDJSON stream of one, not an error |

## Acceptance criteria

- [ ] Every command in PLAN §8's management, hot-path and manual-transition groups exists with the
      printed signature: `stream add|ls|info|edit|rm|purge`, `consumer add|ls|info|edit|rm|pause|resume`,
      `pub`, `sub`, `peek`, `pending`, `lag`, `ack`, `nak`, `term`, `extend`.
- [ ] No file in `internal/cli` imports `net/http`; every call goes through `pkg/client` (enforced
      by a `depguard` rule in CI, not by review).
- [ ] Every command produces all three faces: `--output table` on a TTY, `json` and `ndjson`
      otherwise — verified by a tree-walking test that runs each command against a fixture server;
      no command has a fourth mode.
- [ ] CLI JSON field names are frozen and golden-tested; a renamed field fails the build.
- [ ] `messq lag` renders the PLAN §8-shaped table (stream, consumer, filter, backlog, inflight/max,
      backoff, oldest pending, DLQ, state), marks attention per the documented rule, and ends with a
      per-consumer footer naming the next command.
- [ ] Every number in `lag` equals the corresponding field of `messq consumer info` and of #21's
      gauge for the same consumer (`TestLagMatchesConsumerInfo`).
- [ ] `lag` issues at most `1 + min(dlq_streams, --lag-max-dlq-lookups)` HTTP requests, asserted by
      a counting transport.
- [ ] `backlog_exact:false` renders as `~N`, never as a bare number.
- [ ] Every inspect command (`peek`, `pending`, `lag`, `stream info`, `consumer info`, `sub`
      summary, `pub` receipt) emits at least one next-command hint, and `TestHintsResolve` proves
      every emitted hint resolves to an existing command with parsing flags.
- [ ] `messq peek`, `pending`, `lag`, `*/ls`, `*/info` mutate nothing: a full store snapshot taken
      before and after a scripted run of all of them is byte-identical (no cursor move, no attempt
      increment, no delivery row change).
- [ ] `messq peek --seq N --raw` writes exactly the published bytes to stdout and nothing else
      (byte-compared against the payload) and refuses binary output to a TTY without `--force-raw`.
- [ ] `messq pending --older-than D --tokens` prints only tokens for `inflight` rows, deadline
      ascending, and `messq pending … --tokens | messq term - --reason x` terminates exactly those
      messages.
- [ ] The ack family: `ok`/`stale`/`stale_ack`/`unknown`/`wrong_generation` each render distinctly,
      `stale` and `stale_ack` never share wording, and the batch exit code is the worst outcome
      (`2 > 4 > 3 > 0`).
- [ ] A malformed ack token exits `2` **without** issuing a request (counting transport) and prints
      the grammar; `messq ack <stale-token>` reproduces the #10 transcript (explanation, likely
      cause, `consumer edit --ack-wait` fix) and exits `4`.
- [ ] `messq sub` default-acks only after the message line is written and flushed; a test with a
      writer that fails mid-write asserts no ack was sent for that message.
- [ ] `messq sub --manual` leaves messages in flight and prints tokens that `messq ack` accepts.
- [ ] `messq sub --count 1 --timeout 5s` against an empty queue exits `5` in bounded fake-clock time
      with an empty `messages` array in JSON mode.
- [ ] `hold_reason` (paused, flow control) is reported once per distinct reason, on stderr, and the
      loop keeps polling.
- [ ] `messq pub --msg-id K` twice prints `duplicate` with the original seq and exits `0`; `--count N`
      with `--msg-id` exits `2` explaining that all copies would dedup.
- [ ] `messq pub -H Messq-Origin-Stream=x` exits `2` naming the reserved prefix, client-side.
- [ ] `messq consumer add` prints the daemon-computed retry horizon and the backoff schedule, and
      renders `max_deliver=0` and short-backoff findings as warnings with fix commands.
- [ ] `messq consumer edit` sends only changed flags: setting `--max-deliver 0` transmits `0`, and
      omitting it transmits nothing (asserted on the request body); no flags exits `2`.
- [ ] `messq consumer add` rerun with an identical config prints `unchanged`, exits `0`, and causes
      no `consumer.update` event.
- [ ] `stream rm`/`purge`/`consumer rm` require `--confirm <name>`, require `--yes` on a non-TTY
      stdin, and their `--dry-run` output is produced by the same renderer as the real run.
- [ ] `stream purge` handles a `202` async purge: progress is reported, `Ctrl-C` detaches from the
      poll only, and the message says the purge continues.
- [ ] `stream info` names a DLQ sibling with its depth and whether it has a consumer.
- [ ] Exit codes for every command match the §1 table; a table-driven test asserts each one against
      a fixture server.
- [ ] Every command has `Long` and `Example` (#23's DX lint) and every `Example` block executes in
      CI without error.
- [ ] `--output json` on any command emits no hints, warnings or progress on stdout.
- [ ] Coverage floors from #2 hold; no `time.Sleep` in tests; no `time.Now()` outside the Clock seam.

## Test plan

Per PLAN §11 / D13: `-race` everywhere, real SQLite files in `t.TempDir()` for integration, no
`time.Sleep` (fake clock + `testing/synctest`), every fixed bug landing with a committed
reproduction artifact.

**Unit — rendering (pure, fixture-driven, no daemon)**
- Golden table output for every command against recorded API fixtures: `lag` (mixed states, an
  approximate backlog, an unread DLQ, a paused consumer), `pending` (inflight + scheduled + empty),
  `peek` (list, single, DLQ provenance headers), `sub` (auto-ack, manual, hold reasons), `pub`
  (created, duplicate, batch), `stream info`, `consumer add` with each finding.
- Golden JSON and NDJSON documents for the same fixtures; field-name freeze test.
- Column layout invariants: long names widen rather than truncate, `NO_COLOR`, a 40-column terminal,
  relative-time formatting boundaries (`59s`/`1m0s`/`2h07m`), thousands separators.
- `blocked_by` → state mapping, including an unknown future value.
- Attention rule truth table (age, flow control, paused, DLQ depth, DLQ without consumer).

**Unit — flags and validation (`flagx`)**
- Duration/bytes/headers/patterns/backoff/position parsing: valid, invalid, boundary, overflow.
- Mutual-exclusion matrix for `pub` body sources and `peek` selectors.
- `Flags().Changed` sparse-PATCH construction, including `--max-deliver 0`.
- Ack-token pre-parse rejection (shares #10's `testdata/tokens/` corpus).

**Unit — command wiring**
- `TestEveryViewHasThreeFaces`, `TestHintsResolve`, `TestExitCodes` (table-driven over the §1 table),
  `TestEveryCommandHasLongAndExample` (extends #23's DX lint to this issue's tree).
- Counting-transport assertions: `lag`'s request budget, "no request on a client-side rejection",
  `pub --count` chunking.

**Property (`pgregory.net/rapid`)**
- Settle exit-code precedence: random mixes of the five per-token statuses across random chunk
  boundaries always yield the documented worst-outcome code, and per-token lines are in request
  order with counts that sum to the batch size.
- `pending --tokens` totality: for random pending sets, the emitted token set equals exactly the
  inflight rows, and every emitted token is accepted by the daemon (no fabricated fence failures).
- Failfiles committed to `testdata/regressions/`.

**Deterministic timing (`testing/synctest`)**
- `sub`'s long-poll loop: `--wait`, `--timeout`, `--count`, reconnect backoff, hold-reason
  once-per-reason suppression, SIGINT drain — all in microseconds of wall clock.
- `stream purge` progress polling against a fixture that reports a shrinking `remaining`.

**Integration — real daemon over a Unix socket (`t.TempDir()` data dir)**
- The incident walk-through, end to end: publish → `lag` shows backlog → `sub --manual` claims →
  deadline passes → `pending` shows it → `term` by token → the message is in `orders.dlq` →
  `peek orders.dlq --headers` shows provenance. One test, the whole product.
- Side-effect-free assertion: full store snapshot before/after all inspect commands.
- `pending --tokens | xargs messq term` as a real pipeline (a shell step in the test).
- Destructive discipline: `rm`/`purge` without `--confirm`, with a mismatched confirm, with
  `--dry-run` then for real, and on a non-TTY without `--yes`.
- Daemon restarted mid-`sub`: reconnect, no duplicate ack, no stranded token.
- Daemon unreachable / socket permissions denied → exits `6` / `7` with actionable messages.

**Fuzz** (60 s/target in CI, corpus committed)
- `flagx` duration/bytes/header parsers.
- The table renderer against arbitrary subjects, reasons and payload previews: never panics, never
  emits a control byte or ANSI escape from data, never breaks column alignment.

**Golden/contract**
- The transcripts printed in this issue's Design proposal are the goldens (`-update` flow), adopted
  by #26 into the testscript suite.
- CLI JSON schema snapshots in `docs/schemas/` asserted against the rendered documents.

**Benchmarks**
- `BenchmarkStreamList` at 100/1 000 streams — the number that decides Decision 6's default.
- `BenchmarkRenderLag` at 1 000 consumers (the incident overview must not itself be slow).

**Not tested here:** HTTP handler behaviour, clamping and dry-run correctness (#14/#15); client
transport and the Worker helper (#22); the renderer, exit-code mapping and error envelope
translation (#23); `--exec` semantics (#25); testscript/quickstart/completions (#26); seek/replay
(#28); DLQ ops (#29).
