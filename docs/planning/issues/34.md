## Context

At the `v1.0.0` tag messq makes a written compatibility promise (`#36`): HTTP API shapes, CLI
`--output json` shapes, the log field schema, the error-code enum — **and the on-disk format**. The
first four already have machinery that makes the promise testable: `#18` froze the wire artifacts,
`#26` froze the CLI faces, `#19`/`#21` froze the log and metric schemas. The on-disk format has
nothing. `#5` built the *gate* — forward-only numbered migrations applied in one transaction,
`meta.schema_version`, `ErrSchemaTooNew`, `ErrMigrationDrift`, `PRAGMA user_version` mirroring — but
nothing has ever driven a **real data directory written by an older binary** through it, because
until now there was no older binary and no older directory.

That is the gap this issue closes, and it closes it in the only way that works: with **frozen
artifacts**. A committed data directory produced by a specific build, which today's binary must open,
migrate, verify and keep serving from. A test that regenerates its own input proves nothing; the
value here is entirely in the fact that nobody can regenerate these files.

PLAN.md governs this directly:

- **§11.8 Upgrade tests** — the whole issue in one sentence: *"committed golden data dirs per
  released schema version; current binary must migrate them, pass `verify --deep`, and keep
  delivering; newer-schema dirs must be refused with instructions."*
- **§4.2 Schema** — the `STRICT` v1 schema, `meta` tracking, *"Migrations are numbered, embedded via
  `go:embed`, forward-only, applied in one transaction, tracked in `meta`."* `#5` copied §4.2
  verbatim into `0001_init.sql` precisely so this issue could pin it forever.
- **§4.4 Crash recovery, step 2** — *"Apply migrations; **refuse to start** if the schema is newer
  than the binary."* Refusal is a feature with a user-facing error, so it gets golden text.
- **§5.2 I10** — *"Folding the events table from the beginning reproduces the persisted state
  (checked by `messq verify --deep`)"* — the strongest single assertion available after a migration,
  and the reason `verify --deep` is the acceptance oracle rather than a hand-written row diff.
- **§14 M8 exit** and **§1.5** — *"Codebase … every guarantee has a named test."* "Your data survives
  the upgrade" is a guarantee. Without this suite it is a hope.

Two migrations already exist beyond `0001` and neither has ever been run against real old data:
`#12`'s `0002_msg_id_lineage.sql` (drops the unique `messages_id` index so the DLQ copy can preserve
the original id — D3) and `#27`'s `0003_stream_stats.sql` (adds `stream_stats` **with a backfill**,
which is the dangerous kind of migration). `#27` already writes tests against *"a fixture dir from
`#34`"*; `#12` already reasons about *"`#34`'s golden data-dir fixtures are generated at 1.0, after
this migration"*. Both are waiting on this corpus.

What it unlocks: `#36` can tag `v1.0.0` with an on-disk compatibility promise that has a CI job
behind it, and every post-1.0 migration has an unambiguous, mechanical definition of done — *add a
fixture, keep every older fixture green*. `#2`'s `upgrade-fixtures` nightly job stops being
`echo "TODO(#34)"`.

## Scope

### In scope

- **`test/upgrade/testdata/datadirs/`** — the frozen fixture corpus: one directory per (producer
  version, schema version), each a real data directory carrying non-trivial state, plus a
  `MANIFEST.json` and an `expect/` bundle of assertions.
- **The fixture generator** (`test/upgrade/cmd/mkfixture`) — deterministic, pinned entropy, pinned
  clock, run **once** per schema version and then never again. `#5` shipped a throwaway seeder; this
  issue gives it its final, reproducible form.
- **The immutability guard** — fixtures are content-hashed in a manifest and in
  `testdata/CORPUS.sha256`; a test fails if a committed fixture's bytes change, and CI fails if the
  suite mutated `testdata/` in place.
- **The migrate-forward suite** — for every fixture: open with the current binary, migrate, and
  assert schema version, preserved identity (`node_id`, `created_at`), preserved rows, preserved
  event history, correct `stream_stats` backfill, `verify --deep` clean.
- **The keeps-delivering suite** — after migration, run a behavioural scenario against the migrated
  directory: reclaimed leases redeliver with `attempts` unchanged, the mid-backoff message stays
  invisible until its `visible_at`, pre-upgrade **ack tokens fence correctly**, a new publish gets the
  next seq, the DLQ message redrives.
- **The refusal gate** — a synthetic newer-schema fixture must be refused by `serve`, `verify`,
  `doctor` and `backup` with the same teaching error, the same exit code, and a byte-identical
  database afterwards; plus the not-a-messq-dir, foreign-database and `user_version`-tamper cases.
- **The downgrade-at-equal-schema rule** — the compatibility table (§9), the `meta` key registry that
  enforces it, and the "unknown event name is a warning, not a violation" decision in `verify`'s I10
  fold.
- **`released.tsv` + `TestEveryReleasedSchemaHasAFixture`** — the ratchet that makes "add a fixture"
  a build failure rather than a code-review reminder.
- **`format` in `messq version --json` and `GET /v1/info`** — the on-disk schema version as a
  reported, frozen number (`#36`'s acceptance criterion depends on this field existing).
- **`docs/OPERATIONS.md#upgrading`** — the four-step operator procedure (check, back up, upgrade,
  verify) and the rollback paragraph, with executable command blocks.
- **CI**: the fast lane inside `go test ./...` (every merge) and the `upgrade-fixtures` nightly lane
  (both durability modes, `cgosqlite` tag, released-binary downgrade check).

### Out of scope

- The migration runner, `meta.schema_version`, `ErrSchemaTooNew`, `ErrMigrationDrift`, the
  `user_version` mirror, permission and flock checks → **#5**. This issue *exercises* that gate; it
  does not reimplement it. Any bug it finds is fixed in `internal/store` under this issue's PR.
- `internal/verify`'s checker registry, `verify --deep`, the I10 fold, `integrity_check` plumbing →
  **#8**. This issue adds no checker except the `unknown_event` classification decision in §9.
- Crash-during-migration as part of the **full** fault matrix, the `messq_fault` build tag and the
  `MESSQ_FAULTS` grammar → **#32**. This issue asserts migration atomicity through a store-level
  error hook, which needs no build tag; `#32` re-runs it through the real fault-point machinery.
- Writing migration `0002`/`0003` themselves → **#12** / **#27**. This issue supplies the fixture
  directories their backfill tests consume.
- `messq backup` / restore semantics and `doctor`'s findings → **#30**; this issue only asserts that
  both refuse a newer schema identically.
- The testscript harness, `scriptenv`, the fake-clock lane, `-update` → **#26**; the upgrade scripts
  are written *into* that harness.
- The wire/CLI/log/metric compatibility artifacts → **#18** / **#26** / **#19** / **#21**.
  **#36** copies `test/contract/testdata/` per released version; that is release engineering, not
  this issue.
- The v1.0 compatibility promise document itself and the release-gate checklist → **#36**; the
  general 1.0 docs set → **#35**. This issue owns exactly one docs section: *Upgrading*.
- Data-directory downgrade **across** a schema version (schema 3 → binary supporting 2) →
  **explicitly not supported, ever** (§9). The documented path is restore-from-backup.
- Any online/rolling upgrade story. messq is single-node (§1.4): upgrade is stop, swap, start.

## Design proposal

> Proposal and starting point, not a mandate. Four things **are** contracts because other issues and
> the 1.0 promise depend on them: the fixture directory layout and `MANIFEST.json` fields (§2), the
> immutability rule (§4), the refusal semantics and exit code (§8), and the downgrade compatibility
> table (§9). Everything else is negotiable at implementation time.

### 1. Where the code lives

```
test/upgrade/
  upgrade_test.go            the table-driven suite: one subtest per fixture
  migrate_test.go            assertion set A (schema, rows, history, backfill)
  deliver_test.go            assertion set B (behaviour after migration)
  refuse_test.go             assertion set C (newer schema, foreign db, tamper)
  downgrade_test.go          the equal-schema compatibility rules (§9)
  corpus.go                  manifest parsing, copy-to-tempdir, sha256 guard
  cmd/mkfixture/main.go      the generator — run once per schema version, never re-run
  testdata/
    CORPUS.sha256            sha256 of every committed fixture file
    released.tsv             version <TAB> schema <TAB> fixture_dir <TAB> tag_date
    datadirs/…               the fixtures (§2)
internal/store/
  meta.go                    metaKeyRegistry (§9) — small addition to #5's file
  schema.go                  SchemaVersion(), MigratesFrom(), exported for version/info
test/script/upgrade.txtar    the operator-facing transcript (#26's inproc lane)
docs/OPERATIONS.md           §11 "Upgrading messq"
```

### 2. The corpus layout

```
test/upgrade/testdata/datadirs/
├── v0.5.0-schema1/           # pre-1.0 dev snapshot, schema 1 (pre-#12)
│   ├── MANIFEST.json
│   ├── messq.db              # checkpointed, clean_shutdown=1, no -wal/-shm
│   └── expect/
│       ├── state.json        # canonical logical dump (see §6)
│       ├── tokens.json       # ack tokens minted before freezing (see §7)
│       └── trace-0000…1E.txt # golden `messq trace` for the mid-backoff message
├── v0.8.0-schema2/           # after #12's messages_id relaxation
├── v0.9.0-schema3-dirty/     # SIGKILLed: messq.db + messq.db-wal, clean_shutdown absent
├── v1.0.0-schema3/           # THE fixture — generated at the release commit by #36's workflow
├── refuse-schema-9999/       # synthetic: meta.schema_version=9999, must be refused
├── refuse-user-version-skew/ # meta says 3, PRAGMA user_version says 4 (tamper signal)
├── refuse-no-meta/           # tables present, meta row absent → not a messq data dir
└── refuse-foreign-db/        # somebody else's SQLite file (a `users` table and nothing else)
```

`MANIFEST.json` — the only machine-readable description of a fixture; everything else is derived:

```json
{
  "producer_version": "v0.9.0",
  "producer_commit":  "9f13c0e4…",
  "schema_version":   3,
  "durability":       "full",
  "clock_base":       "2026-11-20T12:00:00Z",
  "reopen_after_ms":  90000,
  "entropy_seed":     "messq-fixture-v0.9.0",
  "clean_shutdown":   false,
  "files":            {"messq.db": "sha256:…", "messq.db-wal": "sha256:…"},
  "expect": {
    "schema_after":       3,
    "node_id":            "01KA8Q5Z3M7N0P2R4T6V8X0Y2A",
    "created_at_ms":      1795334400000,
    "streams":            {"orders": 14, "orders.dlq": 2, "audit": 3, "jobs": 0},
    "deliveries":         6,
    "events":             57,
    "reclaimed_on_open":  2,
    "verify_deep":        "clean"
  },
  "notes": "generated by test/upgrade/cmd/mkfixture; DO NOT REGENERATE — see testdata/README.md"
}
```

`clock_base` and `reopen_after_ms` are what make time-relative state assertable: the harness starts
the migrated daemon on a fake clock at `clock_base + reopen_after_ms`, so "still in backoff" and
"lease already expired" are facts, not race conditions (§5).

### 3. What "non-trivial state" means

A fixture whose only content is three published messages tests the migration runner and nothing else.
The corpus scenario is fixed and every fixture from schema 1 onward contains all of it (later
fixtures simply have the newer columns):

| # | State | Why it is in the corpus |
|---|---|---|
| S1 | `orders` stream, 14 messages, subjects `orders.>`, 3 distinct subjects | the baseline; `messages_subj` index survives |
| S2 | consumer `workers`: 2 rows **READY** at `visible_at ≤ clock_base` | plain pending work must still be delivered |
| S3 | consumer `workers`: 2 rows **INFLIGHT**, `attempts=1`, `delivered_at` set | T9 reclaim must fire on the upgrade boot with `attempts` untouched (D6/I4) |
| S4 | one row **mid-backoff**: READY, `attempts=3`, `visible_at = clock_base + 300s`, `last_reason="upstream 503"` | the assertion that migration does not reset the backoff schedule |
| S5 | consumer `billing`: `generation=2`, `cursor_seq` moved by a seek, zero delivery rows | fencing state must survive (D7/T10) |
| S6 | consumer `audit-tail`: `paused=1`, narrow filter `orders.created` | config columns round-trip |
| S7 | `orders.dlq` with 2 messages: full provenance headers, **origin `id` and `trace_id` preserved** | D3; and after `0002` the two DLQ rows may legally share an id with their origin |
| S8 | one message with an unexpired `dedup_key`, one whose window has passed | the startup dedup trim must be clock-anchored, not "everything expired" |
| S9 | `events` rows covering **every** §9.2 event name reachable at that version, in commit order | gives the I10 fold real arms to run and pins the event vocabulary at that version |
| S10 | one body with NUL bytes and invalid UTF-8; one 8 KiB body; one 4 KiB `hdr` JSON object | catches any migration that ever text-coerces a BLOB (`STRICT` should, but prove it) |
| S11 | `jobs` stream: `retention=workqueue`, zero messages, one consumer | an empty stream is its own edge case in every backfill |
| S12 | `audit` stream: `max_age_ms=0`, `max_msgs=0` | asserted content that retention must never touch, whatever year the test runs in |

Total on disk after `VACUUM INTO`: well under 128 KiB per fixture. A test asserts each fixture
≤ 256 KiB and the whole corpus ≤ 2 MiB — a repo does not get to accumulate megabytes of binary blobs
by accident.

### 4. The generator, and the rule that it is run once

```
go run ./test/upgrade/cmd/mkfixture \
      --out test/upgrade/testdata/datadirs/v1.0.0-schema3 \
      --clock 2026-11-20T12:00:00Z \
      --entropy-seed messq-fixture-v1.0.0 \
      --producer-version v1.0.0 \
      --dirty=false
```

It builds the scenario through the **real** store and queue packages (never hand-written SQL — a
fixture written by a hand-rolled INSERT tests the INSERT, not the product), then:

1. `wal_checkpoint(TRUNCATE)`, set `clean_shutdown=1`, close — unless `--dirty`, in which case the
   process is `SIGKILL`ed mid-load so `messq.db-wal` survives with committed frames and
   `clean_shutdown` is absent.
2. `VACUUM INTO` a fresh file for the clean variants — compacts and normalises page layout, which is
   what makes byte-stability achievable at all.
3. Write `MANIFEST.json`, `expect/state.json`, `expect/tokens.json`, `expect/trace-*.txt`.
4. Append a row to `released.tsv` and refresh `CORPUS.sha256`.

Determinism levers, all of which already exist: `ids.WithEntropy(r)` (`#3`) fed by
`hkdf`/`chacha8`-style stream keyed on `entropy_seed`; `clock.NewFake(clock_base)` (`#3`) as
`store.Options.Clock`; `store.Options.NewID` for `node_id`; `ReclaimJitter=0`; fixed body bytes.
Running the generator twice at the same commit must produce byte-identical output — a test asserts
this (`TestGeneratorIsDeterministic`, regenerating into `t.TempDir()` and comparing to the committed
fixture **for the current schema version only**).

**The rule, in `testdata/README.md` and in a `//go:generate`-shaped comment:** a committed fixture is
immutable. `CORPUS.sha256` is verified at the start of every run; a mismatch fails with

```
fixture corpus modified: v0.8.0-schema2/messq.db
  a committed fixture is a frozen artifact — regenerating it launders the very
  compatibility break this suite exists to catch.
  if this was deliberate (the fixture was wrong from birth): delete the directory,
  regenerate under a NEW name, and say why in the PR.
```

If byte-stability of SQLite output turns out to be fragile across `modernc.org/sqlite` releases (the
one real risk here), the fallback is to hash a **logical dump** — normalised `sqlite_schema` plus
ordered rows — instead of the file bytes, keeping the immutability rule and losing only the
page-layout assertion. Decide on evidence, record the choice in `testdata/README.md`.

### 5. The harness: two lanes, two classes of assertion

```go
type Fixture struct {
	Dir      string    // path under testdata/datadirs
	Manifest Manifest
}

// Load copies the fixture into t.TempDir() (0700/0600, matching #5's permission checks),
// verifies its sha256s, and returns the copy's path. Tests NEVER touch testdata in place.
func Load(t *testing.T, name string) (dir string, m Manifest)

// Boot opens the copy with the current binary's store, at the fixture's anchored clock.
func Boot(t *testing.T, dir string, m Manifest, opts ...BootOption) *Booted
```

| Lane | How | What it may assert | Runs |
|---|---|---|---|
| `inproc` | daemon constructed in-process on `clock.NewFake(clock_base + reopen_after)` via `#26`'s `scriptenv` | **everything**, including clock-anchored state (backoff still pending, dedup key still live, lease deadlines) | every merge |
| `subproc` | real `messq serve` binary, real clock, `--reclaim-jitter 0 --janitor-interval 0` | **clock-invariant** assertions only: schema version, row identity, `verify --deep`, fencing, refusals, exit codes | every merge (fast subset), nightly (full) |

This split is the single most important design decision in the issue. A fixture frozen in November
2026 and replayed in 2028 has a `visible_at` three years in the past and a `max_age_ms` long since
exceeded; without an anchored clock, half the corpus decays into "everything is visible and retention
ate it". Concretely:

- **Anchored lane** — the fake clock makes S4 (mid-backoff) and S8 (unexpired dedup key) assertable.
  This is why the `inproc` lane is the primary one.
- **Real-clock lane** — the janitor is disabled (`--janitor-interval 0`, a small flag ask on `#27`;
  if it declines, set every fixture stream to `max_age_ms=0`/`max_msgs=0` except the dedicated
  retention case and drop S8's clock-anchored half). Startup dedup trimming *will* clear S8's key
  here; the manifest marks that assertion `clock_sensitive: true` and the lane skips it. Assertions
  are never silently weakened — they are tagged, and a tag is reviewable.

`Booted` exposes `Store`, `Client` (`pkg/client`, per D14 — the CLI's own client, so the test drives
the same path a user does), and `Verify(deep bool) verify.Report`.

### 6. Assertion set A — migrate forward

Per fixture, after `Boot`:

- [A1] `store.SchemaVersion() == manifest.expect.schema_after == len(embedded ladder)`;
  `PRAGMA user_version` mirrors it.
- [A2] `meta.node_id` and `meta.created_at` are **unchanged** from the manifest. An upgrade must not
  give the node a new identity; `messq_build_info` and every log line depend on it.
- [A3] The migration was **one transaction**: with a store-level error hook injected before the last
  statement of the last pending migration, `Open` fails, and a reopen finds the *old*
  `schema_version` with `verify` clean. There is no half-migrated state to reason about (`#5` §7,
  step 1).
- [A4] `expect/state.json` — a canonical logical dump — matches, modulo the fields migrations are
  *supposed* to change:

```json
{
  "streams":   [{"name":"orders","retention":"limits","max_age_ms":0,"…":"…"}],
  "messages":  [{"stream":"orders","seq":10,"id":"01K…","subject":"orders.created",
                 "body_sha256":"…","hdr":{…},"size":41,"trace_id":"4bf9…"}],
  "consumers": [{"stream":"orders","name":"billing","cursor_seq":9,"generation":2,"paused":0}],
  "deliveries":[{"stream":"orders","consumer":"workers","seq":12,"state":0,
                 "attempts":3,"visible_at_rel_ms":300000,"generation":1,
                 "last_reason":"upstream 503"}],
  "events":    {"count":57,"digest":"sha256:…","first_id":1,"last_id":57}
}
```

  `visible_at_rel_ms` is stored **relative to `clock_base`** so the file is readable and the
  assertion is clock-independent. `events.digest` is the sha256 of `(id, event, msg_id, seq,
  attempt)` tuples in `id` order: **migrations never rewrite history**, and a one-line digest says so
  more clearly than 57 rows of JSON.
- [A5] `body` BLOBs are byte-identical, NUL bytes and all (S10).
- [A6] `#12`'s `0002` outcome: index `messages_id` exists and is **not** unique; inserting a second
  row carrying an existing id into a `.dlq` stream succeeds; the origin/DLQ id pair from S7 is intact.
- [A7] `#27`'s `0003` outcome: `stream_stats` exists and, per stream, `msgs`/`bytes` equal a full
  scan of `messages` — the backfill is right for the empty stream (S11), the DLQ, and the stream
  with an 8 KiB body. (This is the assertion `#27`'s own test suite already promises to reuse.)
- [A8] `verify --deep` is clean: every structural check plus I2/I4/I5/I6/I8 and the **I10 event
  fold**. I10 is the load-bearing one — it says the migrated state is exactly what the migrated
  journal implies.
- [A9] The first `server.start` event after the upgrade carries `detail.schema_from` and
  `detail.schema_to`. No new event name is invented (§9.2 is closed).
- [A10] `manifest.expect.reclaimed_on_open` matches `RecoveryReport.Reclaimed`, and for the `-dirty`
  fixture `RecoveryReport.Unclean == true` with a `quick_check` actually executed.
- [A11] Re-opening the already-migrated directory is a no-op: `schema_applied_at` unchanged, zero
  further migrations, `verify` still clean.

### 7. Assertion set B — it keeps delivering

Migration success that leaves an undeliverable queue is a failed upgrade. On the migrated copy, in
the anchored lane:

```
$ messq consumer info orders workers --output table          # after upgrade, clock_base+90s
CONSUMER  BACKLOG  PENDING  INFLIGHT  OLDEST UNACKED  GENERATION
workers         6        5         0  —                        1

$ messq sub orders workers --count 2 --manual --output json
{"seq":10,"attempt":2,"of":5,"ack_token":"orders/workers/10/2/1","…":"…"}
{"seq":11,"attempt":2,"of":5,"ack_token":"orders/workers/11/2/1","…":"…"}
```

- [B1] The two S3 rows come back with `attempts` **2**, not 1 and not reset to 0 (D6/T9/I4), and
  their `msg.deliver` events carry `cause=broker_restart` from the reclaim.
- [B2] The S4 mid-backoff row is **not** returned at `clock_base+90s`; after `clock advance 4m`, it
  is, at `attempt 4/5`. Backoff survived the upgrade.
- [B3] Pre-upgrade ack tokens from `expect/tokens.json` fence exactly as D7 says — the ack token is a
  wire contract and an upgrade must not break the worker holding one:

| Token in `tokens.json` | Row state after upgrade | Required result |
|---|---|---|
| `orders/workers/10/1/1` | now `attempts=2` | `409 stale_ack`, row untouched, `msg.ack_stale` WARN (T3b) |
| `orders/billing/7/1/1` | row deleted pre-freeze (acked) | `200`, `stale: true`, `msg.ack_dup` at DEBUG (T3a) |
| `orders/billing/12/1/1` | consumer `generation=2` (S5) | rejected on generation, never mutates a live row (I7) |
| `orders/workers/10/2/1` | freshly minted post-upgrade | `200 ok` |

- [B4] A publish after the upgrade gets `seq = stream_seq.next` — strictly greater than every
  pre-upgrade seq, no reuse (V6).
- [B5] `messq trace <mid-backoff id>` renders the **pre-upgrade** history plus the post-upgrade
  events as one continuous story, matching `expect/trace-*.txt` after `#18`'s normaliser. The events
  table is the product (D11); an upgrade that silently drops history is the worst possible bug here
  and the cheapest one to catch.
- [B6] `messq dlq redrive orders.dlq --limit 1 --confirm orders.dlq` republishes an S7 message into
  `orders` with `Messq-Redrive-Of` and the original `trace_id` (T11).
- [B7] Conservation across the boundary: `published == acked + termed + dead + expired +
  still_pending` computed over the fixture's frozen counts plus the scenario's operations.

### 8. Assertion set C — the refusal gate

```
$ messq serve --data-dir /var/lib/messq
error: database schema is newer than this binary
  found:    schema_version 9999      supports: schema_version 3
  why:      forward-only migrations; a newer messq wrote this directory
  next:     upgrade messq to >= the version that wrote it, or restore a backup
exit status 78
```

- [C1] Exit code **78** (`EX_CONFIG`), matching `#17`'s startup-failure contract; `verify` exits 1
  with the same three explanatory lines; `doctor` and `backup` refuse identically. Four entry points,
  one message — asserted by a table test, not by four hand-written strings.
- [C2] **No writes.** After the refusal, `sha256(messq.db)` is unchanged, and no `messq.db-wal`
  containing frames remains. Precise formulation, because opening a WAL database legitimately creates
  `-shm` and may create a zero-frame `-wal`: *the main database file is byte-identical and any WAL
  present after `Close` has no committed frames*. The gate must fire before the migration transaction
  and before any `meta` write.
- [C3] **Never partially parse.** A test asserts that at schema 9999 the daemon does not open
  listeners, does not run recovery, and does not read `deliveries` at all (a table-level hook counts
  queries; zero non-`meta`, non-pragma statements are permitted).
- [C4] `refuse-no-meta`: tables present, no `meta` row ⇒ `ErrNotAMessqDataDir` (a new sentinel, added
  to `#5`'s taxonomy under this PR), **not** "version 0, migrate from scratch". Creating `streams`
  on top of somebody's half-restored database is unrecoverable; refusing is free.
- [C5] `refuse-foreign-db`: a valid SQLite file that is not ours ⇒ the same sentinel, naming the
  unexpected table in the message.
- [C6] `refuse-user-version-skew`: `meta.schema_version=3`, `PRAGMA user_version=4` ⇒ refuse
  (`#5`'s tamper signal), with a message that says which value is authoritative.
- [C7] A non-SQLite file at `messq.db` ⇒ `SQLITE_NOTADB` mapped to a teaching error naming
  `--data-dir`, never a raw driver string.
- [C8] `ErrMigrationDrift`: a copy of `v1.0.0-schema3` whose recorded `migration_2_sha256` has been
  altered is refused. (The corpus also makes the *inverse* test possible: editing `0001_init.sql` in
  the tree breaks every fixture at once, which is exactly the alarm we want.)

### 9. Downgrade at equal schema version

Downgrade **across** a schema version is not supported and never will be — forward-only migrations
mean the older binary literally lacks the code (D1/§4.2). Downgrade at *equal* schema version must
work, because that is the real rollback path an operator uses when `v1.0.3` misbehaves and `v1.0.2`
is known good. That imposes rules on what a patch release may write:

| Change within one schema version | Allowed? | Enforcement |
|---|---|---|
| New table, column or index | **No** — that is a schema bump | ladder + `TestEveryReleasedSchemaHasAFixture` |
| New **advisory** `meta` key (older binary can ignore it) | Yes | `metaKeyRegistry` entry with `Advisory: true` |
| New **load-bearing** `meta` key | No — bump the schema | `metaKeyRegistry` entry with `Advisory: false` fails the equal-schema test |
| New event name in §9.2's vocabulary | Yes (additive) | I10 fold classifies unknown names as `unknown_event` **warning**, never a violation |
| New key inside an `events.detail` / `hdr` JSON object | Yes | decoders ignore unknown keys; fuzz corpus covers it |
| New `Messq-*` header on a stored message | Yes | headers are opaque JSON in `hdr` |
| Renaming or removing **anything** above | No, post-1.0 | the compatibility promise (`#36`) |

```go
// internal/store/meta.go — small, boring, and the whole enforcement mechanism.
type metaKey struct {
	Key         string
	SinceSchema int
	Advisory    bool // an older binary at the same schema may ignore this key safely
}

var metaKeyRegistry = []metaKey{
	{"schema_version", 1, false}, {"node_id", 1, false}, {"created_at", 1, false},
	{"clean_shutdown", 1, false}, {"schema_applied_at", 1, true},
	{"durability_mode", 1, true}, // written by #5, advisory: verify's V4 cross-check
	// migration_<n>_sha256 handled by prefix rule
}
```

`TestMetaKeysAreRegistered` walks a booted store's `meta` table and fails on any key not in the
registry — so adding one is a deliberate act with a schema decision attached. The classification
decision on unknown event names is deliberate and worth stating plainly: `#8`'s I10 fold is
`exhaustive`-linted so a *new* event name fails compilation in the current tree, but an *older*
binary meeting a newer name at runtime is a supported condition, and it must degrade to a warning
rather than shout "log ≠ state" at an operator mid-rollback.

The nightly `oldbin` lane makes this real rather than notional: given `MESSQ_OLD_BINS` (a directory
of previously released binaries, populated by the nightly workflow from GitHub release assets, or
built from tags with `git worktree` when assets are unavailable), the suite runs, for every released
version at the current schema: current binary writes → old binary opens, `verify`s and fetches.
Absent `MESSQ_OLD_BINS`, the lane skips loudly (`t.Skip` with the reason) — the PR lane must not
depend on the network.

### 10. Freezing the format at 1.0

`released.tsv` is the ratchet:

```
# version   schema  fixture_dir              tag_date
v0.5.0      1       v0.5.0-schema1           2026-09-10
v0.8.0      2       v0.8.0-schema2           2026-09-24
v0.9.0      3       v0.9.0-schema3-dirty     2026-11-06
v1.0.0      3       v1.0.0-schema3           2026-11-20
```

- `TestEveryReleasedSchemaHasAFixture` — every row has a readable fixture directory whose manifest
  agrees, and `max(schema) ≤ len(embedded ladder)`. Adding migration `0004` without adding a fixture
  for the version that introduced it is a **build failure**, which is the entire mechanism by which
  this suite stays alive after the person who wrote it has moved on.
- `#36`'s release workflow gains one step: at the release commit, run `mkfixture` with the tag's
  version, commit the fixture and the `released.tsv` row in the release PR. Cheap, mechanical, and it
  means the `v1.0.0` fixture is produced by the actual released artifact rather than by something
  resembling it.
- `messq version --json` and `GET /v1/info` grow a `format` object. `#36`'s acceptance criterion
  (*"`messq version --json` reports the frozen format version"*) is this field:

```json
{"version":"1.0.0","commit":"9f13c0e4","go":"go1.25.3",
 "format":{"schema_version":3,"migrates_from":1,"frozen_at":"v1.0.0"}}
```

  `migrates_from` is the oldest `meta.schema_version` this binary will migrate (1, forever, unless we
  ever drop old migrations — which would require a fixture-backed deprecation, not a quiet delete).

### 11. The operator documentation

`docs/OPERATIONS.md#upgrading`, four steps, each a command block executed in CI by `#18`/`#26`'s docs
harness (documentation cannot rot — §11.5):

```bash
# 1. what do I have?
messq version --json | jq '{version, format}'
sqlite3 -readonly /var/lib/messq/messq.db 'PRAGMA user_version;'   # works with the daemon down

# 2. back up (online, consistent, one file)
messq backup /var/backups/messq-$(date -u +%Y%m%dT%H%M%SZ).db

# 3. stop, swap the binary, start
systemctl stop messq && apt install -y messq=1.1.0 && systemctl start messq

# 4. prove it
journalctl -u messq -n 20 | grep server.start     # schema_from / schema_to
messq verify --deep
```

Plus the rollback paragraph in the same voice as the refusal error: *downgrade is supported only at
the same `format.schema_version`; across a schema bump, restore the backup from step 2. This is why
step 2 is not optional.* And the honest sentence that belongs next to it: **migration runs before the
listeners open, in one transaction — an interrupted upgrade leaves the old version, never a
half-migrated directory.**

### 12. CI wiring

| Lane | Job | Contents | Budget |
|---|---|---|---|
| PR / merge | existing `test` job (`go test ./...`) | all fixtures, `inproc` + fast `subproc`, current durability default | ≤ 45 s |
| Nightly | `upgrade-fixtures` (`#2`'s placeholder, filled here) | full corpus × {`full`,`relaxed`} × {default, `-tags cgosqlite`}, plus the `oldbin` downgrade lane | ≤ 10 min |
| Release | `#36`'s workflow | `mkfixture` for the tag + corpus green before publishing artifacts | — |

The `cgosqlite` axis matters more than it looks: D1's escape hatch is only real if a directory
written by the pure-Go driver opens under `mattn/go-sqlite3` and vice versa. The corpus is the only
place that gets tested.

### 13. Edge cases, and what we do about them

| # | Edge case | Handling |
|---|---|---|
| 1 | Fixture opened years after freezing; every deadline is in the past | anchored fake clock in the `inproc` lane; clock-sensitive assertions tagged and skipped in the real-clock lane (§5) |
| 2 | The janitor eats fixture content mid-test (retention, event trim, dedup expiry) | `--janitor-interval 0` in the `subproc` lane; fixture streams use `max_age_ms=0`/`max_msgs=0` except the deliberate retention case |
| 3 | `go test` mutates `testdata/` in place | every test works on a `t.TempDir()` copy; CI runs `git diff --exit-code test/upgrade/testdata` after the suite |
| 4 | Dirty-WAL fixture: `-shm` is machine-specific | ship `.db` + `-wal` only; SQLite regenerates `-shm`. `#8` already documents that a lone `.db` beside a missing `-wal` is a phantom-loss trap — the manifest's `clean_shutdown: false` makes the pairing explicit and a test asserts the `-wal` is present before booting |
| 5 | Fixture files copied with the wrong mode ⇒ `#5`'s `ErrDataDirPerms` fires and every test fails confusingly | `Load` chmods the copy to 0700/0600 explicitly and asserts it, rather than trusting `git`'s mode bits |
| 6 | SQLite output stops being byte-stable across driver upgrades | fall back to a normalised logical-dump digest (§4); the immutability rule survives, only the page-layout assertion is lost |
| 7 | Migration is interrupted (power cut, `SIGKILL`) mid-ladder | A3's error hook proves atomicity now; `#32` re-runs it via `store.migrate.mid_ladder` in the real fault matrix |
| 8 | Data directory on read-only media during an upgrade | the migration transaction fails cleanly (`SQLITE_READONLY` → teaching error naming the mount), the directory is untouched; asserted with a 0400 `messq.db` |
| 9 | Disk full during a backfilling migration (`0003` writes a row per stream) | one transaction ⇒ rollback ⇒ old version intact; the test uses a tiny loopback fs when `#32`'s helper is available, otherwise a `SQLITE_FULL` injection hook |
| 10 | Two fixtures share a `node_id` and a test cross-contaminates | `node_id` is derived from the entropy seed; a test asserts all manifests have distinct `node_id`s |
| 11 | A fixture is *wrong* (generated with a bug) and must change | it may not be edited: delete, regenerate under a new directory name, and explain in the PR — the immutability error text says exactly this |
| 12 | Migration `0002` relaxes a **unique** index; an old directory contains data that only validated *because* of it | intentionally include a pre-`0002` fixture whose ids are unique, then assert post-migration inserts that would previously have failed now succeed (A6) — the direction of the relaxation is what makes this safe, and asserting it stops anyone tightening it back |
| 13 | Someone adds migration `0004` and "fixes" old fixtures to match | `CORPUS.sha256` + `TestEveryReleasedSchemaHasAFixture` make the correct action (add a fixture) easier than the wrong one |

### 14. Considered and rejected

| Idea | Why not | Revisit trigger |
|---|---|---|
| Generate fixtures at test time from the current binary | Tests nothing. The entire value is that the bytes predate the code under test. | Never |
| Keep old binaries in-tree (checked-in ELF per version) | Repo bloat, arch-specific, unauditable; release assets or a `git worktree` build give the same thing on demand | Never |
| SQL-script fixtures (a `.sql` file replayed to build the directory) | A hand-written script drifts from what the product actually wrote, and cannot capture page layout, WAL state or `user_version` | If binary fixtures prove unmaintainable across driver versions |
| Reversible / down migrations | Forward-only is D1's design; a down migration is untested code that runs only during an incident | Never |
| Auto-detecting an unknown schema and "best-effort" opening | Directly contradicts §4.4 ("refuse to start") and turns a clean refusal into silent data loss | Never |
| An `messq migrate` subcommand separate from `serve` | A second code path to the same transaction; `serve` migrating on start is one path and is already atomic. `--dry-run`-style preview belongs in `doctor` | An operator needs to migrate a directory without starting a daemon (e.g. a maintenance window with the port closed) |
| Cross-version *wire* replay (old client ↔ new server) | Different contract, different artifacts | **#18**'s directory copied per version by **#36** |
| Property-testing the migration ladder with `rapid`-generated directories | Generated directories are not *old* directories; the bugs live in real historical shapes | If the ladder ever exceeds ~10 migrations |

## Acceptance criteria

- [ ] `test/upgrade/testdata/datadirs/` contains at least four content fixtures (schema 1, schema 2,
      schema 3 clean, schema 3 dirty-WAL) and four refusal fixtures, each with a complete
      `MANIFEST.json` and `expect/` bundle, each satisfying the S1–S12 scenario for its version.
- [ ] Every content fixture: the current binary opens it, migrates to the current schema version in
      **one transaction**, and `messq verify --deep` reports zero violations — including the I10
      event fold.
- [ ] `meta.node_id` and `meta.created_at` are unchanged by migration for every fixture; the first
      `server.start` event after the upgrade carries `detail.schema_from`/`schema_to`.
- [ ] `expect/state.json` matches after migration for every fixture, including byte-identical bodies
      (NUL bytes and invalid UTF-8 included) and an unchanged `events` digest.
- [ ] `stream_stats` after `0003`'s backfill equals a full scan for every stream in every fixture,
      including the empty stream and the DLQ stream.
- [ ] After migration the broker keeps delivering: reclaimed leases redeliver with `attempts`
      unchanged, the mid-backoff message becomes visible only after its `visible_at`, and a new
      publish receives a seq greater than every pre-upgrade seq.
- [ ] Every ack token in `expect/tokens.json` produces the exact result its row in §7 B3 requires;
      no stale token mutates a live row (I7).
- [ ] `messq trace` on the migrated fixture renders pre- and post-upgrade events as one timeline and
      matches the committed golden after normalisation.
- [ ] A fixture whose `meta.schema_version` exceeds the binary's is refused by `serve`, `verify`,
      `doctor` and `backup` with the same three-line teaching error; `serve` exits **78**.
- [ ] After such a refusal `messq.db` is byte-identical and no WAL with committed frames remains;
      a query counter proves no table other than `meta` was read.
- [ ] `refuse-no-meta` and `refuse-foreign-db` yield `ErrNotAMessqDataDir` — never a migration —
      and the message names what was found.
- [ ] An injected failure at the last statement of the last pending migration leaves the directory at
      the **old** schema version, `verify`-clean, and a subsequent unhindered open migrates it.
- [ ] Running the suite leaves `test/upgrade/testdata/` unmodified (`git diff --exit-code` clean),
      and altering any committed fixture byte fails `TestCorpusIsFrozen` with the "do not regenerate"
      message.
- [ ] `TestEveryReleasedSchemaHasAFixture` fails when a migration is added to the ladder without a
      corresponding fixture and `released.tsv` row.
- [ ] `TestMetaKeysAreRegistered` fails on any `meta` key absent from `metaKeyRegistry`; a
      non-advisory key introduced without a schema bump fails the equal-schema downgrade test.
- [ ] `messq version --json` and `GET /v1/info` report
      `format.{schema_version, migrates_from, frozen_at}`, and the value matches the fixture
      manifests' `schema_after`.
- [ ] `docs/OPERATIONS.md#upgrading` exists, its four command blocks execute green in CI, and it
      states the rollback rule (equal schema only; otherwise restore the backup).
- [ ] The corpus is ≤ 2 MiB total and no single fixture exceeds 256 KiB.
- [ ] The fast lane runs inside `go test ./...` in ≤ 45 s; the nightly `upgrade-fixtures` job is real
      (no `echo TODO`) and green across `full`/`relaxed` and the `cgosqlite` build tag.

## Test plan

Consistent with §11: `-race` everywhere, no `time.Sleep` (the anchored fake clock or `synctest`),
real files in `t.TempDir()` (never `:memory:`), goldens normalised through `#18`'s masker.

**Unit — corpus plumbing (`test/upgrade/corpus_test.go`)**
- `TestCorpusIsFrozen`: every file's sha256 matches `CORPUS.sha256` and its `MANIFEST.files` entry.
- `TestManifestsAreWellFormed`: required fields present, `clock_base` parses, `node_id`s distinct,
  `schema_version ≤ len(ladder)`, sizes within cap.
- `TestGeneratorIsDeterministic`: regenerate the current-schema fixture into `t.TempDir()` twice and
  compare byte-for-byte, then compare against the committed one.
- `TestEveryReleasedSchemaHasAFixture`, `TestMetaKeysAreRegistered`.
- `TestLoadIsNonDestructive`: after a full run, `testdata/` hashes are unchanged (belt and braces
  alongside the CI `git diff`).

**Integration — migrate forward (`migrate_test.go`, table-driven over the corpus)**
- A1–A11 above, one subtest per fixture; failures print the fixture name and its producer version
  first, because "which old version breaks?" is the only question that matters when this suite goes
  red.
- Migration atomicity via a store-level `beforeStatement` hook (A3); the same scenario for
  `SQLITE_FULL` and `SQLITE_READONLY` (edge cases 8/9).
- `ErrMigrationDrift` on a tampered `migration_2_sha256`.

**Integration — keeps delivering (`deliver_test.go`, `inproc` lane, `clock.Fake`)**
- B1–B7 driven through `pkg/client` (D14: the client the CLI itself uses), with `clock advance` for
  every time step.
- The `subproc` variant runs the clock-invariant subset against a real `messq serve` from
  `internal/testutil/daemon` (`#18`).

**Integration — refusal gate (`refuse_test.go`)**
- C1–C8 as a table: {fixture} × {`serve`, `verify`, `doctor`, `backup`} → {exit code, stderr golden,
  post-state hash}.
- The query counter that proves C3 (nothing beyond `meta` and pragmas is read).

**Downgrade (`downgrade_test.go`, nightly `oldbin` lane)**
- For each `released.tsv` row at the current schema: current binary writes a fresh directory with the
  S1–S12 scenario, the old binary opens it, runs `verify`, fetches and acks. Skips loudly without
  `MESSQ_OLD_BINS`.
- Equal-schema `meta` compatibility: inject an unregistered non-advisory key, assert the test fails
  (a sabotage case, per `#2`'s discipline of proving a gate bites).

**testscript (`test/script/upgrade.txtar`, `#26`'s harness)**
- The operator transcript: `messq version --json` → `format` block; boot a copied fixture; `messq
  verify --deep`; `messq trace $MSG_ID`; then point the daemon at `refuse-schema-9999/` and assert
  `exitcode 78` plus the exact three stderr lines. This is the golden that keeps the refusal *text*
  honest, not just its behaviour.

**Docs (`test/docs`, `#18`'s harness)**
- Every command block in `docs/OPERATIONS.md#upgrading` executes against a fixture-seeded daemon.

**Sabotage matrix (proving the suite bites, per `#2` §8)**
- Change `0001_init.sql` → every fixture fails on `ErrMigrationDrift`.
- Make migration `0003`'s backfill skip empty streams → A7 fails on the `jobs` fixture.
- Make the reclaim reset `attempts` → A10/B1 fail (this is I4/D6's regression net).
- Remove the `ErrSchemaTooNew` check → C1/C2 fail and the testscript golden fails.
- Regenerate a fixture in place → `TestCorpusIsFrozen` fails with the "do not regenerate" message.

**Bench** — none. This suite is correctness-only; migration duration on a realistic directory is
reported as an informational log line (`server.start detail.migrate_ms`), not gated.
