## Context

#14 built the chassis and the hot path: a `net/http` server on the Unix socket, Go 1.22 `ServeMux`
method+pattern routing, one error envelope with a closed machine-code enum, publish, long-poll fetch
and the settle verbs. A worker can now do its whole job over HTTP. **An operator still cannot.**
There is no way to create a consumer, look at what is stuck, pause a runaway worker, move a cursor,
or ask the daemon what it is.

This issue completes the control plane so that **every endpoint printed in PLAN.md §7 exists and
answers** — M4's exit criterion ("Full HTTP surface"), and the API three downstream issues consume
directly: #18 freezes these shapes as a contract, #22 wraps them in `pkg/client`, #24 renders them
as `messq stream`, `consumer`, `peek`, `pending` and `lag`. Nothing in M6 can start until the
surface it renders is real.

Governing PLAN.md material:

- **§7 API / protocol** — the endpoint list to complete, the error envelope, the `?confirm={name}`
  and `?dry_run=1` conventions, and the wire conventions (raw-body publish, `body_b64` out,
  `trace_id` echoed everywhere).
- **§5.1 T10 (`seek`)** — `generation++`, cursor reset, delivery rows dropped and counted. The
  generation bump fences every outstanding token (D7), so `seek` is not a convenience; it is a
  correctness primitive.
- **§4.2 Schema** — `streams.max_*`, `consumers.cursor_seq`/`generation`/`paused`, `deliveries`
  (the pending set *is* the table, so listings are bounded by `max_ack_pending`).
- **§4.5** — *"`/readyz` is not tied to disk pressure (the RabbitMQ-on-Kubernetes lesson: don't let
  the orchestrator kill the node that is draining itself)."* Already adjudicated; it drives the
  whole probe design below.
- **§4.3 / D4** — the read-only latch after an fsync failure *does* flip `/readyz`: a latched process
  is on its way out. Disk pressure and a dead disk get different answers.
- **§9.4 Metrics** — the cardinality rule (labels are `stream` and `consumer` only) is why
  per-subject and per-message breakdowns live in *this* API; #21's collector reuses the read-pool
  statistics queries defined here.
- **§3.2 Goroutine census** — handlers "never write SQLite directly"; inspection runs on the
  read-only pool, which under WAL never blocks the writer.
- **D8** — flags + `MESSQ_*` env only. Every knob below is a flag.

Two properties this issue owns, because everything downstream assumes them:

1. **Inspection is free.** Looking at a broken system must never make it more broken: no inspection
   endpoint mutates state, enqueues writer work, or can be starved into lying by a busy queue.
2. **A preview is the truth.** `?dry_run=1` reports exactly what the real run does — not an estimate
   from a second code path that can drift. #28 inherits this for `replay` and the CLI; if it is
   approximate here, every destructive command in the product is untrustworthy from birth.

## Scope

### In scope

- **Route registry and dispatch completion**: one declarative table of every route (method, pattern,
  mutating?, required role, summary), JSON-enveloped `404`/`405`, and a completeness test binding the
  registry to `docs/PROTOCOL.md`.
- **Stream control plane**: `POST /v1/streams`, `GET /v1/streams`, `GET /v1/streams/{s}`,
  `PATCH /v1/streams/{s}` (with the **narrowing guard** — a limit change that would evict stored
  messages is refused without `?allow_data_loss=1`), `DELETE /v1/streams/{s}?confirm=`, and
  **`POST /v1/streams/{s}/purge`** (`{up_to_seq?, subject?, keep?}`, `?dry_run=1`) — the first three
  ported from #7's provisional routes onto #14's chassis.
- **Consumer control plane**: `POST …/consumers` (declarative full-document upsert),
  `PATCH …/consumers/{c}` (sparse edit), `GET …/consumers[/{c}]`, `DELETE …/consumers/{c}?confirm=`,
  `POST …/consumers/{c}/pause|resume`, and **`POST …/consumers/{c}/seek`** with `?dry_run=1`
  (T10: cursor move, generation bump, pending drop, counted).
- **Pending inspection**: `GET …/consumers/{c}/pending?older_than_ms=&limit=&after=`, deadline
  ordered, with derived ack tokens for in-flight rows.
- **Message inspection**: `GET /v1/streams/{s}/messages/{seq}`, `…/{seq}/data` (raw bytes with
  `Messq-*` response headers), `GET /v1/streams/{s}/messages?from_seq=&subject=&limit=`, and
  `GET /v1/messages/{id}` — finalised from #7's provisional forms.
- **`GET /v1/info`**: version, commit, uptime, node id, schema version, durability mode with the
  *live* `synchronous` pragma readback, db/WAL bytes, free disk, listeners, counts, `degraded[]`.
- **`GET /healthz` and `GET /readyz`** with distinct, documented meanings, answered from in-memory
  state and **never** by touching SQLite.
- **`POST /v1/admin/log-level`** on an injected `LevelSetter` seam, and the **`/metrics` mount
  point** from an injected `http.Handler` (`503 not_implemented` while nil — never `404`).
- **The dry-run contract**: `plan → impact → (dry_run ? return : apply)`, one code path,
  `applied: false|true` in every response.
- Flags: `--max-list-limit`, `--pending-max-limit`, `--purge-max-rows`, `--purge-chunk`,
  `--info-cache`.

## Design proposal

> A proposed starting point, not a mandate — except the five items marked **_decision_**, which are
> cheap now and expensive once #18 freezes the wire and #22/#24 build on it. Where this clarifies
> PLAN.md rather than restating it, it is flagged and needs a matching `docs/PROTOCOL.md` edit
> (owned with #4/#18).

### 1. The route registry

```go
package api

type Role uint8 // RoleNone | RolePublish | RoleConsume | RoleAdmin  (#16 enforces)

type Route struct {
    Method  string           // "GET", "POST", …
    Pattern string           // Go 1.22 ServeMux pattern, e.g. "/v1/streams/{stream}/purge"
    Handler http.HandlerFunc
    Role    Role             // required role; declared here, enforced by #16's middleware
    Mutates bool             // true ⇒ goes through the writer; false ⇒ read pool only
    DryRun  bool             // true ⇒ accepts ?dry_run=1
    Confirm string           // "" | "stream" | "consumer": which path value ?confirm= must equal
    Summary string           // one line; feeds docs/PROTOCOL.md generation
}

func Routes(d *Deps) []Route
```

**_Decision 1: the registry is the single source of truth for the surface._** Three consumers
already exist: #16's authz-completeness test (every `Mutates` route declares a non-`None` role),
#18's contract suite (iterate routes, assert each has a golden), and `PROTOCOL.md` generation.
Retrofitting it after #16 and #18 hand-write their own lists costs three refactors.

**404 / 405 with an envelope.** `ServeMux` writes a plain-text `405` body, which would be the only
non-JSON response in the product. The stdlib gives the fix for free: a pattern carrying a method is
strictly more specific than the same bare path, so registering both is not a conflict and the bare
path is reached *only* on a method mismatch.

```go
for _, r := range Routes(d) {
    mux.Handle(r.Method+" "+r.Pattern, chain(r))
}
for path, allowed := range methodsByPattern(Routes(d)) {
    mux.Handle(path, methodNotAllowed(allowed))   // 405 + Allow: …, JSON envelope
}
mux.Handle("/", notFoundJSON)                     // 404 + envelope, never an HTML page
```

**_Decision 2: inspection handlers cannot reach the writer._** Handlers with `Mutates: false` are
constructed with a `*store.Reader` (read pool only) rather than the full `*store.Store`. That makes
"peek never mutates" a compile error instead of a code-review habit, and keeps the §3.2 promise that
inspection never blocks the writer. The full-store-diff test below is the belt to that brace.

### 2. Health, readiness, `/v1/info` and the admin knobs

**_Decision 3: probes never touch SQLite._** Readiness is read from in-memory atomics owned by
recovery (#5), the writer latch (#6) and the lifecycle state machine (#17). A probe that runs a
query is a probe that times out exactly when the queue is busiest — and a readiness flap under load
gets the node killed by its supervisor, which is how a latency incident becomes an outage.

```go
type HealthState interface {
    Live() bool                 // process can serve HTTP
    Ready() (bool, string)      // false + reason: "recovering"|"draining"|"read_only"
    Degraded() []Degradation    // {Kind, Since, Detail} — never affects Ready()
}
```

| Endpoint | Question | 200 when | Never affected by |
|---|---|---|---|
| `GET /healthz` | *Is the process alive?* | always, once listeners are bound | recovery, disk, drain, read-only latch |
| `GET /readyz` | *Should clients send work here?* | recovery complete **and** store writable **and** not draining | disk pressure, backlog depth, DLQ depth, consumer lag |
| `GET /v1/info` | *What is actually going on?* | always (authorized, `admin` role) | — |

```console
$ curl -s --unix-socket /run/messq/messq.sock http://x/healthz
{"status":"ok","degraded":[{"kind":"disk_low","since":"2026-09-29T11:02:04Z"}]}

$ curl -si --unix-socket /run/messq/messq.sock http://x/readyz
HTTP/1.1 503 Service Unavailable
Retry-After: 1
{"status":"recovering"}
```

`degraded[]` carries `kind` and `since` only — no version, counts or paths. `/healthz` and `/readyz`
are the two unauthenticated routes in the product (a probe cannot carry a token), so they must be
useless for fingerprinting. Registered kinds: `read_only` (#6), `disk_low` (#27), `draining` (#17),
`purge_in_progress` (this issue) — open for registration, closed for invention (each is a constant
with a doc comment).

```console
$ curl -s --unix-socket /run/messq/messq.sock http://x/v1/info | jq
{
  "version": "0.4.0-dev", "commit": "9f3c1ab", "go": "go1.25.1",
  "node_id": "01J8ZQ0000NODEID0000000000", "schema_version": 4,
  "started_at": 1759140000000, "uptime_ms": 86400123,
  "durability": {"mode": "full", "synchronous": "FULL", "verified_at": 1759140000000},
  "storage": {"db_bytes": 1073741824, "wal_bytes": 4194304,
              "disk_free_bytes": 68719476736, "data_dir_mode": "0700"},
  "counts": {"streams": 4, "consumers": 11, "events_rows": 1840221},
  "listeners": ["unix:///run/messq/messq.sock"],
  "state": "ready", "degraded": []
}
```

`durability.synchronous` is **read back from a live pooled connection** (#5's pragma hook), not
copied from the flag — that is what makes `messq doctor`'s "a 201 survives power loss: YES" (#30) an
observation rather than a claim. `db_bytes`/`wal_bytes`/`disk_free_bytes` are syscalls, cached for
`--info-cache`; `uptime_ms` and `state` are never cached.

**`POST /v1/admin/log-level`** is the one runtime-mutable setting that is not a signal (D8 puts the
rest behind SIGHUP, which #17 owns). It is wired to a seam so this issue does not wait on #19:

```go
type LevelSetter interface {
    Level() slog.Level
    SetLevel(slog.Level) error   // #19 backs this with the process-wide slog.LevelVar
}
```

Body `{"level":"debug"|"info"|"warn"|"error"}`; anything else is `400 bad_request` naming the four.
The response echoes `{"level":"debug","previous":"info","changed":true}`; a real change writes an
`admin.action` event (`detail={"setting":"log_level","from":"info","to":"debug"}`, actor from #16) —
turning the level up mid-incident belongs in the timeline you read afterwards. `Role: RoleAdmin`,
because DEBUG logs ids, subjects and headers. `--log-sample`/`--trace-subjects` stay startup-only.

**`/metrics`** is a mount point, not an implementation: `Deps.Metrics http.Handler`, injected. Nil ⇒
`503 not_implemented` with `next` pointing at #21; a `404` would claim the endpoint does not exist,
which is a different and wrong statement. #21 drops
`promhttp.HandlerFor(reg, promhttp.HandlerOpts{MaxRequestsInFlight: 4})` into the same slot with no
routing change.

### 3. The dry-run contract

**_Decision 4: preview and execution share one plan._** Every destructive control-plane route is:

```go
type Impact struct {                       // rendered identically by dry-run and by the real run
    Messages       int64    `json:"messages,omitempty"`
    Bytes          int64    `json:"bytes,omitempty"`
    PendingDropped int64    `json:"pending_dropped,omitempty"`
    Consumers      []string `json:"consumers_affected,omitempty"`
    FirstSeqAfter  uint64   `json:"first_seq_after,omitempty"`
    CursorBefore   uint64   `json:"cursor_before,omitempty"`
    CursorAfter    uint64   `json:"cursor_after,omitempty"`
    Clamped        bool     `json:"clamped,omitempty"`
    Warnings       []string `json:"warnings,omitempty"`
}

type Plan interface{ Impact() Impact }      // computed by indexed counting queries
func planPurge(tx *sql.Tx, c PurgeCmd) (purgePlan, error)
func planSeek(tx *sql.Tx, c SeekCmd) (seekPlan, error)
func applyPurge(tx *sql.Tx, p purgePlan) error
func applySeek(tx *sql.Tx, p seekPlan) error
```

Both branches run inside the writer's per-command `SAVEPOINT` (#6/#7): `dry_run=1` computes the plan
and returns; the real run computes the plan and applies it. Nothing is estimated twice.

Two hazards, both silent when wrong:

- **A rolled-back command must discard its pending events.** #6 publishes to the fan-out *after*
  commit from a per-command in-memory list. A dry run rolls its savepoint back, so that list must be
  dropped, or `messq events --follow` shows a purge that never happened.
- **A dry run still occupies a writer slot.** It rides the group commit like any other command, so it
  must do the counting and never the work — exactly why `planPurge` is separate from `applyPurge`.

Response shape, identical modulo `applied`:

```console
$ curl -s -XPOST --unix-socket /run/messq/messq.sock \
    -d '{"up_to_seq":10000}' 'http://x/v1/streams/orders/purge?dry_run=1'
{"applied":false,"stream":"orders","impact":{
  "messages":9812,"bytes":11238401,"pending_dropped":37,
  "consumers_affected":["worker","archive"],"first_seq_after":10001,
  "warnings":["37 in-flight messages will fence: their workers' acks will be rejected"]}}
```

`?dry_run=1` is accepted **only** on routes with `DryRun: true`; elsewhere it is
`400 dry_run_unsupported` — a silently ignored `dry_run` is how someone deletes a stream believing
they previewed it. `?confirm=` is **not** required with `dry_run=1`: previewing is the step you take
before you know the name is right.

### 4. Stream control plane

`POST` is the declarative full document, `PATCH` the sparse edit (Decision 5 applies to streams and
consumers alike); both funnel into #7's `StreamConfig.Validate` and surface its `[]Finding`.
`POST /v1/streams` on an existing name with a byte-identical config is `200 {"changed":false}`; with
a *different* config it is `409 stream_exists` whose `next` is the equivalent `PATCH` — a create that
silently rewrites someone else's limits is not idempotency, it is a lost update.

```console
$ curl -s --unix-socket /run/messq/messq.sock http://x/v1/streams/orders | jq
{"config":{"name":"orders","subjects":["orders.>"],"retention":"limits","max_msgs":0,
           "max_bytes":0,"max_age_ms":604800000,"max_msg_size":1048576,"discard":"old",
           "dedup_window_ms":120000,"created_at":1759140000000},
 "state":{"messages":1048201,"bytes":1198234112,
          "first_seq":9001,"last_seq":1057201,"next_seq":1057202,
          "first_ts":1756000000000,"last_ts":1757000042190,
          "consumer_count":3,"dlq_depth":412,"purging":null,"stats_age_ms":1200}}
```

`POST`/`PATCH` return the same `config` object plus `changed` and `findings`. `config` and `state`
are split deliberately: `config` is exactly what `PATCH` accepts, so `GET | jq .config | PATCH`
round-trips and `messq stream edit` (#24) is not an exercise in field filtering.

**Where the numbers come from.** `first_seq`/`last_seq` are indexed `min`/`max`, always exact.
`messages`/`bytes` are `SELECT count(*), coalesce(sum(size),0) FROM messages WHERE stream=:s` — a
scan on a large stream — so they run on the read pool, are cached for `--info-cache`, and carry
`stats_age_ms` so nobody dashboards a number whose freshness they cannot see. `dlq_depth` is the
count of `<stream>.dlq` (#12), `null` when absent, omitted for a DLQ stream itself. If
`BenchmarkStreamStats` exceeds ~50 ms at 10 M messages, the fallback (behind the same JSON shape) is
a `stream_stats(stream, messages, bytes)` row maintained in the writer's transaction.

**Narrowing is a data-loss decision (`?allow_data_loss=1`).** A `PATCH` lowering `max_msgs`,
`max_bytes` or `max_age_ms`, or switching `retention` from `limits` to `workqueue`, hands the janitor
(#27) a licence to delete messages that exist right now: `409 would_lose_data` without
`?allow_data_loss=1`, with the exact count from the same `Impact` machinery as purge — which is also
why `?dry_run=1` works on `PATCH`:

```sql
-- max_age_ms lowered
SELECT count(*), coalesce(sum(size),0) FROM messages
 WHERE stream=:s AND published_at < :now - :new_max_age_ms;          -- messages_age

-- max_bytes lowered (running sum from the head backwards; SQLite window function)
SELECT count(*) FROM (
  SELECT seq, sum(size) OVER (ORDER BY seq DESC) AS running
    FROM messages WHERE stream=:s)
 WHERE running > :new_max_bytes;
```

```console
$ curl -s -XPATCH --unix-socket /run/messq/messq.sock \
    -d '{"max_age_ms":3600000}' http://x/v1/streams/orders
{"error":{"code":"would_lose_data",
  "message":"max_age_ms 7d → 1h evicts 1,041,880 messages (1.1 GiB) on the next retention sweep",
  "next":["messq stream edit orders --max-age 1h --allow-data-loss",
          "messq stream edit orders --max-age 1h --dry-run   # see it first"],
  "trace_id":"…"}}
```

Two changes that look similar and are *not* refusals, because nothing stored is destroyed:

- **`max_msg_size` lowered** — future publishes only. Accepted with a `finding`.
- **`subjects` narrowed** — `streams.subjects` gates *publishes*, not stored messages or consumer
  filters, so stored non-matching messages stay deliverable. Accepted with a warn `finding` that
  samples reality: *"1,204 of the last 10,000 messages were published to subjects the new patterns
  reject"*. Refusing would be wrong (another `PATCH` reverses it); silence would be worse (the
  publisher breaks tomorrow).

**`DELETE /v1/streams/{s}?confirm={s}`** removes the stream row, its `stream_seq`, consumers,
delivery rows and messages in one transaction, reusing §5's chunked path past `--purge-max-rows`.
It does **not** delete `<stream>.dlq`: deleting the thing that failed must not delete the evidence of
how. A `finding` names the surviving DLQ, its depth and the command to remove it. One `stream.delete`
event with `detail={messages, bytes, consumers:[…]}`.

**`GET /v1/streams?limit=&after=`** lists the same `{config,state}` objects (`after` = stream name,
`limit` clamped to `--max-list-limit`, effective value echoed) but computes per-stream
`messages`/`bytes` only with `?stats=1` — the overview must not be the API's most expensive call.

### 5. Stream purge

```
POST /v1/streams/{s}/purge   {"up_to_seq": N?, "subject": PAT?, "keep": K?}   [?dry_run=1]
```

| Field | Meaning |
|---|---|
| *(none)* | Purge the whole stream |
| `up_to_seq: N` | Delete `seq <= N` — **inclusive**; stated in `PROTOCOL.md` because JetStream's `seq` is exclusive and the difference is one message |
| `keep: K` | Keep the newest `K` matching messages, delete the rest |
| `subject: PAT` | Restrict to matching subjects (wildcards allowed — this is a filter, not a publish) |

`up_to_seq` and `keep` together are `400 bad_request` (ambiguous); `subject` combines with either.

One transaction:

```sql
-- impact (indexed counts; the plan)
SELECT count(*), coalesce(sum(size),0) FROM messages WHERE stream=:s AND seq<=:upto;
SELECT DISTINCT consumer FROM deliveries WHERE stream=:s AND seq<=:upto;   -- deliveries_seq

-- apply
DELETE FROM deliveries WHERE stream=:s AND seq<=:upto;                     -- counted
UPDATE consumers SET generation = generation + 1
 WHERE stream=:s AND name IN (:affected);                                  -- fences tokens (D7)
UPDATE consumers SET cursor_seq = :upto+1
 WHERE stream=:s AND cursor_seq < :upto+1;                                 -- unfiltered purge only
DELETE FROM messages WHERE stream=:s AND seq<=:upto;
INSERT INTO events (…, 'stream.purge', …, :detail_json);
```

- **`stream_seq.next` is never touched** (§4.2: "monotonic even across purge"). Sequence numbers are
  never reused, so `stream/seq` stays a valid consumer-side dedup key (PLAN §6) across a purge.
- **The cursor is clamped forward only on an unfiltered purge.** With a `subject` filter,
  non-matching messages survive in the purged range, so moving the cursor would skip live work.
- **Consumers are fenced, not surprised.** Dropping delivery rows without bumping `generation` would
  let an in-flight worker's ack land as T3a ("missing row → idempotent success flagged stale"),
  which reads in `trace` as if the work completed. The generation bump makes it a rejection with a
  named cause — the honest answer.
- **Large purges.** If the planned `messages <= --purge-max-rows` (500 000) it is one transaction and
  a `200` with exact counts. Above that, the **first** transaction does the fencing (delivery rows,
  generation, cursor) and records the range in `meta` as `purge.<ulid>`; deletion proceeds in
  `--purge-chunk` (10 000) row batches as follow-up writer commands; the response is `202 Accepted`
  with a `purge_id`; `GET /v1/streams/{s}` reports `"purging":{"remaining":N}` and `/healthz` carries
  `degraded: purge_in_progress`. Because fencing is immediate, **queue behaviour is atomic** — only
  `peek` can still see corpses, and `PROTOCOL.md` says so in one sentence. The `meta` row makes the
  purge crash-resumable, and #27's janitor adopts the resumption loop.

  *(Rationale: a 5 GiB `DELETE` inside a 2 ms commit window stalls every publisher and every ack —
  during, typically, a disk incident. Blocking the ack path to reclaim disk is the failure D4
  forbids for `ENOSPC`.)*

### 6. Consumer control plane

**_Decision 5: `POST` is a declarative full-document upsert; `PATCH` is the sparse edit._** PLAN §7
says "create/update (idempotent)". Read as a sparse update, a rerun of a provisioning script that
dropped a field silently keeps the old value; read as declarative, it converges. So:

- `POST /v1/streams/{s}/consumers` — body is the **complete** desired config; omitted fields take
  their documented defaults (§4.2), not current values. Identical to stored → `200 {"changed":false}`
  with no `consumer.update` event (#9's no-churn rule).
- `PATCH /v1/streams/{s}/consumers/{c}` — sparse; omitted fields keep current values, with `*T`
  pointer fields so "absent" and "zero" stay distinguishable (`max_deliver: 0` means *unlimited*, and
  omitting it must not mean that). **This route is an addition to PLAN §7**; without it
  `messq consumer edit` (#24) is a racy client-side read-modify-write. One line in `PROTOCOL.md`.

Both funnel into #9's `ConsumerConfig.Validate` and surface its `[]Finding`, so the API teaches the
same footguns the CLI does:

```console
$ curl -s -XPOST --unix-socket /run/messq/messq.sock \
    -d '{"name":"worker","filters":["orders.>"],"ack_wait_ms":30000,"max_deliver":0}' \
    http://x/v1/streams/orders/consumers
{"stream":"orders","name":"worker","filters":["orders.>"],"ack_wait_ms":30000,
 "max_deliver":0,"max_ack_pending":1000,"backoff_ms":[1000,5000,30000,120000,600000],
 "dead_policy":"dlq","cursor_seq":1,"generation":1,"paused":false,"created_at":1759140000000,
 "changed":true,
 "findings":[{"level":"warn","code":"unbounded_redelivery",
   "message":"max_deliver=0 retries a poison message forever; alert on messq_dlq_depth"}],
 "retry_horizon_ms":0}
```

`GET …/consumers/{c}` returns #9's `ConsumerInfo` verbatim — `pending`, `inflight`, `ready`,
`scheduled`, `backlog`, `oldest_pending_age_ms`, `next_visible_at`, `delivery_blocked_by`,
`retry_horizon_ms`. `GET …/consumers` returns the same rows for the stream.

**`GET /v1/consumers?stream=&limit=&after=` (proposed addition to §7)** returns them across all
streams in one call. `messq lag` is "the incident overview" (PLAN §8); as N+1 round trips it is
slowest exactly when it matters, and #21's collector would repeat the same N+1 every 5 s. One line in
`PROTOCOL.md`; if reviewers prefer §7 as printed, the fallback is `GET /v1/streams` plus per-stream
calls and #24 pays for it.

**Pause / resume** are `POST` with an empty body, idempotent (`{"changed":false}` when already in
that state), implemented as the `paused` column.

> **Documented, not fixed:** pausing does **not** freeze `ack_wait` deadlines. In-flight rows keep the
> `visible_at` set at claim time, so the sweeper (#11) still times them out — and, at
> `attempts >= max_deliver`, dead-letters them — while the consumer is paused. Freezing deadlines
> would mean rewriting every in-flight row at pause and at resume, making "paused" a
> durability-relevant state. Instead `POST …/pause` returns a `finding` when in-flight rows exist,
> naming the count and earliest deadline, so `messq consumer pause` (#24) can print *"3 in-flight
> messages will time out within 28s; they will be redelivered on resume."*

### 7. Seek (T10)

```
POST /v1/streams/{s}/consumers/{c}/seek   {"to": "start"|"new"|"seq:N"|"time:2026-09-29T10:00:00Z"}
```

The `to` grammar is parsed by the **same** `queue.ParseStartPosition` that resolves a consumer's
creation-time `start` (#9) — one parser, one fuzz target, no divergence between "where does a new
consumer begin" and "where does seek move it".

```sql
-- plan
SELECT cursor_seq, generation FROM consumers WHERE stream=:s AND name=:c;
SELECT count(*), sum(state=1) FROM deliveries WHERE stream=:s AND consumer=:c;
SELECT min(seq) FROM messages WHERE stream=:s;                       -- clamp floor
SELECT seq FROM messages WHERE stream=:s AND published_at>=:t ORDER BY seq LIMIT 1;  -- time:T

-- apply
DELETE FROM deliveries WHERE stream=:s AND consumer=:c;              -- counted
UPDATE consumers SET cursor_seq=:target, generation=generation+1
 WHERE stream=:s AND name=:c;
INSERT INTO events (…, 'consumer.seek', …);                          -- WARN level (§9.3)
```

Seek **always** drops delivery rows and bumps the generation. Keeping rows across a generation bump
would strand them — #9's claim path deletes stale-generation rows anyway — so a `keep_pending` option
would be a lie. The response reports what the operator is about to do to running workers:

```console
$ curl -s -XPOST --unix-socket /run/messq/messq.sock -d '{"to":"seq:9000"}' \
    'http://x/v1/streams/orders/consumers/worker/seek?dry_run=1'
{"applied":false,"stream":"orders","consumer":"worker","impact":{
  "cursor_before":10500,"cursor_after":9000,"pending_dropped":12,
  "messages":1500,"clamped":false,
  "warnings":["12 outstanding ack tokens will be rejected as stale_generation",
              "1500 messages will be redelivered from seq 9000"]}}
```

Clamping, always reported and never silent: `seq:0` → 1; a target below the retained floor →
`first_seq`; `time:T` after the head and `new` → `stream_seq.next`; `start` → `max(1, first_seq)`.

### 8. Message inspection

`GET /v1/streams/{s}/messages/{seq}` and `GET /v1/messages/{id}` return #7's metadata shape with
`body_b64`. `GET /v1/streams/{s}/messages` is the bounded range listing (`from_seq`, `subject`,
`limit`, `include_body`, `order`) with #7's honest partial-answer fields (`complete`,
`scanned_to_seq`). `GET /v1/messages/{id}/data` is added as the mirror of the seq form (one line,
same handler; `PROTOCOL.md` note).

The raw-data endpoint is where the security-relevant detail lives:

```console
$ curl -si --unix-socket /run/messq/messq.sock http://x/v1/streams/orders/messages/10493/data
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 1231
X-Content-Type-Options: nosniff
Cache-Control: private, max-age=31536000, immutable
ETag: "01J8ZQ4K2M9V0X7Y3B5N6C8D1E"
Messq-Seq: 10493
Messq-Msg-Id: 01J8ZQ4K2M9V0X7Y3B5N6C8D1E
Messq-Subject: orders.eu.created
Messq-Trace-Id: 4bf92f3577b34da6a3ce929d0e0e4736
Messq-Published-At: 1757000042190
Messq-Header-Tenant: acme
{"order":4711,…}
```

- The response `Content-Type` is taken from the user header **only if** it parses with
  `mime.ParseMediaType`, is ≤ 128 bytes and holds no control characters; otherwise
  `application/octet-stream`. Publishers control that header, so it is a header-injection and
  stored-XSS vector — `nosniff` is unconditional and the sanitiser is a fuzz target.
- Messages are immutable, so the ULID doubles as a strong `ETag` and `If-None-Match` gets `304` free
  — which is what makes `messq peek --raw | less` cheap on a 1 MiB payload.
- User headers are echoed as `Messq-Header-*` with the same sanitisation; one that cannot be rendered
  safely is dropped and counted in `Messq-Headers-Dropped` rather than mangled.

### 9. Pending listing

```
GET /v1/streams/{s}/consumers/{c}/pending?older_than_ms=&limit=&after=&state=
```

```console
$ curl -s --unix-socket /run/messq/messq.sock \
    'http://x/v1/streams/orders/consumers/worker/pending?older_than_ms=60000&limit=3'
{"stream":"orders","consumer":"worker","limit":3,"next_after":10510,
 "items":[
  {"seq":10493,"id":"01J8ZQ4K2M…","subject":"orders.eu.created","size":1231,
   "state":"inflight","attempt":2,"max_deliver":5,
   "published_at":1757000042190,"delivered_at":1757000102190,
   "deadline":1757000132190,"age_ms":94000,"last_reason":"upstream 503",
   "ack_token":"orders/worker/10493/2/1","trace_id":"4bf92f35…"},
  {"seq":10501,"id":"01J8ZQ4M…","state":"scheduled","attempt":3,"visible_at":1757000140000,
   "ack_token":null,"last_reason":"timeout","trace_id":"…"}]}
```

- Ordered by **deadline ascending** (`visible_at`), so the first row is the next thing to go wrong —
  the ordering `messq pending` (#24) needs, and the reason `oldest_pending_age_ms` has a face.
- `ack_token` is present **only for `state:"inflight"`** rows. Tokens are pure derivations of
  `(stream, consumer, seq, attempt, generation)` (D7), so minting one on a read path mutates nothing,
  and returning it makes "anything the daemon can do to a message, a human can do by hand" (#24)
  true. A `scheduled`/`ready` row has no live lease, so its token would fence-fail; `null` is the
  honest answer. The endpoint requires `consume` or `admin` (#16), so the token grants nothing the
  caller lacked.
- Bounded by construction: the pending set is `<= max_ack_pending` rows (I5), `limit` is clamped to
  `--pending-max-limit` (1 000) with the effective limit echoed, `after` is a seq cursor.

### 12. Edge cases, decided

| Case | Handling |
|---|---|
| `?dry_run=1` on a non-destructive route | `400 dry_run_unsupported` — never silently ignored |
| `DELETE` without `?confirm=` | `409 confirm_required`, message states the blast radius, `next` prints the exact command |
| `?confirm=` does not match the path | `409 confirm_mismatch` naming both values (copy-paste from the wrong terminal is the real failure mode) |
| Invalid name or non-numeric `{seq}` in a path | `400 bad_request` (fails the #7/#9 grammar) — **not** `404`; a typo and an absent resource are different incidents. A valid but absent resource is `404 not_found` |
| `seq` below `first_seq` / at-or-above `stream_seq.next` | #7's `404` with `reason: "expired" \| "never_published"` plus the relevant boundary |
| `POST /v1/streams` on an existing name, different config | `409 stream_exists`; `next` is the equivalent `PATCH` |
| `limit` above the cap | Clamped; the **effective** limit is echoed (silent clamping builds wrong dashboards) |
| Purge or seek with in-flight work | Rows dropped, generation bumped; `warnings` name how many workers will see `stale_generation` |
| Purge while a purge runs on the same stream | `409 purge_conflict` naming the running `purge_id` and remaining rows |
| Crash mid-chunked-purge | The `meta.purge.<ulid>` row survives; recovery (#5) resumes it and logs `stream.purge` with `detail.resumed=true` |
| Seek `seq:0`, or below the retained floor | Clamped to `1` / `first_seq`, `clamped: true` in the impact |
| `time:T` after the head | Resolves to `stream_seq.next`, `clamped: true` |
| `filters` change without `allow_filter_change=1` | `409 would_change_filters` (#9); `next` names `messq seek` as the back-fill |
| `max_ack_pending` lowered below current pending | Accepted; no rows deleted; top-up stalls until the set drains (#9's rule) — a `finding` says so |
| Mutation while latched read-only (#6) | `503 read_only`, no `Retry-After` (it is not coming back); inspection keeps answering from the read pool |
| Mutation while draining (#17) | `503 shutting_down` |
| Any request before recovery completes | `503 not_ready`, `Retry-After: 1`; `/healthz` still `200` |
| `GET` after a `2xx` mutation | Always observes it — the writer commits before replying (read-your-writes, asserted) |
| `Accept: application/x-ndjson` on a listing | One JSON object per line (D2's kept-open door; the shape #20 uses for `follow`) |

## Acceptance criteria

- [ ] Every endpoint in PLAN.md §7 not owned by #14/#20/#29 is registered and answers; a test binds
      the registry to the endpoint block in `docs/PROTOCOL.md` — a documented-but-unregistered route,
      or a registered-but-undocumented one, fails the build.
- [ ] Every route declares `Role`, `Mutates`, `DryRun`, `Confirm`; a `Mutates` route with
      `Role: RoleNone` fails a test (the hook #16 turns into enforcement).
- [ ] `404`/`405` carry the JSON error envelope and, for `405`, a correct `Allow` header; nothing in
      the surface is non-JSON except `/…/data`.
- [ ] Inspection handlers take a read-only store handle, so reaching the writer from one is a compile
      error; a dump of every table is byte-identical before and after an arbitrary inspection
      sequence; such a workload enqueues zero writer commands (`cmdCh` counter, not timing); and
      inspection keeps answering while the writer is latched read-only.
- [ ] `/healthz` returns `200` while recovering, draining, latched read-only and under disk pressure;
      its `degraded[]` carries `kind`/`since` only — never a version, count or path.
- [ ] `/readyz` returns `503` with a distinct `status` for `recovering`, `draining` and `read_only`,
      and `200` under disk pressure with `disk_low` in `degraded[]` — the §4.5 rule, asserted.
- [ ] Neither probe executes a SQL statement (query counter on both pools).
- [ ] `GET /v1/info` reports the `synchronous` pragma read back from a live pooled connection, so a
      durability flag that did not take effect is detectable from `/v1/info` alone; syscall-backed
      fields obey `--info-cache`, `uptime_ms` does not.
- [ ] `?dry_run=1` is accepted exactly on routes that declare it, `400 dry_run_unsupported`
      elsewhere; a dry run leaves zero `events` rows, zero fan-out events, an empty store diff.
- [ ] For `purge`, `seek` and a narrowing `PATCH`, the `impact` from `?dry_run=1` equals the real run
      field-for-field over randomised parameters (property test, not a hand-picked case).
- [ ] Purge deletes exactly the selected messages, drops their delivery rows, bumps `generation` for
      **only** the affected consumers, leaves `stream_seq.next` unchanged, and clamps `cursor_seq`
      forward only when no `subject` filter was given.
- [ ] An outstanding ack token for a purged or sought message is rejected as `stale_generation`, not
      silently accepted as a stale-but-ok ack.
- [ ] A purge above `--purge-max-rows` returns `202` + `purge_id`, fences consumers in the first
      transaction, reports `purging.remaining` and `purge_in_progress`, and resumes after SIGKILL;
      a concurrent purge on the same stream is `409 purge_conflict` naming the running id.
- [ ] `POST /v1/streams` is idempotent for a byte-identical config (`changed:false`, no event) and
      `409 stream_exists` otherwise; `GET …/{s} | jq .config` round-trips through `PATCH`.
- [ ] A `PATCH` lowering `max_msgs`/`max_bytes`/`max_age_ms`, or switching `retention` to
      `workqueue`, is `409 would_lose_data` with an exact eviction count and succeeds with
      `?allow_data_loss=1`; lowering `max_msg_size` or narrowing `subjects` yields a `finding`.
- [ ] `DELETE` on a stream removes its messages, consumers and delivery rows, leaves `<stream>.dlq`
      intact, and names the surviving DLQ (depth + removal command) in a `finding`.
- [ ] `GET /v1/streams` computes per-stream `messages`/`bytes` only with `?stats=1`; the single-stream
      view reports `stats_age_ms` alongside them.
- [ ] `POST …/consumers` is a declarative upsert: an identical body twice yields `changed:false` and
      no `consumer.update` event; an omitted field resets to default. `PATCH` is sparse and
      distinguishes absent from zero.
- [ ] #9's validation findings (`unbounded_redelivery`, `no_backoff`, retry horizon) appear as
      structured `findings`, not prose in `message`.
- [ ] `pause`/`resume` are idempotent; pausing with in-flight rows returns a finding naming the count
      and earliest deadline; a paused consumer's in-flight rows still time out on schedule.
- [ ] `seek` moves the cursor, bumps the generation, drops and counts delivery rows, writes exactly
      one `consumer.seek` event, and reports clamping for `seq:0`, a sub-floor target and a `time:T`
      after the head; `to` uses the same parser as consumer creation.
- [ ] The pending listing is deadline-ascending, honours `older_than_ms`/`state`/cursor pagination,
      clamps `limit` while echoing the effective value, and emits `ack_token` only for `inflight`.
- [ ] `GET /…/messages/{seq}/data` returns stored bytes exactly (0-byte and arbitrary binary
      included), sets `nosniff` + a ULID `ETag`, answers `If-None-Match` with `304`, and never
      reflects an unsanitised publisher-supplied `Content-Type` or header.
- [ ] `POST /v1/admin/log-level` changes the level through the `LevelSetter` seam, `400`s unknown
      levels, returns `changed:false` on a no-op, writes one `admin.action` event.
- [ ] `/metrics` answers `503 not_implemented` (never `404`) until #21's handler is injected.
- [ ] `DELETE` without `?confirm=` is `409 confirm_required` with the blast radius and the exact
      command in `next`; a mismatched confirm is `409 confirm_mismatch`.
- [ ] An invalid resource name or non-numeric `{seq}` is `400`, an absent resource `404`.
- [ ] Every listing is bounded: no request exceeds its clamped `limit` and `next_after` round-trips
      (I11 holds for the API, not only the engine).
- [ ] A `GET` after a `2xx` mutation always observes it (read-your-writes).
- [ ] Every new error code is in #14's closed enum, produced by a test, documented in `PROTOCOL.md`.
- [ ] Coverage floors from #2 pass; no `time.Sleep` in tests; no `time.Now()` outside the Clock seam.

## Test plan

Per PLAN §11 / D13: `-race` everywhere, real SQLite files in `t.TempDir()` (never `:memory:`), no
`time.Sleep`, timing via `testing/synctest` and the Clock seam, every fixed bug landing with a
committed reproduction artifact.

**Unit — `internal/api`**
- Route registry: `(method, pattern)` uniqueness, role on every mutating route, `DryRun`/`Confirm`
  consistency, and the `PROTOCOL.md` binding test (diff documented endpoints against the registry
  both ways).
- Query parameters (`limit`, `after`, `from_seq`, `older_than_ms`, `dry_run`, `confirm`,
  `allow_data_loss`, `stats`): boundaries, negatives, overflow, repeated keys, empties.
- `Content-Type` sanitiser and `Messq-Header-*` echo: control characters, CRLF, over-long values,
  non-UTF-8, media types that fail `mime.ParseMediaType`.
- Health/readiness: every `HealthState` combination × both probes, table-driven; log-level handler
  against a fake `LevelSetter` (each legal level, unknown level, no-op).

**Unit — `internal/queue` (pure)**
- `ParseStartPosition`: `start`, `new`, `seq:0`, `seq:1`, `seq:max`, `time:` as RFC3339 and unix-ms,
  offsets, garbage, empty, `seq:-1`, `seq:abc`.
- Purge argument validation: the `up_to_seq`/`keep` exclusion, wildcard subjects, empty stream.
- Stream-narrowing classifier: each config field × {lower, raise, unchanged} → {refuse, finding,
  silent}, exhaustive over the field set so a new limit cannot be added without a verdict.

**Unit — `internal/store` (real files)**
- `planPurge`/`applyPurge`, `planSeek`/`applySeek` on seeded fixtures: unfiltered, `up_to_seq`,
  `keep`, `subject`, subject + range, empty result, whole-stream.
- Narrowing eviction counts (`max_age_ms`, `max_msgs`, `max_bytes` window function) with equal-size
  messages, zero-size bodies and a limit exactly on a boundary.
- Generation-bump scoping: two consumers, only one holding rows in range — the other is untouched.
- Cursor clamping: forward only, unfiltered only, never backwards (I6).
- Chunked purge: seeded above `--purge-max-rows`; the fencing transaction is complete and small, the
  `meta.purge.*` row exists, chunks progress, the row disappears at the end.
- Upsert/patch semantics for streams and consumers: declarative reset, sparse keep, `changed:false`
  no-churn, `filters` refusal, `max_ack_pending` lowering, stream delete leaving `<stream>.dlq`.

**Property (`pgregory.net/rapid`)**
- **Dry-run equivalence**: random store state × random purge/seek/narrowing parameters; run
  `?dry_run=1`, snapshot the store, run for real, assert the dry run changed nothing and the real
  run's counters equal the previewed `impact` field-for-field. The property #28 and #29 inherit.
- **Listing totality**: for any listing endpoint and page size, walking `next_after` to exhaustion
  yields every row exactly once and terminates.
- Failfiles committed to `testdata/regressions/` and replayed on every run.

**Integration — `httptest` over a Unix socket**
- One test per route: success shape plus every error code it emits, against committed JSON goldens
  with ULIDs, timestamps and sizes normalised (#18 generalises this into its contract suite).
- Side-effect freedom: a `go-cmp` diff of every table before/after a scripted inspection workload
  (peek by seq/id/range, `/data`, pending, consumer info, `/v1/info`, both probes), plus a `cmdCh`
  counter asserting zero enqueues.
- Read-your-writes: `POST` then immediate `GET` in a loop under concurrent publish load.
- Degraded matrix: inspection and probes while latched read-only (#6's seam), draining (#17's seam,
  stubbed) and recovering.
- `/metrics` with and without an injected handler; `Accept: application/x-ndjson` on every listing.

**Fuzz** (60 s per target in CI, corpus committed)
- Path values (stream/consumer names, `{seq}`, `{id}`): never panic, never `500`, always `400`/`404`.
- The seek target parser (shared with #9's start-position parser — one corpus, two callers).
- The response-header sanitiser: no output ever contains a control character or CRLF.

**Crash** (extends #8's harness)
- SIGKILL mid-chunked-purge at named fault points (`after_purge_fence`, `mid_purge_chunk`): restart,
  consumers stay fenced, the purge resumes, `verify` is clean.
- SIGKILL between a seek's commit and its response: cursor and generation come back both old or both
  new, never split.

**Deterministic timing** (`testing/synctest`): `--info-cache` and stream-stats expiry, `uptime_ms`
monotonicity across a simulated day, `Retry-After` values.

**Golden**
- `create → publish×3 → seek → purge` yields exactly `stream.create`, `msg.publish`×3,
  `consumer.seek`, `stream.purge` with the agreed `detail` shapes (vocabulary golden is #19's).
- The curl transcripts above run in CI as executable documentation (#18 owns the harness).

**Benchmarks**
- `BenchmarkConsumerInfo` / `BenchmarkListConsumers` at 100 / 1 000 / 10 000 consumers — what #21's
  collector runs every 5 s and `messq lag` runs interactively.
- `BenchmarkStreamStats` over 10 M messages — the trigger for the `stream_stats` fallback.
- `BenchmarkPendingList` at `max_ack_pending = 100 000`.
- `BenchmarkPurgePlan` over 10 M messages: the plan must stay index-bound (counts, not scans), so a
  regression here means a purge preview became an outage.

**Not tested here:** long-poll and settle shapes (#14), auth and roles (#16), drain semantics (#17),
the frozen-schema contract (#18), trace/events (#20), metric names (#21), retention interaction
(#27), replay and CLI discipline (#28), DLQ redrive (#29).
