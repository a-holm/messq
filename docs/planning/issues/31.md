## Context

PLAN.md publishes numbers. **§12 Performance targets** states seven of them — 5 000 durable msg/s,
20 000 relaxed, p99 ≤ 10 ms, wake latency < 5 ms, recovery ≤ 2 s, < 0.5 % idle core, ≤ 10 % audit
overhead — and calls them *"honest, measured, published"*. §1.5 makes durable throughput a v1.0
success criterion. **D1** makes one of them a design trigger: if the ≥ 5 000 msg/s gate fails,
payload BLOBs move out of SQLite. §11.9 names the mechanism: *"`messq bench` is a first-class
command (publish/e2e/replay), open-loop; nightly benchstat comparison; published numbers always
state hardware, durability mode, and methodology."* §8 lists `messq bench` in the command tree.

None of that exists yet. What exists is a *fragment*: **#8** shipped a measurement mode of a load
generator (`go test ./test/crash -run TestDurableThroughput -crash.gate`) plus a raw fsync probe,
because M2 needed the D1 verdict before M3 could start, and it wrote `docs/perf/M2-baseline.md`
saying explicitly which number it holds — publish → durable response, no consumers, no events, no
retention. Since then #9–#12 added the delivery engine, #19 added an event row per transition,
#21 added a scrape-time collector, #27 added a janitor that deletes. Every one of those changed the
cost of a message, and nothing has re-measured.

This issue turns the fragment into a product surface:

1. **The load generator ships in the binary.** Anyone can reproduce our table on their hardware in
   one command. That is a trust tactic (§1.4's anti-pitch, §1.2's *"Honest"*) as much as an
   engineering one — the same reasoning that makes `messq doctor` (#30) measure the operator's
   actual fsync latency instead of asking them to believe our README.
2. **The methodology is correct by construction.** Open-loop with coordinated-omission correction,
   percentiles from histograms, a generator that **invalidates its own run** rather than reporting a
   comfortable lie when it cannot keep up.
3. **The durability claim is runnable.** `--kill-every` SIGKILLs and restarts the daemon mid-run and
   reports `lost=0 duplicates=N (all accounted for)` — the operator can execute §1.5's crash-test
   row themselves rather than trusting our CI.
4. **The numbers get published with their configuration attached.** `docs/benchmarks.md`, hardware
   and durability mode next to every figure, a reproduce command per row.
5. **A nightly benchstat lane** fills #2's `bench` placeholder job. A regression opens an issue; it
   is **not** a merge gate — #2 already argued the case (*"a permanently-yellow pipeline trains
   people to ignore it"*), and benchmark noise on shared hardware is the classic way to teach a team
   that a red gate means nothing.

Governing PLAN.md material: **§12** (the targets and the re-baselining promise), **§11.9** and
**§11.7** (bench as a first-class command; soak is #33's, not ours), **D1** (the revisit trigger and
what a failing number obliges us to do), **D4** (group commit is *why* `full` is affordable — the
commit-batch distribution is the interpretive key to every publish number), **§8** (the command
tree, the output/exit-code contract), **§9.4** (the metrics bench samples), **§13** (≤ 8 direct
non-test dependencies — this issue adds **zero**, which is why the histogram is ~120 lines of our
own code), **§14 M7** (bench is part of M7's scope and its exit criterion's evidence).

What it unlocks: **#33**'s soak reuses this generator, its schedule and its ledger instead of
growing a third one; **#35** writes the guarantees and comparison pages with measured numbers and a
methodology page to link; **#36** ships a binary whose README numbers a reviewer can reproduce.

## Design proposal

> Proposal, not mandate — **except** five rules that are cheap now and impossible to retrofit into
> published numbers: latency is always measured from *intended* dispatch time; a saturated generator
> invalidates its run; no report renders a number without its environment stamp; `--gate` refuses
> anything but a run whose daemon bench itself spawned; and the nightly comparison never becomes a
> merge gate.

### 0. Budget and constraints

| Constraint | Value | Why |
|---|---|---|
| New direct dependencies | **0** | §13 caps the module at 8 and requires an ADR per addition. `HdrHistogram-go` (plan-06's choice) would be a ninth for one command; a log-linear histogram is ~120 lines we can fuzz. |
| Non-test LOC | ~1 100 | engine ~400 · hist ~120 · env stamp ~200 · report/render ~250 · CLI glue ~150 |
| Hot-path allocations in the generator | 0/op after warm-up | pre-generated payload pool, per-goroutine histograms, pre-sized in-flight table. A generator that GCs during measurement measures its own GC. |
| `time.Sleep` | **allowed here** | §11's ban is on *tests*. The scheduler takes #3's `Clock` seam so its arithmetic is testable under `testing/synctest`; the real clock's sleep-then-spin is one leaf function. |

### 1. Package layout

### 3. The open-loop scheduler and coordinated-omission correction

The failure this prevents, stated once so it stays in the code comments: *a closed-loop generator
that waits for each response before sending the next one reports a 1 ms p99 while the broker is
stalled for five seconds, because the requests that should have been sent during the stall were
never sent, and therefore never counted.*

```go
// schedule.go — proposal
type Schedule struct {
    start   time.Time     // monotonic base
    gap     time.Duration // 1/rate for uniform
    arrival Arrival
    rnd     *rand.Rand    // seeded; poisson only
    n       atomic.Int64  // ticket counter, shared by all dispatchers
}

// Next returns the ticket index and its INTENDED dispatch time. It never blocks.
func (s *Schedule) Next() (i int64, at time.Time)

type Pacer struct{ clk clock.Clock } // #3's seam
// WaitUntil sleeps to within ~20µs of t, then spins. Returns the actual send time.
func (p *Pacer) WaitUntil(ctx context.Context, t time.Time) time.Time
```

Rules:

- `--publishers N` dispatcher goroutines pull tickets from the shared schedule. Each owns one
  keep-alive connection, so a busy connection delays a *dispatch*, and that delay lands in the
  measured latency because the timer started at `at`, not at the send.
- **Every latency is `now() - intended`.** `service` (send → response) is recorded in a parallel
  histogram and printed *labelled as uncorrected*, so the difference between the two is visible
  rather than a claim.
- **Backlog** = tickets whose intended time has passed and which have not been sent. It is bounded
  by `--max-inflight`; the peak is reported.
- All timestamps are Go monotonic readings taken in this one process. The daemon's clock is never
  used for a latency figure — not for `deadline_ms`, not for `published_at` (#22 already reports
  clock skew; bench stamps it and moves on).

### 4. What exactly is measured

| Series | Start | Stop | Mode | Notes |
|---|---|---|---|---|
| `publish_durable` | intended dispatch | publish 2xx received | publish, e2e | Under `full` this is §12 row 1: a durable promise (D4). |
| `deliver` | intended dispatch | the fetch response carrying that seq returns | e2e | At `--rate 10` this is §12's long-poll wake latency; the report names it when the rate is low enough for the measurement to mean that. |
| `ack_e2e` | intended dispatch | the ack response for that delivery returns | e2e | §12's headline round trip. First successful ack only; attempts > 1 are counted separately. |
| `service` | actual send | response | all | Uncorrected, for comparison with tools that report only this. |
| `replay_throughput` | — | — | replay | msg/s and MiB/s over the measurement window; latency percentiles are per fetch *request*, not per message. |

**Correlation (e2e):** the publish response returns `{seq}` (#14). The generator keeps a pre-sized
ring `intended[seq % cap]` written by the publisher and read by the consumer handler; `cap` is
`--max-inflight`, and an overwrite before the read is precisely the saturation condition, so it is
detected rather than silently wrong. `seq` is used, not `Messq-Msg-Id` — no dedup index cost on the
throughput path (dedup keys are used only in `--kill-every`, where they are the point).

### 5. Histograms without a new dependency

```go
// internal/bench/hist — log-linear, 1µs … 60s, 3 significant digits, ~14 KiB per histogram
type H struct{ buckets [nSub * nExp]uint32; over uint64; min, max, sum uint64; n uint64 }

func New() *H
func (h *H) Record(d time.Duration)          // branchless-ish: bits.Len64 + one array increment
func (h *H) Merge(o *H)                      // read-time merge; no locks on the record path
func (h *H) Quantile(q float64) time.Duration
func (h *H) Snapshot() []Bucket              // {lo_ns, hi_ns, count} — dumped into report.json
```

Each dispatcher and each handler owns a histogram; the collector merges at report time. Guarantees
we test rather than assume: relative error ≤ 1 % at every recorded quantile, `Merge` is associative
and commutative, values above 60 s are counted in `over` and force `max` to be reported as
`>60s` rather than clipped silently.

Raw buckets in `report.json` are a deliberate honesty feature: a reader who distrusts our
percentiles can recompute them, and two runs can be merged after the fact.

### 6. The environment stamp

```go
type Environment struct {
    MessqVersion, Commit, GoVersion, GOOS, GOARCH string
    CPUModel string; Cores, GOMAXPROCS int; RAMBytes uint64
    Kernel string                              // uname -r
    DataDir, FSType, MountOptions, Device string
    Rotational bool; WriteCache string          // /sys/block/<dev>/queue/{rotational,write_cache}
    Ephemeral bool                              // tmpfs/overlay/NFS ⇒ never publishable
    Durability string; Pragmas map[string]string // live readback from /v1/info (§4.1)
    CommitWindow time.Duration; CommitMaxBatch int
    FsyncProbe Summary                          // 4 KiB write + fdatasync × 1000, same filesystem
    Spawned bool; Label, Seed string
    StartedAt time.Time
}
```

Rendering rule, enforced by a test: **`report.txt` and `report.json` are produced by one function
that takes `(Environment, Result)`; there is no path that renders a throughput number without the
stamp.** Filesystem/device discovery is a small `/proc/self/mountinfo` + `statfs` +
`/sys/block/…` reader with a seam so the unit tests feed fixtures instead of the host.

### 7. Validity rules — when bench refuses to be believed

`verdict ∈ {valid, invalid, gate_failed}`; `reasons[]` is always populated for the last two.

| Check | Threshold | Verdict |
|---|---|---|
| Dispatch lag | p99 > 1 ms **and** > 5 % of measured p99 | `invalid` — *generator saturated* |
| Backlog | peak ≥ `--max-inflight` | `invalid` — *generator saturated* |
| Generator CPU | > 50 % of the box for a run where the daemon shares it | `invalid` — *generator CPU-bound*; the message names `--publishers`, a smaller `--rate`, or a second box |
| Correlation ring overwrite | any | `invalid` (implies saturation) |
| Achieved rate vs requested | < 98 % without any of the above | `invalid` — *the broker could not absorb the rate*; the ladder treats this as the knee rather than an error |
| Plausibility (#8's cross-check) | measured msg/s > 3 × `commit_batch_mean / fsync_p50` under `full` | `invalid` — *device is not honouring fsync* (lying write cache), with the arithmetic printed |
| Ephemeral filesystem | tmpfs / overlay / NFS under `full` | run proceeds, `publishable:false`, every rendering carries `NOT A DURABILITY NUMBER` |
| Daemon exited unexpectedly | any (outside `--kill-every`) | `invalid`, with the last 40 lines of daemon stderr |
| `--closed-loop` | always | valid but `publishable:false`; percentiles suppressed |
| Interrupted (SIGINT) | any | partial report, `invalid`, exit 1 |

An `invalid` run still prints everything it measured. Hiding the numbers would teach people to skip
the validity line; printing them under a loud verdict teaches them what saturation looks like.

### 8. The ladder — how the headline number is produced honestly

`--ladder` runs each rate for `--stage-duration` with a fresh histogram (warm-up only before the
first stage), and stops at the first stage that is `invalid` **or** whose p99 exceeds `--slo-p99`.
The headline is the last passing stage:

```
$ messq bench publish --spawn --ladder --slo-p99 10ms --out ./perf/run-1763

   500        499.9    0.9ms    2.1ms    4.4ms            2.1   ok
  1000        999.8    1.0ms    2.4ms    5.1ms            4.6   ok
  2000       1999.4    1.2ms    3.0ms    6.9ms            9.2   ok

  8000       7981.0    2.9ms    9.4ms   22.1ms           37.4   ok
```

### 9. `--kill-every` — the durability claim, runnable by the operator

Reuses #8's oracle rather than inventing a second one. The pure three-valued record type moves from
`internal/testutil/ledger` to `internal/ledger` (it has no `testing` imports; #8's harness keeps its
driver and its reconciler); a test asserts both callers agree on a shared fixture.

```go
type Outcome uint8 // Unknown, OK, Failed
type Record struct { Key string; Outcome Outcome; Seq int64; At time.Time }
```

Flow:

1. Every publish carries `Messq-Msg-Id: <ulid>` — retries after a kill are then dedup-safe (§5.1),
   which is the feature being demonstrated as much as the durability one. The stream is created with
   `dedup_window_ms` well beyond the run length (#8's edge case 4).
2. Record `Unknown` before the request; `OK` on 2xx (which under `full` is post-fsync); leave
   `Unknown` on transport error, timeout, or `503 commit_unknown`; `Failed` on a typed 4xx refusal.
3. On each `--kill-every` tick: `SIGKILL` the process **group**, `Wait`, restart with the same
   flags, poll `/healthz` then `/readyz`, record `recovery_ms`. No cleanup between kill and restart —
   the stale socket inode and the `-wal`/`-shm` files must be handled by the daemon (#8 edge cases
   1 and 8), and if they are not, bench finds it on an operator's machine.
4. At the end: every `OK` key must exist (`GET /v1/messages/{id}` or a re-publish returning
   `duplicate:true` with the original seq); every `Unknown` may or may not; every `Failed` must not.
5. **Duplicate accounting (I9):** every delivery with `attempt > 1` is looked up in
   `/v1/events?msg_id=…` and must be preceded by `msg.timeout`, `msg.nak` or `recovery.reclaimed`.
   Unexplained duplicates are listed by id — that is a broker bug and the report says so.

```
  kills 12 (every 5s) · restarts 12 · recovery p50 310ms p99 690ms (§12 budget 2s: PASS)
  publishes 59 984 → ok 59 902 · unknown 82 (41 present, 41 absent — both legal)
  lost 0 · duplicates 313 — all accounted for (recovery.reclaimed 297, timeout 16)
```

`--kill-every` refuses to run against a daemon bench did not spawn. Killing a process the operator
merely pointed us at is not a benchmark, it is an outage.

```
BenchmarkPublish/rate=8000-16  478860  7981.0 msg/s   9.4 p99-ms   2.9 p50-ms   22.1 p999-ms
```

`--out DIR` writes all four artifacts. `timeline.ndjson` carries one object per second — achieved
rate, p50/p99 for that second, in-flight, backlog, dispatch lag, `messq_wal_bytes`, `db_bytes`,
checkpoint count — so a WAL checkpoint stall shows as a spike in a graph rather than smearing into
the p99 with no explanation.

Server-side sampling (`/metrics`, `/v1/info`) is a **soft** dependency: if the endpoint is missing
or unparsable, those fields are omitted and the report says `server sample: unavailable`. Bench must
work against a daemon built before #21 landed and against a future one that renames a gauge.

### 11. `docs/benchmarks.md`

Fixed structure, because the shape is the honesty:

1. **How to reproduce** — the exact command for every number on the page, first, before any figure.
2. **Methodology** — open loop, CO correction, saturation invalidation, histograms, what `full`
   means (D4: 2xx = fsynced), what is *not* measured.
3. **The reference machine** — the full stamp, verbatim from a report.
4. **Results** — one row per §12 target: target, measured, verdict, date, commit, and mode/hardware
   *in the row*, not in a caption.
5. **A/B deltas** — events on/off (§12's ≤ 10 %), `full` vs `relaxed`, consumers 0/4, audit
   sampling on/off.
6. **Caveats** — cloud disks and lying write caches; tmpfs numbers are not durability numbers;
   shared CI runners are floors, never evidence; one-box generator CPU contention; ≥ 100k msg/s is
   the wrong tool (§1.4, link to the migration guide).
7. **History** — a short table of headline numbers per release, so a regression is visible to a
   reader as well as to CI.

Every command block executes in CI through #26's executable-docs harness with `--duration 2s
--ladder 200` overrides, so the page cannot rot even though its numbers are hardware-specific.

### 12. The nightly lane (filling #2's `bench` placeholder)

| Job | Where | What | On failure |
|---|---|---|---|
| `bench-smoke` | hosted runner, nightly | 20 s `publish` + 20 s `e2e` at a low fixed rate; asserts **floors only** (≥ 200 msg/s, commit batch > 1, zero unexplained duplicates) | fail the job — it catches "one fsync per message" and outright breakage; numbers never published |
| `bench-baseline` | reference box, nightly | full ladder for `publish` and `e2e`, both durability modes, `-count=6`; `benchstat` vs `perf/baselines/<host>/latest.benchfmt` | **open or update one issue** labelled `type:chore, area:ops` with the benchstat table; never fails a merge |
| `bench-kill` | reference box, nightly | 5 min `e2e --kill-every 15s` | fail the job — `lost>0` or an unexplained duplicate is a correctness bug, not a performance one |

Regression policy: report a change only when benchstat gives `p < 0.05` **and** the delta exceeds
`max(5 %, 2 × the measured run-to-run noise for that metric)`. The noise figure is not guessed — the
first baseline run records `-count=6` variance into `machine.json` and the threshold derives from it.
Baseline acceptance is explicit and reviewed: `make bench-accept` copies the run into
`perf/baselines/<host>/` with the commit and a required reason line. Nobody silently ratchets a
baseline down to make a red job green.

### 13. Exit codes

Within #23's closed contract; the two bench-specific rows are registered there so
`TestEveryExitCodeIsProduced` covers them.

| Exit | Condition |
|---|---|
| `0` | valid run (and `--gate` satisfied, if given) |
| `1` | `verdict=invalid` — saturated generator, implausible device, daemon died, interrupted |
| `2` | usage: `--kill-every`/`--no-audit`/`--gate` without `--spawn`, `--gate` with `--closed-loop`, unparsable `--gate` expression, `--rate` and `--ladder` together |
| `4` | valid run, `--gate` not met (this is the D1 trigger's signal in CI) |
| `6` | daemon unreachable / spawned daemon never became ready |

### 14. Edge cases, decided

| # | Case | Handling |
|---|---|---|
| 1 | **Timer resolution.** `time.Sleep` cannot pace 200k msg/s | sleep to within ~20 µs, then spin. `messq bench --self-test` paces against a null sink and reports the generator's own dispatch accuracy and ceiling on this box; the number goes in the report so a reader knows where the tool stops being the measurement. |
| 2 | **The generator shares the box with the daemon** | CPU of both processes sampled from `/proc/<pid>/stat` each second; > 50 % generator CPU invalidates (§7); `docs/benchmarks.md` says how to read the attribution. |
| 3 | **Payload generation cost** | A pool of 64 distinct pre-generated bodies (seeded), reused round-robin: no per-message `rand`, no accidental dedup, no unrealistic all-identical pages. |
| 4 | **First run touches a cold DB; later runs a warm one** | `--warmup` excluded from the histogram; the DB size at start/end is stamped; `--reuse` runs report `db_prewarm_bytes` so a warm-cache run is never compared to a cold one by accident. |
| 5 | **Retention/janitor runs mid-measurement** and distorts a publish number | the bench stream is created with limits far beyond the run's volume; the report counts `retention.expire` events observed during the window and marks the run `suspect` (a reason line, not an invalidation) if any occurred. |
| 6 | **WAL checkpoint stall** | not suppressed — it is real operator-visible latency. It is *attributed*: `messq_wal_bytes` and checkpoint counts appear in the timeline, and the human report prints `N checkpoint stalls` next to p99.9. |
| 7 | **`max_ack_pending` is the limit, not the broker** | flow-control holds are counted per consumer; any nonzero count prints *"the consumer config bounded this run"* with the `messq consumer edit` command. Attributing our own config to the broker would be the most embarrassing possible benchmark error. |
| 8 | **The client's ack coalescing hides latency** | `--ack-batch 1` is the default for e2e so the measured ack is a real round trip; `--ack-batch 256` is offered and stamped, because it is what a throughput-tuned worker actually does. |
| 9 | **e2e duplicates** (timeout under load) | counted, excluded from the latency series (first ack only), reported as a rate, and cross-checked against `messq_redelivered_total`. A run with a duplicate rate > 1 % prints *"ack_wait is too short for this rate"* — the same finding #30's doctor gives. |
| 10 | **Publish batching changes the unit** | with `--publish-batch > 1`, one HTTP request carries K messages; latency is reported per *request* and per *message*, both labelled, never silently divided. |
| 11 | **A remote `--addr` daemon** | allowed; `spawned:false`, network RTT included, `--gate` refused. The report prints the daemon's own `/v1/info` uptime and durability so a mismatch is visible. |
| 12 | **`os.Executable()` on a deleted or symlinked binary** | resolved and `stat`ed at spawn; a failure is a clear error naming `--spawn-cmd` (the override that also lets tests spawn a `-cover` build). |
| 13 | **Spawned daemon leaks after a bench crash** | child in its own process group, killed on every exit path including `SIGINT`/`SIGTERM`; `--data-dir` temp trees are removed unless `--keep`. |
| 14 | **Auth** | a spawned daemon listens on a Unix socket in a 0700 temp dir with no tokens (D12's default is the whole story); `--addr` runs pass `--token-file` through like every other command. |
| 15 | **Clock skew between bench and a remote daemon** | detected via `/v1/info` round trip, reported once, never used in a latency computation. |
| 16 | **`--durability relaxed`** | fully supported and separately targeted (§12: ≥ 20 000 msg/s). Every rendering carries the mode; the results table in `docs/benchmarks.md` never puts the two modes in one column. |
| 17 | **Zero-length or oversized `--size`** | `0` allowed (a real workload shape); above the stream's `max_msg_size` is a usage error naming `messq stream edit --max-msg-size`. |
| 18 | **Replay against a stream shorter than the run** | replay finishes early and reports the actual message count and duration rather than padding to `--duration`; a stream with fewer than 10 000 messages prints a warning that the number is cache-dominated. |

## Acceptance criteria

- [ ] `messq bench publish|e2e|replay` exist in the cobra tree with #23's persistent flags, `RunE`
      error propagation, teaching errors, and the exit codes in §13; `--help` for each states what is
      measured and what "valid" means.
- [ ] Latency is measured from **intended dispatch time** in all three modes, and the uncorrected
      `service` series is reported alongside it, labelled as not comparable.
- [ ] A run whose generator cannot keep up is reported as `verdict:invalid` with a reason naming
      dispatch lag or backlog, exits 1, and still prints the measured numbers under the verdict.
- [ ] Percentiles come from `internal/bench/hist`; `report.json` contains the raw bucket counts for
      every series; no new module appears in `go.mod` (`go list -deps` direct count unchanged).
- [ ] Every rendering — human, JSON, benchfmt — carries the environment stamp: rate, size,
      connections, durability mode, live pragma readback, kernel, filesystem + mount options, device
      and write-cache state, Go version, messq version and commit. A test proves there is no code
      path that renders a throughput figure without one.
- [ ] `--ladder` reports the highest stage meeting `--slo-p99` as the headline, prints the
      commit-batch mean per stage, and identifies the knee.
- [ ] The plausibility cross-check fires: a run on a filesystem that does not honour fsync (tmpfs
      fixture) is `invalid` with the arithmetic printed, and a tmpfs run is never marked publishable.
- [ ] `--kill-every` requires `--spawn`, SIGKILLs and restarts the daemon on schedule, and reports
      `lost=0`, duplicates with named causes drawn from `/v1/events`, and recovery p50/p99; an
      unexplained duplicate is listed by message id and fails the run.
- [ ] `--gate 'msg/s>=5000,p99<=10ms'` exits 0 when met and 4 when missed on a valid run, and is
      refused (exit 2) without `--spawn` or with `--closed-loop`.
- [ ] `--output benchfmt` output parses with the pinned `benchstat`, and `benchstat old new`
      produces a comparison table for `msg/s` and `p99-ms` with the correct better-direction.
- [ ] `--out DIR` writes `report.json`, `report.txt`, `run.benchfmt` and `timeline.ndjson`; the
      timeline has one row per second including WAL/db bytes and dispatch lag.
- [ ] `docs/benchmarks.md` exists with the seven sections of §11, states hardware and durability
      mode **in every results row**, gives a reproduce command per row, and its command blocks
      execute in CI through #26's harness.
- [ ] The measured §12 numbers are recorded on the reference box: durable publish+ack ≥ 5 000 msg/s
      at 1 KiB `full`, relaxed ≥ 20 000 msg/s, p99 ≤ 10 ms at moderate load, wake latency < 5 ms,
      recovery ≤ 2 s, audit on/off delta ≤ 10 %, idle daemon < 0.5 % of a core — each with a
      PASS/FAIL verdict. **A FAIL is a recorded verdict and a D1 escape-hatch decision, not a
      blocked merge.**
- [ ] #2's nightly `bench` placeholder is replaced by `bench-smoke`, `bench-baseline` and
      `bench-kill` as specified; `bench-baseline` opens/updates exactly one issue on regression and
      never fails the PR lane.
- [ ] `perf/baselines/<host>/` contains a committed baseline with `machine.json` (including the
      measured run-to-run noise per metric); `make bench-accept` refuses to write one without a
      commit and a reason.
- [ ] The regression detector is proved to fire: a synthetic 20 % slowdown injected into a stored
      benchfmt file makes the comparison step report a regression (gate self-test, #2's sabotage
      discipline).

## Test plan

Per §11: bench is code, so it is tested like code — and the parts that produce published claims are
tested harder than the parts that print them.

**Unit (`internal/bench`)**
- `TestSchedule_Uniform/Poisson` — intended times are exact for uniform and, for Poisson with a
  fixed seed, byte-identical across runs; mean gap within 1 % of `1/rate` over 10⁶ tickets.
- `TestPacer_UnderSynctest` — the pacer is driven by #3's `Clock` inside a `testing/synctest`
  bubble: no wall-clock sleeps, deterministic assertions on wake times (§11's no-`time.Sleep` rule
  holds for our tests even though the shipped pacer sleeps).
- `TestCorrelationRing_OverwriteDetected` — a forced overwrite yields `invalid`, never a wrong
  latency.
- `TestEnvironmentStamp` — fixture `/proc/self/mountinfo`, `statfs` and `/sys/block` inputs produce
  the expected fs/device/write-cache fields; an unreadable source degrades to `unknown`, never
  panics, and marks the run non-publishable when it is the filesystem that is unknown.
- `TestNoRenderWithoutStamp` — reflection/AST check that the report renderers are only reachable
  through the one `(Environment, Result)` entry point.

**Property (`pgregory.net/rapid`)**
- `hist`: random duration multisets — every quantile within 1 % relative error of a sorted-slice
  reference; `Merge` associative and commutative; `Snapshot` counts sum to `n`; values > 60 s land
  in `over` and are never silently clipped.
- `--gate` expression parser: round-trip parse/format, and a fuzz target (§11.6) proving no input
  panics and no malformed expression is silently accepted as satisfied.

**Integration (real daemon, CI-sized)**
- `TestBenchPublish_Smoke` / `TestBenchE2E_Smoke` — spawn a real daemon on `t.TempDir()`, 2 s at a
  low rate: report is `valid`, achieved ≈ requested, every latency series non-empty, JSON parses
  against the frozen shape.
- `TestBenchSaturationIsInvalid` — a rate deliberately far above what a throttled daemon can absorb
  (`--commit-window 200ms`) must yield `invalid` with a saturation reason and exit 1. This is the
  single most important test in the issue: it proves the tool cannot flatter us.
- `TestBenchClosedLoopIsSuppressed` — `--closed-loop` suppresses percentiles and stamps the
  methodology; `--gate` with it exits 2.
- `TestBenchReplay` — a pre-seeded stream is replayed with correct message and byte counts.
- `TestPlausibilityCrossCheck` — run on tmpfs: `publishable:false` and, with a synthetic
  commit-batch/fsync pair, `invalid` with the arithmetic in the reason.
- `TestServerSampleOptional` — a daemon started without `/metrics` reachable still produces a valid
  report with `server sample: unavailable`.

**Crash (nightly, reuses #8's oracle)**
- `TestBenchKillEvery` — 60 s `e2e --kill-every 10s` under `full` and `relaxed`: `lost=0`, every
  duplicate explained by a `msg.timeout` / `msg.nak` / `recovery.reclaimed` event, recovery p99
  ≤ 2 s, `messq verify` clean afterwards. Disagreement with #8's harness on the same fixture fails
  `TestLedgerAgreement`.

**testscript (`test/script/bench.txtar`, in #26's environment)**
- `--kill-every` / `--no-audit` / `--gate` without `--spawn` → exit 2 with the naming error.
- `--rate` with `--ladder` → exit 2; unparsable `--gate` → exit 2.
- Human output golden with the environment stamp masked; `--output json` golden with times and ids
  masked; `--output benchfmt` piped through the pinned `benchstat` (skipped when absent).
- Exit 4 on a gate deliberately set to an impossible threshold; exit 0 on a trivially met one.

**CI / tooling self-tests**
- `TestBenchstatParses` — generated benchfmt parses and compares; a missing `Unit` metadata line
  fails the test rather than producing a silently wrong direction.
- `make gates-selftest` gains a row: a synthetic 20 % regression in a stored baseline must make
  `bench-baseline`'s comparison step report a regression and open exactly one issue (dry-run mode).
- Executable docs: every command block in `docs/benchmarks.md` runs with duration overrides in the
  #26 lane; the page's reproduce commands cannot drift from the flag surface.

**Explicitly not tested here**: correctness under crashes beyond the ledger reconciliation (#8,
#32), soak-scale drift and conservation (#33), the accuracy of `doctor`'s capacity estimates (#30),
and any assertion that the reference numbers hold on a shared CI runner — the smoke job asserts
floors only, and that limitation is documented on the page rather than papered over.
