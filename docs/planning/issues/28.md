## Context

M7 is the milestone whose exit criterion is *"an operator runs an entire incident
(find → inspect → redrive → replay → purge) from the CLI alone"* (PLAN.md §14). #27 made the
daemon survive a week without eating the disk. **This issue makes the two recovery verbs real and
makes every destructive verb in the product behave the same way.**

Two distinct tools are constantly confused, and the confusion is expensive:

- **`seek` moves one consumer's cursor.** No new data exists afterwards. It is scoped to one
  `(stream, consumer)` pair, it bumps `generation` so every outstanding ack token is fenced (D7),
  and it drops that consumer's delivery rows in the same transaction (T10). It is the tool for
  *"this consumer processed the wrong thing / must reprocess / must skip a poisoned window."*
- **`replay` re-publishes copies of a range.** New seq, new id, new `published_at`, original
  `trace_id` preserved, `Messq-Replay-Of` provenance. It is stream-scoped: **every** consumer of
  the target stream sees the copies. It is the reprocess-yesterday button, and the tool for
  *"the transformation was wrong, run the last two hours through the fixed code."*

Alongside them, this issue makes PLAN.md §8's fourth CLI rule enforceable rather than aspirational:

> *Every destructive command has `--dry-run` (exact preview, same renderer as the real run), and
> confirmation by name (`--confirm orders`), plus an `admin.*` audit event with actor.*

#15 built the server-side half of that contract (`plan → impact → (dry_run ? return : apply)`,
`?confirm=`, one `Impact` shape) for `purge`, `seek` and the two `DELETE`s, and #24 built the first
CLI form of it for `stream rm|purge` and `consumer rm`. Neither made it **uniform or mechanised**:
`seek` does not yet require confirmation, `replay` does not exist at all, nothing proves that a new
destructive verb cannot ship without a preview, and #29's `dlq redrive` is about to inherit whatever
shape this issue leaves behind.

Governing PLAN.md material:

- **§5.1 T10 (`seek`)** — *"`generation++`, cursor reset, delivery rows dropped (counted)"*, event
  `consumer.seek` at WARN. Fencing (D7) is what makes a rewind safe while workers are running.
- **§8 CLI design** — the `seek` and `replay` signatures are frozen there:
  `messq seek <stream> <consumer> --to start|new|seq:N|time:T [--dry-run]` and
  `messq replay <stream> --from-seq A --to-seq B [--subject PAT] [--to-stream X]`; plus the
  dry-run/confirm/audit rule above, data-to-stdout, and the next-command footer.
- **§9.2 event vocabulary (closed set)** — `consumer.seek`, `stream.purge`, `stream.delete`,
  `consumer.delete`, `dlq.redrive`, `admin.action`. **Replay invents no new event name.**
- **D7 (fenced tokens)**, **D10 (ULID ids)**, **D11 (events table is the audit trail)**,
  **D12 (`actor` on every admin action)**, **§4.2 schema** (`consumers.generation`,
  `messages_age`, `stream_seq`), **§5.2 I3/I6/I7** (an acked pair is never redelivered *except via
  explicit seek/replay/redrive* — this issue is that exception, and must make it explicit,
  audited and previewable).

Two properties this issue owns, because #29 and every later verb inherit them:

1. **A preview is the truth.** The number in `--dry-run` is produced by the same plan the real run
   applies, not by a second estimator that drifts.
2. **A destructive verb cannot ship undisciplined.** Discipline is a route attribute plus a test
   that walks the surface — not a code-review convention.

## Design proposal

> A starting point, not a mandate — except the five items marked **_decision_**, which are cheap now
> and expensive after #29 copies them and #18's contract goldens freeze the wire.

### 1. Seek vs. replay, in the product's own words

The help text, the runbook and `messq help concepts` all render this table; it is the whole reason
both verbs exist:

| | `messq seek` | `messq replay` |
|---|---|---|
| Changes | one consumer's `cursor_seq` | the contents of a stream |
| Scope | `(stream, consumer)` | every consumer of the target stream |
| Creates messages | no | yes — one copy per source message |
| Fences tokens | yes (`generation++`) | no |
| Works after retention deleted the range | no (clamped, reported) | no (missing seqs counted, reported) |
| Reversible | yes (seek back) | no (the copies exist; `purge` removes them) |
| Typical trigger | "this worker must reprocess / must skip" | "the code was wrong; run yesterday through the fix" |

### 2. Position grammar and `time → seq` resolution

```go
// internal/queue/position.go — extends #9's parser; ONE grammar for consumer `start`,
// seek `--to`, replay `--from-time/--to-time`, and #27's age arithmetic.
//
//   start | first | new | seq:N | time:2026-11-02T07:12:04Z | time:-2h
func ParseStartPosition(s string) (StartPosition, error)   // #9, extended with time:-<dur>
```

**_Decision 1: relative times are resolved by the daemon, never by the client._** `published_at` was
stamped by the writer's clock (#6's monotonic `batchNow`); a laptop two minutes off would silently
seek to the wrong place. The CLI sends `time:-2h` verbatim; the response echoes the resolved
absolute timestamp *and* seq so the operator sees what the daemon decided.

```sql
-- resolve time:T to the first seq at or after T
SELECT seq FROM messages
 WHERE stream = :s AND published_at >= :t
 ORDER BY published_at, seq LIMIT 1;                       -- messages_age(stream, published_at)
```

The `ORDER BY published_at, seq` tie-break is not decoration: a group commit stamps every message in
the batch with the same millisecond (#6), so ordering by timestamp alone picks an arbitrary member
of the batch. Monotonic `batchNow` makes `published_at` non-decreasing in `seq`, which is what makes
this index seek equivalent to `min(seq)`; `verify` gets a cheap checker (**P-TS1**: no
`published_at` inversion within a stream) so the assumption is proven rather than assumed.

Clamping rules, always reported with `clamped: true`, never silent (extends #15's list):

| Target | Resolves to |
|---|---|
| `seq:0`, or below `first_seq` | `max(1, first_seq)`, warning naming the unrecoverable count |
| `seq:N` above head, `new`, `time:T` after head | `stream_seq.next` |
| `start`/`first` | `max(1, first_seq)` |
| `time:T` before `first_ts` | `first_seq` |
| `time:T` on an empty stream | `stream_seq.next`, impact all zeros |

### 3. Seek: what this issue adds to #15

#15 owns `planSeek`/`applySeek` and the endpoint. Three additions:

**(a) Sharper impact.** The operator needs to know what will be *redelivered* versus *skipped*,
which are opposite mistakes:

```go
type SeekImpact struct {           // marshalled inside #15's Impact (additive, omitempty)
    Direction     string `json:"direction"`               // "back" | "forward" | "none"
    CursorBefore  int64  `json:"cursor_before"`
    CursorAfter   int64  `json:"cursor_after"`
    ResolvedTime  int64  `json:"resolved_time,omitempty"` // echo for time:T / time:-dur
    Redeliver     int64  `json:"redeliver,omitempty"`     // matching msgs in [after, before)
    Skip          int64  `json:"skip,omitempty"`          // matching msgs in [before, after)
    PendingDropped int64 `json:"pending_dropped"`
    InflightFenced int64 `json:"inflight_fenced"`
    GenerationAfter int64 `json:"generation_after"`
    Clamped       bool   `json:"clamped,omitempty"`
    Warnings      []string `json:"warnings,omitempty"`
}
```

`Redeliver`/`Skip` count **filter-matching** messages, using the consumer's compiled filters (#3) —
a consumer filtered to `orders.eu.>` must not be told 1.3 M messages are coming when 40 k are.
Bounded: the count runs over `deliveries_seq`/`messages_subj` and is capped at
`--seek-count-limit` (100 000) with `complete: false` past the cap, rather than scanning 10 M rows
inside the writer's batch.

**(b) A rewind must wake the parked waiters.** `applySeek` publishes a wake for
`(stream, consumer)` into #14's waiter registry after commit. Without it a rewound consumer whose
worker is parked in a 30 s long-poll sits idle until the next publish — the bug report would be
*"seek did nothing"*, and it would be intermittent, which is worse.

**(c) `?confirm=` on seek.** See §5; this tightens a route #15 shipped without confirmation.

```sql
-- apply, one transaction (#15's applySeek, unchanged in shape)
DELETE FROM deliveries WHERE stream=:s AND consumer=:c;                     -- counted
UPDATE consumers SET cursor_seq=:target, generation=generation+1 WHERE stream=:s AND name=:c;
INSERT INTO events (…, 'consumer.seek', …);                                 -- WARN, actor set
```

Delivery rows are **always** dropped — #9's C3 checker (`row.generation = consumer.generation`) is
what lets #10 and #11 treat a mismatch as impossible-by-construction rather than a runtime branch.

### 4. Replay

#### 4.1 Wire

```
POST /v1/streams/{s}/replay        [?dry_run=1] [?confirm=<target stream>] [?force=1]
{
  "from_seq": 9180, "to_seq": 9411,            // or "from_time":"-2h", "to_time":"-1h"
  "subject":  "orders.eu.>",                    // optional filter, #3 matcher
  "to_stream":"orders",                         // default: the source stream
  "limit":    10000,                            // rows this request may copy (server-capped)
  "batch_id": "01JB…"                           // optional; minted when absent, echoed always
}
→ 200 {"applied":true,"replay":{ …ReplayImpact…, "complete":false, "last_origin_seq":9310 }}
```

**_Decision 2: replay is a paced client loop over a bounded server verb — never a server-side job._**
One request copies at most `--replay-max-rows` (10 000) and returns `complete` plus
`last_origin_seq`. The CLI loops with a token bucket (`--rate`, default 1 000 msg/s) and prints
progress. Rationale: no job registry, no crash-resume protocol, no cancel endpoint; `Ctrl-C` leaves
a consistent prefix, and the exact resume command is printed. This is deliberately *unlike* #15's
chunked purge — a half-purged stream is not a state an operator can reason about, whereas a
half-replay is simply fewer copies.

```go
type ReplayImpact struct {
    Source        string `json:"source"`
    Target        string `json:"target"`
    FromSeq       int64  `json:"from_seq"`        // frozen at plan time
    ToSeq         int64  `json:"to_seq"`          // frozen at plan time
    HeadAtPlan    int64  `json:"head_at_plan"`
    Matched       int64  `json:"matched"`
    Bytes         int64  `json:"bytes"`
    Missing       int64  `json:"missing"`          // seqs in range no longer retained
    FilteredOut   int64  `json:"filtered_out"`
    SkippedLoop   int64  `json:"skipped_loop"`     // Messq-Replay-Count >= --max-replay-count
    Copied        int64  `json:"copied"`           // 0 on a dry run
    FirstNewSeq   int64  `json:"first_new_seq,omitempty"`
    LastNewSeq    int64  `json:"last_new_seq,omitempty"`
    LastOriginSeq int64  `json:"last_origin_seq,omitempty"`
    Complete      bool   `json:"complete"`
    PerConsumer   []ConsumerDelta `json:"per_consumer"` // {consumer, matched} incl. zeros
    BatchID       string `json:"batch_id"`
    Warnings      []string `json:"warnings,omitempty"`
}
```

#### 4.2 The copy rules (the part that must not be improvised)

| Field | Copy value | Why |
|---|---|---|
| `seq` | new, from the target's `stream_seq` | the copy is a new row (§4.2) |
| `id` | **new ULID** | #12's **P-ID1** — only a `.dlq` stream may hold duplicate ids. The lineage link is a header + event detail, not a shared id |
| `trace_id` | **preserved** | `messq trace --trace-id T` shows origin and copy as one story (#20) |
| `published_at` | **now** | preserving it would make age retention delete the copies on the next sweep and make every timeline lie |
| `subject` | preserved | routing and consumer filters must behave as they did |
| `body` | byte-identical | asserted by a test |
| `hdr` | user headers preserved verbatim, `Messq-*` provenance added | §5.1's reserved-prefix rule |
| `dedup_key` | **NULL** unless `batch_id` is supplied | see below |

Provenance headers on every copy:

```
Messq-Replay-Of:            01J8ZQ4K2M9V0X7Y3B5N6C8D1E   (origin message id)
Messq-Origin-Stream:        orders
Messq-Origin-Seq:           9184
Messq-Origin-Published-At:  1762063924114
Messq-Replay-At:            1762070000000
Messq-Replay-Batch:         01JBQ8R2Z0K7Y4T3M1N9V5C2D8
Messq-Replay-Count:         1                            (origin's count + 1)
```

**_Decision 3: the copy's dedup key is cleared unless the operator names the batch._** Preserving
the origin's `Messq-Msg-Id` would make a replay inside the dedup window silently copy nothing
(`duplicate: true` on every row) — a catastrophic no-op that looks like success. With an explicit
`--batch-id`, each copy takes `dedup_key = "replay:<batch>:<origin_seq>"`, which makes a *retried*
replay idempotent within `dedup_window_ms`. Beyond that window the honest answer is the resume
command built from `last_origin_seq`, and the help text says exactly that.

**_Decision 4: the source range is frozen at plan time._** `to_seq` defaults to the head observed by
the plan (`head_at_plan`), and every chunk re-reads the same frozen bounds. Replaying into the
source stream otherwise feeds itself: the copies land inside the range still being scanned, and the
loop terminates only when the disk does. A supplied `to_seq` above `head_at_plan` is clamped, and
the clamp is reported.

#### 4.3 The command

```go
// internal/store — one writer command per chunk (#6 Cmd; savepoint per command)
type ReplayCmd struct {
    Src, Dst  string
    FromSeq   int64  // frozen, inclusive
    ToSeq     int64  // frozen, inclusive
    Cursor    int64  // resume point within the frozen range
    Subject   string // "" = all
    MaxRows   int64  // <= --replay-max-rows
    MaxBytes  int64  // <= --replay-chunk-bytes (8 MiB) — protects #6's batch budget
    BatchID   string
    Force     bool
    Actor     string
}
func (s *Store) Replay(ctx context.Context, c ReplayCmd) (ReplayImpact, error)
func (s *Store) PlanReplay(ctx context.Context, c ReplayCmd) (ReplayImpact, error) // read pool
```

`Apply` reads the source rows through the same `tx` (never the read pool — a replay must see a
consistent snapshot of its own writes), then reuses #7's insert path so that limits, the reserved
header prefix, the `messages` insert and the `msg.publish` event are one code path:

```sql
SELECT seq, id, subject, hdr, body, size, trace_id
  FROM messages
 WHERE stream = :src AND seq >= :cursor AND seq <= :to
 ORDER BY seq LIMIT :max_rows;                             -- PK range scan
```

`Bytes()` returns the summed payload so #6's byte budget throttles a replay of 1 MiB messages down
to a few per batch instead of 256.

**Plan-time refusals (all of them, before a single copy exists).** Half a replay that fails at row
4 000 because the target's `max_msg_size` is smaller is the failure mode this list exists to
prevent:

| Condition | Code | `next` |
|---|---|---|
| Target stream missing | `not_found` | `messq stream add <target> --subject …` |
| `max(size)` in range > target `max_msg_size` | `message_too_large` | `messq stream edit <target> --max-msg-size …` |
| A matched subject is rejected by the target's `subjects` | `subject_rejected` | `messq stream edit <target> --subject …` |
| Target at limits with `discard=new` | `insufficient_space` | `messq stream purge` / `edit --max-msgs` |
| Free disk below `--min-free-bytes` (#27) | `disk_full` | `messq doctor` |
| Store latched read-only (#6) / draining (#17) | `read_only` / `shutting_down` | — |
| Source `retention=workqueue` and range partly gone | not a refusal — `missing` count + warning | — |

### 5. The destructive-action discipline (server side)

**_Decision 5: destructiveness is a route attribute, and a test walks the registry._** #15's `Route`
gains one field:

```go
type Route struct {
    // … #15's fields …
    Destructive bool   // deletes, duplicates, or re-delivers data
    Audit       obs.Kind // the audit-class event this route MUST emit when applied
}
```

```go
// TestDestructiveDiscipline — the whole point of this issue, in one test.
for _, r := range api.Routes(deps) {
    if !r.Destructive { continue }
    require(r.DryRun,          "must accept ?dry_run=1")
    require(r.Confirm != "",   "must declare a confirm target")
    require(r.Role == RoleAdmin,"must require the admin role")
    require(r.Audit != 0,      "must declare its audit event")
}
```

The classified surface, and its audit event:

| Route | Confirm | Audit event | `detail` |
|---|---|---|---|
| `DELETE /v1/streams/{s}` | stream | `stream.delete` | `messages`, `bytes`, `consumers[]`, `actor` |
| `POST /v1/streams/{s}/purge` | stream | `stream.purge` | `impact`, `actor` |
| `DELETE …/consumers/{c}` | consumer | `consumer.delete` | `pending_dropped`, `actor` |
| `POST …/consumers/{c}/seek` | consumer | `consumer.seek` | `to`, `to_seq`, `from_seq`, `generation`, `pending_dropped`, `direction`, `actor` |
| `POST /v1/streams/{s}/replay` | target stream | `admin.action` | `action:"replay"`, `params`, `before`, `after`, `actor` |
| `POST /v1/dlq/{s}/redrive` (#29) | stream | `dlq.redrive` | per #19 |

**_Decision 6: one audit row per execution, and it is the domain event where one exists._** The
backlog phrases the rule as *"every execution writes an `admin.action` event"*; taken literally that
means `consumer.seek` **and** `admin.action` for the same act — two rows saying one thing, and a
`trace` that reads double. The rule this issue implements is the same rule with the redundancy
removed: **every destructive execution writes exactly one audit-class event carrying `actor`, the
params and before/after counts**; `admin.action` is that event only for verbs the closed vocabulary
(§9.2) has no name for — today: `replay`, plus #15's log-level and #17's reload. No new event names
are minted, which is exactly why replay had to fit this shape.

**_Decision 7: a preview writes nothing durable._** A dry run is a read that happens to ride the
writer; it emits no event row. Two reasons, one of them load-bearing: (1) `stream.purge` and
`consumer.seek` are `fold: yes` in #19's table, so a rolled-back preview emitting one would break
I10 (*folding the events table reproduces the state*) and #13's fold model; (2) previewing is the
behaviour we want to be free, and taxing it with an audit row discourages the habit the whole
discipline is built to create. Consequence, and an amendment this issue makes to #19: the
`dry_run` key is removed from `stream.purge`'s documented `detail` and from `docs/log-schema.md` —
**a persisted destructive event always means the action happened.** Revisit trigger: if an operator
ever needs "who previewed what", it returns as `--audit-previews` writing `admin.action` with
`dry_run: true`, never as a `fold: yes` event.

**_Decision 8: `confirm_required` is impact-driven._** A route declaring `Confirm` demands
`?confirm=<name>` **when the plan's impact is non-empty**, evaluated inside the same transaction as
the apply, so there is no preview/apply race. A seek that moves nothing, or a purge that would
delete nothing, applies without ceremony; the moment it costs something, the name must be typed.
Deletes are unconditional (the resource itself is the impact). This is what makes it acceptable to
add confirmation to `seek` — a route #15 shipped without it. The tightening lands with #18's
contract golden updated in the same PR; both are pre-1.0.

Error codes added to #14's closed enum: `subject_rejected`, `insufficient_space`,
`replay_loop_guard`. Reused: `confirm_required`, `confirm_mismatch`, `dry_run_unsupported`,
`invalid_seek_target`, `not_found`, `message_too_large`, `disk_full`, `read_only`,
`shutting_down`, `stale_generation`.

### 6. The destructive-action discipline (CLI side)

```go
// internal/cli/destructive.go — #24's helper, generalised. #29 imports this file and adds nothing.
type Destructive struct {
    Verb     string                                   // "seek" | "replay" | "purge" | "rm" | "redrive"
    Resource string                                   // the name the operator must type
    Preview  func(context.Context) (client.Impact, error) // ?dry_run=1
    Apply    func(context.Context) (client.Impact, error)
    Render   func(client.Impact, RenderOpts, bool /*applied*/) View // ONE renderer, both paths
    Hints    func(client.Impact) []Hint
}

func (d Destructive) Run(cmd *cobra.Command, f DestructiveFlags) error
type DestructiveFlags struct{ DryRun bool; Confirm string; Yes bool; Rate int; Limit int64 }
```

Rules, all test-enforced:

1. `--dry-run` → `Preview` → `Render(applied=false)` → exit `0`. It never sends `?confirm=`.
2. No `--confirm` and a non-empty impact → exit `2`, printing the exact command with
   `--confirm <name>` filled in (never a `y/N` prompt — **there is no interactive prompt anywhere in
   messq**; typing the name is the friction, and it is copy-pasteable).
3. Non-TTY stdin without `--yes` → exit `2` naming `--yes`. `--confirm` proves you know *what*;
   `--yes` proves the automation was written to destroy.
4. Server `confirm_mismatch` → exit `4`, rendering both names (copy-paste from the wrong terminal is
   the real failure mode).
5. Preview and apply render through the same function; a golden test diffs the two renderings on a
   quiesced fixture and requires them to differ only in the leading verb tense and `applied`.

### 8. Flags added by this issue

| Flag | Env | Default | Meaning |
|---|---|---|---|
| `--replay-max-rows` | `MESSQ_REPLAY_MAX_ROWS` | `10000` | Server cap on copies per replay request |
| `--replay-chunk-bytes` | `MESSQ_REPLAY_CHUNK_BYTES` | `8MiB` | Payload budget per replay writer command |
| `--max-replay-count` | `MESSQ_MAX_REPLAY_COUNT` | `3` | `Messq-Replay-Count` above this is skipped without `--force` |

| `--rate` | — | `1000` | CLI pacing for `messq replay` (msg/s; `0` = unpaced, warned) |
| `--limit` | — | `0` | CLI cap on total copies (`0` = the whole plan) |

| `--force` | — | `false` | Include loop-guarded messages |
| `--to-stream` | — | source | Replay target |
| `--yes` / `--confirm` / `--dry-run` | `MESSQ_YES` | — | #24's flags, now uniform across all destructive verbs |

### 9. Edge cases, decided

| Case | Handling |
|---|---|
| Seek while workers hold tokens | Rows dropped, generation bumped; the workers' next ack is `409 stale_generation` → exit `4` with `messq consumer info` as the hint. Preview states the count up front |
| Seek forward (skipping work) | `direction: "forward"`, warning *"N matching messages will never be delivered to this consumer"* — the opposite mistake from a rewind and never rendered with the same words |
| Seek to the current cursor | Impact all zeros, `direction: "none"`, no confirm required, **generation still bumped and rows still dropped** (T10 has one behaviour), `applied:true` |
| Seek on a paused consumer | Allowed and recommended: pause → seek → resume is the runbook, and the hints print it |
| Seek with a parked long-poll | Waiter woken after commit (§3b); asserted with `testing/synctest`, not a sleep |
| Seek below the retained floor | Clamped to `first_seq`, `clamped:true`, warning naming how many messages are gone for good |
| Seek on a `workqueue` stream | Allowed; rewound messages may already be deleted. The preview counts *existing* messages, so the number is the truth |
| Two seeks race | Serialized by the single writer; the second observes the first's generation. `generation` is monotone (checker) |
| Replay into the source stream | Legal and common; range frozen at plan time (Decision 4); the preview prints the `!` line naming every consumer that will receive copies |
| Replay of a range containing earlier copies | `Messq-Replay-Count` increments; at `--max-replay-count` they are skipped as `skipped_loop` unless `--force`. `replay_loop_guard` explains it |
| Replay from a `.dlq` stream | Allowed, but the hint names `messq dlq redrive` (#29), which strips provenance and applies the redrive guard rails. Replay preserves DLQ provenance headers verbatim — it is a copy, not a rehabilitation |
| Replay when the target has consumers with `start:new` | They receive the copies (the copies are new); stated in the per-consumer preview |
| Replay matching zero messages | `applied:true`, `copied:0`, exit `5`, message names the likely cause (subject filter vs. retention) |
| Replay interrupted (Ctrl-C, daemon restart, network) | A committed prefix survives; the CLI prints the exact `--from-seq` resume command. No server-side job exists to be orphaned |
| SIGKILL mid-replay | Each chunk is one transaction: the copies from committed chunks exist, the rest do not. No torn copy, no duplicate copy from a re-run **with** `--batch-id` inside the dedup window |
| Replay + `--rate 0` | Allowed; prints a warning that the writer will be saturated and names `--rate` |
| Replay hitting `retention.blocked`/disk pressure mid-run | Chunk fails with the typed error; prior chunks stand; resume command printed. Publishes are rejected while acks keep flowing (§4.5) |
| `--dry-run` with `--confirm` | Accepted; the confirm is ignored and a stderr note says so (refusing it would punish the safest possible habit) |
| `--dry-run` on a non-destructive route/command | `400 dry_run_unsupported` / CLI exit `2` — never silently ignored |
| Destructive verb while latched read-only or draining | `503 read_only` / `shutting_down`; the *preview* also fails, because a preview that cannot be executed is misleading |
| `--confirm` on a stream whose name contains uppercase | Compared byte-exactly; #7's case-insensitive *uniqueness* rule does not make confirmation case-insensitive |
| Replay of messages with no user headers | `hdr` is the provenance object alone (#12's rule for the DLQ copy, reused) |
| Non-UTF-8 subjects/reasons in a preview | Escaped per #24's rule before rendering; the fuzz target covers it |

### 10. Considered and deferred

| Idea | Why not now | Revisit trigger |
|---|---|---|
| `--into consumer:<name>` (plan-04: replay into a throwaway consumer) | PLAN §8 froze `replay` as stream-scoped re-publish; "replay for one consumer" is `seek` on a consumer created with `start:seq:N` — two existing verbs, zero new concepts | Three users ask for a replay that no other consumer observes |
| `--speed original` (replay at the original inter-message timing) | A load-shape tool wearing a recovery tool's clothes; `messq bench` (#31) owns load shapes | Someone needs to reproduce a timing-dependent bug |
| Server-side replay job with progress/cancel endpoints | Decision 2 — a job registry, a crash-resume protocol and a cancel race, for a verb run a handful of times a year | A replay must survive the operator's SSH session dying |
| Preserving the origin `published_at` on copies | Age retention would delete them instantly and every timeline would lie; the origin timestamp is a header | Never |
| `admin.action` on previews | Decision 7 (I10 fold safety + previewing must stay free) | An audit requirement for reads; ships as `--audit-previews` |
| Interactive `y/N` confirmation | PLAN §8 says confirmation by name; a prompt cannot be copy-pasted into a runbook and trains muscle-memory `y` | Never |
| Undo for replay (`messq purge --batch <id>`) | `stream purge --subject`/`--up-to-seq` plus the reported `new seq` range already removes exactly the copies; a batch index is a new index for a rare op | Replays routinely need reversal |

## Acceptance criteria

- [ ] `messq seek <stream> <consumer> --to start|new|seq:N|time:T|time:-<dur>` renders the impact in
      all three output faces; `--dry-run` counts (`cursor_before/after`, `redeliver`, `skip`,
      `pending_dropped`, `inflight_fenced`, `generation_after`, `clamped`) are **field-for-field
      identical** to the real run's on a quiesced fixture.
- [ ] A seek bumps `generation`, deletes every delivery row for that consumer in the same
      transaction, and emits exactly one `consumer.seek` event at WARN carrying `actor`, `to`,
      `to_seq`, `from_seq`, `generation`, `pending_dropped`, `direction`.
- [ ] After a seek, an ack minted before it is rejected with `stale_generation` (409 / exit `4`), and
      #9's C3 checker reports zero rows whose generation differs from their consumer's — under a
      concurrent fetch/settle workload.
- [ ] A consumer parked in a long-poll receives the rewound messages without waiting for the next
      publish or timeout (waiter wake, asserted under `testing/synctest`).
- [ ] `time:T` and `time:-<dur>` resolve through one parser shared with #9's `start`, are resolved by
      the daemon's clock, echo the resolved absolute timestamp and seq, and clamp per §2 with
      `clamped: true`.
- [ ] `POST /v1/streams/{s}/replay` exists, is registered `Destructive`, accepts `?dry_run=1` and
      `?confirm=<target>`, and is documented in `PROTOCOL.md` (the registry↔doc test from #15 passes).
- [ ] A replayed copy has a **new** seq and a **new** ULID id, preserves `trace_id`, `subject` and
      body bytes exactly, sets `published_at = now`, carries `Messq-Replay-Of`,
      `Messq-Origin-Stream/-Seq/-Published-At`, `Messq-Replay-At/-Batch/-Count`, and preserves user
      headers verbatim.
- [ ] `messq trace --trace-id <T>` shows the origin's lifecycle and the replayed copy's lifecycle as
      one story; `verify`'s **P-ID1** (no duplicate ids outside a `.dlq` stream) stays clean after a
      replay into the source stream.
- [ ] The source range is frozen at plan time: replaying a range into its own stream terminates with
      exactly `matched` copies, proven by a test that would loop forever without the freeze.
- [ ] Every plan-time refusal in §4.3 is returned **before any copy is written** (`not_found`,
      `message_too_large`, `subject_rejected`, `insufficient_space`, `disk_full`), each with a
      teaching `next`.
- [ ] A replay larger than `--replay-max-rows` completes through the paced CLI loop, honours
      `--rate` within ±10 %, and an interruption prints a resume command that, when run, produces
      exactly the missing copies and no duplicates.
- [ ] Re-running an interrupted replay with the same `--batch-id` inside `dedup_window_ms` copies
      each origin message at most once (dedup on `replay:<batch>:<origin_seq>`).
- [ ] `TestDestructiveDiscipline` fails the build if any `Destructive` route lacks `?dry_run=1`, a
      `Confirm` target, `RoleAdmin`, or a declared audit event.
- [ ] Every destructive execution writes **exactly one** audit-class event with `actor` set and
      before/after counts in `detail`; a dry run writes **none** (asserted by an events-table diff).
      `admin.action{action:"replay"}` is used only where §9.2 has no domain event.
- [ ] `confirm_required` is impact-driven: a zero-impact seek or purge applies without `?confirm=`;
      a non-zero-impact one is refused with the exact command in `next`; the check runs in the apply
      transaction (no preview/apply race).
- [ ] Every destructive CLI command (`seek`, `replay`, `stream purge`, `stream rm`, `consumer rm`)
      goes through the one `Destructive` helper: `--dry-run`, `--confirm <name>`, `--yes` on non-TTY,
      no interactive prompt anywhere, and a preview rendered by the same function as the apply.
- [ ] #13's `wantBlocked` is `{retention:"#27", redrive:"#29"}`; the `seek` and `purge` SUT adapters
      are live and a `replay` action is registered; the property suite is green over the M3 budget
      with the new actions enabled.
- [ ] `messq_replayed_total{stream}` and `messq_seeks_total{stream,consumer}` are exported; #21's
      cardinality golden is updated and still forbids subject/id labels.
- [ ] `SEMANTICS.md`, `OPERATIONS.md` (the reprocess-the-last-two-hours runbook), `PROTOCOL.md` and
      `docs/log-schema.md` are updated in this PR, and their command blocks execute in CI (#18).

## Test plan

**Unit (`internal/queue`, `internal/store`)**
- Position grammar table test: every form, every clamp case, malformed inputs; `FuzzParsePosition`
  (differential against a naive reference, corpus committed) extends #9's target.
- `time → seq` resolution: same-millisecond batches (the `ORDER BY published_at, seq` tie-break),
  before-first, after-head, empty stream; a property test asserting `resolve(t) = min{seq |
  published_at ≥ t}` against a brute-force scan.
- Seek plan/apply: direction classification, redeliver/skip counts with narrow filters, the
  `--seek-count-limit` truncation flag, zero-impact seek still bumping generation.
- Replay copy rules: golden `Message` before/after (body bytes, headers, trace_id, new id/seq,
  `published_at`), loop-guard arithmetic, dedup-key construction with and without `--batch-id`.

**Property (`pgregory.net/rapid`, #13)**
- `seek` and `purge` SUT adapters go live; a `replay` action (bounded ranges, both same-stream and
  cross-stream targets) is added. All of I1–I11 checked after every action, plus the new checkers
  P-TS1 (no `published_at` inversion) and re-verification of #9's C1/C3 and #12's P-ID1.
- Targeted invariant: **I3 holds except through seek/replay/redrive** — every redelivery of an acked
  pair in the history is preceded by a `consumer.seek` for that pair's generation.
- Committed failfiles under `testdata/regressions/rapid/` per usual.

**Crash (`internal/testutil`, #8's harness)**
- SIGKILL at random points during a paced replay of 50 k messages; on restart assert: the copy set
  is a prefix of the plan (contiguous by origin seq), no torn or duplicate copy, `verify --deep`
  clean, `integrity_check` clean, and the CLI resume command produces exactly the remainder.
- SIGKILL between the delivery-row delete and the generation bump is impossible by construction
  (one transaction) — asserted by a fault point that kills inside the seek command and shows the
  post-restart state is one of exactly two, never a hybrid.

**Integration**
- Fencing: 8 workers holding tokens, seek, assert every outstanding ack returns `stale_generation`,
  `messq_stale_acks_total` moves, and `trace` shows the rejection with a named cause.
- Waiter wake: consumer parked in a 30 s long-poll, seek back, message arrives within the
  synctest bubble's virtual milliseconds (no `time.Sleep`, lint-enforced).
- Full incident rehearsal (M7's exit criterion, a single testscript file): `lag` → `pending` →
  `trace` → `consumer pause` → `seek --dry-run` → `seek --confirm` → `resume` → `replay --dry-run`
  → `replay --confirm` → `trace --trace-id` → `stream purge --dry-run`.

**testscript / CLI goldens (#26's suite)**
- For each destructive verb: dry-run output, missing `--confirm` (exit 2 + exact command), mismatched
  confirm (exit 4), non-TTY without `--yes` (exit 2), applied output, JSON and NDJSON faces.
- `TestPreviewEqualsApply`: preview and apply renderings differ only in verb tense and `applied`.
- `TestHintsResolve` (#24) extended with the new hints, including the `messq dlq redrive` hint that
  #29 will re-point.

**Golden events / logs / API (#18, #19)**
- Event-sequence golden for a seek and for a replay of 3 messages: exact kinds, order, `actor`,
  `detail` keys; a dry run of both produces a byte-identical events table (diff assertion).
- `docs/log-schema.md` golden updated for `msg.publish.replay_of`/`origin_seq` and the
  `admin.action{action:"replay"}` detail; the removal of `stream.purge.dry_run` is a golden change
  with a one-line rationale in the same commit.
- Contract goldens for the replay route and for `seek`'s new `?confirm=` requirement.

**Bench**
- `BenchmarkReplay` (1 KiB messages, `--durability=full`): replay throughput within 20 % of the
  publish path, since it is the publish path with a read in front. Recorded by #31's benchstat job;
  a regression means the chunk read is scanning rather than seeking.
