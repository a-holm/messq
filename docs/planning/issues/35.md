## Context

By M8 messq *is* trustworthy: #8 and #32 prove it under SIGKILL, #13 proves the state machine
against an independent model, #19–#21 make every transition answerable, #27–#31 give an operator
the tools. **None of that is legible to a stranger.** This issue writes the documents that convert
a proven system into a system someone will actually adopt — and, per PLAN.md's ethos, makes those
documents *executable* so they cannot quietly become false.

PLAN.md makes documentation a product feature in four places:

- **§1.2** — *"**Honest.** Durability modes are named and printed at startup; guarantees are stated
  precisely and **each is backed by a named test**; the README says **when not** to use messq."*
  That sentence is a specification for `docs/guarantees.md`, not a mood.
- **§1.4** — the permanent non-goals are *"printed in the README"*, and *"Publishing the anti-pitch
  is a trust tactic, not modesty."*
- **§6** — the guarantee statement is marked *"README verbatim"*: the delivery contract has a
  canonical wording, and the README carries it unedited.
- **§11.5** — *"the README curl transcript and every doc command block execute in CI (`testscript`)
  — **documentation cannot rot**."*

And **§14 M8's exit criterion** names this issue's output directly: *"1.0 docs (guarantees,
runbooks, comparisons, anti-pitch)"*.

Everything needed to write it now exists. **#4** produced `SEMANTICS.md` and the invariant register
I1–I11 that `guarantees.md` cites. **#18** produced the executable-docs harness, the normaliser and
`internal/wirecheck`. **#26** produced the testscript suite, the help topics, `docs/cli/*.md` and
man pages — one source of truth to generate prose from instead of retyping it. **#31** produced
`docs/benchmarks.md` with measured numbers and their hardware, so the README can quote a number
instead of inventing one. **#21** shipped `contrib/prometheus/alerts.yml` whose every rule already
carries a `runbook: RB-NN` label pointing at pages **that do not exist yet** — an alert whose
`runbook_url` 404s at 3 a.m. is worse than no alert.

What it unlocks: **#36** cannot tag v1.0 without it (it is a formal blocker), and the release-gate
checklist item *"docs command blocks green"* is this issue's CI job. Practically, it is also the
last cheap moment to find claims we cannot support — a guarantee that no test proves is discovered
here, in a table, rather than in a bug report from someone who believed us.

Governing PLAN.md material: **§1** (positioning, the anti-pitch, the §1.5 success criteria),
**§6** (delivery semantics, README-verbatim), **§9** (three surfaces one vocabulary; the log field
schema *"versioned like an API"*), plus **§4.3–4.5** (durability, recovery, retention, backup) and
**§12** (*"honest, measured, published"*) as the sources for operations content, **§7** for
`PROTOCOL.md`, **§10/D12** for `SECURITY.md`, **§13** for `GOVERNANCE.md` (Apache-2.0, DCO, no
relicensing — due *"at v0.9"*, i.e. before #36 tags), and **D3/D14/D15** for the comparison and
non-goals pages.

## Design proposal

> Proposal, not mandate — the prose is the deliverable and this sketch is scaffolding. **Four rules
> are not negotiable**, because they are cheap now and expensive after people build on them:
> (1) every guarantee cites an invariant, a test and a CI job or it is deleted; (2) every fenced
> command block either executes in CI or carries a reason from a closed set; (3) every performance
> number in prose is a citation into `docs/benchmarks.md`, never a literal; (4) every alert's
> `runbook_url` resolves to a page, and every page names the alerts it answers.

### 2. `README.md`

Its only job is to make the reader run `messq quickstart`. Proposed skeleton, in order — the order
*is* the argument:

```markdown
# messq
<one line: what it is>            <= 4 badges: CI, release, Go report, licence

<Two sentences. Proposal:>
messq is a single-binary, single-node queue daemon for Linux: durable at-least-once delivery with
explicit acks, redelivery with backoff, and a dead-letter stream, all in one SQLite file.
It records every state transition of every message in the same transaction as the transition, so
`messq trace <id>` can tell you exactly what happened to any message you can name.

## The point                      <- the trace block (executed, see §7)
## Install                        <- 3 lines: deb/rpm, container, go install
## 60 seconds                     <- `messq quickstart` + the 3-command manual version
## A worker in five lines of shell
## What you get                   <- 5 bullets, each linking docs/guarantees.md#GN
## When NOT to use messq          <- BEFORE the feature list (§1.4)
## How it compares                <- one screen, links to docs/compare/
## Documentation                  <- the map
## Status, versioning, licence
```

The delivery-contract paragraph from PLAN §6 appears **verbatim** under *What you get*, checked
byte-for-byte by `TestReadmeCarriesGuaranteeStatement` against the same string SEMANTICS.md S14
carries — one wording, three places, one test.

*When NOT to use messq* is a list of honest disqualifiers, each pointing somewhere useful:
`> 50k msg/s sustained` → Kafka/JetStream; multi-node HA or zero-RPO → JetStream/Kafka (messq is a
single node with a single disk; §1.4); terabyte retention; payloads > 8 MiB (use the claim-check
pattern); exactly-once; consumers you cannot make idempotent; Windows/macOS servers; a broker
shared across an org's teams with per-team isolation needs (three roles, no RBAC engine — D12).

**README lint** (`internal/docsguard`, PR lane): ≤ 250 lines; the required H2 set present, in order;
install + first command inside the first 60 lines; ≤ 4 badges; no `TODO`/`coming soon`; every
number-with-unit inside a `<!-- messq:number src=… -->` span (§9); every fence carrying a run
directive or a closed-set `no-run` reason; no relative link that does not resolve.

### 3. `docs/guarantees.md` — the trust artifact

One table. A row is a *falsifiable sentence* plus three citations. **A row that cannot cite all
three is deleted, not softened** — that rule is printed at the top of the page, because it is the
reason to believe the page.

| ID | Guarantee | Invariant | Proven by | CI job | Mode |
|---|---|---|---|---|---|
| G1 | A publish that returned `201` survives power loss | I1 | `TestCrash_LedgerReconciles/full` | `crash-fast` (PR), `crash-matrix` (nightly) | `full` |
| G2 | A publish that returned `201` survives `SIGKILL` of the daemon | I1 | `TestCrash_LedgerReconciles/relaxed` | `crash-fast` | both |
| G3 | An `ack` that returned `200` is durable; that message will not be redelivered | I3 | `TestCrash_NoAckedRedelivery` | `crash-fast` | `full` |
| G4 | A message is delivered at most `max_deliver` times, across restarts | I4 | `TestSweeper_MaxDeliverBound`, `rapid/I4` | `property`, `crash-matrix` | both |
| G5 | Every duplicate delivery has a named cause in `events` | I9 | `rapid/I9`, `TestTraceExplainsEveryDuplicate` | `property`, `golden-logs` | both |
| G6 | A stale ack never mutates a live delivery and is always reported | I7 | `TestAck_FenceRejectsStaleAttempt` | `unit`, `property` | both |
| G7 | `max_ack_pending` is never exceeded | I5 | `rapid/I5` | `property` | both |
| G8 | Every dead-lettered message appears exactly once in `<stream>.dlq` | I8 | `TestDeadLetter_AtomicWithProvenance` | `unit`, `property` | both |
| G9 | Folding `events` reproduces persisted state | I10 | `TestVerifyDeep_FoldMatchesState` | `soak`, `crash-matrix` | both |
| G10 | A full disk never blocks acks, naks or dead-lettering | — (§4.5) | `TestENOSPC_AckPathStaysOpen` | `fault-matrix` | both |
| G11 | An fsync failure latches the daemon read-only rather than continuing | — (D4) | `TestEIO_LatchesReadOnly` | `fault-matrix` | both |
| G12 | A data dir written by an older release migrates forward and keeps delivering | — (#34) | `TestUpgrade_Fixtures` | `upgrade` | both |
| G13 | A ±1 h clock jump does not expire or extend an in-flight lease | — (S7) | `TestClockJump_DeadlinesUnaffected` | `fault-matrix` | both |

Followed by **non-guarantees** (N1…), stated as flatly: no exactly-once; no ordering across
concurrent in-flight messages; no global cross-subject ordering; no delivery of retention-expired
messages; no survival of disk loss (that is what `messq backup` is for); no multi-node HA; no
guarantee that a `relaxed`-mode `201` survives power loss.

### 4. `docs/OPERATIONS.md`

Sections: **Install and first boot** · **Choosing a durability mode** (§4.3's table, what a 2xx
means, `doctor`'s measured fsync verdict) · **Configuration** (links `docs/cli/messq_serve.md`;
does not retype flags) · **Sizing and capacity** · **Monitoring** (the SLI, the shipped alerts, the
dashboard) · **Backup and restore** · **Upgrade and rollback** · **Routine operations** (log level
via SIGHUP, pause/resume, purge with `--dry-run`) · **Incident index** (the runbook register) ·
**Filing a bug** (the evidence bundle).

The sizing section is arithmetic, not adjectives — proposal:

```
db_bytes  ≈ Σ_streams msgs × (payload + headers + ~120 B row & index overhead)
          + event_rows × ~180 B
          + WAL (≤ --wal-max-bytes, default 256 MiB)
event_rows ≈ rate × --event-retention × (2 + avg_attempts)     # publish + deliver + settle

Worked example — 20 msg/s, 1 KiB payloads, retention=limits max_age=7d, one consumer:
  messages   20 × 86 400 × 7            = 12.1 M rows  × ~1.15 KiB  ≈ 14 GiB
  events     20 × 86 400 × 3 (72 h)     = 15.5 M rows  × ~180 B     ≈ 2.8 GiB
  →  budget ≈ 17 GiB + 256 MiB WAL.  Halve it with retention=workqueue (delete on ack);
     quarter the event cost with --event-retention 24h.  Check yours: messq doctor.
```

Backup/restore is PLAN §4.5's one sentence expanded into a procedure with commands, plus the
explicit warning that `cp messq.db` under load is **not** a backup (#30 owns the implementation;
this page owns the procedure and the systemd-timer example).

**Filing a bug** prescribes an evidence bundle, so the first maintainer reply is never "please run…":
`messq version --output json`, `messq doctor --output json`, `messq verify --deep`,
`messq events --since 1h --output ndjson`, the `server.start` log line (durability, versions), and
`messq trace <id>` for the message in question.

### 5. Runbooks

**Template** (front-matter is machine-checked; sections are required in order):

```markdown
---
id: RB-01
title: A consumer has stopped acking
alerts: [MessqConsumerStalled]
severity: critical
first_command: messq lag
---
## Symptom          what fired, or what a human noticed
## Confirm          ≤ 60 s, executable, read-only commands only
## Diagnose         the branch table: what each observation means
## Mitigate         per branch, with the exact command and its blast radius
## Verify           the observation that proves it is over
## Prevent          the config or code change that stops the recurrence
## Still stuck      the evidence bundle and where to file it
```

**Register** (all IDs used by #21's `alerts.yml` must appear; free IDs fill the non-alert cases):

| ID | Page | Alerts | First command |
|---|---|---|---|
| RB-01 | A consumer has stopped acking | `MessqConsumerStalled` | `messq lag` |
| RB-02 | The DLQ is filling | `MessqDlqGrowing`, `MessqDlqNonEmpty` | `messq dlq ls <s>` |
| RB-03 | Writes have stopped: disk full or read-only latch | `MessqReadOnly`, `MessqDiskWillFill` | `messq doctor` |
| RB-04 | Backlog is growing faster than it drains | `MessqBacklogGrowing` | `messq lag --output json` |
| RB-05 | Retention is blocked by a pending delivery | `MessqRetentionBlocked` | `messq pending <s> <c> --older-than 1h` |
| RB-06 | Consumers are seeing duplicates | — | `messq trace <id>` |
| RB-07 | Stale acks / tuning `ack_wait` | `MessqStaleAcks` | `messq consumer info <s> <c>` |
| RB-08 | Redelivery storm / a poison message | `MessqRedeliveryStorm` | `messq pending <s> <c>` |
| RB-09 | Unclean shutdown, torn tail, recovery | — | `messq verify --deep` |
| RB-10 | Accidental purge, seek or delete | — | `messq events --event consumer.seek,stream.purge` |
| RB-11 | Upgrade went wrong / rolling back | — | `messq version --output json` |
| RB-12 | An invariant violation was reported | `MessqDeadOrphan` | `messq verify --deep` |
| RB-13 | The sweeper is behind | `MessqSweeperBehind` | `messq doctor` |
| RB-14 | Commit latency is high | `MessqCommitLatency` | `messq doctor` |
| RB-15 | Metrics are stale or missing | `MessqMetricsStale` | `curl …/metrics \| head` |
| RB-16 | The daemon will not start | — | `messq serve --data-dir … ; echo $?` |

**RB-01, worked**, as the template for the rest (blocks marked `messq:run` execute against a seeded
`--dev` daemon; `mitigate` blocks that would be destructive on real data still run, because the
daemon is throwaway):

```markdown
## Confirm
<!-- messq:run session=rb01 -->
$ messq lag
CONSUMER  STREAM  BACKLOG  INFLIGHT  DLQ  OLDEST UNACKED
billing   orders    1,272    12/1000    0  17m04s          (!)
next: messq pending orders billing --older-than 15m

## Diagnose
| Observation | Meaning | Go to |
|---|---|---|
| `INFLIGHT` at the `max_ack_pending` cap, oldest growing | workers took work and vanished | Mitigate A |
| `INFLIGHT` ≈ 0, backlog growing | nobody is fetching: workers down, or consumer paused | Mitigate B |
| `INFLIGHT` cycling, `messq_redelivered_total` climbing | handlers fail or exceed ack_wait | RB-07, RB-08 |
| `messq_readonly == 1` | this is not a consumer problem | RB-03 |

## Mitigate — A: the leases must expire before the work moves
Nothing is lost. `ack_wait` (see `messq consumer info`) bounds the wait; after it, the sweeper
returns each message to READY with `cause=timeout` and the next fetch gets it.
To stop waiting, restart the workers — they will be re-delivered the same messages.
Do NOT seek: seeking discards the pending set (RB-10).
```

Each runbook ends by naming the *next* runbook when the branch is not its own — an operator who
lands on the wrong page must be routed, not dead-ended.

### 6. `docs/tutorial-lost-message.md` — "A message went missing. Find it."

The signature document, and the only one written as a story. It seeds a real incident and solves
it with the real CLI, in eight steps, every one executed in CI: publish a batch into `orders`; a
worker that fails one message permanently and stalls on another; then —

```console
$ messq lag                                   # 1. is anything suffering?
$ messq pending orders billing --older-than 5m # 2. which messages, how old
$ messq peek orders --seq 10493                # 3. what was in it
$ messq trace 01J8ZQ4K2M9V0X7Y3B5N6C8D1E       # 4. its whole life story
$ messq dlq ls orders                          # 5. where the dead one went
$ messq dlq show orders --id 01J8…             # 6. cause, attempts, last error
$ messq dlq redrive orders --id 01J8… --dry-run # 7. exactly what would happen
$ messq dlq redrive orders --id 01J8…           # 8. and the trace continues
```

The closing section, *"What you just learned that a Redis list could not tell you"*, is the pitch
stated as a fact the reader has now verified themselves. The whole tutorial is also a `.txtar`
script in #26's suite, so it is a regression test for the CLI as much as a document.

### 7. Keeping the `trace` block pretty *and* executed

The README's `trace` block is the product's screenshot; masking its ULIDs to `<ULID>` would ruin
it, and leaving it unexecuted would let it rot. Proposal: a **presentational mask** mode in #18's
normaliser — instead of replacing volatile tokens with placeholders, it substitutes them
deterministically per session with fixed, real-looking literals.

```markdown
<!-- messq:run session=readme lane=inproc-clock mask=presentational clock=2026-08-21T09:14:02.114Z -->
```

- `lane=inproc-clock` runs CLI blocks against #26's in-process fake-clock daemon, so relative
  offsets (`waited 30.0s`, `resolved in 53.2s`) are exact, not masked.
- `mask=presentational` maps the first ULID seen in a session to `01J8ZQ4K2M9V0X7Y3B5N6C8D1E`, the
  second to a second fixed literal, and so on from a committed table; trace ids likewise. The map is
  per-session and order-stable, so a diff shows a *behaviour* change, never id churn.
- Everything #18 declares never-maskable stays never-maskable: `seq`, `attempt`, counts and ack
  tokens are compared literally — a token in a golden is a free assertion about fencing arithmetic.

### 8. `PROTOCOL.md`, `log-schema.md`, `compatibility.md`

`PROTOCOL.md` is generated-then-edited: the endpoint table, the error-code enum with HTTP statuses,
and the reserved `Messq-*` header set come from #14's registries via `make docs`; the conventions
(raw body in / `body_b64` out, long-poll semantics, batch endpoints, `Accept: application/x-ndjson`)
are hand-written prose. Bindings: every code in the enum is documented exactly once and exercised
by a #18 contract case; every route in the registry appears exactly once.

`compatibility.md` states, per surface, what is frozen and what may change:

| Surface | Frozen at 1.0 | May change in a minor release |
|---|---|---|
| HTTP request/response shapes | field names, types, error `code` values, status per code | new optional fields, new endpoints, new error codes (clients must tolerate unknown codes — stated here, tested in #18) |
| CLI `--output json` | field names and types | new fields; human/table output is **not** contract |
| Exit codes | 0–7 meanings | new codes above 7 |
| Log/event schema | event names, existing field names | new fields, new events |
| On-disk format | forward migration always works (#34) | schema version bumps that migrate |
| Flags | existing names and semantics | new flags; deprecations announced one minor ahead |

Anything not listed is explicitly not a promise — including human-readable output, metric help
strings, and log *ordering*.

**Comparisons.** Four pages (JetStream, Redis Streams, Postgres jobs table, Kafka), each with a
`Checked against:` front-matter stamp (product, version, date, doc URL), a claims table where every
row that asserts something about the other system carries a source link, and a mandatory closing
`## Choose <X> if` section that is *genuinely persuasive* — the fairness test is that an advocate of
the other system would sign the section. The README table is the one-screen summary of all four:

| | messq | Redis Streams | Postgres jobs table | JetStream | Kafka |
|---|---|---|---|---|---|
| Processes to operate | 1 | 1 (+HA) | your DB | 1–3+ | 3+ & coordination |
| Delivery | at-least-once | at-least-once | at-least-once | at-least-once | at-least-once |
| Server-enforced ack timeout | yes | via `XAUTOCLAIM` | your `SELECT … FOR UPDATE` | yes | no (rebalance) |
| Backoff + `max_deliver` | built in | build it | build it | built in | build it |
| Dead-letter | a real stream | build it | build it | advisories + wiring | build it |
| Per-message audit trail | **built in** (`trace`) | no | if you write one | advisories, sampled | no |
| Ceiling | ~5k msg/s durable | very high | ~your DB | very high | very high |
| HA / multi-node | **no** | yes | yes | yes | yes |

`TestComparisons_Fair`: front-matter present; every claim row has a source link; the `Choose X if`
section exists and is ≥ 3 bullets; no superlatives from a banned list ("blazing", "simply better",
"unlike X, we"); stamps older than 180 days fail the **nightly** job (never the PR lane — a stale
competitor version must not block an unrelated PR; the nightly opens an issue, exactly as #31's
benchstat regression does).

**`docs/graduating-to-jetstream.md`** — the anti-lock-in page D2/§1.3 promised: a
messq↔JetStream mapping table (`stream`→stream, `consumer`→durable pull consumer, `ack_wait`→
`AckWait`, `max_deliver`→`MaxDeliver`, `backoff`→`BackOff`, `max_ack_pending`→`MaxAckPending`,
`term`→`TERM`, `nak --delay`→`NAK` with delay, `<s>.dlq`→advisory + a sink stream, `trace`→*no
equivalent*), a five-step cutover (stand up JetStream → dual-publish → drain messq to `lag 0` →
cut consumers → keep `messq.db` as the audit archive), and a candid *"what you lose"* list. Ending
the page with "you will not need us to leave" is the cheapest trust we can buy.

### 11. Docs CI

| Job | Lane | Budget | Contents |
|---|---|---|---|
| `docs-exec` | PR | ≤ 240 s | #18/#26 harness over the full document set, both lanes |
| `docs-lint` | PR | ≤ 30 s | fence directives, `no-run` reason enum, README lint, runbook template, internal links |
| `docs-xref` | PR | ≤ 30 s | guarantees↔invariants↔tests↔jobs, alerts↔runbooks, errors↔PROTOCOL, events↔log-schema, numbers↔benchmarks |
| `docs-generated` | PR | ≤ 30 s | `make docs && git diff --exit-code` (extended set) |
| `docs-clients` | PR | ≤ 120 s | Python and TypeScript snippets executed against a `--dev` daemon |
| `docs-external` | nightly | — | external link check, comparison freshness, prose lint; failures open an issue |

The closed `no-run` reason set — `requires-root`, `requires-systemd`, `requires-package-manager`,
`external-service`, `interactive`, `illustrative-output-only` — is enforced, and a page may not be
more than half `no-run` blocks. Runbooks additionally require **≥ 2 executed blocks**, because a
runbook of unexecuted commands is the exact artifact this issue exists to prevent.

### 12. Edge cases, decided

| Case | Handling |
|---|---|
| A guarantee we want but cannot prove | It does not go in the table. It may go in `docs/faq.md` as prose that says *"we believe, we do not prove"* — the split is the point |
| A test cited by `guarantees.md` is renamed | `docs-xref` fails naming the row; renaming a cited test is a documentation change |
| An invariant with no guarantee row | `TestGuarantees_CoverEveryInvariant` fails — silence about an invariant is the failure mode |
| A runbook needs a command that does not exist | Fails `docs-exec` immediately; the fix is to rewrite the runbook, not to add a command in this issue |
| A runbook's `Mitigate` block is destructive | It still runs — against the throwaway `--dev` daemon of that session. Blast radius is stated in prose next to the command |
| Alert added in #21 with no runbook | `docs-xref` fails; the register is bound both ways |
| Docs commands need root/systemd/apt | `no-run` with a reason from the closed set; the nightly VM job in #36 covers the install path end to end |
| README number drifts from `benchmarks.md` | `TestNumbersMatchBenchmarks` fails; `-update` rewrites the span from the published table |
| Benchmarks re-measured on new hardware | The spans update; the sentence's mode/hardware clause is asserted to still be present |
| A comparison page's competitor releases a new version | Nightly staleness warning at 180 days → an issue, never a merge failure |
| A comparison claim is wrong | Treated as a bug with the same severity as a wrong guarantee; the fairness rule is that we would accept the correction from their maintainer |
| `messq.dev` is not live yet | `runbook_url`s point at the fixed scheme; a test binds `RB-NN` → `docs/runbooks/RB-NN.md`; #36 makes the URL resolve. A dead link in a shipped alert is a release blocker |
| The trace block changes because the renderer changed (#20) | `docs-exec` fails; the README is updated by `-update` in the same PR as the renderer change — which is exactly the review we want |
| Two documents state the same fact | Forbidden: one includes/links the other. `TestNoDuplicatedFactBlocks` compares generated-block hashes across `docs/` |
| A doc block leaks a real token or a payload | The canary-leak test from #16/#19 also scans `docs/`; the harness's fixtures use obviously-fake tokens matched by the `gitleaks` rule's own prefix |
| Help topic and docs page diverge | Impossible by construction: `docs/concepts.md` is generated from the topic sources; drift shows as a `docs-generated` diff |
| `SEMANTICS.md` and `guarantees.md` disagree | The spec wins; the guarantee row is a bug. Stated in `docs/README.md`'s precedence note: SEMANTICS > PROTOCOL > guarantees > OPERATIONS/runbooks > everything else |
| A very long PR touching docs blows the CI budget | `docs-exec` runs only the sessions whose documents changed on PRs, the full set nightly and on `main` |

| Idea | Why not now | Revisit trigger |
|---|---|---|

## Test plan

Per PLAN §11 / D13. Documentation tests are the deliverable's gates; there is no new production
code here, so the suite is parsers, bindings and execution.

**Unit — `internal/docsguard` (extending #4)**
- `ParseGuarantees`, `ParseRunbooks` (front-matter + section order), `ParseComparison`
  (stamp + claim links + `Choose X if`), `ParseNumberSpans`, `ParseFenceDirectives` — table-driven
  against `testdata/` fixtures, one fixture per failure mode. No network, no daemon, < 1 s.
- README lint rules as individual table cases (length, badge count, section order and presence,
  first-command position, banned strings).

**Cross-reference (`docs-xref`)**
- `TestGuarantees_Grounded` / `TestGuarantees_CoverEveryInvariant` (§3), including the `rapid/IN`
  citation form resolved through #13's invariant registry.
- `TestAlertsHaveRunbooks` and `TestRunbooksNameRealAlerts` over `contrib/prometheus/alerts.yml`.
- `TestProtocolDocumentsEveryRouteAndCode` against #14's route/error registries (#18's enum is the
  source; this asserts the document is its complete image).
- `TestLogSchemaEventsAreVocabulary` against #19's generated vocabulary.
- `TestNumbersMatchBenchmarks` against `docs/benchmarks.md`'s published table.
- `TestNoDuplicatedFactBlocks`, `TestReadmeCarriesGuaranteeStatement` (byte-for-byte against
  SEMANTICS.md S14), `TestDocsLinksResolve` (internal only).

**Executable documentation (`docs-exec`, #18 + #26 harness)**
- Every session in `README.md`, `docs/OPERATIONS.md`, all 16 runbooks, the tutorial,
  `docs/PROTOCOL.md`, `docs/clients/*.md`, `docs/compare/*.md` (their few command blocks),
  `docs/graduating-to-jetstream.md` (messq-side commands only; the `nats` side is `no-run
  external-service`).
- Both lanes exercised: `lane=inproc-clock` for timeline-bearing CLI output (README trace, tutorial,
  RB-01/RB-06/RB-07 confirm blocks), the real-daemon lane for curl transcripts.
- `-update` rewrites document output in place and is idempotent; a second run produces no diff.

**testscript (#26's suite)**
- `tutorial.txtar` — the incident tutorial as a golden CLI test, including the redrive and the
  continuous post-redrive trace.
- `runbooks.txtar` — one script that walks each runbook's *Confirm* commands against a seeded
  daemon, asserting each exits 0 and prints its documented first line.

**Client snippets (`docs-clients`)**
- Python (stdlib `urllib` + `http.client` over the Unix socket) and TypeScript (Node `undici`)
  publish→fetch→ack→nak→term against a `--dev` daemon; Go snippets compile *and* run via
  `go test ./docs/clients/...` using `pkg/client` (#22); the shell snippets are the #18 five-line
  worker, reused, not re-invented.

**Nightly (`docs-external`)**
- External link check across all docs (HTTP 200 or a documented redirect).
- Comparison freshness: any `Checked against:` stamp older than 180 days opens an issue.
- The full `docs-exec` set (PRs run only changed-document sessions).

**Gate self-tests** (extending #2's sabotage matrix — a gate nobody has seen fail is a gate nobody
knows works)
1. Change a guarantee row's invariant ID to `I99` → `docs-xref` fails naming the row and line.
2. Rename a test cited by `guarantees.md` → `docs-xref` fails.
3. Add an alert with `runbook: RB-99` → `TestAlertsHaveRunbooks` fails.
4. Edit a README number without touching `benchmarks.md` → `TestNumbersMatchBenchmarks` fails, and
   still fails under `-update`.
5. Add a fenced command block with no directive → `docs-lint` fails naming the file and line.
6. Delete a runbook's `## Verify` section → the template check fails.
7. Break a command inside a runbook (rename a flag) → `docs-exec` fails at that block.

**Manual review, recorded in the PR description** (the part no test can do)
- A fairness pass over each comparison page, reading the current upstream documentation, with the
  version and date recorded in the stamp.
- A cold read of `README.md` → `quickstart` → `guarantees.md` by someone who has not read PLAN.md,
  timed; the §1.5 criterion is that they reach a first acked message in under 60 s.
- A pass asserting every claim in the README maps to a guarantees row, a benchmark id, or a
  non-goal — nothing floats free.

**Not tested here:** the harness itself (#18/#26), the numbers (#31), alert expressions (#21), the
implementations every runbook drives (#27–#30, #34), install paths and the site (#36).
