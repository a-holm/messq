## Context

Multiple workers sharing one consumer **already works**, and it has worked since #10 merged. Two
processes long-polling `POST /v1/streams/orders/consumers/billing/fetch` get disjoint messages
because the claim runs inside the single writer (§3.2), and a slow worker's late ack is rejected
with `409 stale_ack` because tokens are fenced (**D7**). There is no race to fix and no protocol to
add. What is missing is the ability to *answer questions about it*:

- which worker is holding `orders/10493` right now?
- worker `billing-3` was SIGKILLed — what is it still holding, and when does that redeliver?
- one box has 32 cores and one has 2; can I stop the small one from claiming a third of the queue?
- `messq trace` says the ack was stale — **stale from whom?**

That is the entire feature. PLAN.md **D15** names it and scopes it in one clause:

> worker attribution ("groups-lite" — multiple workers per consumer already works because acks are
> fenced; the feature is visibility and per-worker caps)

Governing PLAN.md material:

- **D15** — phase 2, strictly demand-ordered; this is the "groups-lite" line, and the scope boundary
  it draws (visibility + caps, *not* a group protocol) is normative for this issue.
- **D7 — plain fenced tokens.** The fence is what makes several workers per consumer safe, and it is
  also the reason a worker name can be an untrusted hint rather than a credential: *a name is not a
  capability*, exactly as #10 said *a token is not a capability*.
- **D5 — durable rows, ack = DELETE.** Attribution is one nullable column on a table that is bounded
  by `max_ack_pending`. There is no membership state machine, no session, and no lease outside the
  one that already exists: **the ack deadline is the lease.**
- **D6 — attempts increment at claim.** A dead worker's messages are already handled: `ack_wait`
  expires, `msg.timeout` fires, the row redelivers with `attempt+1` and a named cause. This issue
  adds no recovery path because #11 already is the recovery path.
- **D11 / §9.2 — the event vocabulary is closed.** This feature invents **no event names**. It adds
  documented `detail` keys to events that already exist, and one new `hold_reason` value.
- **§9.4 — cardinality rule** (`labels are only stream and consumer`). A `worker` label is an
  identity label with an unbounded value set, so §8 below bounds it, makes it opt-in, and forbids it
  on counters. This is the one place the feature could do real operational damage, and it is the one
  place the design is most conservative.
- **§14 M9 exit criterion** — *"Each feature ships with a new invariant, events, metrics, docs — or
  it does not ship."* This issue's four: **I12** (a seq is INFLIGHT to at most one worker),
  `detail.worker`/`detail.holder`/`detail.current_worker` on existing events, `messq_workers` plus
  the opt-in per-worker gauges, and `docs/OPERATIONS.md` + `SEMANTICS.md` amendments.

Because #36 (v1.0.0) is a hard dependency, everything here lands in a **1.1 minor** and is bound by
the 1.0 compatibility contract: JSON field names are frozen (§8), error codes are a closed enum
(§7). Every wire change below is therefore **additive and optional** — #18's contract tests and
#20's byte-for-byte `trace` golden must stay green **without being edited**, and that is an
acceptance criterion, not a hope.

## Scope

### In scope

- **Worker identity on fetch**: an optional `worker` object (`name`, `instance`, `client`) on the
  fetch request, validated against the existing name grammar, recorded on every row it claims.
- **`deliveries.worker`** — the holder of the current (or most recent) attempt; one nullable column,
  no new index.
- **A durable worker registry** (`workers` table): per `(stream, consumer, name)` first-seen,
  last-seen, self-reported host/pid/client, authenticated `actor`, optional per-worker cap. Bounded,
  reaped, cascades on consumer delete.
- **Per-worker in-flight caps**: consumer field `max_worker_inflight` (0 = off), optional per-worker
  override, enforced at **claim** as an admission rule, with a new `hold_reason: "worker_limit"`.
- **`require_worker`** consumer flag: reject unattributed fetches with a typed error.
- **A single documented hold-reason precedence order** for the claim path, so `hold_reason` is
  deterministic when several limits bite at once (and so #38/#39 have a defined slot).
- **Attribution in the read surfaces**: `pending` listings, consumer info, `GET …/workers`,
  `messq workers`, `messq pending --worker`, and a `by=`/`holder=` token in `messq trace` detail.
- **Attribution in the journal**: `detail.worker` on `msg.deliver` / `msg.ack` / `msg.nak` /
  `msg.term` / `msg.extend` / `msg.timeout` / `msg.dead`, and `detail.holder` +
  `detail.current_worker` on `msg.ack_stale` — the line that finally names both sides of a duplicate.
- **Metrics**: `messq_workers{stream,consumer}` always; `messq_worker_inflight` /
  `messq_worker_last_seen_seconds` **only** under `--worker-metrics`, capped, gauges only.
- **Invariant I12** + `internal/verify` checkers `I12` and `W1`, and a `worker` dimension in #13's
  `rapid` action registry including a `worker_dies` action.
- **Client/CLI plumbing**: `pkg/client` `WorkerConfig.Name` (default: hostname), `messq sub --worker`,
  `MESSQ_WORKER` in the `--exec` child env, `messq workers ls|show|rm|limit`.
- One forward-only migration (`000N_worker_attribution.sql`) plus its #34 upgrade fixture.

### Out of scope

- **Any group protocol**: partition assignment, rebalance barriers, generation/epoch negotiation,
  join/leave/heartbeat RPCs, a coordinator, static membership, sticky assignment. Permanently out
  (D15, §1.4); `docs/non-goals.md` (#35) gains a line so "can it do consumer groups" is a link.
- **Per-worker ordering guarantees.** Ordered-by-subject delivery is **#38**; if it lands first, this
  issue composes with it in the precedence order below and nothing more.
- **Per-consumer rate limiting** — **#39**; it occupies a documented slot in the same precedence list.
- **Revoking a live lease.** `messq workers rm` never touches messages; the operator recipe is
  `messq pending … --worker X --tokens | xargs messq nak`, which is #24's machinery unchanged.
- **Worker names as an authorization principal.** `actor` (#16) stays the authenticated identity;
  `worker` is a self-reported hint. No role, no scope, no token binding.
- **Changing the ack-token grammar** to carry a worker. The token stays five fields forever (#10's
  parser, its fuzz corpus, and #12's DLQ headers all depend on it).
- **Audit export of worker activity** — **#42** exports the events this issue enriches; no separate
  worker feed.
- **Per-worker fairness/scheduling** (round-robin across members, weighted claim). The cap is a
  *ceiling*, not a scheduler. Deferred with no issue: revisit only if an operator demonstrates
  starvation that the cap cannot express.

## Design proposal

> Proposal, not mandate: concrete enough to argue with. Three things below are **binding** because
> other issues depend on them — the cardinality rule in §8, the "names are untrusted" rule in §2,
> and the precedence order in §3.

### 0. What makes this two days instead of two weeks

The entire correctness argument is inherited. Written out, so a reviewer can check that nothing new
is being claimed:

| Question a group protocol exists to answer | Why messq already answers it |
|---|---|
| Who owns this message? | The row is INFLIGHT with one `attempts` value; only a token naming that attempt can settle it (D7). |
| What happens when an owner dies? | `ack_wait` expires, the sweeper releases the row, `msg.timeout` records the cause (#11). No failure detector, no session timeout, no fencing epoch. |
| How is work distributed? | Pull. A worker takes what it can handle. Nothing is assigned, so nothing needs reassigning. |
| How do we avoid double processing on rebalance? | There is no rebalance. The fence is per attempt, not per member. |
| How do members agree on membership? | They do not have to. Membership is an **observation** the broker records, not a contract it enforces. |

Everything this issue adds is therefore *descriptive* — with exactly one exception, the per-worker
cap, which is an admission rule in the claim path and is **cooperative by construction** (§3).

### 1. Data model and migration

```sql
-- internal/store/migrations/000N_worker_attribution.sql
-- (take the next free number at implementation time; #37–#40 may land first)

ALTER TABLE deliveries ADD COLUMN worker TEXT;                     -- NULL = unattributed
ALTER TABLE consumers  ADD COLUMN max_worker_inflight INTEGER NOT NULL DEFAULT 0;  -- 0 = off
ALTER TABLE consumers  ADD COLUMN require_worker      INTEGER NOT NULL DEFAULT 0;

CREATE TABLE workers (
  stream       TEXT    NOT NULL,
  consumer     TEXT    NOT NULL,
  name         TEXT    NOT NULL,
  first_seen   INTEGER NOT NULL,
  last_seen    INTEGER NOT NULL,
  host         TEXT,                    -- self-reported, may be NULL
  pid          INTEGER,                 -- self-reported, may be NULL
  client       TEXT,                    -- self-reported, e.g. "messq-go/1.1.0"
  actor        TEXT,                    -- #16 Principal.Actor() at last fetch; authenticated
  instances    INTEGER NOT NULL DEFAULT 1,  -- distinct (host,pid) pairs seen under this name
  max_inflight INTEGER NOT NULL DEFAULT 0,  -- 0 = inherit consumers.max_worker_inflight
  PRIMARY KEY (stream, consumer, name),
  FOREIGN KEY (stream, consumer) REFERENCES consumers(stream, name) ON DELETE CASCADE
) STRICT;
CREATE INDEX workers_seen ON workers(last_seen);   -- the janitor's reap scan
```

Notes that matter:

- **No index on `deliveries.worker`.** The per-worker counting query (§3) is a `GROUP BY` over rows
  the fetch path already reads, and that set is bounded by `max_ack_pending` (D5's payoff, exactly
  as #9's flow-control count). An index on a hot table would add write amplification to every claim
  and every top-up for a query that is already index-satisfiable on the `(stream, consumer)` prefix
  of `deliveries_ready`. If `BenchmarkClaimWorkers` at `max_ack_pending = 100 000` disagrees, add a
  **partial** index `WHERE worker IS NOT NULL` so unattributed deployments keep paying nothing.
- `ALTER TABLE ADD COLUMN` is legal on `STRICT` tables; the nullable `TEXT` costs one header byte per
  existing row and rewrites nothing.
- `ON DELETE CASCADE` means `messq consumer rm` cleans the registry for free (`_foreign_keys=1` is
  already asserted per connection, §4.1).
- **`worker` is the holder of the *current or most recent* attempt.** On release (nak/timeout/
  restart) the column is *not* cleared: a READY row that says `worker=billing-3` is the honest
  statement "billing-3 had this and let it go". The API renders it as `worker` for INFLIGHT rows and
  `last_worker` otherwise — one column, two names, each true for its state.

### 2. Identity on the wire (binding: names are untrusted)

```json
POST /v1/streams/orders/consumers/billing/fetch
{"batch":16,"wait_ms":30000,
 "worker":{"name":"billing-7","instance":"ip-10-0-1-7/4242","client":"messq-go/1.1.0"}}
```

```go
// internal/queue
type WorkerRef struct {
    Name     string // required if the object is present; queue.ValidateName grammar
    Instance string // free-form, <= 128 bytes; conventionally "host/pid"
    Client   string // free-form, <= 64 bytes; conventionally "name/version"
}

// UnmarshalJSON accepts "billing-7" as sugar for {"name":"billing-7"} and nothing else.
// Unknown object keys are rejected (#14's strict decoding policy is preserved by decoding
// the object through a json.Decoder with DisallowUnknownFields).
func (w *WorkerRef) UnmarshalJSON(b []byte) error
```

**Decision — the string shorthand is worth the union type.** #14's rule *"two ways to say the same
thing is the bug factory"* was about the same value in two *places* (query param vs. body). Here it
is one field with a total function `string → WorkerRef`, and the payoff is PLAN §7's five-line shell
worker staying five lines:

```bash
W=${MESSQ_WORKER:-$(hostname -s)}
T=$(curl -s --unix-socket /run/messq/messq.sock \
     -d "{\"batch\":1,\"wait_ms\":5000,\"worker\":\"$W\"}" \
     http://localhost/v1/streams/jobs/consumers/w/fetch | jq -r '.messages[0].ack_token')
```

**Name grammar:** the #3/#9 validator, unchanged — ASCII, 1–64 bytes, `[A-Za-z0-9_.-]`, starts and
ends alphanumeric, no `/`. Reusing it means no new grammar to fuzz, and the leading-alphanumeric rule
reserves `_` for the daemon (`_other` in §8). Rejection is `400 bad_request` naming the rule.

**Binding rule: a worker name is a hint, never a credential.**

- It is never checked against the ack token, and **settling from a different name than the holder is
  allowed** — a worker may legitimately hand a token to a sidecar, and #22's `Worker` batches settles
  from one goroutine anyway. When the settler's name differs from `deliveries.worker`, both are
  recorded (`detail.worker` = settler, `detail.holder` = holder). Visible, never rejected.
- Under TCP auth (#16) the authenticated `actor` is stored next to the self-reported name, so
  "who claimed to be `billing-7`" is answerable. `messq workers --output json` shows both.
- A client that omits or lies about its name evades **its own** per-worker cap. It cannot evade
  `max_ack_pending` (I5), which stays the hard bound. Said plainly in `--help` and in
  `docs/OPERATIONS.md`: *per-worker caps are a capacity tool, not a security control.*

### 3. Claim-time allowance, and the precedence order (binding)

#9's `Fetch` already runs one counting query. It becomes grouped:

```sql
SELECT IFNULL(worker,''), COUNT(*) AS pending, IFNULL(SUM(state),0) AS inflight
  FROM deliveries
 WHERE stream = :s AND consumer = :c
 GROUP BY 1;                    -- <= max_ack_pending rows, <= max_workers groups
```

One extra `GROUP BY` on a query that already ran. The consumer totals are the sum of the groups, so
flow control and worker allowance read the *same* numbers and cannot disagree.

```go
// internal/queue — pure, table-tested, no I/O
type WorkerState struct{ Name string; Pending, Inflight int64 }

// Allowance returns how many rows this fetch may claim, and why it is short.
// cap == 0  ⇒ unlimited (only the consumer bound applies)
// ref == "" ⇒ unattributed: exempt unless cfg.RequireWorker (see below)
func Allowance(cfg ConsumerConfig, ws WorkerState, cap int64, batch int) (n int, hold HoldReason)
```

**The precedence order for `hold_reason`** — evaluated top to bottom, first one that bites is
reported. Fixed here so the value is deterministic when several apply, and so #38/#39 have a slot
rather than an argument:

| # | Condition | `hold_reason` | Owner |
|---|---|---|---|
| 1 | consumer paused | `paused` | #9 |
| 2 | storage latched read-only / shutting down | `shutting_down` | #6/#17 |
| 3 | `pending >= max_ack_pending` | `max_ack_pending` | #9 |
| 4 | rate limiter has no tokens | `rate_limit` | **#39** |
| 5 | ordering constraint blocks the head | `ordered_hol` | **#38** |
| 6 | **`worker.inflight >= cap`** | **`worker_limit`** | **this issue** |
| 7 | nothing visible yet (`visible_at` in the future) | `backoff` | #9 |
| 8 | cursor still scanning | `catching_up` | #9 |
| 9 | nothing to deliver | `no_messages` | #9 |

The consumer-level bound outranks the per-worker bound deliberately: `max_ack_pending` is the
invariant (I5), `max_worker_inflight` is a preference. An operator seeing `max_ack_pending` knows the
queue is saturated; seeing `worker_limit` knows *this* worker is, and that another worker could take
the work. `worker_limit` is a new enum value: #24 already renders unknown `blocked_by`/`hold_reason`
strings verbatim "for forward compatibility for #37–#41", and this issue submits the one-line map
addition (`worker_limit → worker-limit`) rather than relying on that fallback.

**Cap resolution:** `workers.max_inflight` if non-zero, else `consumers.max_worker_inflight`, else
unlimited. **Admission form, exactly like #9's `max_ack_pending` shrink:** lowering a cap below a
worker's current in-flight count revokes nothing; the worker simply claims nothing new until it
drains. Revoking would manufacture the duplicates D7 exists to prevent.

**Rejected — `max_worker_inflight: auto` (= `max_ack_pending / active_workers`).** Attractive on a
slide, wrong in practice: a worker's capacity would change because an *unrelated* worker's TTL
expired, making fetch sizes irreproducible and turning every scale-in into a claim stampede. A number
an operator typed is a number an operator can reason about.

**`require_worker = 1`** rejects a fetch with no `worker` field: `400 worker_required`, message
*"this consumer requires worker attribution; pass \"worker\":\"<name>\" in the fetch body"*, `next:
["messq consumer edit orders billing --require-worker=false"]`. Default off, because turning
attribution on must never break a fleet mid-upgrade.

### 4. Registry lifecycle (bounded, per I11)

Registration rides the fetch command — same transaction, same group commit, zero extra fsyncs:

```sql
INSERT INTO workers (stream, consumer, name, first_seen, last_seen, host, pid, client, actor)
VALUES (:s,:c,:w,:now,:now,:host,:pid,:client,:actor)
ON CONFLICT (stream, consumer, name) DO UPDATE SET
  last_seen = :now,
  host = :host, pid = :pid, client = :client, actor = :actor,
  instances = instances + (CASE WHEN workers.host IS NOT :host OR workers.pid IS NOT :pid
                           THEN 1 ELSE 0 END)
WHERE :now - workers.last_seen >= :resolution;    -- coarse last_seen; see below
```

- **`--worker-seen-resolution` (default 5 s).** A parked long-poll that returns empty still runs the
  fetch command; writing `last_seen` on every one of them would turn an idle fleet into a write
  stream and break §12's *"idle daemon < 0.5 % of one core"*. The stored `last_seen` is therefore
  coarse to 5 s, `messq workers` prints ages rounded accordingly, and the help text says so. A fetch
  that actually **claims** rows always writes (it is writing rows regardless).
- **`--max-workers-per-consumer` (default 128).** On overflow: first evict registry rows with zero
  in-flight and `last_seen` older than `--worker-ttl`; if none can be evicted, reject the fetch with
  `429 too_many_workers` and an `api.error` event (existing name, WARN, repeat-limited). A hard
  failure is correct here — >128 distinct names on one consumer is nearly always a client deriving
  its name from a fresh UUID per process, and the teaching error says exactly that:

  ```
  too many workers on orders/billing (128); this usually means worker names are not stable
    (a new name per process restart fills the registry)
    fix: use a stable name — hostname, pod name, or a systemd instance name
    or:  messq workers rm orders billing --idle 1h
  ```
- **Reaping** runs in the 60 s janitor (§3.2): delete `workers` rows with zero in-flight deliveries
  and `last_seen < now - --worker-ttl` (default 1 h). Reaping writes **no event row**: the events
  table records message lifecycle and admin actions, and a membership timeout is neither. The history
  is not lost — every `msg.deliver` carries `detail.worker` for as long as event retention holds.
  `messq workers rm` *is* an operator action and does emit `admin.action` with `actor` (#16).
- **Restart:** the registry is durable, so `messq workers` immediately after a restart shows the
  fleet as it was, with `last_seen` in the past and in-flight counts recomputed from `deliveries`
  (which survived, with their `worker` column). `recovery.reclaimed` gains `detail.workers = N`
  (distinct workers whose leases were reclaimed) — a `detail` key, not a new event.

### 5. Events, trace, and the line this whole issue exists for

No new event names (D11). New `detail` keys, all added to `docs/log-schema.md` (#19's versioned
schema) and all optional so existing consumers of the schema keep parsing:

| Event | New `detail` keys |
|---|---|
| `msg.deliver` | `worker` (claimant) |
| `msg.ack` / `msg.nak` / `msg.term` / `msg.extend` | `worker` (settler), `holder` (only when it differs) |
| `msg.ack_stale` | `worker` (settler), `holder`, `current_worker` (who holds the live attempt) |
| `msg.timeout` / `msg.dead` | `worker` (who was holding it when it expired) |
| `flow.blocked` | `worker`, `worker_inflight`, `worker_cap` when `hold_reason="worker_limit"` |
| `recovery.reclaimed` | `workers` (count of distinct workers) |

`messq trace` renders attribution **inside the existing free-form detail area**, so a deployment with
no worker names produces byte-identical output and #20's frozen golden stays green **unedited**:

```json
{"stream":"orders","consumer":"billing","max_ack_pending":256,"max_worker_inflight":16,
 "workers":[
  {"name":"billing-7","host":"ip-10-0-1-7","pid":4242,"client":"messq-go/1.1.0",
   "actor":"tok:billing","instances":1,
   "inflight":12,"pending":14,"max_inflight":16,"oldest_held_ms":4210,
   "first_seen":1764500000000,"last_seen":1764500402000,"last_seen_ms_ago":400,"state":"active"},
  {"name":"billing-3","host":"ip-10-0-1-3","pid":3987,"instances":1,
   "inflight":11,"pending":11,"max_inflight":16,"oldest_held_ms":114000,
   "last_seen_ms_ago":111000,"state":"stale"}],
 "unattributed":{"inflight":3,"pending":3}}
```

`state ∈ {active, stale, idle, gone}`: `active` = seen within `ack_wait`; `stale` = not seen within
`ack_wait` **and** holding messages (its work is about to redeliver — the alertable state); `idle` =
not seen but holding nothing; `gone` = past `--worker-ttl`, next janitor pass reaps it.

Existing shapes gain optional fields (frozen-name rule respected — additions only):

- fetch response: `hold_reason` may now be `"worker_limit"`, plus `worker_inflight` / `worker_cap`
  when it is; header mirror `Messq-Worker-Inflight` for the jq-less shell worker.
- `GET …/consumers/{c}/pending`: `worker` on inflight items, `last_worker` otherwise; new
  `?worker=` filter (`?worker=` with an empty value selects the unattributed set).
- `GET …/consumers/{c}`: `workers` (count), `max_worker_inflight`, `require_worker`.
- `POST/PATCH …/consumers`: `max_worker_inflight`, `require_worker`.

`DELETE …/workers/{w}` **never touches messages.** Without `force=1` it refuses (`409 conflict`) when
the member holds in-flight rows, naming the recipe that actually does what the operator meant:

```
worker billing-3 still holds 11 in-flight messages; removing the registry row would not free them
  they redeliver on their own at 09:15:04 (ack_wait 30s)
  to redeliver them now:
    messq pending orders billing --worker billing-3 --tokens | xargs -r messq nak --reason "host lost"
  to remove only the registry entry: --force
```

Follows §8's rules unchanged: human table on a TTY / JSON otherwise, data to stdout, narration to
stderr, every inspect command ends with the next useful command, `rm` is destructive so it takes
`--dry-run` and `--confirm`-by-name, exit `5` when the filtered set is empty (`messq workers --stale
&& page-oncall` works in cron). `messq lag` gains a `WORKERS` column only when at least one consumer
in the table has members — a column of `-` on every row is noise.

`messq doctor` (#30) gains three findings: a `stale` worker holding messages; `max_worker_inflight`
set while >20 % of deliveries are unattributed (*"the cap is not doing what you think"*); and a
registry above 50 % of `--max-workers-per-consumer` with `instances > 1` on many rows (*"worker names
look unstable"*).

`--exec` children (#25) get `MESSQ_WORKER` in the env table; the parent strips any inherited
`MESSQ_WORKER` first, per #25's existing rule.

### 8. Metrics and the cardinality rule (binding)

`worker` is an identity label whose value set is operator-controlled. #21's rule permits extra labels
only for closed compile-time enums, so this issue proposes a **third, narrower category** and the
allow-list test must encode it:

> **Registry-bounded labels.** A label may carry a `worker` value only on a **scrape-time gauge**
> whose series are recomputed from the `workers` table each scrape, only when `--worker-metrics` is
> enabled, and only up to `--max-worker-metric-series`. Never on a counter or a histogram.

The reason is the asymmetry between the two: a gauge computed by the Collector **disappears** when
the member is reaped, while a counter series lives for the process's lifetime — a fleet with unstable
names would leak series into Prometheus forever, and the operator's first symptom would be their
monitoring bill.

| Metric | Type | Labels | Enabled | Source |
|---|---|---|---|---|
| `messq_workers` | gauge | `stream`,`consumer` | always | `COUNT(*)` from `workers` (5 s cache, #21's Collector) |
| `messq_unattributed_inflight` | gauge | `stream`,`consumer` | always | `deliveries WHERE worker IS NULL AND state=1` |
| `messq_worker_inflight` | gauge | `stream`,`consumer`,`worker` | `--worker-metrics` | grouped count |
| `messq_worker_last_seen_seconds` | gauge | `stream`,`consumer`,`worker` | `--worker-metrics` | `now - last_seen` |
| `messq_worker_series_truncated` | gauge | `stream`,`consumer` | `--worker-metrics` | 1 when the cap collapsed series |

Over `--max-worker-metric-series` (default 100), the Collector emits the top members by in-flight
count plus one aggregate row `worker="_other"`, and sets `messq_worker_series_truncated=1`. A
truncated graph that says it is truncated beats a complete graph nobody can afford.

Alerts (`contrib/prometheus/alerts.yml`, #21): `MessqWorkerStale` — `messq_worker_last_seen_seconds >
2 × ack_wait` **and** `messq_worker_inflight > 0` (only meaningful under `--worker-metrics`); and the
label-free version everyone gets, `MessqUnattributedInflight` on a consumer with `require_worker`.

### 9. Flags and consumer fields (D8: flags + `MESSQ_*` env only)

| Flag | Env | Default | Meaning |
|---|---|---|---|
| `--max-workers-per-consumer` | `MESSQ_MAX_WORKERS_PER_CONSUMER` | `128` | Registry bound (I11) |
| `--worker-ttl` | `MESSQ_WORKER_TTL` | `1h` | Idle members with no in-flight are reaped by the janitor |
| `--worker-seen-resolution` | `MESSQ_WORKER_SEEN_RESOLUTION` | `5s` | Coarseness of durable `last_seen`; keeps idle polling write-free |
| `--worker-metrics` | `MESSQ_WORKER_METRICS` | `false` | Enable `worker`-labelled gauges |
| `--max-worker-metric-series` | `MESSQ_MAX_WORKER_METRIC_SERIES` | `100` | Hard cap on `worker`-labelled series |

| Consumer field | Default | Meaning |
|---|---|---|
| `max_worker_inflight` | `0` | Per-worker in-flight ceiling; `0` = off. Bounded by `[0, max_ack_pending]` at validation (a larger value is accepted with a warning — the consumer bound dominates) |
| `require_worker` | `false` | Reject unattributed fetches with `400 worker_required` |

Both are SIGHUP-irrelevant (they are durable consumer config, changed through `consumer edit`), and
both appear in `consumer info`, `--output json`, and the `consumer.update` `changes[]` detail.

### 10. Invariant I12 and the verify checkers

> **I12 — a `(consumer, seq)` is INFLIGHT to at most one worker at a time**, and every settle that
> mutates it names the attempt that worker was given.

I12 is *structurally* true under D5 (one row, one `attempts`, one `worker`) — which is the point.
Its checker exists to prove the phase-2 columns did not quietly break the property, and to catch the
one way it could go wrong in practice: a claim path that writes `worker` outside the transaction that
flips `state`.

```go
// internal/verify additions
{ID: "I12", Name: "one worker per inflight delivery", Query: `
   SELECT stream, consumer, seq FROM deliveries
    WHERE state = 1 AND worker IS NOT NULL AND attempts = 0 LIMIT 100;`},  -- structural
{ID: "W1", Name: "per-worker inflight within cap (advisory on shrink)", Query: `
   SELECT d.stream, d.consumer, d.worker, COUNT(*) AS inflight, cap.n
     FROM deliveries d JOIN (…resolve cap…) cap USING (stream, consumer, worker)
    WHERE d.state = 1 AND cap.n > 0
    GROUP BY 1,2,3 HAVING COUNT(*) > cap.n;`},
```

The behavioural half of I12 lives in #13's fold (it has the event stream): between two `msg.deliver`
events for one pair there must be a release (`msg.nak`, `msg.timeout`, `recovery.reclaimed`), and no
two `msg.deliver` events for one pair may share an `attempt`. `W1` is **advisory** exactly like I5 —
a lowered cap leaves legal overshoot, asserted only to be non-increasing.

`SEMANTICS.md` (#4) gains: I12, the attribution rules from §2, the precedence table from §3, and one
sentence that matters more than the rest — *messq has no consumer groups; it has fenced deliveries
and a record of who took them.*

### 11. Edge cases

| Case | Handling |
|---|---|
| Worker dies mid-batch (SIGKILL) | Nothing new happens: `ack_wait` expires, `msg.timeout` fires with `detail.worker=<dead>`, rows redeliver to whoever fetches. The registry shows `stale`; the janitor reaps after `--worker-ttl`. **This is the acceptance test.** |
| Two processes use the same name | Allowed. They share a bucket and a cap. `instances` increments when `(host,pid)` changes; `messq workers` marks `(!) 2 instances`; `doctor` explains. Never rejected — reusing names across a rolling deploy is normal. |
| Name changes on every restart (UUID) | Registry fills → idle members evicted → `429 too_many_workers` with the teaching error naming stable-name options. Loud beats leaky. |
| Settle arrives from a different name than the holder | Accepted (D7: the token is the fence). `detail.worker` = settler, `detail.holder` = holder; both rendered by `trace`. |
| Cap lowered below current in-flight | Admission form: nothing revoked, no new claims until the worker drains. Same rule and same wording as #9's `max_ack_pending` shrink; `W1` reports advisory overshoot. |
| `max_worker_inflight > max_ack_pending` | Accepted with a validation warning; the consumer bound dominates and `hold_reason` reports `max_ack_pending`. |
| Both bounds bite at once | §3's precedence: `max_ack_pending` wins. Deterministic, tested. |
| One worker, cap set | Cap applies. A single worker can absolutely rate-limit itself, and that is a legitimate use (`--max-inflight 1` = strict serial processing per host). |
| `require_worker` on, legacy client fetches | `400 worker_required` with the exact JSON to add. Default off so an upgrade never triggers it. |
| Unattributed fetch with a cap set | Exempt from the per-worker cap (a mixed fleet during upgrade must not deadlock), counted in `messq_unattributed_inflight`, surfaced by `doctor`. |
| Worker sends a 5 KiB name | `400 bad_request`, grammar named. Bounded before it reaches the registry, the log, or a metric label. |
| Worker name `_other` / leading `_` | Rejected by the grammar (must start alphanumeric); `_` prefix is reserved for daemon-generated label values. |
| Registry row for a deleted consumer | Impossible: `ON DELETE CASCADE`. `verify` has a foreign-key check (V3) already. |
| `workers` row exists, `deliveries` has none | Normal (idle member). `inflight: 0`, state `idle`, reaped at TTL. |
| `deliveries.worker` names a reaped member | Normal and harmless: the column is data, not a foreign key. Listings show the name with `last_seen: null` and state `gone`. |
| Clock jumps backwards | `last_seen_ms_ago` clamps at 0 and the row is annotated, mirroring #20's clock-jump rule. Lease deadlines are unaffected (monotonic, §11 fault family). |
| Ordered consumers (#38) also enabled | Precedence §3: ordering filters candidates first, worker allowance truncates the survivors. Composition is order-independent because both are pure filters over the same candidate list; a joint table test pins it if #38 landed first. |
| Rate limiting (#39) also enabled | Same table, slot 4, evaluated before the worker allowance. |
| `messq workers rm` on a member with in-flight | `409` + the `pending --worker … \| xargs messq nak` recipe; `--force` clears only the registry row. |
| Registry write during `--durability=full` | Rides the fetch's group commit. Zero extra fsyncs, and the coarse `last_seen` keeps idle long-polls from committing at all. |
| Disk below `--min-free-bytes` | Registry upserts are part of the fetch/settle path, which §4.5 keeps alive; only publish is rejected. |

## Acceptance criteria

- [ ] The migration applies forward-only on a v1.0 data dir, is refused when older than the file's
      schema version, and has a committed #34 golden fixture that the current binary migrates and
      passes `verify --deep`.
- [ ] A fetch with `"worker":"billing-7"` and one with `"worker":{"name":"billing-7"}` are accepted
      and produce identical stored state; an object with an unknown key is `400 bad_request`.
- [ ] A fetch with no `worker` field behaves exactly as it did before this issue: rows are claimed
      with `worker IS NULL`, no registry row is written, and #18's contract tests pass **unmodified**.
- [ ] Every row claimed by an attributed fetch records `deliveries.worker` in the **same transaction**
      that sets `state=INFLIGHT` and increments `attempts`; a forced commit failure leaves neither.
- [ ] A released row (nak/timeout/restart) keeps its `worker` value and is reported as `last_worker`;
      an INFLIGHT row reports `worker`.
- [ ] `max_worker_inflight = N` prevents a single worker from holding more than `N` INFLIGHT rows,
      while a second worker on the same consumer claims freely up to the consumer bound.
- [ ] A capped fetch returns `hold_reason:"worker_limit"` with `worker_inflight` and `worker_cap`,
      and emits a repeat-limited `flow.blocked` carrying the same three values.
- [ ] When both bounds apply, `hold_reason` is `max_ack_pending` — asserted against the full
      precedence table, including the #38/#39 slots when those features are absent.
- [ ] Lowering a cap below current in-flight revokes nothing, blocks new claims for that worker only,
      and leaves `W1` advisory-clean once the worker drains.
- [ ] `require_worker` rejects an unattributed fetch with `400 worker_required` and a `next` hint;
      with it off, unattributed fetches are exempt from the cap.
- [ ] A settle from a name different from the holder succeeds, and the event carries both `worker`
      and `holder`.
- [ ] A stale ack records `worker`, `holder` and `current_worker`, and `messq trace` renders
      `from=…` / `… holds attempt N` on that line.
- [ ] `messq trace` output for a deployment with **no** worker names is byte-identical to #20's
      frozen golden (the golden file is not edited by this PR).
- [ ] `GET …/workers` lists members with in-flight, pending, oldest-held, last-seen and state, plus
      an `unattributed` roll-up; `state` is `stale` exactly when `last_seen > ack_wait` and
      `inflight > 0`.
- [ ] `messq workers` renders the table above on a TTY, JSON otherwise, exits `5` on an empty
      filtered set, and ends with a next-command hint naming the stale worker.
- [ ] `messq workers rm` refuses a member with in-flight rows without `--force`, never mutates
      `deliveries` in either case, and emits `admin.action` with `actor`.
- [ ] `messq pending --worker NAME` filters correctly, and `--worker ""` selects the unattributed set.
- [ ] Registering member 129 evicts an idle member if one exists, otherwise returns
      `429 too_many_workers` with the unstable-names teaching error and one repeat-limited
      `api.error` event.
- [ ] The janitor reaps members with zero in-flight and `last_seen` older than `--worker-ttl`, writes
      no event rows, and drops their metric series on the next scrape.
- [ ] `last_seen` is written at most once per `--worker-seen-resolution` per worker: 10 000 empty
      long-polls from one idle worker produce ≤ `10000 × interval / resolution` registry writes
      (asserted on commit count, not wall clock).
- [ ] With `--worker-metrics=false` (default) **no** metric family carries a `worker` label —
      asserted by #21's allow-list test, which fails if any counter ever gains one.
- [ ] With `--worker-metrics=true`, only the two gauges carry `worker`, series are recomputed at
      scrape time, and above `--max-worker-metric-series` the collector collapses to top-N plus
      `worker="_other"` and sets `messq_worker_series_truncated=1`.
- [ ] `verify` runs `I12` and `W1`; a sabotaged claim that writes `worker` outside the state
      transition is caught by `I12`.
- [ ] `SEMANTICS.md`, `docs/log-schema.md`, `docs/OPERATIONS.md` and `docs/non-goals.md` are updated
      in the same PR; every new `detail` key is documented and every documented key has a renderer or
      an explicit "raw detail" note (#20's binding test).
- [ ] `internal/queue` ≥ 90 %, `internal/store` ≥ 85 % (#2 floors); no `time.Now()` outside the Clock
      seam; no `time.Sleep` in tests.

## Test plan

Per §11: `-race` everywhere, real SQLite files in `t.TempDir()`, timing through the Clock seam and
`testing/synctest`, every fixed bug landing with a committed reproduction artifact.

**Unit — pure (`internal/queue`)**
- `TestAllowance`: table over `cap ∈ {0,1,8}` × `inflight ∈ {0, cap-1, cap, cap+1}` × `batch` ×
  attributed/unattributed × `require_worker`, asserting both the count and the `hold_reason`.
- `TestHoldPrecedence`: the §3 table as data — every combination of simultaneously-true conditions
  yields the highest-priority reason. Written so #38/#39 add a row rather than a branch.
- `TestWorkerRefUnmarshal`: string sugar, object form, unknown key, missing name, oversize name,
  bad grammar, `null`, `""`, non-ASCII, leading `_`.
- `FuzzWorkerRefUnmarshal`: never panics; accepted input round-trips; no accepted name escapes the
  #3 grammar (which is what keeps names safe as CLI columns, log fields and label values).

**Unit — store (real DB)**
- Claim writes `worker` in the same transaction as `state`/`attempts`; injected commit failure at
  #6's seam leaves none of the three.
- Grouped counting query returns the same consumer totals as #9's ungrouped one over randomized
  states (`TestGroupedCountMatchesConsumerCount`) — the "two numbers that must never disagree" test.
- Registry upsert: `instances` increments only on `(host,pid)` change; `last_seen` respects the
  resolution window; overflow evicts idle first, then rejects.
- Cascade: `consumer rm` deletes the registry rows; `verify` V3 clean.
- Two workers, `max_ack_pending=4`, `max_worker_inflight=2`: each claims exactly 2, third fetch from
  either holds with `worker_limit`, an unattributed fetch still claims the remainder.

**Deterministic timing (`testing/synctest`)**
- Worker goes silent → `state` transitions `active → stale → gone` at exactly `ack_wait` and
  `--worker-ttl`; reaping happens on the first janitor tick after the TTL, not before.
- `--worker-seen-resolution` write suppression over 10 000 simulated empty polls.

**Property (`rapid`, extending #13)**
- The action registry gains a small worker pool (3 names + unattributed); `fetch` picks one,
  `settle` may use a *different* one (exercising the holder/settler split).
- New action `worker_dies(w)`: that worker stops fetching and settling; its rows must be redelivered
  to another worker within `ack_wait` and never to itself while dead.
- Invariants checked after every action: all of §5.2 plus **I12** and `W1`; the reference model in
  `internal/model` gains one map (`holder[pair]`) and nothing else — if the model needs more than
  that, the feature is bigger than D15 allows and the design is wrong.
- Sabotage entries (#13's `messq_sabotage` tag): `worker_written_late` (write `worker` in a second
  statement outside the state transition) must fail `I12`; `worker_cap_off` must fail `W1`.

**Crash (#8's harness) — the named acceptance scenario**
- Three `messq sub --exec` workers (`w1`,`w2`,`w3`) on one consumer, steady load, `ack_wait=5s`.
  SIGKILL `w2` mid-batch. Assert: (a) only rows with `worker='w2'` redeliver; (b) they redeliver
  within `ack_wait + jitter`; (c) each redelivery has a `msg.timeout` with `detail.worker="w2"`
  followed by a `msg.deliver` with a different worker (**I9**: every duplicate has a named cause,
  now with a named *machine*); (d) `w1`/`w3` lose nothing and see no stale acks; (e) the ledger
  oracle is clean; (f) `messq workers` shows `w2` stale, then gone after the TTL.
- SIGKILL the **broker** with attributed in-flight rows: after restart, `deliveries.worker` survives,
  `recovery.reclaimed` carries `detail.workers`, and `messq workers` shows the fleet with in-flight
  counts recomputed from the surviving rows.
- Fault points `store.fetch.after_worker_upsert` and `store.fetch.before_commit` added to the
  `MESSQ_FAULTS` grammar (#32).

**API / golden**

- `testscript` goldens (#26): `messq workers` table, `--output json`, empty-set exit `5`,
