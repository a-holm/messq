## Context

A queue's job is to absorb a burst so the thing behind it does not have to. messq does that on the
*inbound* side (durable stream, `max_ack_pending`, long-poll backpressure) and does nothing at all on
the *outbound* side: a consumer with 200 000 messages of backlog and 32 workers will deliver as fast
as the workers ask, which is exactly how a recovered downstream gets knocked over a second time.

This is the single most-requested feature after a DLQ redrive goes badly. The shape of that incident
is always the same: a downstream fails, 8 000 messages dead-letter, the downstream comes back, an
operator redrives, and the redriven traffic — arriving with no natural pacing, because a queue drains
at the speed of the fastest consumer — takes the downstream down again. `messq dlq redrive --rate`
(#29) already paces the *republish* side for exactly this reason. This issue supplies the other half:
**a per-consumer ceiling on delivery rate, enforced by the broker, so pacing does not depend on every
client behaving.**

The implementation is deliberately tiny, and the reason it is tiny is a property of the design that
already exists. #9 put every delivery decision inside one writer command, and made the claim guard a
conjunction: *deliver this row iff `now >= visible_at` and `pending < max_ack_pending` and not
paused*. A rate limit is one more conjunct. It can only ever **narrow** the guard, so it cannot
create a delivery, cannot skip a message, cannot touch `attempts`, and cannot break a single §5.2
invariant by construction. Everything hard about rate limiting elsewhere — coordinating limiters,
racing buckets, deciding who owns the counter — is absent because §3.2 gives us exactly one writer
goroutine, so the bucket has no concurrency at all.

Governing PLAN.md material:

- **D15 (§2)** — phase 2 is *strictly demand-ordered*, and per-consumer rate limiting is named in it.
  The M9 rule from §14 is the acceptance bar: *"Each feature ships with a new invariant, events,
  metrics, docs — or it does not ship."* This issue ships **I14-a**, `flow.blocked{reason=rate_limit}`,
  three metrics, an alert rule, a runbook and a `guarantees.md` row.
- **§8 CLI design** — the feature is a subcommand flag (`messq consumer edit --max-rate 10/s`), it is
  live-editable, `consumer info` must *say* it is engaged, and the inspect output ends with the next
  useful command.
- **§5 / §5.1 T2** — the claim transition, unchanged except for a narrower guard. **§5.2 I4/I5/I9**
  keep holding because nothing else moves.
- **§9.2 / §9.4** — the event vocabulary is **closed**; this issue invents no event name. It uses
  `flow.blocked` with a new `reason` value, and adds metrics under #21's cardinality policy (identity
  labels `stream`/`consumer`, plus closed-enum labels).
- **D8** — configuration is per-consumer, not a flag. This issue adds **zero new server flags**.
- **§7 / D2** — a throttled fetch is a `200` with an empty batch and a hold reason, never an error.
  #14 already made that choice for `max_ack_pending`; this issue follows it and, in doing so, settles
  the two reserved `429` rows that #23 explicitly deferred here.

Because this lands after **#36**, everything it touches is a frozen surface. Every change below is
strictly additive: new columns with off-by-default values, one new enum value in two enums, new
metric names, new JSON fields. No rename, no removal, no behaviour change for a consumer that does
not opt in.

## Scope

**In scope**

- **Migration `000N_consumer_rate.sql`** — four columns on `consumers`: the configured rate, the
  burst, and the durable token-bucket state. Defaults mean *off*, so every existing consumer in every
  existing data directory is unaffected.
- **`internal/queue/rate.go`** — the pure limiter: `Rate`, `ParseRate`/`String` (the `10/s`, `600/m`,
  `1/h` grammar shared with #29), `RateState` with `TokensAt`/`Allowed`/`ReadyAt`/`Consume`/
  `Reconfigure`/`DrainETA`. No I/O, no `time.Now`, integer arithmetic only.
- **The claim guard** in `internal/store/fetch.go`: one gate between the flow-control counts and the
  top-up, plus the token write-back inside the *same* transaction as the claim (D11 — zero extra
  fsyncs, and the bucket cannot disagree with the deliveries it authorised).
- **Config plumbing**: validation and bounds, `findings` for the footguns (a rate that cannot drain
  the backlog inside the stream's retention window), the materialize-then-reconfigure rule for live
  edits, and `consumer.update` audit detail naming the actor and the old/new rate.
- **Wire**: `max_rate_mmps` + `rate_burst` on consumer create/PATCH/info; `rate_tokens`,
  `rate_ready_at`, `drain_eta_ms` and `delivery_blocked_by:"rate_limit"` on consumer info;
  `hold_reason:"rate_limit"` + `retry_after_ms` on fetch.
- **Long-poll integration** (a surgical change to #14's loop): a `RateReadyAt` on `FetchResult` that
  caps the parked sleep, and **wake suppression** so a publish storm cannot turn a 1/s consumer into
  a fetch storm through the single writer.
- **CLI** (#24's tree): `consumer add|edit --max-rate|--rate-burst`, the `consumer info` delivery
  line, the `lag` STATE value, and the drain-ETA sentence that makes the feature self-explaining.
- **`pkg/client`** (#22): the `rate_limit` `HoldReason` constant and its row in the `Worker` hold
  matrix (sleep `retry_after_ms`, not a hot loop).
- **Invariant `I14-a`** in `SEMANTICS.md` + `docs/guarantees.md`, `verify` checkers `R1`–`R3`, and the
  events-derived deep check `R4` (the bound is provable *after the fact* from the audit trail — the
  answerability thesis applied to this feature).
- **Metrics** `messq_rate_limited_total`, `messq_rate_tokens`, `messq_flow_control_engaged`, their
  catalogue rows, one alert rule, and one dashboard panel.
- **Cross-issue bookkeeping**: #18's `codes.tsv` markers for the two reserved `429` codes; #34's
  upgrade-fixture matrix gains this migration; #29's `--rate` parser is replaced by the shared one.
- Docs: `OPERATIONS.md` runbook *"drain a backlog into a fragile downstream"*, `PROTOCOL.md` fields,
  `log-schema.md` reason value, and the phase-2 page in #35's set.

**Out of scope**

- **Per-worker** rate limits and any fairness guarantee between workers sharing one consumer —
  **#41**. The bucket here is per consumer; workers race for it, and that is documented, not fixed.
- **Publish-side** quotas or per-token API rate limiting. messq does not rate-limit *requests*
  anywhere (#16 rejected auth lockouts as a DoS vector); it paces *deliveries*. See §12 for the
  consequence for the reserved `429 rate_limited` code.
- Redrive pacing, the redrive loop guard and `--dlq-max-rate` — **#29** (shipped). This issue only
  lifts its rate grammar into `internal/queue`.
- Ordered-by-subject delivery and `ordered_hol` in the hold/blocked enums — **#38**, which owns its
  own slot in the precedence list defined in §6.
- Delayed delivery (`Messq-Deliver-At`) — **#37**. Scheduling *when a message becomes eligible* and
  throttling *how fast eligible messages leave* are different machines; they compose without either
  knowing about the other (§11).
- Any change to `ack_wait`, backoff, `max_deliver` or the sweeper (#11). A throttled delivery is a
  delivery that has not happened yet, not a delayed deadline.
- Adaptive/closed-loop rate control (raise the rate while the downstream is healthy) — see §13.
- New event names. The §9.2 vocabulary is closed and frozen at 1.0.

## Design proposal

> Proposal, not mandate — concrete enough to argue with. Four items are marked **decision** because
> they are either on a frozen surface or expensive to reverse.

### 2. Schema (**decision**: the bucket is durable)

```sql
-- 000N_consumer_rate.sql
ALTER TABLE consumers ADD COLUMN max_rate_mmps   INTEGER NOT NULL DEFAULT 0;  -- milli-msg/s, 0 = off
ALTER TABLE consumers ADD COLUMN rate_burst      INTEGER NOT NULL DEFAULT 0;  -- messages
ALTER TABLE consumers ADD COLUMN rate_tokens     INTEGER NOT NULL DEFAULT 0;  -- MICRO-tokens
ALTER TABLE consumers ADD COLUMN rate_updated_ms INTEGER NOT NULL DEFAULT 0;
```

`ALTER TABLE … ADD COLUMN` with a constant default is legal on `STRICT` tables and rewrites nothing.
No index: the bucket is read and written on a row we already have by primary key.

**Milli-messages per second** (`10/s` → `10000`, `1/m` → `17`) so sub-1/s rates are expressible —
"drain this DLQ at one message a minute" is a real request — while the column stays an integer and
the schema stays `STRICT`. **Micro-tokens** (1 message = 1 000 000) make the refill exact; see §3.

The alternative — an in-memory `map[consumerKey]bucket` on the writer, like #9's `flow.blocked`
limiter — was rejected. That map governs *event emission*; this governs *delivery*, and in-memory
state would mean a restart hands out a fresh full bucket. An operator restarting a daemon during an
incident would silently defeat their own throttle, and I14-a could not be stated across restarts.
The durable version costs **one `UPDATE` on a row already loaded, inside a transaction already
committing, only on fetches that actually claimed something, and only for consumers that opted in.**

### 3. The pure limiter (**decision**: exact integer refill, no float, no drift)

```go
package queue

// Rate is milli-messages per second. 10/s = 10_000; 1/m = 17 (ceil); 0 = off.
type Rate int64

const (
    RateOff      Rate  = 0
    MicroPerMsg  int64 = 1_000_000
    MaxRate      Rate  = 1_000_000_000 // 1e6 msg/s — far above anything messq can deliver
    MaxRateBurst int64 = 1_000_000
)

// "10/s" · "600/m" · "1/h" · "0.5/s" · "10" (per second) · "off" / "0".
// Canonical String() round-trips: 10_000 -> "10/s", 17 -> "1/m", 0 -> "off".
func ParseRate(s string) (Rate, error)
func (r Rate) String() string

// RateState is the whole limiter. It is a value: no clock, no mutex, no goroutine.
type RateState struct {
    Rate      Rate  // 0 = off
    Burst     int64 // messages
    Tokens    int64 // micro-tokens, in [0, Burst*MicroPerMsg]
    UpdatedMS int64
}

func (s RateState) TokensAt(nowMS int64) int64            // refilled, clamped to cap
func (s RateState) Allowed(nowMS int64) int64             // TokensAt / MicroPerMsg  (floor)
func (s RateState) ReadyAt(nowMS int64) int64             // first ms at which Allowed >= 1
func (s RateState) Consume(nowMS, n int64) RateState      // n messages; panics if n > Allowed
func (s RateState) Reconfigure(nowMS int64, r Rate, burst int64) RateState
func (s RateState) DrainETA(pending int64) time.Duration  // for consumer info / findings
```

The refill is one multiplication, and it is exact:

```go
func (s RateState) TokensAt(now int64) int64 {
    if s.Rate == RateOff { return 0 }
    cap := s.Burst * MicroPerMsg
    d := now - s.UpdatedMS
    if d <= 0 { return min(s.Tokens, cap) }          // clock went backwards: never refill
    if d >= cap/int64(s.Rate)+1 { return cap }       // long idle: clamp BEFORE multiplying
    return min(cap, s.Tokens+d*int64(s.Rate))
}
```

Why micro-tokens: at `Rate` in milli-msg/s, tokens gained over `d` ms are
`d/1000 × Rate/1000 = d·Rate/10⁶` messages — which is **exactly `d·Rate` micro-tokens, with no
division**. A milli-token unit would need `d·Rate/1000` and would round away up to a millitoken per
call; at one call per fetch that is a systematic under-delivery drift, and "my 10/s consumer does
9.2/s" is a bug report nobody enjoys. The pre-multiplication clamp keeps the product under ~10¹²
for any legal input, so overflow is impossible without a 32-bit build we do not ship.

`ReadyAt` when the bucket is short: `now + ceil((MicroPerMsg - TokensAt(now)) / Rate)` ms.

**Reconfiguration is one rule** — *materialize at `now` with the old parameters, then apply the new
ones, then clamp to the new cap* — which covers all four cases uniformly:

| Change | Result |
|---|---|
| off → on | `Tokens = Burst·10⁶` (one full bucket), `UpdatedMS = now`. Starting empty would stall a consumer for a full window for no reason; starting full is exactly the documented `burst` allowance. |
| on → off | `Tokens = 0`, `UpdatedMS = 0` — a clean, checkable "off" state (checker R2). |
| rate raised | Tokens materialized, then carried over unchanged. **No instant burst**: raising a limit does not hand out arrears. |
| rate/burst lowered | Tokens materialized, then clamped to the new cap. Takes effect on the very next fetch. |

### 4. The gate: one branch in the fetch pipeline (**decision**: before top-up)

#9's `Fetch` becomes seven steps instead of six; the new one is step 4.

| # | Step | Change |
|---|---|---|
| 1 | Load consumer row | now also reads the four rate columns |
| 2 | `paused` → `Hold = paused`, return | unchanged |
| 3 | `pending` / `inflight` / `ready_now` counts | unchanged (one indexed count) |
| **4** | **Rate gate** | `allowed := rs.Allowed(now)`; if `allowed == 0` → return early |
| 5 | Top-up (T1) | bounded by `effBatch = min(Batch, allowed)` |
| 6 | Claim (T2) | at most `effBatch` rows |
| 7 | Write back the bucket | only if rows were claimed; same transaction |

```go
// internal/store/fetch.go — the entire feature on the hot path
effBatch := req.Batch
var rs queue.RateState
if c.Rate != queue.RateOff {
    rs = queue.RateState{Rate: c.Rate, Burst: c.RateBurst, Tokens: c.RateTokens, UpdatedMS: c.RateUpdatedMS}
    allowed := rs.Allowed(now)
    if allowed == 0 {
        readyAt := rs.ReadyAt(now)
        return FetchResult{
            Hold:         holdFor(counts, readyAt), // rate_limit when work is being held back
            RetryAfterMS: readyAt - now,
            RateReadyAt:  readyAt,
            Pending:      counts.Pending, Backlog: counts.Backlog,
        }, nil
    }
    effBatch = min(effBatch, int(allowed))
}
// … top-up(effBatch) … claim(effBatch) …
if c.Rate != queue.RateOff && len(claimed) > 0 {
    rs = rs.Consume(now, int64(len(claimed)))
    // UPDATE consumers SET rate_tokens = :t, rate_updated_ms = :now WHERE stream = :s AND name = :c
}
```

Five properties of this placement, each load-bearing:

1. **It can only narrow.** `effBatch` never grows; nothing else in the claim changes. Every §5.2
   invariant is preserved without argument — this is the whole reason the issue is an `S`.
2. **Tokens are spent per *delivered message*, not per fetch.** A fetch that claims nothing (no
   ready rows) spends nothing and writes nothing. A batch of 16 against 3 tokens claims 3 and spends
   3.
3. **The empty-bucket path does no scan and no write.** It still runs step 3, because a fetch
   response that lied about `pending`/`backlog` would break `messq lag` and every worker heuristic —
   so the honest cost is *one bounded index count*, not "zero SQL".
4. **Skipping top-up is a feature, not an optimisation.** A throttled consumer does not materialise
   delivery rows it has decided not to hand out, so it does not pin thousands of messages against
   retention (§4.5's `retention.blocked`) and does not sit at `max_ack_pending` for the wrong
   reason. Backlog stays in `messages`, where it is cheap.
5. **No concurrency.** Two fetches for one consumer are serialised by the single writer (§3.2), so
   the bucket needs no atomics and cannot be double-spent. Same argument as #9's no-double-claim.

Redeliveries consume tokens exactly like first deliveries — the fragile downstream cannot tell them
apart, and pretending otherwise would make the limit a lie under retry load. The consequence is
stated in the docs: **rate limiting delays deliveries, it never expires them**, so under a binding
throttle `TimeToDead` (#11 §5) becomes a lower bound rather than an estimate.

### 5. Validation, bounds and findings

| Field | Bounds | Notes |
|---|---|---|
| `max_rate_mmps` | `0` or `[1, 1_000_000_000]` | `0` = off. Registered in #4's Appendix A1 |
| `rate_burst` | `[1, 1_000_000]` when rate > 0; `0` when off | Omitted ⇒ `max(1, ceil(rate/s))` — one second's worth |

`findings` (#15's `[]Finding` shape, `{level, code, message}`), warnings not errors:

| Code | Fires when | Message |
|---|---|---|
| `rate_below_drain` | `DrainETA(backlog) > stream.max_age_ms` | *"at 1/m the 8 214 pending messages need 5d17h; stream `orders` keeps messages for 7d — some will expire before they are delivered"* |
| `rate_burst_below_batch` | `burst < 16` | *"burst 4 caps every fetch at 4 messages regardless of `batch`"* |
| `rate_below_retry` | `Rate < 1/ack_wait × inflight` | *"at this rate, redeliveries alone consume the budget; `max_deliver` will take longer than `time_to_dead` suggests"* |

`rate_below_drain` is the one that matters: a throttle set below the arrival rate is not a throttle,
it is a slow-motion data-loss device, and messq should say so at the moment it is configured rather
than in a post-mortem. `messq doctor` (#30) re-runs the same check against live numbers.

### 6. Hold reasons and the `delivery_blocked_by` precedence

Both enums gain exactly one value, `rate_limit`:

- fetch wire (`hold_reason`, #14): `{"", "no_messages", "max_ack_pending", "backoff", "paused",
  "shutting_down"}` **+ `"rate_limit"`**.
- consumer info (`delivery_blocked_by`, #9/#15) precedence, first match wins:

```
paused → rate_limit → max_ack_pending → backoff → catching_up → no_messages → none
```

`rate_limit` sits directly behind `paused` because both are **deliberate operator policy, not a
symptom**. Reporting `max_ack_pending` for a consumer that an operator throttled on purpose sends the
next responder hunting for a stuck worker.

One refinement so the report stays honest (`holdFor` above): **the bucket names itself only when it is
holding work back.** If `ready == 0 && backlog == 0`, an empty bucket is irrelevant and the reason is
`no_messages` — otherwise an idle throttled consumer would render as "rate-limited" in `messq lag`
forever. `retry_after_ms` is populated in both cases.

(#38 owns its own `ordered_hol` slot in this list; the pre-existing cosmetic divergence between the
two enums — `no_messages`/`""` vs `none`, `catching_up` present in one — is inherited, not fixed
here.)

### 7. Long-poll: capping the sleep and suppressing the wake

#14's loop already sleeps `min(deadline, NextVisibleAt)`. `FetchResult` gains `RateReadyAt` and the
sleep target becomes:

```go
wakeAt := maxTime(res.NextVisibleAt, res.RateReadyAt) // work must exist AND a token must exist
timer := s.clock.NewTimer(sleepFor(deadline, wakeAt, s.cfg.EmptyWakeDamper))
```

`max`, not `min`: a delivery needs a visible row *and* a token, so the binding constraint is the
later of the two.

**The wake must also be suppressed (decision).** A rate-limited fetch *does* park — unlike `paused`
and `max_ack_pending`, time alone unblocks it — but every publish on the stream signals its waiter.
At 1 000 publishes/s against a 1/s consumer that is 1 000 empty fetch commands per second through
the single writer, and #14's 5 ms empty-wake damper only reduces it to 200/s. So while
`now < RateReadyAt`, a `sub.C` wake **resets the timer instead of re-fetching**:

```go
case <-sub.C:
    if s.clock.Now().Before(rateReadyAt) { continue } // drain the level, do not re-fetch
```

Asserted directly: `TestRateLimitedParkDoesNotBusyLoop` publishes 1 000 msg/s at a 1/s consumer in a
`synctest` bubble and requires **≤ 1 fetch command per token interval**.

### 10. Events, metrics and the audit trail

**Events — no new names** (§9.2 is closed and frozen):

| Event | Level | `detail` |
|---|---|---|
| `flow.blocked` | WARN, never sampleable | `reason:"rate_limit"`, `retry_after_ms`, `max_rate_mmps`, `rate_burst`, `pending`, `backlog` |
| `consumer.update` | INFO | `max_rate_mmps:{from,to}`, `rate_burst:{from,to}`, `actor` — *who throttled this consumer, and when* is an incident question |

`flow.blocked` reuses #9's writer-owned rate limiter, with the key widened from `consumer` to
`(consumer, reason)` so a consumer flapping between `max_ack_pending` and `rate_limit` reports both.
Bounded by `--max-consumers × |reasons|` (I11).

> **Log-schema note.** `detail.reason` gains a value. `docs/log-schema.md` (#19) declares `detail`
> values additive-compatible; this PR bumps the log-schema minor version and adds the row. If review
> finds the reason enum was frozen as closed at 1.0, the fallback is a schema-version bump with a
> migration note — not a silent new value.

**Metrics** (#21's catalogue; identity labels `stream`/`consumer`, `reason` a closed Go enum):

| Metric | Type | Labels | Meaning |
|---|---|---|---|
| `messq_rate_limited_total` | counter | `stream`, `consumer` | fetches the bucket shortened or emptied |
| `messq_rate_tokens` | gauge | `stream`, `consumer` | whole tokens available at scrape time, recomputed from the row by #21's collector — a gauge derived from truth cannot drift |
| `messq_flow_control_engaged` | gauge | `stream`, `consumer`, `reason` | `1` for the consumer's current `delivery_blocked_by`, `0` otherwise. `reason ∈ {paused, rate_limit, max_ack_pending, backoff}` |

Shipped alert (`contrib/prometheus/alerts.yml`): `messq_flow_control_engaged{reason="rate_limit"} == 1`
**and** `deriv(messq_backlog[30m]) > 0` for 1 h — *a throttle below the arrival rate is a queue that
never drains*. A steady rate-limited consumer with a falling backlog alerts on nothing.

### 11. Edge cases, decided

| Case | Handling |
|---|---|
| Bucket empty | Early return: one bounded count, no scan, no write, `hold_reason:"rate_limit"`, `retry_after_ms` set |
| `batch=16`, 3 tokens | Returns up to 3 messages **with** `hold_reason:"rate_limit"` — #9 defines hold as "why the batch is short *or* empty" |
| Tokens available, nothing ready | No tokens spent, no write; hold is `no_messages` |
| Empty bucket, empty stream | Hold is `no_messages`, not `rate_limit` (§6) — an idle consumer must not render as throttled |
| Redelivery under a throttle | Consumes a token like any delivery. `time_to_dead` becomes a lower bound; `consumer info` labels it as such |
| Restart | Bucket is durable: tokens and `rate_updated_ms` survive. A restart grants **no** free burst — the property an in-memory bucket could not give |
| Enable → disable → enable | One full bucket per enable, by design, audited in `consumer.update`. I14-a is scoped to windows without a rate-config change, and says so |
| Rate raised mid-incident | Materialize-then-reconfigure: no arrears burst, new ceiling effective on the next fetch, no restart |
| Rate lowered below current tokens | Tokens clamped to the new cap immediately |
| Wall clock jumps forward 1 h | Bucket fills to at most `burst` — bounded by construction. #6's `batchNow()` is monotone-clamped, so this is the same bounded exposure #11 documents for deadlines |
| Wall clock jumps backwards | `d <= 0` ⇒ no refill, tokens unchanged, `UpdatedMS` unchanged. Never negative, never a free burst |
| `burst < batch` | Every fetch is capped at `burst`; the `rate_burst_below_batch` finding says so at config time |
| Very high rate (≥ 10⁶/s) | The guard never binds; cost is one comparison. `TokensAt` clamps at cap; no overflow |
| Rate on a `.dlq` consumer | Normal, and the headline use case: redrive fast, *consume* slowly |
| Paused **and** rate-limited | `paused` wins the precedence; no claim, so no token is spent while paused |
| `seek` / generation bump | Does **not** reset the bucket. A replay must not be a way around the throttle — deliberate, and stated in `SEMANTICS.md` |
| Consumer deleted | The columns go with the row; no orphan bucket state anywhere (there is no other state) |
| Many workers, one throttled consumer | They race for a shared bucket; no fairness guarantee. Documented; #41 is the tool if it ever matters |
| Store latched read-only (#6) | Fetch already fails `503 read_only` before the gate; the bucket is untouched |
| `messq bench` (#31) against a rate-limited consumer | The run is reported **invalid** with the reason naming the consumer — measuring a throttle and calling it throughput is exactly the dishonesty §12 of PLAN.md forbids |
| Upgrading a 1.0 data dir | Migration adds four columns defaulting to off; every existing consumer behaves identically. #34's fixture matrix gains a case that proves it |
| Composition with #37 (delayed delivery) | Orthogonal: `visible_at` decides *eligibility*, the bucket decides *egress*. A scheduled message becomes ready at its time and then waits for a token; no code in either feature mentions the other |

### 12. The two reserved `429` rows (**decision**, and the hand-off #23 deferred here)

#14 reserved `flow_control` (429) and `rate_limited` (429) in the error enum, produced neither, and
#23 wrote *"#39 revisits the two 429 rows."* The revisit concludes: **neither code is ever emitted,
and both become permanently reserved.**

- A throttled fetch is a normal, expected, successful outcome. Making it an error would force the
  five-line shell worker (§7, a CI-executed golden) to grow error handling for the case the feature
  exists to create.
- messq rate-limits *deliveries*, never *requests*. There is no other place a `429` could come from,
  and adding request-rate limiting would contradict #16's reasoning about lockouts as DoS vectors.

Consequences to land in the same PR: #18's `codes.tsv` moves both rows from *owned by #39* to
*permanently reserved — never emitted* (otherwise its "still reserved after #39 ships" check fails);
`PROTOCOL.md` says so in one line; #23's exit-code table keeps both rows mapped to exit `4` so a
future daemon that ever did emit one is still bucketed correctly by an old client.

### 13. Considered and deferred

| Idea | Why not now | Revisit trigger |
|---|---|---|
| Adaptive rate (raise while the downstream is healthy) | Needs a health signal messq does not have; a broker guessing at downstream health is a new failure mode | A user asks for it *with* the signal they would feed it |
| Per-worker rate limits | #41 owns worker identity; without it a per-worker limit has nothing to key on | #41 ships and someone needs it |
| Byte-rate limiting (`--max-rate 1MiB/s`) | Same bucket, different unit — a two-line extension once someone needs it. Shipping both units now doubles the config surface for a use case nobody has asked for | First request |
| A rate limit on publish | Different problem (the stream is the buffer; `discard`/`max_msgs` already answer it) | Never, absent a multi-tenant story |

### 14. Invariant and checkers

> **I14-a.** For a consumer whose rate configuration is unchanged over `[t0, t1]`, the number of
> `msg.deliver` events for that consumer in the interval is at most
> `floor(Rate·(t1−t0)/10⁶) + Burst`. Enabling a limit grants exactly one full bucket; a restart
> grants nothing.

`R1`–`R4` in `internal/verify` (numbered like #9's `C*` and #11's `S*`):

| ID | Statement |
|---|---|
| R1 | `0 <= rate_tokens <= rate_burst · 10⁶` for every consumer with `max_rate_mmps > 0` |
| R2 | `max_rate_mmps = 0 ⇒ rate_tokens = 0 AND rate_updated_ms = 0` (the clean "off" state) |
| R3 | `max_rate_mmps > 0 ⇒ 0 < rate_updated_ms <= now` |
| R4 | **deep only** — folding `msg.deliver` and `consumer.update` from the events table, no window between two consecutive rate-config changes exceeds the I14-a bound |

```sql
-- R1
SELECT stream, name, rate_tokens, rate_burst FROM consumers
 WHERE max_rate_mmps > 0 AND (rate_tokens < 0 OR rate_tokens > rate_burst * 1000000) LIMIT 100;
```

R4 is the point of the whole design being event-sourced: **the throttle is provable from the audit
trail after the fact**, by `messq verify --deep`, on a copied database, without trusting the running
process — which is the same claim `messq trace` makes about delivery.

## Acceptance criteria

- [ ] Migration `000N` adds the four columns with defaults meaning *off*; an existing v1.0 data
      directory migrates, passes `verify --deep`, and every pre-existing consumer delivers exactly as
      before (added to #34's fixture matrix).
- [ ] `ParseRate`/`String` are stable on `string → Rate → string` for the whole grammar (`10/s`,
      `600/m`, `1/h`, `0.5/s`, `10`, `off`, `0`) — the reverse direction is explicitly lossy, since
      `1/m` rounds up to 17 mmps, and the test states the direction it asserts. Everything else is
      rejected with a teaching error, and this is the **only** rate parser in the tree (#29's
      CLI-side parser is replaced; a test asserts no second implementation exists).
- [ ] `TokensAt` is exact: over 10⁶ random `(rate, burst, elapsed)` draws, the token count equals a
      big-rational reference computation with **zero** accumulated drift, and no input overflows.
- [ ] A backlogged consumer with `--max-rate 10/s` receives **10 ± 1 messages per second** measured
      over 60 simulated seconds in `synctest`, and a second consumer on the same stream with no limit
      is **unaffected** (its delivery rate is statistically indistinguishable from the unlimited
      baseline).
- [ ] Sub-1/s rates work: `--max-rate 1/m` delivers 10 ± 1 messages over 10 simulated minutes.
- [ ] Disabling the limit (`--max-rate off`) resumes full-speed delivery on the **next fetch**, with
      no restart, and leaves `rate_tokens = 0, rate_updated_ms = 0` (R2).
- [ ] Tokens are spent per delivered message: a fetch that claims nothing spends nothing and issues
      **no `UPDATE`** (asserted by counting statements, not by inspecting the result).
- [ ] With `max_rate_mmps = 0` the fetch path is byte-identical to #9's: a store-level statement trace
      shows no extra read or write, and `BenchmarkFetchClaim` shows no regression outside noise (delta
      recorded in the PR with hardware and durability mode).
- [ ] An empty bucket returns early: a `go-cmp` diff of a full store dump taken before and after the
      rate-limited fetch is empty — no top-up scan, no cursor advance, no delivery row, no token
      write.
- [ ] `hold_reason:"rate_limit"` and a correct `retry_after_ms` are returned when work is being held
      back; an idle throttled consumer returns `no_messages` instead.
- [ ] A partial batch (tokens < requested batch) returns the available messages **and** the hold
      reason.
- [ ] `delivery_blocked_by` reports `rate_limit` ahead of `max_ack_pending` and behind `paused`, and
      `consumer info` reports `rate_tokens`, `rate_ready_at` and `drain_eta_ms` matching a
      recomputation from the row.
- [ ] A parked long-poll wakes at `max(NextVisibleAt, RateReadyAt)` capped by its deadline, and a
      1 000 msg/s publish storm against a 1/s consumer produces **≤ 1 fetch command per token
      interval** (no busy loop).
- [ ] `pkg/client`'s `Worker` sleeps `retry_after_ms` on a `rate_limit` hold and fires
      `OnEvent{Hold}` once per distinct reason; a 10/s throttle with 8 workers produces 10 ± 1
      handler invocations per second and no fetch storm.
- [ ] Restart mid-throttle: the bucket is reloaded from disk, no burst is granted, and I14-a holds
      across the restart boundary (checked by the crash harness, not only in `synctest`).
- [ ] Live reconfiguration: enable grants exactly one bucket; raise grants none; lower clamps
      immediately; each emits `consumer.update` with the old/new values and the actor.
- [ ] `flow.blocked{reason="rate_limit"}` is emitted at most once per `--flow-blocked-interval` per
      `(consumer, reason)`, is never sampled, and carries `retry_after_ms`, `max_rate_mmps`,
      `rate_burst`, `pending`, `backlog`.
- [ ] `messq_rate_limited_total`, `messq_rate_tokens` and `messq_flow_control_engaged` exist with
      exactly the catalogue's names, types and label sets; the `reason` enum values are asserted as a
      closed set; #21's cardinality and `promlint` tests stay green.
- [ ] The `rate_below_drain` finding fires when the configured rate cannot drain the backlog inside
      the stream's `max_age`, in the API response, in `messq consumer edit` output and in
      `messq doctor`.
- [ ] `R1`–`R3` are registered in `internal/verify` and clean across the suite; each reports its
      seeded violation. `R4` proves I14-a from a recorded events table for a run with rate changes in
      the middle.
- [ ] No new event name exists; `git diff` touches the §9.2 vocabulary list not at all.
- [ ] No new server flag exists (`messq serve --help` is unchanged).
- [ ] `codes.tsv` marks `rate_limited` and `flow_control` permanently reserved; #18's reserved-code
      check passes and no test produces either code.
- [ ] `SEMANTICS.md` (I14-a, the seek/generation rule, the `TimeToDead`-is-a-lower-bound note),
      Appendix A1 bounds rows, `PROTOCOL.md`, `log-schema.md`, `docs/guarantees.md` (I14-a → its CI
      job) and the `OPERATIONS.md` drain runbook all land in the same PR, with every command block

## Test plan

Per §11 / D13: `-race` everywhere, real SQLite files in `t.TempDir()`, no `time.Sleep`, all timing via
`testing/synctest` and the Clock seam, every fixed bug landing with its reproduction artifact.

**Unit — pure (`internal/queue`, no DB)**

- `TestParseRate` — the full grammar table plus every rejection, and `String()` round-trips.
- `TestTokensAtExact` — the big-rational differential from the acceptance criteria, plus the three
  clamps (backwards clock, long idle, cap) and the overflow boundary at `MaxRate × MaxRateBurst`.
- `TestReconfigureMatrix` — the four transitions of §3 × `{tokens empty, partial, full}`.
- `TestReadyAt` — `Allowed >= 1` at exactly `ReadyAt` and not one millisecond earlier, over the full
  rate range including `1/h`.
- Property (`rapid`, local to this issue): for random action sequences of
  `{advance_time, consume(n), reconfigure}`, tokens stay in `[0, cap]`, are monotone in elapsed time
  between consumes, and the cumulative consumption never exceeds `Rate·Δt/10⁶ + Burst` within a
  configuration epoch — **I14-a proven on the pure type before any SQL exists.**

**Deterministic timing (`testing/synctest`) — the centre of gravity**

- `TestRateSteadyState` — the acceptance criterion: 10/s over 60 simulated seconds, 10 ± 1 per
  second, and an unthrottled sibling consumer unaffected.
- `TestRateSubSecond` — `1/m` over 10 simulated minutes (10 ± 1 deliveries).
- `TestRateBurstThenSteady` — a full bucket delivers `burst` immediately, then the steady rate.
- `TestRateLimitedParkDoesNotBusyLoop` — the publish-storm case, counting writer commands.
- `TestRateWakeAt` — parked fetch wakes at `max(NextVisibleAt, RateReadyAt)`, not earlier.
- `TestRateLiveEdit` — enable/raise/lower/disable mid-run, each asserted on the very next fetch.

**Unit — store (real DB)**

- Gate behaviour per row of §11's edge-case table, each asserting rows, events, statements issued and
  the returned `hold_reason`.
- Statement-count assertions for the two cheap paths (limiter off; bucket empty).
- Token write-back is in the claim's transaction: an injected commit failure (#6's seam) leaves both
  the deliveries **and** the bucket unchanged after reopen — no token spent for a delivery that never
  happened.
- `verify` `R1`–`R3` after every test in the package via the shared `assertInvariants` helper.

**Property / model (#13's suite, extended)**

- New generator dimension `max_rate ∈ {off, 1/m, 10/s, 1000/s}` and a `set_rate` action; the
  reference model gains the same pure `RateState` (it is I/O-free, so the model uses the real type —
  the one place sharing code with the model is legitimate, because the *placement* of the guard, not
  its arithmetic, is what the model is checking).
- I14-a joins the invariant hook, evaluated after every action; observational equivalence must hold
  with rate limiting on, including across the `restart` action.

**Crash (#8's harness)**

- SIGKILL between the claim commit and the fetch response on a throttled consumer: after restart,
  tokens reflect the committed claim exactly once, no burst is granted, `verify` clean.
- Repeated kill/restart during a throttled drain: total deliveries over the whole run still satisfy
  I14-a — the property an in-memory bucket would fail, stated as the reason the columns exist.

**Integration / golden**

- `testscript` (#26): `consumer add --max-rate`, `consumer info`, `lag` STATE, the attention block for
  `rate_below_drain`, and `--max-rate off`, in human and JSON faces with a fake clock.
- API goldens (#18): the throttled fetch response, the consumer info shape, the PATCH response with
  findings, plus the negative case that a string `max_rate` is refused with the teaching error.
- The `OPERATIONS.md` drain runbook executes end to end in CI.

**Bench**

- `BenchmarkFetchClaim` with the limiter off (regression gate: in the noise) and on (cost of the gate
  plus one `UPDATE`), both durability modes, recorded in the PR.

**Not tested here:** per-worker fairness (#41), ordered interaction (#38), delayed-delivery
composition beyond one smoke case (#37), TLS (#40).
