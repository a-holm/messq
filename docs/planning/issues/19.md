## Context

PLAN.md §1.2 lists four things messq *is*, and the third — **"observable by construction"** — is the
differentiator: *every state transition writes a durable event row inside the same SQLite transaction
as the state change, is emitted as a structured log line, and updates a metric — one vocabulary
across all three surfaces. The audit trail cannot disagree with reality.* That sentence is the
product. This issue is where it becomes code.

Everything up to here has been written *against* a pipeline that does not exist. #6 defined
`obs.Event` and `obs.Sink` as a stub with a `NopSink` default. #5 writes its two recovery rows with a
hand-written `INSERT INTO events`. #7, #9, #10, #11, #12, #14 and #15 all return `[]obs.Event` values
built against **local string constants**, each with an "Out of scope → #19" bullet pointing here. The
`events` table exists and nothing but recovery has ever inserted into it; there is no logger beyond
whatever `slog.Default()` happens to be. This issue closes every one of those loops at once, which is
why it is 3 days and P0 rather than a wiring task.

Governing material:

- **D11 / §9.1 — "events table in-transaction is the source of truth; logs and metrics are
  projections."** Three surfaces, one closed vocabulary; the table is never sampled. `log/slog` with a
  JSON handler for machines and a ~180-line human handler for people (validated with
  `testing/slogtest`), `slog.LevelVar` + SIGHUP for runtime level changes.
- **§9.2 — the closed vocabulary** (35 names). Renaming is a breaking change; the field schema is
  versioned like an API in `docs/log-schema.md`, which this issue creates.
- **§9.3 — volume control, the honest answer to "first-class logging at 5 000 msg/s."** Hot-path
  events at DEBUG and sampleable; problem events at WARN/ERROR and **never** sampleable, enforced by
  an allow-list in code. `--log-sample 1/N` samples **per message** (`hash(trace_id) % N`) so a
  sampled message shows its *entire* lifecycle — half a story is worse than none.
  `--trace-subjects PAT` forces full logging during an incident.
- **§4.2 — the `events` schema** and the note that matters most: *"The event row commits with the
  state change. Same transaction ⇒ zero extra fsyncs and an audit trail that structurally cannot
  lie."* **§4.5** adds the retention knobs #27's janitor drives. **§3.2** budgets *one* fan-out
  goroutine — committed events → slog → counters → `/v1/events` followers, bounded rings that
  "overflow drop loudly", never on the writer's latency path.
- **§10 / D12 — payloads never enter logs**: redaction type + `ReplaceAttr` denylist + a CI
  canary-leak test. **§5.2 I10** — folding the events table reproduces the persisted state, which
  requires every state-changing command to emit a foldable event. **§12** — journalling overhead
  ≤ 10 % throughput, *measured and published*.

What this unlocks: **#20** (`trace` and `/v1/events` read exactly the rows and `detail` shapes defined
here; the follower ring plugs into this issue's Hub), **#21** (every §9.4 counter is driven from the
fan-out, so a counter cannot disagree with the journal) and **#27** (the janitor calls `TrimEvents`,
and `retention.blocked` / `disk.degraded` finally have somewhere to land). It retires seven "replaced
by #19" TODOs across shipped packages, and it is the M5 exit criterion: *`messq trace` renders the §8
timeline for a timed-out / naked / acked message; golden log tests green.*

## Scope

**In scope**

- `internal/obs` — the package that has been a stub since #6: the closed vocabulary as a typed enum
  with per-kind level / sampleability / required-field metadata, the `Event` type and its
  constructors, validation, and the redaction types.
- **In-transaction event persistence**: `store.persistEvents`, the *only* place in the process that
  writes the `events` table, called by #6's writer **inside each command's savepoint**, so a rejected
  or dry-run command discards its events structurally rather than by convention.
- **The audited-transaction assertion** — a test/build-tag `*sql.Tx` wrapper that fails any savepoint
  which mutated `messages`/`deliveries`/`consumers`/`streams` without writing an event row. This is
  what turns "we always emit an event" from a code-review habit into a test gate.
- **The fan-out goroutine** (`obs.Hub`): non-blocking `Publish` from the writer, bounded ring,
  batch-granular drop accounting, ordered delivery to subscribers, `Drain` for #17's shutdown.
- **Both slog handlers**: `slog.NewJSONHandler` with a `ReplaceAttr` enforcing the frozen field schema
  and the redaction denylist; a hand-written `HumanHandler` (aligned columns, colour on a TTY)
  validated with `testing/slogtest`. **`slog.LevelVar`** wired to `--log-level`, #15's `LevelSetter`
  and #17's SIGHUP reload.
- **Sampling**: the pure `Sampler` (per-message `fnv32a(trace_id) % N`), the never-sampleable rule
  derived from the vocabulary table, `--trace-subjects` targeted verbosity, and **the repeat limiter**
  — ratifying #10's open proposal and absorbing #9's `--flow-blocked-interval`.
- **Event retention**: `TrimEvents` (bounded, resumable) plus the `meta.events_trimmed_before_*`

- **`docs/log-schema.md`**, generated from the vocabulary table and diffed in CI; metric names for the
  pipeline's own health (registered by #21); the harness for §12's ≤ 10 % overhead measurement.

**Out of scope**

- `messq trace`, `GET /v1/events`, `follow=1` NDJSON streaming and the per-follower ring — **#20**.

### 2. The vocabulary is a typed enum, not a string (**decision**)

PLAN §9.2 says the set is closed and renaming is a breaking change; a `string` field cannot express
that. `Kind` is a `uint8` over one metadata table, and the DB column, log field and metric label all
come from `Kind.String()` — drift between the three surfaces is not expressible.

Rules read off the table, all test-enforced:

1. **`sample` implies `level == DEBUG`.** Sampling only ever removes DEBUG records — stricter than
   §9.3's allow-list wording and strictly safer: an operator cannot lose a WARN by turning sampling
   on, and the allow-list becomes a derived property rather than a second list to maintain.
2. **Every `fold` kind must have a rule in #13's fold model**, cross-referenced by a test. This is
   what keeps I10 true as the vocabulary is extended in M9.
3. **No new names.** `consumer.pause` covers resume (`detail.paused=false`), `msg.ack_stale` covers
   wrong-generation (`detail.reason`, #10's decision), `stream.purge` covers dry runs. Adding a
   `Kind` is a reviewable diff in one file plus a `docs/log-schema.md` golden change.

### 3. `Event`, and where its fields come from

```go
type Event struct {
    Kind     Kind
    TS       int64            // unix ms — ALWAYS #6's batch timestamp, never the handler's clock
    ID       int64            // events.id, back-stamped by persistEvents; the ordering key (§5)
    Stream, Consumer, Subject, MsgID, TraceID string
    Seq      int64
    Attempt  int32
    Actor    string           // token id or uid, from #16; never a secret
    Level    slog.Level       // 0 ⇒ use Kind.Level(); may only RAISE (Validate enforces)
    Detail   Detail           // ordered, typed, size-capped (§4)
}

type Detail []slog.Attr       // ordered so JSON output is deterministic and goldens are stable
func D(kv ...any) Detail      // D("held_ms", 30001, "late", true)
```

**`Detail` is `[]slog.Attr`, not `map[string]any` (decision).** Deterministic ordering makes goldens
possible without sorting; `slog.Attr` carries a typed `Value` so an int encodes as an int; and
`LogValuer` resolution (redaction) happens for free on the log path. The DB column is
`json_object(...)` built from the same slice, so log and row cannot disagree.

Constructors keep call sites honest: `Msg(k, MsgRef, …)` fills stream/subject/msg_id/seq/trace_id
from one argument, `Delivery(k, DeliveryRef, …)` adds consumer/attempt, plus `Admin` and `Server`.

`Validate(e) error` checks: kind in range; required fields present; `Level >= Kind.Level()`; no
`Detail` key colliding with a canonical field name; serialised `Detail` ≤ `--event-detail-max-bytes`
(1 KiB) after truncation. It runs **always** in `persistEvents` — an invalid event is a programming
error, and the honest response is to fail the command rather than write a lie. In test builds a
failure is a `t.Fatal` via the audited tx; in production it is a `CmdError`, rolled back to the
command's savepoint with siblings still committing.

### 4. Size caps and untrusted text

The one field an attacker (or a broken worker) controls is `reason` — #25's `--exec` puts the child's
first 4 KiB of stderr there, and it flows into `deliveries.last_reason`, the `Messq-Last-Reason` DLQ
header, the events table and the log. Three caps, one sanitiser:

`--max-reason-bytes` (4 KiB, #10) already bounds `deliveries.last_reason` and the DLQ header;
`events.detail.reason` is capped at 512 B (rune-boundary truncation, `reason_truncated:true`) and the
log line at 256 B (the row keeps the longer form).

`obs.sanitize` strips C0/C1 controls (including `\r`, `\n` and **ESC** — an ANSI escape in a nak
reason must not repaint a terminal or forge a log line), replaces invalid UTF-8 with U+FFFD, and runs
at `Event` construction so the DB row is clean too. It is fuzzed: it is the only untrusted-input
parser this issue owns.

### 5. In-transaction persistence: one writer, inside the savepoint (**decision**)

#6's writer already collects `[]obs.Event` from each `Cmd.Apply` and publishes them to the sink
*after* commit. The change here is one line in the batch loop and it is load-bearing:

```go
res, evs, err := r.cmd.Apply(ctx, tx, now)
switch {
case err == nil:
    if err := persistEvents(ctx, tx, now, evs); err != nil {  // ← NEW: inside command i's savepoint
        w.abortBatch(batch, "events", err); return
    }
    _, err = tx.ExecContext(ctx, fmt.Sprintf("RELEASE c%d", i))
case isCmdError(err):
    _, _ = tx.ExecContext(ctx, fmt.Sprintf("ROLLBACK TO c%d", i)) // discards its rows AND its events
    r.err = err
```

Consequences, all of them wanted:

- **A rejected command's event rows roll back with its state changes**, and a dry run writes nothing,
  by the same mechanism with no special case. #15 flagged this as a hazard ("a rolled-back command
  must discard its pending events, or `messq events --follow` shows a purge that never happened");
  the savepoint makes it structural rather than a convention somebody must remember.
- **Zero extra fsyncs** (§4.2) — the rows ride the group commit that was happening anyway.
- **If the audit row cannot be written, the state change does not commit.** An `INSERT` failure
  aborts the batch: the D11 promise taken literally, and unreachable in practice because `Validate`
  has already bounded every field.

```go
// internal/store/events.go — the ONLY place in the process that writes the events table.
// A lint rule (#2) fails the build on `INSERT INTO events` anywhere else.
func persistEvents(ctx context.Context, tx *sql.Tx, now time.Time, evs []obs.Event) error
```

```sql
INSERT INTO events (ts, event, stream, consumer, subject, msg_id, seq, attempt,
                    trace_id, actor, detail)
VALUES (?,?,?,?,?,?,?,?,?,?,?)
RETURNING id;
```

- Empty strings are stored as `NULL`, not `''`: `WHERE consumer IS NULL` means *"not
  consumer-scoped"*, indexes stay small, and #20's filters get clean three-valued semantics.
- **`events.id` is the ordering key, never `ts` (decision).** `RETURNING id` back-stamps `Event.ID`
  so the fan-out, the followers (#20) and `verify --deep` share one key. Two events in a batch share
  a timestamp and only `id` totally orders them; #20's `since=` cursor is an id and `trace` sorts by
  id. `events_ts` serves the retention sweep and `--since <time>` range starts, not ordering.
- **Ids have gaps** — a rolled-back savepoint consumes rowids. Followers must never assume
  contiguity; documented in `log-schema.md` and asserted by a test that rejects one command mid-batch
  and shows the gap.

### 6. The audited transaction — proving no state change escapes (**decision**)

The summary asks for a choke point making it *"structurally impossible to change state without its
event."* A single `applyTransition(tx, mutation) → event` would achieve it, but it means rewriting
the SQL of #7, #9, #10, #11 and #12 — shipped, crash-tested code — for no additional guarantee. The
cheaper and stronger mechanism is an assertion:

```go
// internal/store/audittx.go — active under the messq_audit_assert build tag and ALWAYS in tests.
// Wraps *sql.Tx, records the first table token of every executed statement, and at RELEASE time
// asserts: if this savepoint touched a state table, it also inserted >= 1 events row.
type auditTx struct {
    *sql.Tx
    touched map[string]int
}

var stateTables = []string{"messages", "deliveries", "consumers", "streams", "stream_seq"}
```

Exemptions are declared per command kind, not per call site, and are few: `CmdRecoveryReclaim`,
`CmdTrimEvents`, `CmdTrimDedup`, `CmdCheckpoint`. Anything else that mutates state silently fails the
suite, naming the command kind and statement. Production pays nothing — the wrapper compiles out.
This is the test that catches the M9 feature that forgets its event, which is the entire point.

### 7. The fan-out goroutine

```go
type Sink interface{ Publish([]Event) }   // #6's seam, unchanged. MUST NOT block.

type Subscriber interface {
    Name() string
    Deliver(batch []Event, dropped DropReport)  // called on the Hub goroutine, in id order
}

// Hub holds a bounded ring (--event-fanout-buffer, 4096 batches) and a subscriber list fixed at
// construction: slogProjector, metricProjector (#21), follower registry (#20).
func (h *Hub) Publish(evs []Event)             // Sink; select-default; NEVER blocks the writer
func (h *Hub) Run(ctx context.Context) error   // the §3.2 goroutine
func (h *Hub) Drain(ctx context.Context) error // #17 calls before exit; flushes then returns
```

- **`Publish` drops the whole batch or none of it (decision).** A transaction's events belong
  together; delivering three of five would produce a `msg.deliver` with no matching `msg.publish` and
  a follower that cannot tell. On a drop, the **next** delivered batch carries
  `DropReport{Batches, Events, SinceID}` — what #20 needs for its "lost events" marker and what #21
  counts.
- **Subscribers run on the Hub goroutine, in order** — no per-subscriber goroutine, no reordering, no
  second bounded queue. The follower registry (#20) is the one subscriber that fans out further, and
  it owns its per-follower ring.
- **A wedged log consumer degrades logs, never durability.** If stderr blocks the Hub blocks, the
  ring fills, `Publish` drops and `messq_events_dropped_total` climbs — while the writer, the commit
  path and every ack run at full speed and the events table, written before the commit, is untouched.
  `docs/OPERATIONS.md` states this as a designed trade-off.
- **`storage.fatal` bypasses the ring (decision).** A fatal line sitting in a buffer while the
  process exits is a fatal line nobody reads: `obs.Fatalf` (already called by #6) logs synchronously,
  then hands the event to the Hub.

### 8. Sampling, the repeat limiter, and targeted verbosity

```go
type Sampler struct {
    N        uint32              // --log-sample; 1 = log everything
    Subjects []subject.Pattern   // --trace-subjects (#3's matcher, allocation-free)
}

func (s Sampler) Log(e Event) bool {   // pure, total, never allocates
    if e.Level > slog.LevelDebug || !e.Kind.Sampleable() { return true }  // §2 rule 1
    if s.N <= 1                                          { return true }
    if len(s.Subjects) > 0 && subject.MatchAny(s.Subjects, e.Subject) { return true }
    if e.TraceID == ""                                   { return true }  // lifecycle events
    return fnv32a(e.TraceID)%s.N == 0
}
```

- **Hashing `trace_id`, not `msg_id` (decision).** §9.3 says "per message"; the practical unit is the
  *story*. A redrive publishes a new message with a new seq but the **same** `trace_id` (D3), so
  hashing the trace keeps the DLQ hop and its redrive in one decision, where `msg_id` would split
  that story in half — the exact failure §9.3 exists to prevent. Documented cost: a publisher reusing
  one `traceparent` across many messages samples them together, which is what a trace *means*.
- The events table and the metrics are **never** sampled. #21's counters are driven from the raw
  batch, before the slog projector's sampler runs, so a sampled log and an exact counter are not a
  contradiction.
- **Honesty line.** Once per `--log-sample-report` (60 s) the projector emits the `obs.sampled`
  diagnostic (§9) with per-kind dropped counts. A sampler that hides how much it hid gets blamed for
  events it never saw.
- **The half-a-story edge case, answered.** A message sampled *out* that later times out still logs
  its WARN — never-sampleable wins. That line would be an orphan, so it is stamped `sampled:false`
  and rendered with `→ messq trace <msg_id>`: the history is in the table, the log says where to look.

**Repeat limiting** (ratifies #10's open proposal, absorbs #9's `--flow-blocked-interval`): kinds with
`repeat=true` in §2 are limited to **one event row per `(scope, kind)` per `--event-repeat-interval`**
(10 s) — scope is `(stream, consumer)` for delivery kinds, `(token_id, route)` for `auth.denied`,
`(route, code)` for `api.error` — and the suppressed count rides on the next emitted row as
`detail.suppressed = N`. The limiter is a lock-free map owned by the writer goroutine, capped at
`--event-repeat-scopes` (4096) with LRU eviction (I11). Metrics stay exact; only rows and lines are
limited, and **state changes are never limited** (#11 §9 is right: 100 000 timeouts are 100 000 real
redeliveries).

`--flow-blocked-interval` (#9) becomes a hidden alias, warned once at startup and removed before
1.0. One knob, one behaviour.

### 9. Log records: the frozen field schema

A log record is one of two things, and `docs/log-schema.md` enumerates both:

1. **Event lines** — a projection of a durable `events` row. `event` is a §2 vocabulary name.
2. **Diagnostics** — narration with no durable row: `recovery.check|migrate|checkpoint` (#5),
   `api.incomplete` (#7), `obs.dropped|sampled|trimmed`, `sweep.late` (#11). They carry
   `durable:false` and live in a second, also-closed table in the same file, so *every string an
   operator can grep for* is documented in one place.

> **Spec refinement.** PLAN §9.2 lists only the durable vocabulary, while #5's and #7's merged
> transcripts already print `recovery.check` and `api.incomplete`. Rather than inventing durable rows

Built-in key mapping via `ReplaceAttr`, identical for both handlers:

| slog built-in | Emitted as | Note |
|---|---|---|
| `time` | `ts` | RFC3339 with milliseconds, UTC, from `Event.TS` (not the handler's clock) |
| `level` | `level` | `DEBUG`/`INFO`/`WARN`/`ERROR` |
| `msg` | `event` | **the event name is the message** — one identifier across grep, SQL and PromQL |
| `source` | dropped | never in production; `--dev` re-enables it |

Canonical attributes, in this order: `event_id`, `stream`, `consumer`, `subject`, `msg_id`, `seq`,
`attempt`, `max_deliver`, `trace_id`, `actor`, then the flattened `detail`. **`detail` is flattened
into top-level attributes in logs and stored as a JSON object in the DB** — `held_ms=30001` must be
greppable, not buried one level down; `Validate`'s collision check is what makes flattening safe.

```json
{"ts":"2026-10-09T09:14:32.191Z","level":"WARN","event":"msg.timeout","event_id":88213,
 "stream":"orders","consumer":"worker","subject":"orders.created","seq":10493,
 "msg_id":"01J8ZQ4K2M9V0X7Y3B5N6C8D1E","attempt":1,"max_deliver":5,
 "trace_id":"4bf92f3577b34da6a3ce929d0e0e4736","held_ms":30001,"lateness_ms":1,
 "schedule_ms":1000,"delay_ms":1100,"retry_at":"2026-10-09T09:14:33.291Z"}
```

The JSON handler is `slog.NewJSONHandler` unmodified apart from `HandlerOptions{Level: levelVar,
ReplaceAttr: schemaAndRedact}`. We do not hand-roll JSON — this is the one place where the stdlib's
escaping correctness outranks our formatting preferences.

### 10. `HumanHandler` — the ~180 lines that make `serve` readable

Implements the four-method `slog.Handler` contract (`Enabled`, `Handle`, `WithAttrs`, `WithGroup`)
and is validated by `slogtest.TestHandler`, which checks the parts everybody gets wrong: group
qualification, empty-group elision, zero `Time`, `LogValuer` resolution, `WithAttrs` ordering.

```
TIME         LEV   EVENT         SCOPE                FIELDS
09:14:02.114 INFO  msg.publish   orders               subject=orders.created seq=10493 size=1.2KiB
09:14:02.190 DEBUG msg.deliver   orders/worker        seq=10493 attempt=1/5 deadline=09:14:32.190
09:14:32.191 WARN  msg.timeout   orders/worker        seq=10493 attempt=1/5 held=30.0s retry_in=1.1s
                                                      msg=01J8ZQ4K… trace=4bf92f35…
09:14:44.771 WARN  msg.nak       orders/worker        seq=10493 attempt=2/5 reason="upstream 503"
```

Rules:

- Columns: time 12, level 5, event 13, scope 20, then key=value pairs wrapped and indented to the
  fields column at `--log-width` (terminal-detected, 120 default, `0` = never wrap). **Scope** is
  `stream`, `stream/consumer` or `—`; over-long names are middle-elided (the JSON handler never
  elides anything).
- Durations and sizes are human (`30.0s`, `1.2KiB`); ULIDs and trace ids elide to 8 chars + `…`
  unless `--log-full-ids` — the log is for scanning, `trace` (#20) is for reading. Colour only when
  `--log-color=auto`, stderr is a TTY, `NO_COLOR` is unset and `TERM != dumb`, and only on the level.
  Values are quoted only when they contain spaces or `=`.
- `--log-format=auto` (default) picks `human` on a TTY and `json` otherwise, so `serve` in a shell is
  readable and under systemd is parseable with no flag — the same rule as the CLI output contract.

### 11. Event retention (the janitor's query, the janitor is #27)

```go
// TrimEvents is a writer command: bounded by TrimConfig{MaxAge, MaxRows, Batch} (§13's flags),
// resumable, and it emits NO event of its own.
func TrimEvents(ctx context.Context, tx *sql.Tx, now time.Time, c TrimConfig) (TrimResult, error)
```

```sql
-- age pass (events_ts), id-bounded so it is never an unbounded DELETE
DELETE FROM events
 WHERE id IN (SELECT id FROM events WHERE ts < :cutoff ORDER BY id LIMIT :batch);

-- row-count pass, after the age pass
DELETE FROM events
 WHERE id IN (SELECT id FROM events ORDER BY id LIMIT :batch)
   AND id <= (SELECT MAX(id) - :max_rows FROM events);

-- and, in the same transaction, the honesty markers
INSERT INTO meta(k, v) VALUES ('events_trimmed_before_id', :id),
                              ('events_trimmed_before_ts', :ts)
ON CONFLICT(k) DO UPDATE SET v = excluded.v;
```

- **The trim emits no event** — one that wrote an event row would feed itself. It emits the
  `obs.trimmed` diagnostic and increments `messq_events_trimmed_total`.
- **`trace` must be able to say "I don't know" (decision).** #20 compares a message's first event id
  against `events_trimmed_before_id` and prints `history before 2026-10-06T09:00Z has been trimmed`
  rather than rendering a partial timeline as if it were complete. A forensic tool that silently
  omits is worse than one that admits it cannot see.
- **Trimming is age-and-count only, never "keep events for unresolved messages"** — that predicate
  needs a join against `deliveries` per candidate row and makes the sweep unbounded. The headroom
  rule buys the same safety for a constant: `TimeToDead` (#11) for the default consumer is 306 s
  against a 72 h retention, `doctor` (#30) warns below `10 × max(TimeToDead)`, and startup warns
  below 1 h.

### 14. Edge cases, decided

| Case | Handling |
|---|---|
| Command rejected mid-batch (`CmdError`), or a dry run (#15) | `ROLLBACK TO` discards its event rows; its events never reach the Hub; siblings commit with theirs. Zero rows, zero fan-out events, no special case. |
| `persistEvents` fails | Infrastructure error → whole batch aborted → #6's `ErrCommitUnknown`. We refuse the transition rather than commit it unaudited. Unreachable in practice: `Validate` bounds every field first. |
| Crash between commit and fan-out | The rows are durable; the log lines are missing. **Logs are lossy, the table is not.** `messq events --since <id>` re-reads from the table, so nothing is operationally lost. Fault point `obs.after_commit_before_fanout`. |
| stderr blocks (full pipe, stuck journald) | The Hub blocks, the ring fills, events drop, the broker keeps committing at full speed. Trade-off stated in `OPERATIONS.md`. `storage.fatal` bypasses the ring, so a stuck logger cannot prevent the fatal exit (bounded by `--fatal-drain`, #6). |
| Lifecycle event with no `trace_id` | `Sampler.Log` returns "log it"; `TraceID` is in no server-scoped kind's `required` set. (The sampled-out-then-failed case is §8.) |
| `detail` key collides with a canonical field, or exceeds 1 KiB | Collision → `Validate` rejects at construction; flattening must be unambiguous. Oversize → deterministic truncation (drop trailing attrs, then shorten the longest string) plus `detail_truncated:true`. Never silently dropped, never unbounded. Covers `server.reload`'s `changes[]`, whose secrets are already `Redacted` (#17). |
| ANSI escape, newline or invalid UTF-8 in a nak reason | `sanitize` strips C0/C1 including ESC and repairs UTF-8 at construction. Fuzzed. Neither the `STRICT`/`TEXT` row, the JSON line nor the terminal can be poisoned. |
| Two events in the same millisecond; gaps in `events.id` | `id` totally orders them and nothing sorts by `ts` alone. Gaps are expected (rolled-back savepoints consume rowids); followers must not assume contiguity. Both tested. |
| A kind added without a fold rule, a schema entry, or with `sample=true` at WARN | `TestFoldCoverage`, the `go:generate` doc diff and `TestVocabConsistency`. Extending the vocabulary is a reviewable diff, never a silent one. |
| `--trace-subjects` invalid pattern / DLQ hop | Invalid → startup error from #3's matcher, never a silent no-match. The DLQ copy keeps the original subject (D3), so a traced subject stays traced through dead-lettering — the reason the pattern matches `subject`, not `stream`. |
| Level raised to DEBUG on a busy broker | 5 000 msg/s × 3 hot events ≈ 15 000 lines/s. `messq_log_records_total` makes the cost visible and `admin.action` records who did it, so "why did we log 40 GB on Tuesday" has an answer. |

## Acceptance criteria

- [ ] The vocabulary is a closed `Kind` enum whose `String()` values are exactly the 35 names in
      PLAN §9.2, asserted against a literal list, so a rename is a failing golden and not a silent
      behaviour change. `internal/obs` imports no project package but `internal/clock` and
      `internal/subject` (#1's import-graph lint).
- [ ] `TestVocabConsistency` enforces `sample=true` ⇒ DEBUG, a name/level/`required` set and
      documented `detail` keys per kind, no duplicate names, and levels that raise but never lower.
- [ ] `docs/log-schema.md` is generated by `go:generate` from the vocabulary table and CI fails on any
      diff against a regeneration.
- [ ] Event rows are written **inside the emitting command's savepoint**: a command rejected with a
      `CmdError`, and a `?dry_run=1` purge or seek (#15), each leave zero `events` rows and publish
      zero fan-out events, while batch siblings commit theirs — tested in both orderings.
- [ ] `persistEvents` is the only `INSERT INTO events` in the repository (grep lint in `make lint`),
      #5's recovery path has been migrated onto it, and the audited-tx assertion is active in every
      `internal/store` test: a deliberately event-less mutation fails the suite, naming the command
      kind and the statement.
- [ ] `Event.ID` is back-stamped from `RETURNING id`; ordering is by `id` everywhere; a forced
      mid-batch rejection demonstrates an id gap that a follower tolerates.
- [ ] `Hub.Publish` never blocks: 100 000 events against a stalled subscriber return in bounded time,
      drop whole batches, and the next delivered batch carries a correct `DropReport`. Publish
      throughput with a stalled log sink stays within noise of baseline (asserted on commit counts).
- [ ] `slogtest.TestHandler` passes for `HumanHandler` (group qualification, empty groups, zero
      `Time`, `LogValuer` resolution, `WithAttrs` ordering). Both handlers emit `ts`/`level`/`event`
      for the built-ins, flatten `detail`, and are byte-golden per kind; the log timestamp equals
      `Event.TS`, proven by a synctest that delays the fan-out 5 simulated seconds.
- [ ] `Sampler.Log` is pure and sticky: events sharing a `trace_id` get one decision and no event
      above DEBUG is ever dropped **for any input** (property test); `--trace-subjects 'orders.eu.>'`
      forces full logging at `--log-sample=1000`, including through a DLQ hop.
- [ ] The repeat limiter emits at most one row per `(scope, kind)` per `--event-repeat-interval`,
      carries `detail.suppressed`, is bounded at `--event-repeat-scopes` with LRU eviction, and leaves
      counters exact; state-change kinds are never limited (10 000 timeouts ⇒ 10 000 rows).
- [ ] **The scripted `publish → deliver → timeout → deliver → nak → deliver → ack` scenario produces
      the exact golden sequence on all three surfaces**: `events` rows (kind, order, field set,
      `detail` keys), log lines (both formats) and counter deltas — one fixture, three assertions.
- [ ] **The payload canary never appears in any log output**: distinct canaries in body, headers and
      `Messq-Msg-Id`, a full lifecycle to DLQ at `--log-level=debug`, and a grep of all stdout+stderr
      finds none. `Redacted[T]`/`Secret` render `REDACTED`, and the `ReplaceAttr` denylist drops
      `body`, `body_b64`, `payload`, `authorization` and `token` keys even when passed directly.
- [ ] `sanitize` strips C0/C1 controls (including ESC) and repairs invalid UTF-8; a 60 s fuzz run is
      clean.
- [ ] `TrimEvents` is bounded by `--event-trim-batch`, resumable, emits no event of its own, updates
      `meta.events_trimmed_before_id`/`_ts`, and trims a 1 000 000-row table without a long
      transaction.
- [ ] `slog.LevelVar` is honoured live: `POST /v1/admin/log-level` (#15) and SIGHUP (#17) both change
      output within one record and write an `admin.action` / `server.reload` event. `Hub.Drain` runs
      in #17's shutdown and `server.stop` reaches stderr before exit (real subprocess).
- [ ] Every `fold=true` kind has a rule in #13's fold model (`TestFoldCoverage`), and `verify --deep`
      passes on a run of the golden scenario (I10).
- [ ] §12's overhead number is measured and recorded in the PR: `BenchmarkPublish` with and without
      event persistence, stated hardware and durability mode, delta ≤ 10 %.
- [ ] `internal/obs` ≥ 90 % coverage; `internal/store` stays ≥ 85 % (#2 floors); no `time.Now()`
      outside the `Clock` seam; no `time.Sleep` in tests.

## Test plan

Per PLAN §11: `-race`, real SQLite files in `t.TempDir()`, no `time.Sleep`, all timing through
`testing/synctest` and #3's `Clock`, every fixed bug landing with a reproduction artifact.

**Unit — vocabulary, events, sampler, limiter (`internal/obs`, pure, no DB)**

- `TestVocabularyNames` — the 35 names against a literal list copied from PLAN §9.2. The test a
  reviewer should read first; it is the compatibility contract. `TestVocabConsistency` covers §2's
  derived rules.
- `TestValidate` / `TestDetailTruncation` — table-driven over every kind: missing required field,
